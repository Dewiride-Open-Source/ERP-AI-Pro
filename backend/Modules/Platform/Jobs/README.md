# Platform / Jobs

HTTP surface of the background jobs building block (`BuildingBlocks/Jobs`, `IJobAdministration`): list the jobs the ERP runs on its own with their schedules, list and read their runs, run a run again and cancel one ([ADR-0059](../../../../docs/adr/0059-background-jobs-a-persistent-queue-leases-ist-schedules-and-the-nightly-account-check.md)). The queue, the runner, the scheduler and the tables live in the building block, so that a module enqueues and schedules jobs without referencing this module and the runner works whatever this module's flag says; this module adds the routes and the handlers.

| Aspect | Value |
|---|---|
| Assembly | `Dewiride.Erp.Modules.Platform.Jobs` |
| Schema | none of its own; the building block owns `platform_jobs` (`JobsDbContext`: `JobRuns`, `JobRunEvents`, `JobSchedules`) |
| Route group | `/api/platform/jobs`: `GET /` (every job this release defines, by name, with the schedule of each recurring one), `GET /runs` (paged: `page`, `pageSize`, `sort` on `createdAt`, `dueAt` and `finishedAt`, newest first by `createdAt` by default with the id breaking ties, `filter` on `jobName` and `status` with `eq`, `ne` and `in`, on `idempotencyKey` also with `contains`, and on `createdAt` and `finishedAt` also with `gt`, `gte`, `lt` and `lte`), `GET /runs/{id}`, `POST /runs/{id}/rerun`, `POST /runs/{id}/cancel`; no route takes an idempotency key |
| Feature flag | `Erp.Modules.Platform.Jobs`; it gates the routes only, and the runner, the scheduler and every scheduled job run while it is off |
| Permissions | `platform.jobs.runs.read` (the three `GET` routes), `platform.jobs.runs.rerun` (`POST /runs/{id}/rerun`) and `platform.jobs.runs.cancel` (`POST /runs/{id}/cancel`), Administrator's alone (declared in `JobsPermissions`, [ADR-0041](../../../../docs/adr/0041-roles-and-permissions.md)); anyone else answers 403 `request.forbidden` |
| Answers | a job is `JobResponse` (name, title, description, the attempts a run makes, and for a recurring job `JobScheduleResponse`: the expression in India Standard Time, the next occurrence, or the reason the job is not scheduled, and the latest occurrence with its run and that run's status); a run is `JobRunResponse` (job, idempotency key, status `pending`, `running`, `failed`, `succeeded`, `deadLettered` or `cancelled`, due, created, started and finished times, the attempts started and the failures counted, the cancel request and the latest error code and message, and who enqueued it as `JobActorResponse`: `person`, `system` or `anonymous`, the Entra object id or fixed id, and the name the person's record has today); `GET /runs/{id}` adds the run's events oldest first (`JobRunEventResponse`: the kind, the actor, the attempt, the runner, the attempt's trace id, the error and the time of the next attempt) |
| Re-run | a run that failed, gave up or was cancelled is put back as due at once with its failures counted from zero, a `rerun` event naming the administrator, and the local runner woken; a run of a job this release does not define answers 409 `job.not-defined` whatever its status, and otherwise a run that succeeded, waits or runs answers 409 `job.run-not-rerunnable` |
| Cancel | a run that waits to start or to try again, or whose runner stopped renewing its lease, is cancelled at once; a running run is asked to stop, which its runner sees at its next lease renewal and the job's token then fires, and asking again answers the run as it stands; a stop request wins over every ending but success, so a run asked to stop that then fails, times out or is interrupted is recorded cancelled; a finished run answers 409 `job.run-finished`, and a run that kept changing through three attempts 409 `concurrency.conflict` |
| Names | the people who enqueued a run or took a step of its history are named through every registered `IPersonNames` when the run is read, never stored; a run never shows its payload |
| Contract | `JobsPermissions` |
| Events | none |

Each route that names a run answers 404 `job.run-not-found` for an id that no run has. A run is changed only by the building block's compare-and-set statements, which commit on their own, so the module owns no context and its commands run without a unit of work.
