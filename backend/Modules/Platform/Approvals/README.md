# Platform / Approvals

HTTP surface of the approvals building block (`BuildingBlocks/Approvals`): the requests waiting for a person's decision, those they asked for and those they decided, every request for administrators, each request with its steps, the decisions and withdrawals on it, and the kinds of request with the administrators' settings. The kinds, the tables, the routing and the decisions live in the building block, so that a module asks for approval inside its own command with `IApprovals` and moves its record in its `IApprovalOutcomeHandler` without referencing this module, whatever this module's flag says; this module adds the routes, their handlers and `UsersReportingManagers`, which answers the building block's `IReportingManagers` with the managers `IReportingLines` of `Identity.Users.Contracts` gives on a date.

| Aspect | Value |
|---|---|
| Assembly | `Dewiride.Erp.Modules.Platform.Approvals` |
| Schema | none of its own; the building block owns `platform_approvals` (`ApprovalsDbContext`: `ApprovalRequests` and `ApprovalSteps`, which the context of every module that asks for approval maps too, and `ApprovalKindSettings`) |
| Route group | `/api/platform/approvals`: `GET /requests?box=` (`waiting`, the default, late first; `mine`; `decided`; `all`), `GET /requests/counts`, `GET /requests/{id}`, `POST /requests/{id}/approve`, `/return`, `/reject` and `/withdraw` (each with the version the action was made from), `GET /kinds`, `POST /kind-settings` (idempotency key) and `PUT /kind-settings/{id}` (with the version the change was made from) |
| Feature flag | `Erp.Modules.Platform.Approvals`; it gates the routes only: while it is off, a module still asks for approval of its records and its requests are routed as ever, while nobody can decide or withdraw one on the Approvals page; a module's own command still withdraws its record's request through `IApprovals.WithdrawAsync` |
| Permissions | `platform.approvals.requests.read` (the three `GET /requests` routes and `GET /kinds`), `platform.approvals.requests.decide` (approve, send back, reject) and `platform.approvals.requests.withdraw`, held by Employee; `platform.approvals.requests.read-all` (the box `all`, and every request's page), `platform.approvals.requests.decide-any` (deciding a waiting request in place of the person or role it waits for) and `platform.approvals.kinds.change` (both `kind-settings` routes), held by administrators alone (declared in `ApprovalsPermissions`, [ADR-0041](../../../../docs/adr/0041-roles-and-permissions.md)); a caller without a route's permission answers 403 `request.forbidden`, and so does the box `all` without `read-all` |
| Who sees and decides | the building block's, from the roles the request carries (`ICallerRoles`) and whether it holds `read-all` and `decide-any` (`ICallerPermissions`), with the person the request signs in: a request is seen by the person it is for, the person who submitted it, anyone who decided one of its steps, anyone its waiting step waits for and a holder of `read-all`, and any other request answers 404 `approval.request-not-found` as an unknown one does, the earlier requests a request lists being those the caller asked for, submitted or decided, or every one for a holder of `read-all`; nobody decides a request they asked for or submitted, administrators included (403 `approval.own-request`), a step waits for one person or every holder of a role (403 `approval.not-yours` for anyone else), a holder of `decide-any` decides in place of them, and only the person a request is for or its submitter withdraws it (403 `approval.not-yours-to-withdraw`) |
| Answers | a list holds `ApprovalRequestSummaryResponse` (the kind and its title, the record approved by its change key, id and the name its module gives, the person it is for and its submitter by object id and name, whether a person or the ERP itself submitted it (`submittedByKind`), when it was submitted, its state, the step it waits at with who it waits for and when it is due, whether it is late, when it closed); a request is `ApprovalRequestResponse`, the summary's fields with its version, its steps (`ApprovalStepResponse`: title, rule, state, who it waits for, its working days, when it started and is due, who decided it, when, whether in place of the approver, the note or reason), the earlier requests of its record (`EarlierApprovalRequestResponse`, newest first, at most ten) and `canDecide`, `decidesInPlace` and `canWithdraw`; the counts are `ApprovalCountsResponse` (`waitingForMe`, `lateForMe`, `mineWaiting`); a kind is `ApprovalKindResponse` (key, title, description, its steps as `ApprovalKindStepResponse`, the working days it declares, and `ApprovalKindSettingResponse`, null until set up) |
| Decisions | a decision runs in a unit of work on the kind's own module context under the request's lock and calls the module's outcome handler there, so the record moves with the request or nothing changes; sending back and rejecting need a reason (400 `approval.reason-required` keyed `comment`), a version that is not one the API gave answers 400 `approval.version-invalid` keyed `version`, an older one 409 `concurrency.conflict`, a closed request 409 `approval.not-waiting`, a kind no release declares 422 `approval.kind-retired`, and a module refusing to approve its record answers its own problem while the request still waits |
| Kind settings | `POST /kind-settings` answers 201 with the kind and its new setting and `Location: /api/platform/approvals/kind-settings/{id}`, the address it is changed at; a kind no release declares answers 400 `approval.kind-unknown`, a kind already set up 409 `approval.setting-exists`, and `PUT /kind-settings/{id}` an id no setting has 404 `approval.setting-not-found`; working days run from 1 to 30. A change applies to the requests submitted after it. Switching a kind off lets each of its records go through at once without a request, so nobody but the person who made one looks at it: that kind then has no maker-checker either |
| Contract | `ApprovalsPermissions` |
| Events | none |

A decision and a withdrawal run in the building block's own unit of work on the kind's context, and a kind setting in one on `ApprovalsDbContext`, so the module owns no context and its commands run without a unit of work.
