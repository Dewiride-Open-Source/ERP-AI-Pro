# Routing register

Every API route group and web route in the system. API routes follow `/api/<domain>/<module>/<resource>`; web routes mirror them without the `/api` prefix. Exempt prefixes: `/api/auth/*`, `/api/platform/*`, `/healthz/*`.

Every API route requires a signed-in person unless this register marks it anonymous ([ADR-0031](adr/0031-sign-in-through-entra-in-the-api.md)): without a session a request answers 401 `request.unauthenticated` without a `Location` header, and so does an anonymous request to a path no route matches (a signed-in one answers 404 `resource.not-found`); a signed-in request a policy refuses answers 403 `request.forbidden`. The anonymous routes are `/healthz/live`, `/healthz/ready`, `GET /api/auth/login`, `POST /api/auth/logout` (which also serves a page of this site whose session already ended), the front-channel sign-out `GET /api/auth/signout-oidc`, and in Development `/openapi/erp.json` and `/scalar`; `ModuleCatalogTests` fails on any other. Every page of the web app except `/login` needs a session as well (section "Web-only routes"). On every route, a POST, PUT, PATCH or DELETE that the session cookie signs in also carries the antiforgery token in `X-XSRF-TOKEN`, or answers 400 `antiforgery.token-missing` or `antiforgery.token-invalid` ([HTTP conventions](architecture/http-conventions.md), section "Antiforgery"; [ADR-0033](adr/0033-antiforgery-for-requests-the-session-cookie-signs-in.md)).

Every API response carries `X-Correlation-ID`, and every non-2xx body is `application/problem+json` with `type` (`/problems/<code>`), `code`, `status`, `title`, `instance` and `traceId` (the correlation id); validation problems add `errors`, keyed by camelCase member paths (`orderItems[0].description`; `""` for a result that names no member, except a class-level attribute result on a nested object, keyed by that object's path such as `customer`; the exact table is in HTTP conventions). Every module route also documents 400 (validation), 401 (no session), 404 (unknown resource or disabled module), 429 (rate limit), 500 and 504 (timeout). Any route except `/healthz/*` may answer 429 `rate-limit.exceeded` with `Retry-After` (anonymous callers are counted per client address, signed-in callers per actor; `Erp:Platform:RateLimiting`; the attachments upload also answers it when `Erp:Platform:Attachments:MaxConcurrentUploads` uploads are already in flight). Any route may also answer 400 `request.host-not-allowed` (a `Host` outside `Erp:Platform:Host:AllowedHosts`), 413 `request.too-large` (a body over `Erp:Platform:Host:MaxRequestBodyBytes`, or for the attachments upload over `Erp:Platform:Attachments:MaxSizeBytes` plus 64 KiB) and 504 `request.timeout` (a request running past `Erp:Platform:Host:RequestTimeout`); see [request pipeline](architecture/request-pipeline.md). The committed contract of these routes is [`docs/openapi/erp.json`](openapi/erp.json); the rules are in [HTTP conventions](architecture/http-conventions.md).

## Host endpoints

| Route | Auth | Purpose |
|---|---|---|
| `GET /healthz/live` | anonymous | process liveness (container health check); runs no check; never rate limited and left out of request metrics |
| `GET /healthz/ready` | anonymous | readiness including dependencies (`self`, `database:<schema>` per catalogue context, `storage:attachments`, which only degrades, and `app-configuration` with the App Configuration source, which only degrades), each check limited to 2 seconds: `200 text/plain` `Healthy` or `Degraded`, or `503 application/problem+json` `service.unavailable` naming no check; never rate limited and left out of request metrics |
| `GET /openapi/erp.json` | anonymous, Development only | OpenAPI 3.1 document, identical to the committed [`docs/openapi/erp.json`](openapi/erp.json) apart from formatting |
| `GET /scalar` | anonymous, Development only | API reference UI |
| `GET /api/platform/features` | signed in | every feature flag of the catalog with its evaluated state (`{ features: [{ name, enabled }] }`), read by the web shell and the start page to hide disabled modules; documents 401 |

Two conventions apply to the routes this register lists, from the module that first uses them: a route that creates something carries `.RequireIdempotencyKey()`, so the caller sends an `Idempotency-Key` header with a UUID, a repeat of the same request replays the first response with `Idempotency-Replayed: true`, and the same key with a different body answers 422; a route that lists something accepts `?page=&pageSize=&sort=&filter=` with per-route field allow-lists; a route that changes a record takes the `version` the API last returned for it and answers 409 `concurrency.conflict` when the record changed since (`Identity / Users` first). Both grammars are in `docs/architecture/application-pipeline.md`. `system-info/startups` predates the paging convention and takes `?take=` instead; `GET /api/platform/attachments` is the first paged route. The two attachment routes that create something, the upload and `download-links`, deliberately carry no idempotency key (ADR-0022): the middleware would buffer a whole upload before the endpoint runs, and would store a download link's token in plain text, while repeating either request is harmless.

## Sign-in endpoints

The API signs people in with Microsoft Entra ID and keeps the session in the cookie `__Host-erp-session` ([HTTP conventions](architecture/http-conventions.md), section "Sign-in and the session"; [ADR-0031](adr/0031-sign-in-through-entra-in-the-api.md)). The group `/api/auth` (tag `Auth`, no feature flag) documents 429, 500 and 504. Every sign-in path (the login, both handler paths, the front-channel sign-out and the logout) has an allowance of its own per client address, `Erp:Platform:RateLimiting:SignInPermitLimit` per `SignInWindow`, enforced before authentication, so a request over it answers 429 `rate-limit.exceeded` with `Retry-After` ([ADR-0038](adr/0038-sign-in-limit-security-events-and-the-audit-schema.md)); the two handler paths, which the authentication middleware answers, never reach the global limiter, and they are not in the OpenAPI document. A session starts only for a person whose record in `identity_users.Users` admits them, which the sign-in creates or brings up to date, and every request of a person whose record an administrator deactivated or deleted is refused from then on with 401 `request.unauthenticated`, the session and antiforgery cookies cleared ([ADR-0039](adr/0039-people-and-their-admission.md)).

Registered only on a sign-in registration whose web origin is https, because Entra refuses an http front-channel logout URL |

## Web-only routes

Every page except `/login` needs a session ([ADR-0036](adr/0036-web-sign-in-the-session-in-the-browser-and-single-sign-out.md)). A `GET` or `HEAD` of a page without the session cookie answers `307` to `/login?returnUrl=<the page's path and query>` from `proxy.ts` (`/` to plain `/login`; an address the API would refuse to return to, to plain `/login`), which can only see whether the cookie is there; a page whose cookie the API refuses (`GET /api/auth/me` or any read answering 401) redirects to `/login?returnUrl=<page>&reason=session-ended` while it renders, and so does a Server Function, whose first statement checks the session and which is refused when the session cannot be read. While a page is open, the shell keeps the session alive from the browser (`POST /api/auth/session` on a load, a navigation, a click or a key press, at most once a minute), warns two minutes before the idle timeout ("Are you still there?", Stay signed in or Sign out) or five minutes before the session lifetime ("Your session ends soon"), and once `GET /api/auth/session` answers 401 shows "Your session has ended" with Sign in again, `/api/auth/login?returnUrl=<the page>`, and Sign out, which ends the browser's Microsoft sign-in too. `/robots.txt` stays public, so crawlers read its rules.

## List addresses

A list page keeps its view in its address ([ADR-0026](adr/0026-server-driven-lists-and-the-data-table.md), `apps/web/src/shared/lists`): each filter of its definition (`<param>=<text>`, `<param>=<value>` repeated for a choice, `<param>From` and `<param>To` as `yyyy-MM-dd` for a date range), then `sort=<field>:<asc|desc>`, `size=<page size>`, `page=<n>` and `hide=<column>,<column>`. A value equal to its default is left out, so the first page in the default order is the bare path; an address with an unknown parameter, a malformed value, a page size the list does not offer, a page past the last or a reversed date range redirects to the address of the view it can show. A list's API call always sends `sort` explicitly and turns a date range on a timestamp into India Standard Time days (`gte` the first day's midnight, `lt` the midnight after the last day).
