## Running

The solution run and every test project that declares the `BlobTestContainer` fixture need `ERP_TEST_SQL_CONNECTION`, `ERP_TEST_BLOB_EMULATOR_HOST` and a running Azurite ([local development](local-development.md), sections "Configuration and secrets" and "Attachments storage").

```bash
cd backend && dotnet test --solution Dewiride.Erp.slnx --report-trx --coverage --coverage-output-format cobertura
cd backend && dotnet test --project Modules/Platform/SystemInfo/Tests/UnitTests/Dewiride.Erp.Modules.Platform.SystemInfo.UnitTests
node --test "scripts/roadmap/tests/*.test.ts"
node --test "scripts/checks/tests/*.test.ts"     # seed-file conventions, the secret-pattern check, the frontend structure and import rules and every other repository check
node --test "scripts/api-client/tests/*.test.ts" # the client generator arguments and the drift comparison
node scripts/api-client/drift.ts                 # the committed client matches what docs/openapi/erp.json generates
cd frontend && pnpm test:unit                    # web, design-system and ESLint-rule unit tests (src/**/*.test.ts in apps/web and packages/ui, eslint/*.test.mjs in packages/config)
cd frontend && pnpm e2e                          # all projects
cd frontend && pnpm e2e --project=chromium       # one project
```

Results land in `backend/artifacts/TestResults/` (TRX + Cobertura) and `frontend/e2e/playwright-report/`.

## Rules

- Names: `Method_Condition_ExpectedResult` for .NET tests, web unit tests (`src/**/*.test.ts`, `packages/config/eslint/*.test.mjs`) and the frontend structure and import tests (`scripts/checks/tests/web-structure.test.ts`, `web-imports.test.ts`, `web-source.test.ts`); sentence-style titles for the other `node --test` files under `scripts/**/tests`. One behaviour per test. No sleeps, no order dependence, no shared mutable state.
- Frontend structure and import boundaries (ADR-0024): every rule of the register in `docs/architecture/dependency-rules.md` has an allowed and a refused case, the script rules (S1–S6, I1–I7) in `scripts/checks/tests/web-{structure,imports}.test.ts` over in-memory file lists (no committed fixture trees, so no other scan sees a violating file) and the ESLint rules (L1–L6, X1–X2) in `frontend/packages/config/eslint/feature-boundaries.test.mjs` through the full presets, so the order of the flat-config objects is tested too. A new or changed rule changes the register, its enforcer and its test table together. No Playwright spec belongs to these rules. The existing specs of sign-in, navigation, system information, attachments and the kitchen sink cover the moved sign-in frame and the not-found content a person sees; no spec asserts the loading skeletons, `ErrorPage` or `ApplicationFailure` yet, which `web-foundation-feedback-motion-and-accessibility-baseline` adds with their restyle.
- Database under test: a SQL-backed test project declares `[assembly: AssemblyFixture(typeof(SqlTestDatabase))]` once, which creates the per-process database before the first test, migrates it and runs every seeder the way the migrator does, and drops it after the last; a test of the migration path itself uses `EmptyTestDatabase`, a fresh database no migration has touched (`Dewiride.Erp.Host.Migrator.IntegrationTests`); `ErpApiFactory` injects `SqlTestDatabase.Current.ConnectionString` as `Erp:Platform:Database:ConnectionString` into every test host and throws a message naming that `AssemblyFixture` line when no test database exists, so a test host can never reach the developer's own `ErpAiPro` database; `WithConfiguration("Erp:Platform:Database:ConnectionString", ...)` overrides the injection for a test that needs its own database; a test that needs a context outside the host (a migration test, a convention test) takes it from a class fixture built on `SqlTestDatabase.Current`. Every test host reports the readiness checks `self`, `database:files`, `database:platform_idempotency`, `database:platform_system_info` and `storage:attachments`. A test that needs its own endpoints maps them with `ErpApiFactory.WithTestEndpoints(routes => …)`, which runs after the whole request pipeline, so the middleware under test sees them like any module route.
- Blob storage under test: a test project whose tests start API hosts through `ErpApiFactory` also declares `[assembly: AssemblyFixture(typeof(BlobTestContainer))]` (from `Dewiride.Erp.Testing`) next to its `SqlTestDatabase` line. Before the first test the fixture reads `ERP_TEST_BLOB_EMULATOR_HOST` (`127.0.0.1` locally and in CI), fails with a message naming it when it is missing, deletes `erptest-` containers older than 24 hours (left by a process that was killed) and creates the container `erptest-<yyyyMMddHHmmss>-<8 hex>` on the emulator's built-in development account; it deletes the container after the last test. `ErpApiFactory` points every test host at that container (`Erp:Platform:Attachments:EmulatorHost` and `ContainerName` from `BlobTestContainer.Current`, `BlobServiceUri` blanked), so a storage endpoint in a developer's user secrets never reaches a test, and gives every host the same random encryption key for the whole test process (`test:<32 bytes>`), so content one host stored stays readable, and deduplicable, for every other; a test that sets `ErpApiFactory.AttachmentsEmulatorHostKey` or `AttachmentsBlobServiceUriKey` with `WithConfiguration` gets no injected storage setting at all (the container name then comes from `AttachmentsContainerNameKey` or defaults to `attachments`), one that sets only `AttachmentsContainerNameKey` keeps the test emulator with that container, and one that sets `AttachmentsEncryptionKeyKey` gets no injected key. Without the fixture and without its own storage settings, `ErpApiFactory` throws naming the missing `AssemblyFixture` line. Azurite enforces neither role-based access nor the refusal of account keys, so Entra-only access to the real storage account is proven against the development account, never in tests. In CI `.github/actions/start-azurite` runs the emulator (digest-pinned, in-memory, strict about API versions) for `ci-backend.yml`, whose test step receives `ERP_TEST_BLOB_EMULATOR_HOST`, and for `e2e.yml`, whose two API hosts receive `Erp__Platform__Attachments__EmulatorHost` and an encryption key generated and masked for the run; `docker-build.yml` smoke-tests the compose stack with its own `azurite` service and a generated key file. The fixture builds its `BlobServiceClient` with `AttachmentBlobClients.ServiceVersion` (internal, visible to `Dewiride.Erp.Testing`), so the fixture and the product send the same pinned service version to Azurite.
- Attachments behaviour that depends on timing is made deterministic, never slept on: `UploadConcurrencyTests` sets `Erp:Platform:Attachments:MaxConcurrentUploads` to 1 with `WithConfiguration` and registers `HeldScanner`, an `IAttachmentScanner` whose `StartAsync` signals `Entered` and waits for `Release()`, so one upload is known to be in flight inside the endpoint while the next one is refused with 429; `AttachmentsSweeperTests` call `SweepReservationsAsync` and `PurgeUnusedLinksAsync` directly instead of waiting for `SweepInterval`; `StoredContentTests` damage or delete the stored blob, or store content through one host (`WithConfiguration(ErpApiFactory.AttachmentsEncryptionKeyKey, …)`) and upload or link it through a second host whose key has the same id with other material, an id differing only in case, or another id, to prove that deduplication keeps its own copy and that link creation answers 404. Endpoint metadata (the `platform.attachments.transfer` timeout policy and the `platform.attachments.uploads` rate-limiter policy) is asserted from the endpoint data source in `TransferPoliciesTests`.
- Configuration under test: `ErpApiFactory.WithConfiguration(key, value)` passes the value to the test host as a command-line setting, the highest-priority source in a test host, so it overrides `appsettings.json` and also the values the host reads while it is being built (such as `Erp:Platform:Configuration:*`); call it before the first client or service is requested (it throws afterwards). The factory's own `APPCONFIG_ENDPOINT` and `ERP_CONFIGURATION_SOURCE` settings are applied last, so a test can never re-point the host at the store. `ErpApiFactory.WithFeature(name, enabled)` writes a flag in the Microsoft schema the same way, so a test proves both the enabled and the disabled state of a module without Azure (a later `WithFeature` for the same name wins, mirroring provider order).
- Disabled-module states in Playwright come from a second API and web pair (`E2E_GATED_API_BASE_URL`, `E2E_GATED_BASE_URL`; ports 5081 and 3002 when Playwright starts them) whose API runs with `feature_management__feature_flags__<n>__id` and `__enabled=false` for every flag in `gatedFeatureFlags` (`frontend/e2e/fixtures/targets.ts`: `Erp.Modules.Platform.SystemInfo` as flag 0, `Erp.Modules.Platform.Attachments` as flag 1; `e2e.yml` sets the same pairs); specs that need it `test.skip` when the pair is absent and `test.use({ baseURL })` to target it. The gated API still validates its attachment settings at startup although the module is off, so locally Playwright starts it with `AZURE_TOKEN_CREDENTIALS=AzureCliCredential` (it runs with `--no-launch-profile`) and it reads the endpoint and key from user secrets, and in CI it receives the Azurite host and the generated key like the first API.
- Transport: the in-memory test server has no client address and ignores Kestrel limits, so tests of forwarded headers, body limits and response headers on the wire call `ErpApiFactory.WithKestrel()` (a real listener on port 0) on a factory of their own; never combine it with `WithWebHostBuilder`, which silently falls back to the in-memory server. Request timeouts work on either server; the timeout middleware does nothing while a debugger is attached, so run those tests without one.
- Contract: `OpenApiSnapshotTests` (in `Tests/Host`) fails when the running API differs from `docs/openapi/erp.json`; after an intended API change rewrite the file with `cd backend && ERP_OPENAPI_SNAPSHOT=update dotnet test --project Tests/Host/Dewiride.Erp.Host.Api.IntegrationTests/Dewiride.Erp.Host.Api.IntegrationTests.csproj --filter-class "*OpenApiSnapshotTests"` (or `node scripts/api-client/generate.ts`, which also regenerates the web client) and commit both. `OpenApiSchemaShapeTests` keeps generator-hostile constructs out of the document.
- Playwright starts its own servers on ports 5080, 3000, 3001, 5081 and 3002 unless `E2E_BASE_URL` is set; when another program holds one of those ports, start the five servers on free ports and set `E2E_BASE_URL`, `E2E_API_BASE_URL`, `E2E_OFFLINE_BASE_URL`, `E2E_GATED_BASE_URL` and `E2E_GATED_API_BASE_URL` (the same mode `e2e.yml` uses). Locally both API hosts Playwright starts keep attachments in the development storage account as your `az login` identity, the first with the endpoint and key from the store, the gated one (store-less) with those from user secrets ([local development](local-development.md), section "Attachments storage"); in CI both use Azurite. The attachments specs (`tests/platform/attachments/`) therefore write real, encrypted blobs locally: `files.spec.ts` uploads through the real "Choose a file" chooser (`page.waitForEvent("filechooser")`), lists (ARIA snapshot of the table), downloads (compared byte for byte; the page stays on `/platform/attachments`) and deletes (focus lands on the "Stored files" heading) a PNG whose content is fixed per size and whose name is unique, so repeated runs deduplicate to one stored file per size; it also uploads one file by drag and drop, shows the API's 415 reason in `upload-error` for a file whose bytes are not the declared type, checks the drop zone's refusals (an empty file, a type outside the policy) without any request reaching the API, pages through 21 files it seeds through `POST /api/platform/attachments` (Next and Previous, a page far past the end, the malformed `?page=` values `abc`, `0`, `-2`, `1.5` and `999999999999`; deleted again in `finally`), and on Chromium desktop only refuses a file one byte over the 25 MiB limit before sending it and uploads a 12 MiB file through the web origin of `next start`, whose `experimental.proxyClientMaxBodySize` is `"101mb"` (the image's standalone server keeps the 10 MB default, so the suite runs against `next start`, locally and in `e2e.yml`, never against the compose stack's web container); `files-gated.spec.ts` covers the disabled module inside the shell and `files-unavailable.spec.ts` the page without an API.
- When `az login` cannot give your Dewiride identity a token (for example, when the CLI holds two accounts with the same user name, which `AzureCliCredential` refuses to choose between), start the main API store-less against Azurite, as `e2e.yml` does: `APPCONFIG_ENDPOINT=` (empty, so user secrets do not select the store), `Erp__Platform__Attachments__EmulatorHost=127.0.0.1`, `Erp__Platform__Attachments__BlobServiceUri=` (empty, so exactly one storage target is set) and `Erp__Platform__RateLimiting__AnonymousPermitLimit=6000` (the `local-dev` value), with `erp-azurite` running; the database connection string and the attachments key still come from user secrets.
- Drag and drop in Playwright: the spec builds the `DataTransfer` inside the page (`page.evaluateHandle`) and raises `dragenter`, `dragover` and `drop` from inside the page with `new DragEvent(type, { bubbles: true, cancelable: true, dataTransfer })` on the drop zone (`AttachmentsPage.dragOver`, `drop`), because WebKit does not deliver drag events raised with `locator.dispatchEvent` to React's delegated listeners; the drag is retried with `expect(...).toPass()` until the drop zone reports `data-dragging="true"`, and only then is the file dropped.
- Console errors: the auto fixture `consoleErrors` (`frontend/e2e/fixtures/test.ts`) fails a test on any `console` error and any uncaught `pageerror`; `test.use({ expectedConsoleError: /pattern/ })` tolerates one expected message in both, and each pattern names the status or failure it provokes, never every failed load. The API-refusal test expects the browser's 415 resource log line, the form kit's failed-call test only the lines of its aborted call (`net::ERR_CONNECTION_RESET`) and its 502, and its out-of-date-page test only the 404 line (Chromium logs both failed calls and the 404, WebKit the 502 and the 404, Firefox none of them), and the pagination test expects WebKit's report of a Next.js router prefetch (`?_rsc=`) that a navigation cancels, which WebKit words as an access-control failure (`/\?_rsc=[\w-]+ due to access control checks\.$/`).
- Rate limit locally: without `KnownNetworks` every browser request and every server-side call of the web app reaches the API from loopback, so a local run over five browser projects shares one anonymous partition; the `local-dev` label raises `Erp:Platform:RateLimiting:AnonymousPermitLimit` to 6000 for that reason ([configuration](../configuration.md)). CI runs store-less, one project per job, under the default 600.
- Statutory logic: dated, table-driven `[Theory]` cases from the parameter sets, including the boundary dates on both sides of a change.
- Coverage: at least 80 % line coverage for Domain + Application per module; a pull request never lowers it.
- Every feature ships a Playwright spec that visits every page it adds and clicks every button, menu item, tab, dialog and form control (happy path plus one validation failure), asserts no console errors and takes an ARIA snapshot of key screens.
- Playwright runs every visual test in light and dark theme (`forEachTheme`) on desktop Chromium, Firefox, WebKit and the newest Pixel and iPhone descriptors; behavioural tests that render nothing theme-specific (redirects, header checks, the API smoke) run once, and `tests/smoke/**` runs on Chromium only. Pull requests run Chromium and one mobile project, `main` runs the full matrix. Screenshots are named `<spec>/<name>--<project>--<theme>.png`; under `--repeat-each` the copies after the first append `--repeat<N>` to the name, because the copies of a test run side by side and two of them writing one file fail with `EBUSY` on Windows. A second web instance started without an API (`E2E_OFFLINE_BASE_URL`) covers the unavailable states.
- Screenshots: the `capture(name, target?)` fixture takes a screenshot of the element when a locator is given and of the full page otherwise, both with `animations: "disabled"`, which fast-forwards finite animations and transitions to their end and cancels infinite ones, so a capture never shows a dialog half faded in or the login glow mid-cycle. An element capture hides the sticky elements outside the target while it is taken, so the app header never appears partway down a tall section. Chromium paints at most 16,384 device pixels of a capture's height and leaves the rest blank, and WebKit refuses a capture taller than 32,767, so the fixture fails any page or element capture taller than 16,384 device pixels (its CSS height times `devicePixelRatio`) instead of keeping a cut image as evidence; a target that tall on a phone is captured in parts. Screenshots are gitignored artefacts that CI uploads; no test compares them with a baseline.
