# Authentication threat model

How the sign-in, the session, the API's bearer tokens and the audit trail resist the attacks that matter for a single-tenant ERP signed in through Microsoft Entra ID, what is left, and which tests prove each answer. The decisions behind it are ADR-0004, ADR-0031 to ADR-0036, [ADR-0038](../adr/0038-sign-in-limit-security-events-and-the-audit-schema.md), [ADR-0039](../adr/0039-people-and-their-admission.md), [ADR-0040](../adr/0040-directory-invitations.md), [ADR-0041](../adr/0041-roles-and-permissions.md) and [ADR-0043](../adr/0043-change-records-and-the-append-only-audit-schema.md); the request pipeline order is in [request pipeline](../architecture/request-pipeline.md) and the wire rules in [HTTP conventions](../architecture/http-conventions.md). The protection of PAN, Aadhaar, bank and salary fields arrives with its own sub-phase and is not covered here.

## What is protected

| Asset | Where it lives | Protection |
|---|---|---|
| The session | the cookie `__Host-erp-session`, a ticket protected by the Data Protection key ring (`DataProtectionKeyRing.ApplicationName` `Dewiride.Erp`; in production the key ring folder on the volume `erp-ai-pro-data-protection-keys`, wrapped by the Key Vault key `Erp:Platform:DataProtection:KeyIdentifier`, ADR-0032) | HttpOnly, Secure, SameSite=Lax, path `/`, no Domain, ends with the browser session (`IsPersistent` false), slides within `SessionIdleTimeout` (30 minutes) and is refused after `SessionLifetime` (12 hours) |
| Entra's tokens (access, refresh, id) | MSAL's token cache, the table `platform_caching.DistributedCacheEntries`, each value protected by `ProtectedTokenCacheStore` | never sent to the browser, the web container or a log; `SaveTokens` is false |
| The API's credential at Entra | the certificate `Erp:Platform:Identity:ClientCertificate`, a Key Vault reference | no client secret exists; the code is redeemed, and the application token of the account check (`User.Read.All`, ADR-0047) is requested, with a certificate-signed client assertion, so the certificate reads the directory without a session |
| The antiforgery pair | `__Host-erp-antiforgery` (HttpOnly) and `__Host-erp-xsrf` (readable by the page) | Secure, SameSite=Strict, path `/`, end with the browser session |
| The record of each person | `identity_users.Users`, which admits a person to a session or a bearer route while it is active and not deleted, and holds the roles assigned to them in the ERP | changed only through `/api/identity/users` by holders of its permissions, today administrators alone, and by each person's own sign-in for their name, work email and sign-in time; the colour theme each person chooses is a row of its own beside the record (`PersonThemes`), changed only by that person through `PUT /api/identity/users/me/theme`, which needs no permission, reaches the caller's own row only and is recorded under them ([ADR-0046](../adr/0046-organisation-pages-my-profile-and-the-saved-theme.md)) |
| The company directory | Microsoft Entra, read through Microsoft Graph with an administrator's own delegated token for `User.ReadBasic.All` (`GraphPeopleDirectory`): display name, mail and user principal name; each person's own photo, read with their own delegated token for `User.Read`; and whether the accounts linked to people's records are enabled, read with the application's own token for the application permission `User.Read.All` (`GraphDirectoryAccounts`) | the search and the lookup only by the people routes that require `identity.users.people.register`, which administrators alone hold, a photo only by `GET /api/identity/users/me/photo`, for the signed-in person whose it is, and the account states only by `POST /api/identity/users/directory/account-check`, which requires `identity.users.people.change-status` and asks for `id` and `accountEnabled` of the linked accounts alone ([ADR-0047](../adr/0047-user-lifecycle-the-account-check-and-the-team-handover.md)); the token stays in the token cache, and neither it nor the search text reaches a log or a span of the API (`TelemetryTests`) or of the web server, whose spans keep no query string (`queryFreeSpans`) |
| The audit trail | `audit.SecurityEvents` (sign-in, sign-out, refused tokens, exports of the history) and `audit.ChangeRecords` (every change to a person's record, a department, a designation, a position or an attachment, with its before and after values) | the API's database user may only insert into the schema `audit`: it is a member of `erp_audit_append_only`, which is denied `UPDATE`, `DELETE` and `ALTER` there; rows past their retention are deleted only by the migrator, under its own principal; the change records are read only by the routes of `Platform/Audit`, which administrators alone may use (section "The audit trail") |
| The proxy's certificate authority | the root and intermediate with their keys and the issued certificates, on the external volume `erp-ai-pro-proxy-data` mounted at `/data` of the proxy container (`/data/caddy/pki/authorities/local`, ADR-0048) | the files are owned by the proxy's non-root user with mode 0600 in folders of mode 0700, and Docker keeps the volume under its root-only directory, so reading the key takes root or the `docker` group on the server, whose only member is the deploy account `erp-ai-pro`, which signs in with its keys alone (ADR-0049); only `root.crt`, the public root, is ever copied to the devices that trust it (`docs/operations/runbooks/proxy.md`) |

Trust boundaries: the browser and the edge proxy (TLS from the proxy's own certificate authority while people open the server's local address, from Let's Encrypt once the ERP has a public name; HSTS only then, because a browser ignores it for an IP address, RFC 6797 section 8.1.1; ADR-0048); the edge proxy, the web container and the API on the compose network, whose peers alone may send `X-Forwarded-For` (`Erp:Platform:Host:KnownNetworks`); the API and `login.microsoftonline.com` (code redemption, refresh-token redemption, discovery, keys); the API and `graph.microsoft.com` (the directory); the API and SQL Server; the API and Key Vault.

## Cross-site request forgery

- An attacker's page makes the browser send a request that changes data with the person's session.
- The session cookie is SameSite=Lax, so no cross-site POST, PUT, PATCH or DELETE carries it. Every such request the session cookie signs in must also carry the request token in `X-XSRF-TOKEN`, which only a page of this origin can read from `__Host-erp-xsrf`; the Strict cookie token travels with no cross-site request at all. `AntiforgeryValidationMiddleware` refuses a missing or wrong token with 400 `antiforgery.token-missing` or `antiforgery.token-invalid` before the feature gate, idempotency and the module (ADR-0033). No product endpoint disables the check (`ModuleCatalogTests.Endpoints_NeverDisableTheAntiforgeryCheck`).
- `GET` never changes data. `GET /api/auth/antiforgery` issues the pair again only for a request whose `Sec-Fetch-Site` is absent or `same-origin`, because issuing it for another site's navigation would replace the cookie token and refuse every page of this site. `GET /api/platform/audit/changes/export` records each export as a security event, so it too answers only such a request (`FetchMetadata.IsFromThisOrigin`, which both use) and refuses every other, a `same-site` one and an address typed into the browser (`none`) included, with 400 `request.invalid` before anything is recorded: another site's link cannot make an administrator's browser download the history and leave an export in the trail that they never made (`ExportChangesTests`).
- The sign-out: `POST /api/auth/logout` with a session needs a valid request token, in `X-XSRF-TOKEN` or in the form field `__RequestVerificationToken` that the sign-out form fills; without a session, a request from another site (`Sec-Fetch-Site` neither absent nor `same-origin`) answers 401, and a same-origin one only reaches Entra's end-session endpoint, changing no cookie (ADR-0036).
- Login CSRF, signing the person in as someone else: the callback needs the protected `state` the handler issued and the correlation cookie it wrote in the same browser, and the code is redeemed with the PKCE verifier kept in that state; a code and state taken from the attacker's own sign-in fail in another browser with a correlation failure (`SignInCallbackTests.Post_CallbackWithAValidStateButNoCorrelationCookie_LandsOnTheSignInFailedPage`). The nonce cookie is written but no nonce is compared: Microsoft.Identity.Web redeems the code itself, and the OpenID Connect handler then skips its validation of the token response, the only place it compares the nonce (ADR-0031), so the state and the correlation cookie are the defence. The registrations require an app role assignment (`appRoleAssignmentRequired`), so an attacker would first have to be an assigned user of the tenant.
- No CORS: the browser calls `/api/*` on the web origin, so the API answers no cross-origin request with credentials.

## Session fixation

- An attacker plants a session cookie of their own in the person's browser and waits for the person to use it, or plants the sign-in's cookies to steer the callback.
- The `__Host-` prefix makes the browser refuse a session or antiforgery cookie that lacks Secure or path `/` or names a Domain, so neither a sibling subdomain nor a page served over plain HTTP can set one. The API issues a new ticket at every sign-in, from `SignInEvents.TicketReceived`, never from a value in the request.
- The account a session is bound to, `<uid>.<utid>` (the key of the person's token cache entry and sign-out record, and the account their Entra session record names), comes from the token Microsoft.Identity.Web redeems with the code, never from a `client_info` posted to the callback, which the sign-in does not ask Entra for. A callback whose posted `client_info` names another person signs in only the person whose code it carried, and the session of one whose redeemed token carries no `client_info` is refused at its next request, even while the person's account is in the token cache (`SignInCallbackTests.Post_CallbackWithTheClientInfoOfAnotherPerson_IssuesASessionOfTheAccountTheCodeRedeems`, `Post_CallbackWhoseCodeRedeemsNoClientInfo_IssuesASessionTheNextRequestRefusesAndClears`).
- The correlation and nonce cookies carry the `__Secure-` prefix (`MicrosoftIdentityOptionsSetup.CorrelationCookiePrefix`, `NonceCookiePrefix`): HttpOnly, Secure, SameSite=None (Entra posts the callback from its own site), path `/api/auth/signin-oidc`, expiring after the 15-minute remote authentication timeout (`web-security.spec.ts`). A page served over plain HTTP cannot set them. The `__Host-` prefix would need path `/`, which the handler does not use for them, so a host under the same registrable domain served over https could still set one with a Domain attribute (residual risk 4).
- The session check refuses a cookie signed in at or before the person's last sign-out (`SessionRevocations`), one whose Entra session record is missing or names another account (`EntraSessions`), and one whose account is no longer in the token cache, so a cookie copied before a sign-out does not come back to life.

## Open redirects

- An attacker sends the person a sign-in link that returns them to another site.
- `GET /api/auth/login?returnUrl=` accepts only a local path: it starts with `/` but not `//` or `/\`, contains visible ASCII only (`!` to `~`), is not the virtual form `~/` and is at most 2048 characters (`LoginRequest.IsLocalPath`, `RedirectHttpResult.IsLocalUrl`); anything else answers 400 `request.invalid` with `errors.returnUrl` and writes no cookie (`LoginEndpointTests`). The return path travels inside the protected `state` and is read back from it after the callback, so it cannot be changed on the way.
- The web app applies the same rule: `localReturnPath` (`frontend/apps/web/src/shared/auth/sign-in-addresses.ts`) drops a value that fails, never repairs it, and counts a repeated parameter as absent; `proxy.ts` sends a visitor without a session to `/login?returnUrl=<path and query>` built from the request's own path (`signInRedirectFor`), and a `/login` address carrying a foreign `returnUrl` loses that parameter (`loginAddressWithoutForeignReturn`); the sign-in page sends a signed-in visitor straight to the validated path (ADR-0036).
- `redirect_uri` and `post_logout_redirect_uri` are `Erp:Platform:Identity:WebOrigin` plus the callback path, never built from the request host (`RedirectPathsTests`), and Entra accepts only the registered redirect URIs: the web origin's `/api/auth/signin-oidc` and `/api/auth/signout-callback-oidc`. The local-dev registration lists no API-origin redirect URI since 2026-10-10 (`scripts/azure/lib/graph.sh`, `signin_redirect_uris`; `verify.sh --entra`), so Entra sends no code to a port the web app does not serve.
- Every failure and sign-out lands on a fixed page: `/login?error=sign-in-failed`, `/login?reason=signed-out`, `/login?reason=session-ended`.

## Token leakage

- The browser never holds a token: the API is the confidential client of the backend-for-frontend (ADR-0004, ADR-0031), the session cookie is opaque, and Entra's tokens stay in the protected token cache.
- The code reaches the API in the body of Entra's form post (`response_mode=form_post`), never in an address, so no browser history, `Referer` or proxy log holds it; PKCE (S256) and the certificate client assertion mean a stolen code cannot be redeemed elsewhere.
- Logs carry no token, error description, query or posted form: a failed callback logs its category and OAuth error code only, `Microsoft.Identity.Web` logs at `Warning` and the OpenID Connect handler at `Critical`, `IdentityModelEventSource.ShowPII` is never set, the request lines of `Microsoft.AspNetCore.Hosting.Diagnostics` stay at `Warning` and trace query values are redacted ([observability](../guides/observability.md)). Security events hold no token, name or email.
- Responses: the API answers `Cache-Control: no-store` (except reference data marked otherwise, and the caller's own photo, which the browser keeps privately only for the sign-in it was answered to: `Vary: Authorization, Cookie`) and `Referrer-Policy: strict-origin-when-cross-origin`, and so do the pages.

## Token replay and id-token misuse

- An attacker replays a token they obtained, or presents the sign-in's id token, whose audience is the same registration, as a bearer token.
- A bearer route accepts only a v2.0 access token of the tenant: authority and exact issuer `<TenantId>/v2.0`, audience exactly the client id, RS256, its lifetime with the default clock skew, `ver` 2.0, `tid` the tenant, a GUID `oid`, and a holder: a person's token carries `scp` with `idtyp` absent or `user`, an application's carries no `scp` and either `idtyp` `app` or a `sub` equal to its `oid` (`BearerTokenEvents`, `BearerTokenClaims.HolderOf`, ADR-0034). The id token carries no `scp`, so it is refused as `not-an-access-token` (`BearerTokenSignInTests`, "an id token of the sign-in"). A person's token is granted by the route's scopes, an application's by its application roles, never by the person's own roles.
- A copied access token is not bound to its sender (no proof of possession), so it works until it expires; Entra issues access tokens for a random 60 to 90 minutes by default (Microsoft identity platform, "Access tokens", section "Token lifetime"). No product route takes bearer tokens until `integrations-public-api-and-webhooks`, and the platform flag `Erp.Platform.Identity.BearerTokens` is off under both labels (residual risk 5).
- A copied session cookie works until its idle timeout, its lifetime or the person's sign-out; HttpOnly, Secure and SameSite=Lax close the usual ways of taking it.
- An authorization code is single-use at Entra and bound to the PKCE verifier kept in the protected state.

## The front-channel sign-out

- `GET /api/auth/signout-oidc?iss=&sid=` is anonymous by necessity: Entra loads it in a hidden cross-site frame that carries no session cookie (ADR-0036).
- The Entra session id `sid` is no secret: every app of the tenant signed in within that Entra session receives it. A request naming one can therefore end at most the ERP sessions signed in from that Entra session, in that browser, never another session of the person and never a sign-in (owner decision of 2026-10-08). A request whose `iss` is not the tenant's issuer, in either of its two forms, changes nothing and is recorded as `FrontChannelSignOutRefused`; every well-formed request answers the same 200 without a body, so the answer never says whether a session ended (`FrontChannelSignOutTests`).
- The path falls under the sign-in limit, so a caller cannot try `sid` values faster than `SignInPermitLimit` per address.

## People who must lose access

- A person leaves, or must lose access at once, while they hold open sessions on several devices; removing their app role assignment in Entra stops only their next sign-in at Entra.
- The person's record decides (`IPersonAdmission`, ADR-0039): a sign-in whose record is deactivated starts no session, lands on `/login?error=account-deactivated` and is recorded as `SignInRefused`, and every session and person's bearer token of someone whose record is deactivated or deleted is refused from their next request, on every device and API instance, because the session check and the bearer handler read the record on every request (`SessionAdmissionTests`, `SignInCallbackTests.Post_CallbackOfADeactivatedPerson_LandsOnTheAccountDeactivatedPageWithoutASessionAndRecordsTheRefusal`, `BearerTokenSignInTests`). A record that cannot be read fails the request with 500 and admits nobody.
- An account disabled or deleted in Entra is deactivated in the ERP by the account check (`POST /api/identity/users/directory/account-check`, ADR-0047), with the reason `accountDisabled` or `accountDeleted` in the change records, so its sessions end at their next request; an answer of the directory without one enabled account, or without the enabled account of the administrator running the check, deactivates nobody, so a wrong or empty answer never deactivates the administrator who could reactivate the others (`AccountCheckEndpointsTests`, `GraphDirectoryAccountsTests`). It runs when an administrator presses its button and, once `business-building-blocks-background-jobs-and-scheduling` schedules it, every night.
- Two administrators who deactivate or delete each other at once leave one of them active: every status change, deletion and account check takes the organisation lock and is refused with 409 `user.actor-inactive` when no active record names the person making it any more (`ActingAdministratorTests`).
- Only holders of the people permissions change records, today administrators alone, whom only the app role `Erp.Admin` makes, a role the registration gives people only (`AppRolesTests`); an administrator cannot deactivate or delete their own record (`PeopleEndpointsTests`). The name and work email follow Entra at every sign-in and no route edits them.
- A record an administrator registers before the person's first sign-in is linked by the work email only while it names no Entra account, so a linked record can never be taken over through an email address; taking an unlinked one needs an account of the tenant whose sign-in name is that address and which holds an app role of the registration, that is, a directory administrator. A record that names an Entra account before the first sign-in comes only from an invitation, which reads the object id, the name and the sign-in name from the directory, never from the caller (ADR-0040).

## The company directory

- A person who is not an administrator reads the directory through the ERP, an administrator reads more of it than Entra lets them, or a search text, which names people, leaks into the logs.
- `GET /api/identity/users/directory` and `POST /api/identity/users/invitations` require `identity.users.people.register`, which administrators alone hold (`PeopleEndpointsTests.EveryRoute_AsPersonWithoutItsPermission_Returns403RequestForbidden`). The token is the administrator's own, issued for `User.ReadBasic.All` only, so Microsoft Graph answers what that person may read and no more: the basic profile, never a phone number, a manager or a group (`GraphPeopleDirectoryTests`, `InvitationEndpointsTests`).
- The account check reads with an application token for `https://graph.microsoft.com/.default`, made from the sign-in registration's certificate (`CreateAuthorizationHeaderForAppAsync`), which holds the application permission `User.Read.All`; it asks only for `id` and `accountEnabled` of the linked object ids, 15 at a time, follows a next page only on `graph.microsoft.com`, where the token may go, and logs the operation, the status and the error code, never an id, a name or the token (`GraphDirectoryAccountsTests`).
- Entra refusing the token (consent missing, a sign-in interaction required) and Graph refusing the request answer 403 `directory.access-denied`, and a directory that cannot be reached answers 503 `directory.unavailable`; neither starts an interactive sign-in from the API.
- Redeeming the session's refresh token for Graph writes the person's token cache entry again; `SessionBoundTokenCacheStore` gives that write the end of the session as its absolute expiry, so the entry never outlives `SessionLifetime` after the sign-in plus the margin (`SessionBoundTokenCacheStoreTests`, `TokenCacheStorageTests.Get_DirectorySearch_WritesTheEntryAgainExpiringWhenTheSessionEndsNotALifetimeAfterTheWrite`).
- The search text travels only in the query strings of `GET /api/identity/users/directory` and of Graph's search. The server span records the API's query values as `Redacted`, and the runtime shows Graph's whole query as `*` in its span and in the HTTP client's logs; the API logs the operation, the status and Graph's error code, never the text, Graph's message or a token (`TelemetryTests.Get_DirectorySearch_ExportsNoSpanOrLogCarryingTheSearchTextOrTheDirectoryToken`, which reaches the directory over a real TLS connection, so the runtime records the Graph client span).

## Permissions

- A person reaches data or an action their roles do not allow, gives themselves a role, keeps a role after it was taken, or an application borrows a person's roles (ADR-0041).
- Every product route either allows anonymous callers (the permanent list), is one of the routes any signed-in caller may use (`ModuleCatalogTests.SignedInRoutes`: the person, the session, the antiforgery pair, the feature flags, and the caller's own record, photo and theme under `/api/identity/users/me`, [ADR-0046](../adr/0046-organisation-pages-my-profile-and-the-saved-theme.md), which reach only the record linked to the caller's `IActorContext.ActorId` and read the photo with the caller's own delegated `User.Read` token), or requires one permission through `RequirePermission`, whose policy also requires a signed-in caller of the route's scheme. The architecture tests fail on any other route, on a permission route that also allows anonymous callers (authorization would skip it entirely) and on a permission no module declares, and each module's tests pin the permission of each of its routes (`Route_OfEachUseCase_RequiresItsOwnPermission`); such a permission throws at the first request rather than refusing everyone silently (`PermissionAuthorizationHandlerTests`).
- Roles cannot be raised from inside the ERP:
  - Administrator comes only from the app role `Erp.Admin` in the request's token, and Employee only from `Erp.User`. The record cannot hold either: the API's `PersonRole` cannot express them, and `User.AssignRoles` refuses them.
  - Finance, HR and Manager are assigned only by holders of `identity.users.people.assign-roles`, today administrators alone, and naming roles in a registration or an invitation needs the same permission (`RoleAssignmentTests`, `InvitationEndpointsTests`).
  - A record's stored roles count only as Finance, HR or Manager, so a row written outside the API that names Administrator or Employee grants neither (`PermissionAuthorizationHandlerTests.HandleAsync_RecordNamingTheRolesOnlyAppRolesGive_GrantsNeither`, `UserAdmissionTests.AdmissionOfAsync_RecordWhoseStoredRolesNameRolesTheErpDoesNotAssign_ReturnsOnlyTheAssignableOnes`).
- Every assignment of roles, and every change of a record's status, is a change record of the person's record, naming who made it, when, from which address and the roles or status before and after (section "The audit trail").
- Roles assigned in the ERP are read with the admission on every request, never written into the cookie, so a role taken counts for nothing from the person's next request, on every device (`AssignedRoleTests`). App roles follow the session's ID token and change at the next sign-in (residual risk 10).
- The assigned roles reach the request only once the session check or the bearer handler accepted the caller, and count only for the caller's own object id (`PermissionAuthorizationHandlerTests.HandleAsync_RolesAssignedToAnotherPerson_DoNotCount`, `AssignedRoleTests.Get_PermissionRouteWithASessionWhoseAccountTheTokenCacheNoLongerHolds_AnswersUnauthenticated`).
- An application's token holds no role whatever its `roles` claim names, so it reaches no permission route; a refusal of a token the route admits is answered with a plain `Bearer` challenge and recorded as `missing-permission` (`AssignedRoleTests.Get_ApplicationTokenNamingThePersonAppRoles_HoldsNoRole`, `BearerTokenPermissionTests`).
- The web app hides the navigation entries and controls a person may not use, but it is not the boundary: every route checks its permission, and every Server Function checks it again before it calls the API.

## Brute force and flooding

- The sign-in paths (`AuthPaths.SignInPaths`: the login, both OpenID Connect callbacks, the front-channel sign-out and the logout, in any case and with any trailing slashes) are limited by `SignInRateLimitingMiddleware`, before authentication, because the handler answers the callbacks inside it: each path has an allowance of its own per client address, `Erp:Platform:RateLimiting:SignInPermitLimit` (60) per `SignInWindow` (1 minute), so the sign-ins of a busy office never refuse its sign-outs, then 429 `rate-limit.exceeded` with `Retry-After` (`SignInRateLimitingTests`, `AuthPathsTests`). Every other request meets the global limiter: an anonymous caller per address, a signed-in one per actor (ADR-0019).
- `GET /api/auth/login` challenges only a page the browser opens itself (`Sec-Fetch-Mode: navigate`, `Sec-Fetch-Dest: document`), because every challenge writes two cookies and images or frames that another site loads again and again could otherwise fill the person's cookies until this site refused them.
- IdentityModel writes a `Warning` or `Error` record for every token it refuses; `BoundedIdentityModelLogger` lets at most ten of them through per minute and counts the rest, so refused tokens cannot fill the log through IdentityModel. The refusals themselves are security events.
- A security event that names no actor can be caused by anyone, from any number of addresses, so `AnonymousSecurityEventBudget` writes at most 60 of them a minute across the API and only counts the rest (owner decision of 2026-10-10): a caller with many addresses cannot fill the database with failed callbacks, other-issuer front-channel requests or refused bearer tokens (`AnonymousSecurityEventBudgetTests`, `SignInCallbackTests.Post_FailedCallbacksNamingNobodyOverTheBudget_LeaveOnlyTheBudgetsRecordsInTheMinute`). An event that names an actor is never held back. While the table cannot be written, each event that names an actor and fails logs one `Error`; the budget is spent before an event without an actor is tried, so those failures are bounded too.

## The audit trail

The schema `audit` (`BuildingBlocks.Auditing`) holds two append-only tables: the security events (ADR-0038) and the change records ([ADR-0043](../adr/0043-change-records-and-the-append-only-audit-schema.md)).

- `audit.SecurityEvents` records:

  | Kind | Written by | Detail | Actor |
  |---|---|---|---|
  | `SignedIn` | `SignInEvents.TicketReceived`, before the session is returned; a sign-in whose record cannot be written starts no session | — | the person's object id |
  | `SignInFailed` | `SignInEvents.RemoteFailure`, and `TicketReceived` when the session cannot start | `<category>:<OAuth error code>`, such as `identity-provider:access_denied`, `code-redemption:invalid_grant`, `callback:none`, `session:none` | the person's object id when the ticket names one |
  | `SignedOut` | `POST /api/auth/logout` with a session | — | the person's object id |
  | `FrontChannelSignedOut` | `FrontChannelSignOut`, when a recorded Entra session ends | — | the object id of the account the Entra session record names |
  | `FrontChannelSignOutRefused` | `FrontChannelSignOut`, for another issuer | `other-issuer` | — |
  | `SignInRefused` | `SignInEvents.TicketReceived`, when the person's record does not admit them | `deactivated` | the person's object id |
  | `BearerTokenRefused` | `BearerTokenEvents` (`AuthenticationFailed`, `TokenValidated`, `Forbidden`), only while the bearer flag is on | `expired`, `not-yet-valid`, `invalid-audience`, `invalid-issuer`, `unknown-signing-key`, `invalid-signature`, `invalid-algorithm`, `malformed`, `invalid`, `validation-error`, `not-an-access-token`, `not-admitted` (a person's token whose record does not admit them), `insufficient-scope`, `missing-permission` (a token the route admits whose holder lacks the route's permission) | the token's `oid` once its signature was valid |
  | `ChangeHistoryExported` | `ExportChangesHandler` (`Platform/Audit`), before the export's first byte; an export whose record cannot be written is refused with 500, and a refused export records nothing | the number of records exported (`records:<count>`) | the administrator's object id |

- Every row carries the time (UTC), the client address that forwarded headers resolved (an IPv4-mapped address as IPv4), the client application a bearer token names (`azp`, else `appid`; unverified for a token that failed validation) and the request's correlation id, the `X-Correlation-ID` its answer carries. No row holds a name, an email, a user agent or a token: an investigation needs no more, and the Digital Personal Data Protection Act, 2023 asks for no more than the purpose needs (owner decision of 2026-10-10).
- A record that cannot be written is logged by `SignInAudit` at `Error` with its exception and the request goes on, except a sign-in, whose session is then not started and whose failure is recorded instead; a record that failed leaves the request's context, so a later record of the same request never writes it after all (`SqlSecurityEventRecorderTests`). A request its caller abandoned while its bearer token was read is no refusal and is not recorded, and a token that cannot even be read, an encrypted one whose segments are not base64url included, is recorded as `malformed` naming no application.
- The front-channel sign-out names the account its Entra session record holds only when that account's home is this tenant, so the actor is the same `oid` the person's other records carry; a guest's home object id belongs to another tenant, so a guest's front-channel sign-out names no actor.
- Events that name no actor are written at most 60 a minute (section "Brute force and flooding").
- `audit.ChangeRecords` holds one row per change to a recorded type (a person's record with its status and roles, a department, a designation, a position, an attachment), written in the same save as the change, so a change whose record cannot be written is not saved, a sign-in's admission included: the actor's object id (a person signing in for the first time is the actor of their own record's creation), the time of the change, the operation, the record and the subject it is filed under by their change keys, the client address, the correlation id and the before and after values of the changed fields. The values keep names, work emails and phone numbers, readable by administrators alone (`platform.audit.changes.read`); actors are never copied but named when the history is read; PAN, Aadhaar, bank details and salary are never readable there (owner decision of 2026-10-16). The rule that a row names no one is the security events' own.
- Append-only by database rights: the API's database user is a member of `erp_audit_append_only`, which the migration `AddChangeRecords` denies `UPDATE`, `DELETE` and `ALTER` on the schema, so the running API can only insert into either table, and cannot truncate one either (`AppendOnlyAuditTests`, under `EXECUTE AS USER`). In code, the capture refuses a change or a deletion of an append-only row and the bulk guard an `ExecuteUpdate` of one, no product code calls `Update` or `Attach`, and no module sets an entry's state, runs SQL of its own or uses the database driver (architecture tests), so the API itself never tries.
- Only the migrator deletes, under its own principal: past `Erp:Platform:Auditing:SecurityEventRetention`, one year (owner decision of 2026-10-10), for security events, and past `Erp:Platform:Auditing:ChangeRecordRetentionYears`, eight financial years after the financial year of the change (owner decision of 2026-10-16), for change records; after the seeders of every `migrate`, and on `retain`, which runs no migration and which `erp-ai-pro-retain.timer` runs on the server every night at 01:00 India time (ADR-0049; residual risk 14). Direction (iv) of the CERT-In Directions under section 70B(6) of the Information Technology Act, 2000, of 28 April 2022, requires every service provider and body corporate to keep the logs of all its ICT systems securely for a rolling 180 days within Indian jurisdiction and to provide them to CERT-In with an incident report or on its order; one year exceeds that, and the setting must never go below 180 days (residual risk 9). Rules 6(1)(e) and 8(3) of the Digital Personal Data Protection Rules, 2025 ask for logs to be kept at least one year from about 13 May 2027, which one year meets.
- Only the two routes of `Platform/Audit` read the change records, and only administrators hold their permissions; each export is a `ChangeHistoryExported` row. No route reads the security events yet (`operations-hardening-admin-console`).

## Headers and the content security policy

- Pages (`proxy.ts`): a nonce-based CSP with `strict-dynamic`, `object-src 'none'`, `frame-ancestors 'none'`, `upgrade-insecure-requests` and `form-action 'self' https://login.microsoftonline.com/common/oauth2/v2.0/logout`, plus `X-Content-Type-Options: nosniff`, the referrer policy and the permissions policy. Chrome checks the sign-out form's redirect to the tenant's end-session endpoint against `form-action`, and a redirected request is matched on its origin only (CSP Level 3, section 7.6), so the path of that source lets no form of a page post to another Microsoft address while the sign-out's redirect still passes (ADR-0036).
- API: `default-src 'none'; frame-ancestors 'none'`, `nosniff`, `Cross-Origin-Resource-Policy` and `Cross-Origin-Opener-Policy` `same-origin`, `X-Permitted-Cross-Domain-Policies: none`, `Cache-Control: no-store`, no `Server` header; the edge proxy owns HSTS.
- `frontend/e2e/tests/smoke/web-security.spec.ts` checks the headers of a page and of an API answer through the web origin, and the prefix, Secure, HttpOnly, SameSite, path and lifetime of every cookie the sign-in start, the session and antiforgery write.

## Residual risks

1. **Refused bearer tokens are not rate limited before they cost work.** Authentication runs before the global limiter so that a signed-in caller is limited as its actor, so a client sending refused tokens costs a signature check and an insert into `audit.SecurityEvents` each. No route takes bearer tokens yet and the flag is off; `integrations-public-api-and-webhooks` bounds it before the first one does.
2. **The trail binds the API's own database user only.** A compromised API can still insert forged rows into `audit`, or change business tables with raw SQL that writes no change record. Members of `sysadmin`, the `dbo` user, the owner of `audit`, members of `db_owner` (who could also revoke the denial) and the migrator's user are not bound and can rewrite the trail. Host processes and tests run as the developer's sysadmin login and CI's container stack as `sa`, so nothing is enforced there; only the local container stack's api login `erp_local` and production's api user (`first-deployment-production-database-provisioning`) are members of `erp_audit_append_only`.
3. **The 180 days within India hold only if the data stays in India.** The production database and its backups, and every other ICT log, must stay in India (`first-deployment-production-database-provisioning`, `first-deployment-go-live-checklist-and-production-smoke`).
4. **The correlation cookie can be planted from the same registrable domain.** A host under the ERP's registrable domain served over https could set a correlation cookie for the attacker's own sign-in start, and so complete a login CSRF with the attacker's state and code, since no nonce is compared; the attacker must also be an assigned user of the tenant. The ERP's host must share its registrable domain with no host the company does not control (`first-deployment-go-live-checklist-and-production-smoke`).
5. **Bearer tokens are not bound to their sender.** A copied access token works until it expires (60 to 90 minutes).
6. **People behind one public address share each sign-in path's allowance.** An office whose people reach the ERP through one address shares 60 requests a minute on each path: about 60 sign-ins, and as many sign-outs on their own paths; a larger office raises `SignInPermitLimit` in App Configuration.
7. **The local-dev registration has no front-channel sign-out**, because Entra refuses an http front-channel logout URL; signing out of another Microsoft app leaves local sessions to their own sign-out or expiry.
8. **A flood can hide events that name no actor.** Beyond 60 a minute such events are only counted in the log, so a genuine failed callback or refused token sent during a flood may go unrecorded; the log names how many were held back.
9. **Nothing refuses a retention below 180 days.** `SecurityEventRetention` is validated from 1 day, because a statutory minimum belongs in a parameter record with its government source, never a literal in code; a value below 180 days breaks direction (iv), and the migrator's next run deletes the rows irrecoverably.
10. **Changes in Entra reach open sessions only at their next sign-in or the next account check.** An app role assignment removed or changed in Entra stops or changes the next sign-in, but an open ERP session keeps the app roles of its sign-in, Administrator included, until it ends (30 minutes idle, 12 hours at most). An account disabled or deleted in Entra keeps its open sessions until the account check deactivates its record: when an administrator runs it, and nightly only once `business-building-blocks-background-jobs-and-scheduling` schedules it; deactivating the record refuses its requests only while the record stays deactivated.
11. **The account check believes Microsoft Graph.** An id missing from Graph's answer reads as a deleted account, so a directory that wrongly left out some linked accounts would deactivate their people; an answer without one enabled account, or without the enabled account of the administrator running the check, changes nothing, and that administrator reactivates anyone the check deactivated wrongly, whose reason the change records keep. Once the check runs every night without a person, a wrong answer could deactivate every administrator; someone who manages Microsoft Entra then gives `Erp.Admin` to a person without a record, whose first sign-in starts an active one.
12. **The directory can be read at any time.** The consent for `User.ReadBasic.All` covers the whole organisation, so the refresh token of any open session can be redeemed for it, and the application permission `User.Read.All` (ADR-0047) needs no session at all: whoever takes over the API process, which holds the sign-in certificate, can read the full profiles of the directory at any time (owner decision of 2026-10-18). Every member of the tenant can read most of the same details in Entra by default.
13. **A directory search racing its sign-out can write the token cache entry back.** The sign-out removes the person's entry after recording the sign-out, and a search that redeemed the refresh token just before can write the entry again just after; the sign-out record refuses every session of that person, and the entry, unread, expires 35 minutes after that write at most.
14. **Retention runs only with the migrator.** Rows past their retention are deleted when the migrator runs: at every deployment, and every night through `retain`, which `erp-ai-pro-retain.timer` runs once the migrator's certificate is on the server (ADR-0049). Until then, and whenever the timer stops or a run fails (the journal keeps its exit code), a security event can outlive its year (owner decision of 2026-10-16).
15. **A module could hide a change from the capture.** The capture compares each recorded property's current value with its original one, and code can set an original value (`PropertyEntry.OriginalValue`, `OriginalValues.SetValues`). The update handlers set `RowVersion`'s for the concurrency check, so no architecture rule can refuse the call; review keeps it to `RowVersion`, which no record holds.
16. **The proxy's root can vouch for any name.** Every device that opens the ERP at the server's local address trusts the proxy's root certificate, which carries no name constraint, so whoever reads its private key from the volume `erp-ai-pro-proxy-data` can make a certificate for any site that those devices accept. Only root and members of the `docker` group can read it, the deploy account `erp-ai-pro` is the only member and signs in with its keys alone, from the home network only (ADR-0049), and backups of the volume are to be encrypted (`first-deployment-backups-and-restore-drill`); a public name with a Let's Encrypt certificate ends the need for the root, and the devices then remove it (ADR-0048).
