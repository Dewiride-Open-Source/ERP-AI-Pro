# ADR-0038: The sign-in limit, security events and the audit schema

Status: accepted
Date: 2026-10-10

## Context

- The OpenID Connect handler answers the callbacks `/api/auth/signin-oidc` and `/api/auth/signout-callback-oidc` inside `UseAuthentication`, ahead of the global rate limiter, which runs after authentication so a signed-in caller is limited as its actor (ADR-0019, ADR-0031): the callbacks were never limited, and `GET /api/auth/login`, the front-channel sign-out `GET /api/auth/signout-oidc` and `POST /api/auth/logout` met only the general limits of 600 requests a minute.
- The framework's rate limiting middleware applies, besides its global limiter, the policy an endpoint names, and only the options of the one `AddRateLimiter` registration define those policies: a second `UseRateLimiter(options)` placed before authentication failed every upload with 500, because the attachments upload names `platform.attachments.uploads`.
- Nothing recorded who signed in, failed to or signed out except log lines. IdentityModel writes an `Error` record for every token it refuses, through Microsoft.Identity.Web's adapter, which it installs in IdentityModel's process-wide logger only while that logger is still the null logger; the framework's own records of the other refusals (`insufficient_scope`, the `TokenValidated` refusals) are `Information` and are dropped by the `Microsoft.AspNetCore` level (ADR-0034).
- `user-management-audit-trail-building-block` plans `BuildingBlocks/Auditing` with an `audit` schema for change records. `BuildingBlocks.Persistence/Auditing` is the unrelated interceptor that stamps the audit columns (ADR-0015).
- Direction (iv) of the CERT-In Directions under section 70B(6) of the Information Technology Act, 2000, of 28 April 2022 requires every service provider, intermediary, data centre, body corporate and Government organisation to keep the logs of all its ICT systems securely for a rolling 180 days within Indian jurisdiction and to provide them to CERT-In with an incident report or on its order (cert-in.org.in, CERT-In_Directions_70B_28.04.2022.pdf). The Digital Personal Data Protection Rules, 2025 may set a period for logs as well; their text could not be read when this was decided.
- The correlation and nonce cookies had the framework's names (`.AspNetCore.Correlation.`, `.AspNetCore.OpenIdConnect.Nonce.`) and no prefix. The handler scopes both to the callback path, and the `__Host-` prefix requires path `/`.
- The local-dev sign-in registration listed redirect URIs on the API's own origin (`http://localhost:5080`), although the API builds every `redirect_uri` from `Erp:Platform:Identity:WebOrigin` (ADR-0031).
- Owner decisions of 2026-10-10: the sign-in records start the shared audit area now (`BuildingBlocks/Auditing`, schema `audit`), which `user-management-audit-trail-building-block` extends; they are kept one year; a record holds the Microsoft Entra object id, the time, the event and the full client address, never a name, an email or a user agent; the new settings are seeded and the API-origin redirect URIs removed, each only after a preview that shows exactly that change.

## Decision

- **The audit building block.** `Dewiride.Erp.BuildingBlocks.Auditing` owns the schema `audit`: `AuditingDbContext`, registered with `AddModuleDbContext<AuditingDbContext>("audit")` (readiness check `database:audit`) by `AddErpAuditing()`, which `ErpHostComposition.AddErpPlatform` calls after `AddErpIdempotency()`, so the catalogue and the migrator run `platform_caching`, `platform_idempotency`, `audit`, `files`, then the modules. Its table `SecurityEvents` (migration `InitialAuditing`) has `Id` (`SecurityEventId`, a version 7 GUID), `OccurredAt` (UTC `datetimeoffset`), `Kind` (`tinyint`, `SecurityEventKind`), `Detail` (`varchar(128)`), `ActorObjectId`, `ClientApplicationId`, `ClientAddress` (`varchar(64)`) and `CorrelationId` (`varchar(64)`), indexed by `OccurredAt` and by (`ActorObjectId`, `OccurredAt`). `SecurityEventKind` is `SignedIn` = 1, `SignInFailed` = 2, `SignedOut` = 3, `FrontChannelSignedOut` = 4, `FrontChannelSignOutRefused` = 5 and `BearerTokenRefused` = 6, values never reused. Other building blocks write through `ISecurityEventRecorder.RecordAsync(SecurityEventEntry, CancellationToken)` (scoped, `SqlSecurityEventRecorder`: one insert and its own `SaveChangesAsync` per event, the entity detached once its save has run, so a record whose save failed is never written by the next save of the same request's context); `SecurityEvent.Record` refuses an undefined kind and a value longer than its column. Nothing updates a row. `SecurityEventRetentionSweeper`, a hosted service, deletes the rows older than `Erp:Platform:Auditing:SecurityEventRetention` (one year) with one `ExecuteDelete`, which the bulk-write guard allows because the type is neither auditable nor soft-deletable, once as the host starts and then every `SweepInterval` (one day); a failed sweep is logged and the next one retries. `AuditingOptions` are validated on start.
- **What is recorded.** `SignInAudit` (`BuildingBlocks.Authentication/SecurityEvents`) writes each event with the client address forwarded headers resolved (an IPv4-mapped address as IPv4) and the correlation id of the request (`ICorrelationIdFeature`, else the trace identifier when it fits), always without the request's cancellation, so a browser that leaves before the answer still leaves the record. `RecordAsync` throws when the record cannot be written; `TryRecordAsync` logs that failure at `Error` with the exception and returns. A completed callback records `SignedIn` with the person's object id before it returns the session (`SignInEvents.TicketReceived`), so a sign-in that cannot be recorded starts no session and lands on `/login?error=sign-in-failed` like any other failure, recorded as `SignInFailed` `session:none`. A failed callback records `SignInFailed` with `<category>:<OAuth error code>` (`SignInEvents.FailureDetail`, the same category and code the log record names), never the description. The logout with a session records `SignedOut` once the sign-out record is written and the Entra session record forgotten; the front-channel sign-out records `FrontChannelSignedOut` with the object id of the account the forgotten Entra session record names when that account's home is this tenant (a guest's home object id belongs to another tenant and no other record carries it, so a guest's names no actor), or `FrontChannelSignOutRefused` `other-issuer` with no account. `BearerTokenEvents` records `BearerTokenRefused` for every refusal while the bearer flag is on: from `AuthenticationFailed` with the reason of the validation failure (`BearerTokenRefusals.Describe`; an argument or format failure, such as an encrypted token whose segments are not base64url, is `malformed`) and the client application the unverified token claims (`azp`, else `appid`; reading it is best effort and any failure to read it names no application), from `TokenValidated` with `not-an-access-token` and from `Forbidden` with `insufficient-scope`, both with the token's `oid` and client application; a request whose caller abandoned it while the token was read refused nothing and is not recorded. Every record but a sign-in's goes through `TryRecordAsync`, which writes an event that names no actor only within `AnonymousSecurityEventBudget` (a singleton): anyone can cause one, from any number of addresses, so at most 60 are written per minute across the process and the rest are counted, the first held back in a minute logged and the count logged before the next one written (owner decision of 2026-10-10: cap the junk records rather than record every attempt and watch the database's size). An event that names an actor is never held back. No record holds a name, an email, a user agent or a token.
- **The sign-in limit.** `SignInRateLimitingMiddleware` (`BuildingBlocks.Endpoints/RateLimiting`), added by `UseErpSignInRateLimiting(AuthPaths.SignInPaths)` right before `UseAuthentication` and only while `Erp:Platform:RateLimiting:Enabled` is `true`, limits `AuthPaths.SignInPaths` (the login, both callbacks, the front-channel sign-out and the logout, in any case and with any trailing slashes, which routing also matches), each path with an allowance of its own per client address (`ClientAddressPartition`), so the sign-ins of a busy office behind one address never refuse its sign-outs: a fixed window of `Erp:Platform:RateLimiting:SignInPermitLimit` requests (60) per `SignInWindow` (1 minute) and no queue, and answers a refusal like the global limiter: 429 `rate-limit.exceeded` with `Retry-After` from `RateLimitRejection`. Every other path passes it unlimited. It holds its own `PartitionedRateLimiter` (`SignInRateLimiter`) instead of a second framework middleware, for the reason above. Test hosts allow 600 unless a test sets its own value (`ErpApiFactory.SignInPermitLimitKey`), because every request of a test host comes from one address.
- **The sign-in cookies.** The correlation and nonce cookies are `__Secure-erp-correlation.` and `__Secure-erp-nonce.` (`MicrosoftIdentityOptionsSetup`), so the browser refuses one set without `Secure`; they keep the handler's path `/api/auth/signin-oidc`, which `__Host-` would forbid.
- **IdentityModel's log.** `IdentityModelLoggerInstaller`, a hosted service, puts `BoundedIdentityModelLogger` in IdentityModel's process-wide logger as the host starts, replacing whatever is there, and the first request builds the OpenID Connect options only afterwards, when Microsoft.Identity.Web finds a logger other than the null one and leaves it in place (`IdentityModelLoggingTests`): at most ten records at `Warning` or above pass per minute, the next one that passes preceded by how many were held back, and weaker records pass subject to the configured levels.
- **Registrations and settings.** `signin_redirect_uris` (`scripts/azure/lib/graph.sh`) registers only the web origin's callback paths, and `ERP_AZURE_LOCAL_API_ORIGIN` is gone; on 2026-10-10 `entra.sh` removed the two `http://localhost:5080` redirect URIs of the local-dev registration after a preview that listed exactly that change, and `seed.sh --no-sentinel` added the four settings unlabelled after a preview that listed exactly those four additions, the sentinel left alone because each of them is read only when the API starts.
- **The threat model.** `docs/security/auth-threat-model.md` records the threats, their answers, the tests that prove them and the residual risks.
- **Earlier decisions this changes.**
  - ADR-0019: the sign-in paths have a limit of their own ahead of authentication; the global limiter and its partitions are unchanged.
  - ADR-0031: the callbacks are rate limited, the correlation and nonce cookies carry the `__Secure-` prefix, and no registration lists an API-origin redirect URI.
  - ADR-0034: every bearer refusal is a security event, and IdentityModel's records no longer write one `Error` per refused token.

## Consequences

- Every sign-in, sign-out and refused bearer token costs one insert into `audit.SecurityEvents`. Sign-in fails closed: when the table cannot be written, nobody signs in, as when the token cache, in the same database, cannot be written.
- An office whose people reach the ERP through one public address shares 60 requests a minute on each sign-in path, about 60 sign-ins and as many sign-outs; a larger one raises `SignInPermitLimit` in App Configuration.
- Unauthenticated callers can add at most 60 rows a minute to `audit.SecurityEvents`, about 86,400 a day, however many addresses they use; during such a flood a genuine event that names no actor may be only counted.
- A refused bearer token still costs its signature check before any limit applies, and its insert within the budget above, because authentication precedes the global limiter; `integrations-public-api-and-webhooks` bounds that before the first route takes bearer tokens.
- The trail is append-only by convention, not by database rights; `user-management-audit-trail-building-block` adds its change records to this building block and decides whether to deny the API's login the rights to update and delete them.
- The 180 days within Indian jurisdiction hold only while the production database, its backups and every other ICT log stay in India (`first-deployment-production-database-provisioning`, `first-deployment-go-live-checklist-and-production-smoke`); the one-year retention is checked against the Digital Personal Data Protection Rules, 2025 once their text is read.
