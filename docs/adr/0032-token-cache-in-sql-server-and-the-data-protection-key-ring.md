# ADR-0032: The token cache in SQL Server and the Data Protection key ring

Status: accepted
Date: 2026-10-02

## Context

ADR-0031 signs people in through Microsoft Entra ID in the API and accepts a session cookie only while the person's account is in MSAL's token cache. It left two limits to sub-phase `authentication-token-cache-and-data-protection-key`: the token cache lived in memory, so every restart of the API signed everyone out; and the Data Protection key ring, which protects the session cookie, the OpenID Connect state and nonce and every later antiforgery token, kept the framework's default storage. The owner's decisions of 2026-10-02:

- The sub-phase is Community edition (ADR-0030, confirmed 2026-09-29).
- A restart of the API keeps people signed in in every environment that reads the store, a developer's `dotnet run` included; the roadmap scope's "in-memory in Development" is dropped.
- The API's identity on the production vault gets only what it uses: Key Vault Crypto Service Encryption User instead of Key Vault Crypto User.
- Every new setting lives in Azure App Configuration (owner rule of 2026-09-29), and the Azure changes run only after a dry run that shows exactly them.

Facts that shape the design, read in the released source:

- Microsoft.Identity.Web 4.15.0 (tag `4.15.0` = commit `2f227c6`; 4.16.0 changes nothing under `src/Microsoft.Identity.Web.TokenCache`). `AddDistributedTokenCaches()` only calls `AddDistributedMemoryCache()` (an unkeyed `TryAdd` of `MemoryDistributedCache`) and `TryAddSingleton<IMsalTokenCacheProvider, MsalDistributedTokenCacheAdapter>`, and `AddInMemoryTokenCaches()` uses `TryAddSingleton` too, so the first registration wins. The adapter stores each user cache under MSAL's suggested cache key, the home account id `<uid>.<utid>`, and deletes the key when the person's last token is removed. Its L1 memory cache is on by default and never re-reads the second level on a hit, so a second API instance would keep accepting a signed-out person until its own L1 entry expired. Every exception of the second level is caught in `L2OperationWithRetryOnFailureAsync`, logged at Error and swallowed: a failed read becomes an empty cache, so a transient SQL error would make `GetAccountAsync` return null and the session check would sign the person out, and a failed delete at sign-out would leave every other session alive while the sign-out looked successful. `OnL2CacheFailure` only grants one retry; its XML documentation and the Microsoft Learn troubleshooting page say a `false` result or a failed retry propagates the exception, which the source does not do, but an exception thrown by the callback itself leaves the catch block and reaches the caller (issue AzureAD/microsoft-identity-web#2086 is open; pull request #4016 was closed unmerged). With `Encrypt` on, an entry that Data Protection cannot unprotect is handed to MSAL as raw bytes, whose deserialisation throws `MsalClientException` `json_parse_failed`, rethrown as IDW10802, on every session check that reads it and on the person's first sign-in. The adapter logs the account id in five Debug messages, and its base class in a deserialisation Warning. Token acquisition and `IConfidentialClientApplicationProvider` are registered per request (`AddTokenAcquisition` with `isTokenAcquisitionSingleton: false`), so MSAL's in-memory copy of a cache starts empty in every request; when a read of a person's entry fails during a sign-in, MSAL's finally block still reports that copy, and the adapter then deletes the entry (or, with tokens in the copy, would overwrite it). Signing out removes only the account from the cache, and a cookie copy carries no server-side state, so once the person signs in again under the same `<uid>.<utid>` an older copy within its idle window would pass the account check again.
- Microsoft.Extensions.Caching.SqlServer 10.0.12 (MIT, the shared framework's version). `SqlServerCache` runs raw `Microsoft.Data.SqlClient` commands, never DDL, so `db_datareader` and `db_datawriter` suffice; `AddDistributedSqlServerCache` registers it as the unkeyed `IDistributedCache`, which `AddHybridCache()` adopts as its second level (it ignores only an exact `MemoryDistributedCache`). The table the `dotnet sql-cache` tool creates is `Id nvarchar(449) COLLATE SQL_Latin1_General_CP1_CS_AS NOT NULL` primary key, `Value varbinary(max) NOT NULL`, `ExpiresAtTime datetimeoffset NOT NULL`, `SlidingExpirationInSeconds bigint NULL`, `AbsoluteExpiration datetimeoffset NULL` and the index `Index_ExpiresAtTime`; its upsert tolerates only duplicate-key error 2627, which a unique index would not raise. Expiry compares against `SqlServerCacheOptions.SystemClock` (`ISystemClock`, never `TimeProvider`), and expired rows are deleted by a fire-and-forget `DELETE ... WHERE @UtcNow > ExpiresAtTime` over the whole table at most every `ExpiredItemsDeletionInterval` (minimum 5 minutes). It never retries, unlike EF Core's `EnableRetryOnFailure` on the same database. `Microsoft.Data.SqlClient` 7.1.0 offers its own retry logic as a public API, `SqlConfigurableRetryFactory.CreateExponentialRetryProvider(SqlRetryLogicOption)`, whose `Execute` and `ExecuteAsync` run any operation and retry its baseline transient SQL errors. Its declared `Microsoft.Data.SqlClient >= 6.1.1` resolves to the pinned 7.1.0, where `Authentication=Active Directory Default` works through `Microsoft.Data.SqlClient.Extensions.Azure`, which `BuildingBlocks.Persistence` already references.
- ASP.NET Core Data Protection 10.0 (`dotnet/aspnetcore` tag `v10.0.12`). The default key folder is `%LOCALAPPDATA%\ASP.NET\DataProtection-Keys` with DPAPI on Windows, shared by every ASP.NET Core app of that user, and `$HOME/.aspnet/DataProtection-Keys` unencrypted on Linux; an explicit repository switches the default at-rest encryption off. The application discriminator is the first purpose of every protector, so changing `SetApplicationName` makes every payload unreadable. `FileSystemXmlRepository` writes one `key-{guid}.xml` per key through a temporary file in `/tmp` on Linux and an atomic rename, with no locking. `DataProtectionHostedService` loads the ring at start and swallows any failure at Information level; a failed cold-start load is retried by every request; and when the default key cannot be decrypted but a new one can be wrapped, Data Protection silently creates a new default key, which signs everyone out. There is no Data Protection health check.
- Azure.Extensions.AspNetCore.DataProtection.Keys 1.6.4 (MIT; Azure.Core >= 1.61.0, Azure.Security.KeyVault.Keys >= 4.10.0). With a versionless key identifier, each new Data Protection key is wrapped locally with the public key of the version a `GET` returns and its XML records that version's kid, so unwrapping always targets the version that wrapped it; without `keys/read` the versionless identifier is recorded instead and a later rotation breaks unwrapping. The wrap algorithm is fixed at RSA-OAEP (OAEP-SHA1) with an AES-128-CBC envelope. The `Func<IServiceProvider, IKeyEncryptionKeyResolver>` overloads resolve the resolver from dependency injection for both encryption and decryption. Azure.Security.KeyVault.Keys 4.10.1 resolves the authentication challenge per request endpoint, so a token acquired for one vault is never sent to another.
- The .NET 10 runtime images run as `app` (UID and GID 1654) with home `/home/app`, which runc derives from `/etc/passwd`; `Environment.GetFolderPath(LocalApplicationData)` is `$XDG_DATA_HOME` or `$HOME/.local/share` on Linux, and the one-argument overload returns an empty string for a folder that does not exist. Docker copies an image folder's contents, owner and mode into an empty named volume mounted on it, and BuildKit's `COPY --chown --chmod` of an empty folder creates the target and its missing parents with that owner and mode.

## Decision

- **The token cache is a table in the ERP database, owned by `BuildingBlocks.Caching`.** `AddErpCaching`, which `ErpHostComposition.AddErpPlatform` composes for every host, registers `CachingDbContext` (schema `platform_caching`, ef key `caching`) with the entity `DistributedCacheEntry` mapped to `platform_caching.DistributedCacheEntries` exactly as the `dotnet sql-cache` tool would create it, so the migrator creates it and the API's data-only login uses it. It also registers a `SqlServerCache` as a keyed `IDistributedCache` under `CachingRegistration.SqlServerCacheKey` (`sql-server`), with named `SqlServerCacheOptions` built from `DatabaseOptions` (the same connection string, its command timeout), `ExpiredItemsDeletionInterval` 5 minutes and the system clock, behind `RetryingSqlServerCache`, which runs every operation through SqlClient's exponential retry provider with `NumberOfTries` = `Erp:Platform:Database:MaxRetryCount` + 1, a 1-second delta and `MaxTimeInterval` = `MaxRetryDelay` (the limits EF Core uses on the same database), logs a Warning for each retry, and lets an exhausted retry surface as SqlClient's `AggregateException`. It is never the unkeyed `IDistributedCache`, so `HybridCache` stays in process as ADR-0019 decided, and the cache clock is never the host's `TimeProvider`, because its purge deletes every expired row of the table.
- **Microsoft.Identity.Web reads it through an adapter configured to fail loudly.** `AddErpAuthentication` no longer calls `AddInMemoryTokenCaches()` and never calls `AddDistributedTokenCaches()`; `AddErpTokenCache` registers `IMsalTokenCacheProvider` as `new MsalDistributedTokenCacheAdapter(new ProtectedTokenCacheStore(<the keyed SQL Server cache>, …), …)` with `MsalDistributedTokenCacheAdapterOptions`: `DisableL1Cache = true`, so every session check reads SQL Server and signing out on one instance ends the person's sessions on every instance; `SlidingExpiration` = `SessionIdleTimeout` + 5 minutes and `AbsoluteExpirationRelativeToNow` = `SessionLifetime` + 5 minutes, so a refresh token expires about 35 minutes after the person's last request, never outlives a session by more than the margin, and leaves the table at the next purge; `OnL2CacheFailure` throws `TokenCacheUnavailableException`, so a failed read, write or delete fails the request (500 `server.error`) instead of signing the person out, skipping a sign-out or leaving a session alive, and rethrows a cancellation as itself, so a request that timed out or was abandoned answers 504 or 499; `ProtectedTokenCacheStore` hands the store the request's own cancellation token, because MSAL passes none, so the retries stop with the request; `Encrypt = false`, because `ProtectedTokenCacheStore` protects below the adapter: it protects every value with the Data Protection purpose `Dewiride.Erp.Authentication.TokenCache` and reads a value no key opens (a `CryptographicException` without an inner exception) as missing, so an entry written under another key ring counts as signed out and the person's next sign-in overwrites it, instead of failing deserialisation on every request; a key ring Data Protection cannot reach, which it reports as a `CryptographicException` wrapping the cause (Key Vault or the key folder failing), fails the request like any other store failure. A callback that fails on the token cache lands on `/login?error=sign-in-failed` and logs the failure category `token-cache` (`SignInEvents.TokenCacheFailure`). Once a read of a key has failed in a request, `ProtectedTokenCacheStore` refuses to write or remove that key for the rest of the request (`ChangeAfterFailedReadMessage`, recorded in `HttpContext.Items`), so the delete MSAL issues after a failed sign-in read can never remove a person's entry and end their other sessions, and nothing MSAL never loaded is written over it. The logging filter `Microsoft.Identity.Web.TokenCacheProviders` at `Error` keeps the adapter's Debug and Warning records, which carry the account id, out of every log.
- **Signing out is recorded, so a sign-in afterwards revives no older session.** `POST /api/auth/logout` first writes the person's sign-out time (`SessionRevocations.RevokeAsync`: key `signed-out:<uid>.<utid>` in the keyed SQL Server cache, eight bytes of UTC ticks, `AbsoluteExpirationRelativeToNow` = `SessionLifetime` + 5 minutes, after which no cookie issued before it is alive), and only then signs out, writing the record whatever happens to the request meanwhile, so a sign-out the browser abandons still takes effect; a failed write answers 500 and leaves the person signed in, and a written record ends every older session even when the removal of the account fails. `SessionCookieEvents.ValidatePrincipal` accepts a cookie only while it is within `SessionLifetime`, its `erp.signed-in-at` is after the person's recorded sign-out (read first, so a refused copy costs one read and never slides the person's token cache row) and its account is in the token cache; a failure to read either row answers 500 and keeps the cookie.
- **The key ring lives on disk, wrapped by the Key Vault key, under a fixed application name.** `AddErpDataProtection` calls `SetApplicationName(DataProtectionKeyRing.ApplicationName)` (`Dewiride.Erp`, the same in both editions and never changed; it is not `Erp:Platform:Host:ApplicationName`, whose display value differs per label). When `Erp:Platform:DataProtection:KeyIdentifier` is set (read from configuration at registration, because the extension takes it then, and read once, like every `Erp:Platform:Identity` value), keys are kept by `PersistKeysToFileSystem` in `DataProtectionKeyRing.DefaultDirectory`, `<LocalApplicationData>/ERP-AI-Pro/DataProtection-Keys` (`%LOCALAPPDATA%\ERP-AI-Pro\DataProtection-Keys` on Windows, `/home/app/.local/share/ERP-AI-Pro/DataProtection-Keys` in the container), and wrapped by `ProtectKeysWithAzureKeyVault(<identifier>, <factory>)`, whose factory builds a `KeyResolver` over the API's one `TokenCredential` with two retries and a 10-second network timeout, because Data Protection calls are synchronous and take no cancellation token. `KeyRingOptions` (`Erp:Platform:DataProtection`) validates the identifier when the API starts: an absolute `https` URI `https://<vault>.vault.azure.net/keys/<name>` without a version, so rotating the Key Vault key needs no setting change, and required whenever the API reads App Configuration or runs in Production. A run without the store (tests by default, CI, the local compose stack, the gated Playwright API, a store-less `dotnet run`) keeps its keys in memory (`InMemoryKeyRepository` with `NullXmlEncryptor`) and writes nothing to disk, so a throwaway run can never add an unwrapped key to a real key ring. The package's fixed RSA-OAEP and AES-128-CBC envelope is accepted: a home-made `IXmlEncryptor` would add custom cryptography under a threat model in which the repository is already write-protected.
- **The API refuses to start with a key ring it cannot use.** `KeyRingStartupCheck`, an `IHostedLifecycleService` whose `StartingAsync` runs before `DataProtectionHostedService`, (1) writes and deletes a `.tmp` probe in the repository folder (`KeyDirectoryProbe`; outside Windows it is staged through `Path.GetTempFileName()` and moved in, as `FileSystemXmlRepository` stages every key, so an unusable temporary folder stops the start too), (2) resolves the versionless identifier, refuses a key id that is not versioned (missing `keys/read`), and wraps and unwraps 16 random bytes, (3) refuses a key file that is not wrapped by Key Vault (no `encryptedSecret` of `AzureKeyVaultXmlDecryptor`, or a `masterKey` in the clear), which enforces that the folder holds only wrapped keys (an operator copying in a key from an unprotected ring), not a defence against someone who can write the folder, whom Data Protection's threat model excludes, (4) decrypts every key that is not revoked and could still protect a live payload (`ExpirationDate` at or after now − `SessionLifetime` − 5 minutes), so an existing key that cannot be unwrapped stops the start instead of being silently replaced, and (5) round-trips a probe through a protector, which creates the first key of an empty ring. A failure logs Critical with the exception type and, for `RequestFailedException`, its status and error code, and stops the host; in memory only step 5 runs.
- **The setting is written by the script that owns the key.** `scripts/azure/provision.sh` writes `Erp:Platform:DataProtection:KeyIdentifier` under `local-dev` and `production` from the Bicep outputs `developmentDataProtectionKeyUri` and `productionDataProtectionKeyUri` (the versionless `keyUri` of `Erp--Platform--DataProtection--Key` in each vault, which Azure may report with an explicit `:443`; `canonical_uri` normalises it), without a sentinel bump because the API reads it only when it starts; `seed-files.ts` refuses it in a seed file, and `verify.sh --labels` compares it under each label with that vault key's `kid` without its version. The Bicep template assigns Key Vault Crypto Service Encryption User (`e147488a-f6f5-4113-8e2d-b22465e65bf6`: read keys, wrap and unwrap; the built-in role also carries Event Grid subscription management on the vault, its only control-plane part) to the runtime service principal on the production vault and to the optional developers group on the development vault, in place of Key Vault Crypto User, which would also let the API update the key; `verify.sh` fails while a Crypto User assignment remains. The operator keeps Crypto Officer, which rotation needs.
- **The production stack keeps the key ring on an external named volume.** The API image creates `/home/app/.local/share/ERP-AI-Pro/DataProtection-Keys` owned by `app` with mode 0700 (`COPY --chown --chmod` of an empty folder) and sets `XDG_DATA_HOME=/home/app/.local/share`; `compose.production.yaml` mounts the volume `erp-ai-pro-data-protection-keys`, declared `external`, so `docker compose down -v` can never delete it, and keeps the tmpfs `/tmp` that key creation needs under the read-only root. The compose smoke test checks the folder's owner and mode in the built image. The local stack keeps its keys in memory and mounts nothing.
- **Tests never reach Azure or a developer's key folder.** Every `ErpApiFactory` host belongs to a `TestDeployment`: its token cache rows carry the deployment's key prefix (test personas share account ids across hosts in the one per-process database), and its key ring is in memory unless the deployment persists one, which sets a throwaway versionless identifier, replaces the repository with a temporary folder and registers an `IKeyEncryptionKeyResolver` over a local `CryptographyClient(JsonWebKey)`, so the product's Key Vault encryptor and decryptor run unchanged and no `TokenCredential` is ever built. A Production factory gets a persisted ring by default, because the validator refuses an in-memory one there, and a host that the API put in Key Vault mode without a persisted deployment refuses to start. Two factories that share a deployment prove that a session survives a restart.
- **Earlier decisions this changes.** ADR-0031: the token cache lives in SQL Server, a restart keeps every session, a failure of the cache fails the request, and the limits it left to this sub-phase are resolved. ADR-0010: the runtime service principal and the developers group hold Key Vault Crypto Service Encryption User instead of Key Vault Crypto User. ADR-0019: `HybridCache` stays in process; the SQL Server cache is keyed and holds only the token cache entries and the sign-out records of `SessionRevocations`. The plan in `docs/configuration.md` to reuse `Erp:Platform:Host:ApplicationName` as the Data Protection application name is dropped.

## Consequences

- People stay signed in across restarts of `dotnet run` and of the api container, and across a container replacement in production, for as long as the key ring folder and the table survive. Every request whose session cookie is accepted costs two SQL Server round trips (the sign-out record, then the token cache row in one batch of an `UPDATE` that slides it and a `SELECT`) and one Data Protection unprotect of the row, and a copy its sign-out record refuses costs the first round trip only; both come before the rate limiter can refuse an over-limit person, because it limits a signed-in caller by the person the session names, and only a cookie that Data Protection opens reaches those reads. A sign-out record lives `SessionLifetime` + 5 minutes (12 hours 5 minutes by default).
- A developer's `dotnet run` needs `keys/read`, wrap and unwrap on `Erp--Platform--DataProtection--Key` in the development vault (the operator's Crypto Officer, or Crypto Service Encryption User through the developers group); without it the API does not start and says why.
- Losing the key ring (the volume deleted, a server rebuilt without a restore) signs everyone out, fails sign-ins in progress and makes the stored tokens unreadable, which then read as signed out; nothing else is lost, because no data outlives a session under Data Protection (attachments use their own envelope key, ADR-0022). Key Vault never re-wraps existing keys: after a rotation every older version must stay enabled while a key file names it, and expired versions still unwrap. The [secrets runbook](../operations/runbooks/secrets.md) covers rotation, loss and the volume's backup; the backup itself belongs to `first-deployment-backups-and-restore-drill`.
- Rows of idle sessions stay in the table, unreadable by any read, until the next purge: `SqlServerCache` starts it after a cache operation once 5 minutes have passed since the last one, so on an API that serves no signed-in request they stay until the next one. The account id is the table's plain primary key; the value, which holds the tokens, is protected.
- Re-read `MsalDistributedTokenCacheAdapter` and the registration of token acquisition on every Microsoft.Identity.Web upgrade: the session check relies on how the adapter swallows, retries and deletes, and on MSAL's in-memory cache starting empty in every request.
