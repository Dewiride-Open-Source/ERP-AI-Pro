# ADR-0011: Configuration source selection and runtime credential

Status: accepted
Date: 2026-09-20

## Context

ADR-0005 fixes the configuration model (one App Configuration store, labels `local-dev` and `production` selected by `ERP_ENVIRONMENT`, secrets reached only as Key Vault references, `DefaultAzureCredential` everywhere) and ADR-0010 fixes the Free tier, the 30-minute check and the operational credential model (`az login` on developer machines, a certificate-only runtime service principal on the server). The API host has to turn those rules into code: decide at startup where configuration comes from, connect the App Configuration provider with Key Vault references so the store is the only path to a secret, refresh at the agreed interval, validate the credential prerequisites before the first call to Azure, and stay deterministic under test without reaching Azure at all. Two constraints shape the code. `Microsoft.Azure.AppConfiguration.AspNetCore` ships no `net10.0` asset and its middleware throws when the provider is absent, so it cannot sit in a pipeline whose source varies. The refresh interval is read by the provider when it is built, before dependency injection exists, so it cannot be a store value like the other typed options.

## Decision

- `AddErpConfiguration` resolves one `ErpConfigurationSource` in this order and records it as `ErpConfigurationInfo` for the health checks and the pipeline: `APPCONFIG_ENDPOINT` set → `AppConfiguration` (the value must be an absolute `https` URI and `ERP_ENVIRONMENT` must be `local-dev` or `production`, otherwise startup fails naming the variable); else `ERP_CONFIGURATION_SOURCE=InMemory` → `InMemory`; else `ASPNETCORE_ENVIRONMENT=Development` → `LocalDevelopment` (`appsettings.json` plus the user secrets the framework adds because the host project carries a `UserSecretsId`); else startup fails naming `APPCONFIG_ENDPOINT`. `ERP_CONFIGURATION_SOURCE` is a test-only bootstrap value: `ErpApiFactory` sets it through `UseSetting` and blanks `APPCONFIG_ENDPOINT`, so every test host, Development or Production, resolves `InMemory`; it is never set by hand and never appears in a compose file.
- For `AppConfiguration` the provider is connected with `DefaultAzureCredential`, selects every key unlabelled and then with the label, registers the labelled `Erp:Sentinel` for a full refresh, resolves Key Vault references with the same credential and a one-hour secret cache, selects feature flags the same way, and applies a startup timeout. `builder.Services.AddAzureAppConfiguration()` and the `app-configuration` readiness health check are registered only for this source.
- The intervals are bootstrap-only options `Erp:Platform:Configuration:{RefreshInterval, SecretRefreshInterval, StartupTimeout}` (defaults 00:30:00, 01:00:00, 00:01:00) read from `appsettings.json`, environment variables or user secrets before the provider is added, validated with `Validator.ValidateObject` so an out-of-range value fails startup, and registered as a singleton instance rather than bound with `AddOptions`. They are never seeded in the store: a store value would be read after the provider was built with the previous value, so the two could diverge and the running interval would differ from the configured one.
- The production credential is a certificate only. `AZURE_TOKEN_CREDENTIALS` is mandatory (`AzureCliCredential` on developer machines, `EnvironmentCredential` in the api container) and a validating factory checks the process environment before `DefaultAzureCredential` is created: outside `Development` the selection must be `EnvironmentCredential`, `AZURE_TENANT_ID` and `AZURE_CLIENT_ID` must be set, `AZURE_CLIENT_CERTIFICATE_PATH` must name a `.pem` or `.pfx` file that the process can open for reading, and `AZURE_CLIENT_SECRET` must be absent, each violation failing startup with a message naming the variable and the fix. The developer selection supersedes the `dev` value named in ADR-0010: `dev` selects the whole developer-tools chain with the Visual Studio and VS Code sign-ins ahead of the Azure CLI, so a machine signed in to another tenant in those tools would present the wrong identity, whereas `AzureCliCredential` uses exactly the `az login --tenant` session the onboarding steps create. The certificate reaches the container as a compose secret file under `/run/secrets`; the key-per-file source reads that directory through a filtering file provider that hides `.pem`, `.pfx`, `.crt` and `.key` files, so the certificate is never opened as configuration, not even by the provider's own enumeration.
- Refresh is triggered by an in-repo middleware over `IConfigurationRefresherProvider`, driven by `TimeProvider`, throttled to one attempt per second and started without awaiting under `ExecutionContext.SuppressFlow`; the provider then decides, per its 30-minute interval, whether the sentinel is actually read. The refresh task is observed: an exception the provider does not handle itself (an expired or revoked runtime certificate surfaces as `AuthenticationFailedException`) is logged at error level with the store endpoint instead of vanishing as an unobserved task. `Microsoft.Azure.AppConfiguration.AspNetCore` is not used for the two reasons given in the context. `UseErpConfigurationRefresh` adds the middleware only for the `AppConfiguration` source.

## Consequences

- The user-secrets fallback for local development is framework behaviour and needs no code: the endpoint stored with `dotnet user-secrets` is what switches a developer machine from `LocalDevelopment` to `AppConfiguration`.
- Every `ErpApiFactory` resolves `InMemory`, so the backend test suite never needs Azure access or an endpoint, and a developer's user secrets cannot switch a test host to the store. A Development test host still loads the user-secrets file itself, as `dotnet run` does; the sub-phase that adds `ErpApiFactory.WithConfiguration` gives tests explicit values that override it.
- The refresh middleware sits between forwarded headers and host filtering in the API pipeline, so a request that fails later in the pipeline still keeps the configuration current, and the throttle bounds the cost of that to one asynchronous check per second regardless of request volume. `WebApplication.CreateBuilder` also registers the framework's own host-filtering startup filter ahead of the whole pipeline with the same `HostFilteringOptions`, so a request for a host outside `Erp:Platform:Host:AllowedHosts` is rejected before any middleware in `RequestPipeline` runs.
- A setting change reaches the API within 30 minutes on the Free tier; shortening the interval after an upgrade to Standard is the environment variable `Erp__Platform__Configuration__RefreshInterval` on the api service in `compose.production.yaml` followed by `docker compose up -d api`, not a store edit (the image is read-only, so its `appsettings.json` cannot be edited in place).
- The `first-deployment` phase places the runtime certificate on the server and fills `infra/compose/.env`; until then the production stack validates but refuses to start, by design.
