# ADR-0013: Persistence conventions, per-process test databases and the CI SQL Server action

Status: accepted
Date: 2026-09-22

## Context

ADR-0008 fixes one database with one schema per module, `UseSqlServer` with compatibility level 170 locally and `UseAzureSql` in production, migrations owned by the module and applied outside the running process, and a real SQL Server for integration tests. Turning that into code raises questions the ADR leaves open: how a module wires its `DbContext` without repeating the provider configuration, how strongly-typed ids, money and timestamps are mapped consistently across hundreds of modules, how `dotnet ef` obtains a configured host when the developer's user secrets point the API at Azure App Configuration (and `dotnet ef` never reads `launchSettings.json`, so `ERP_ENVIRONMENT` would be missing and the host would refuse to start), how tests obtain a database without touching the developer's own `ErpAiPro`, and how CI gets a SQL Server 2025 instance when a GitHub `services:` container needs its `sa` password stored in the workflow or in a repository secret.

The owner's local instance is SQL Server 2025 Developer (17.x, compatibility level 170). Host processes on that machine sign in with Windows authentication; Linux containers cannot, so the container stack needs a SQL login. Every `ErpApiFactory` forces the in-memory configuration source, so the test host never resolves the Key Vault reference and needs the connection string injected.

## Decision

- `Dewiride.Erp.BuildingBlocks.Persistence` owns the provider. A module `DbContext` derives from `ModuleDbContext`, lives in `<Module>.Persistence` and is registered from the module's `AddServices` with `builder.AddModuleDbContext<TContext>(schema)`, which configures `HasDefaultSchema`, the `__EFMigrationsHistory` table inside the module schema, the provider selected by `Erp:Platform:Database:Provider` (`UseSqlServer` with compatibility level 170 or `UseAzureSql`, both with `EnableRetryOnFailure(MaxRetryCount, MaxRetryDelay)` and `CommandTimeout`), a readiness health check `database:<schema>` and an entry in the `DbContextCatalog` that `DatabaseMigrator.MigrateAllAsync` walks in registration order. `DatabaseOptions` binds `Erp:Platform:Database` with data-annotation validation; the connection string is required at run time and optional at EF design time.
- Conventions live in `ModuleDbContext.ConfigureConventions`: every `readonly record struct` implementing `IStronglyTypedId<TSelf>` found in the context assembly and the `Dewiride.Erp.*` assemblies it references is mapped to `uniqueidentifier` by `StronglyTypedIdConverter<TId>`; `decimal` defaults to precision 19, scale 4; `DateTimeOffset` is normalised to UTC on write and read by `UtcDateTimeOffsetConverter`; `IDomainEvent` is ignored. Value objects are readonly record structs mapped as complex types through `ComplexProperty` in the entity configuration (`[ComplexType]` is class-only), by table splitting with `<Property>_<Member>` columns.
- `Hosts/Composition/Dewiride.Erp.Host.Composition` holds `Modules.All` and `ErpHostComposition.AddErpPlatform(builder, hostAssembly)`, which runs the design-time rule, `AddErpConfiguration`, `AddErpPersistence` and `AddModules`. The API host, the test database host and the migrator (migration-tooling sub-phase) all call it, so no context can be missing from the catalogue or the migrations.
- `dotnet ef` always runs the API host offline: `AddErpPlatform` sets `ERP_CONFIGURATION_SOURCE=LocalDevelopment` when `EF.IsDesignTime` is true, before `AddErpConfiguration` runs, and `ErpConfigurationSourceResolver` honours that value ahead of `APPCONFIG_ENDPOINT` in any environment. The connection string then comes from `dotnet user-secrets` on a developer machine or `Erp__Platform__Database__ConnectionString` in CI. No module carries an `IDesignTimeDbContextFactory`; the only factory in the repository is the test-only `SampleDbContextDesignTimeFactory`, because a test executable cannot host the API at design time.
- Tests: `SqlTestDatabase` is an xunit v3 assembly fixture declared in every SQL-backed test project. It reads `ERP_TEST_SQL_CONNECTION` (server-level, no `Database=`), drops leftover `ErpAiProTest_%` databases older than 24 hours, creates `ErpAiProTest_<yyyyMMddHHmmss>_<8 hex>`, migrates every catalogue context through a non-started host built with `AddErpPlatform`, and drops the database when the test process ends. `ErpApiFactory` injects that connection string into every test host unless `WithConfiguration` supplied one and refuses to start when no test database exists, so a Development test host can never reach the developer's `ErpAiPro` through the user-secrets value.
- CI: the composite action `.github/actions/start-sql-server` runs `docker run` of the digest-pinned `mcr.microsoft.com/mssql/server:2025-CU9-ubuntu-24.04` image with an `sa` password generated at run time and masked, waits until `sqlcmd` answers, creates the database and outputs server-level, database and container (`host.docker.internal`) connection strings. `ci-backend.yml` passes the server-level string as `ERP_TEST_SQL_CONNECTION` and runs `dotnet ef migrations has-pending-model-changes`; `e2e.yml` applies the migrations and starts both API instances with `Erp__Platform__Database__ConnectionString`; `docker-build.yml` applies the migrations from the runner and writes the compose secret file before the compose smoke. This supersedes the "SQL Server 2025 service container in CI" clause of ADR-0006 and ADR-0008.
- Local containers: `compose.override.yaml` mounts the git-ignored file `infra/compose/secrets/Erp__Platform__Database__ConnectionString` as a compose secret, read by the key-per-file provider as `Erp:Platform:Database:ConnectionString`. On the owner's machine it carries a SQL login limited to `db_datareader`, `db_datawriter` and `db_ddladmin` on `ErpAiPro` (the migrator container of the migration-tooling sub-phase shares the file and needs the DDL right); the instance has TCP/IP and mixed-mode sign-in enabled for that stack only, and `sa` stays disabled.
- Schemas owned by building blocks (`platform_idempotency`, `files` in later sub-phases) are named by concern and sit outside the `<domain>_<module>` descriptor rule; `ModuleCatalog` and `DbContextCatalog` still reject two owners of one schema.
- The App Configuration reference `Erp:Platform:Database:ConnectionString` carries `"labels": ["local-dev"]` in `infra/appconfig/key-vault-references.json`; `seed.sh` and `verify.sh --labels` honour that list, and the `production` label is added by the first-deployment phase once the production secret exists.

## Consequences

- A new module needs one context class and one `AddModuleDbContext` call; provider, history table, retry, health check and migration order come for free, and `PersistenceTests` fail the build on a context outside `<Module>.Persistence`, a foreign entity type, a schema that differs from the descriptor or an id mapped without the converter.
- `EF.IsDesignTime` decides the configuration source, so a design-time host never depends on Azure or on `launchSettings.json`; the price is that `dotnet ef` reads a second copy of the connection string from user secrets, which the local-development guide and the secrets runbook keep in step with the Key Vault value.
- Every test project pays one database creation and one migration run per process (about two seconds on the owner's machine); tests of one project share that database, so a test that inserts rows asserts on its own rows rather than on totals.
- The CI SQL Server image digest is not bumped by Dependabot (no ecosystem scans a `docker run` command); it is bumped by hand when the cumulative update changes.
- `Microsoft.Data.SqlClient` 7.1 and `Microsoft.Data.SqlClient.Extensions.Azure` 7.1 are referenced together so `Authentication="Active Directory Default"` resolves in production; the first-deployment phase verifies the contained Entra users against it.
