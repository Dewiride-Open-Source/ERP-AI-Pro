# ADR-0024: Frontend structure and import boundaries

Status: accepted
Date: 2026-09-27

## Context

The `web-foundation-feature-folder-conventions-and-routing` sub-phase asks for `features/<domain>/<module>/<feature>/{components,server,forms,ai}`, an `app/` kept routing-only under the `(auth)` and `(app)` route groups, `typedRoutes`, a `proxy.ts` scaffold, a fetch wrapper skeleton with ProblemDetails mapping, and an ESLint rule that fails on cross-feature deep imports. Facts that shape the decision (paths relative to `frontend/apps/web/src/`):

- **Most of it existed, unenforced.** Four modules already used `<feature>/components` and three `<feature>/server`; both route groups, `typedRoutes: true`, the complete `proxy.ts` (the `/api` and `/openapi` rewrite, the nonce CSP, the security headers) and the web client (`shared/api/client.ts`, `problem-details.ts`, `upload.ts`, ADR-0017) were in place. A "scaffold" or "skeleton" next to them would be a stub, which root `CLAUDE.md` §3 forbids. ADR-0007 declared `app/` routing only and that "Import boundaries are enforced by `scripts/checks/feature-boundaries.ts`", but that script checked only module internals, a domain's `_shared/` and `app/` importing a module's internals, had no tests, and knew nothing about file names in `app/`, `app/` importing anything that is not a module, `shared/` importing `features/` (`shared/layout/app-shell.tsx` imported `@/features/registry`) or anything importing `app/`. `app/` itself held UI: both `loading.tsx` files (42 and 53 lines of skeleton), the decorative frame of `(auth)/layout.tsx`, the content of `error.tsx` and `global-error.tsx`, and the `<main>` of the root `not-found.tsx`.
- **The one ESLint rule.** `packages/config/eslint/next.mjs` carried one undocumented, untested `no-restricted-imports` group, `["@/features/*/*/*", "!@/features/*/*/index"]`. It saw only the `@/` alias, so a relative `../../../system-info/...` passed, and it refused the same-domain `_shared` alias that the script and `module-anatomy.md` allowed. ESLint's core `no-restricted-imports` tests the raw specifier text, never a resolved path, covers static imports, re-exports and `export *` but not `import()` ("It applies to static imports only, not dynamic ones", eslint.org), and a later flat-config object that sets a rule's options replaces the earlier options instead of merging them. `import/no-restricted-paths` resolves paths, but `eslint-plugin-import` reaches the lockfile only transitively through `eslint-config-next` and is not named in ADR-0009, so relying on it would be a package decision.
- **Next.js.** The project-structure guide calls Next.js "unopinionated" and lists "Store project files outside of `app`" as the strategy that keeps "the `app` directory purely for routing purposes", the one ADR-0007 chose; nothing in the framework refuses other files in `app/`. The root layout, `global-error`, the root `error` and `not-found`, the redirect `page.tsx`, `healthz/route.ts` and `icon.svg` must sit at the root of `app/`, outside both groups. `forbidden` and `unauthorized` (behind `authInterrupts`) and `global-not-found` are experimental file conventions.
- **Typed routes were not checked before the build.** `.next/` and `next-env.d.ts` are gitignored, and before `next dev`, `next build` or `next typegen` has run `Route` is the stub `string & {}` (`next/dist/types.d.ts`), so `pnpm typecheck` (a bare `tsc --noEmit`, run before `pnpm build` in CI) validated no route on a clean checkout. The CLI reference says "running `tsc --noEmit` directly wouldn't validate your route types" and documents `next typegen && tsc --noEmit`. The object `href` of `attachments-pagination.tsx` (`{ pathname, query }`, a `UrlObject`) was never checked at all.
- **The boundary unit.** ADR-0007, `frontend/CLAUDE.md`, `dependency-rules.md` and the script all set the boundary at the module, with one `index.ts` per module. `features/platform/system-info/info/components/system-info-overview.tsx` renders the recent-startups table of its sibling feature `startups` through a relative import.

## Decision

- **The module is the boundary.** `features/<domain>/<module>/` is the unit other code sees: its `index.ts` is its only public surface and re-exports the components `app/` renders (page components, loading skeletons) and the `nav` manifest, never Server Functions, queries or schemas. The features of one module share code by relative path. A domain's `_shared/` is imported only from that domain. The scope's "cross-feature" is read as cross-module, as ADR-0007 records; a wall around every feature would add a public surface per feature and break the system-information page for no gain.
- **A fixed, checkable shape.** A file in `app/` is a stable Next.js special file (`layout`, `page`, `loading`, `error`, `not-found`, `template`, `default` as `.tsx`, `route.ts`, and the documented metadata files; `global-error.tsx`, `favicon.ico`, `robots` and `manifest` at the root only). A folder in `app/` is a route segment (a static name, `(group)`, `[param]`, `[...param]`, `[[...param]]`, `@slot`), never a private `_folder`. The root of `app/` holds the root files, the only two groups `(auth)` and `(app)`, and folders that hold only `route.ts` (`healthz/`); every other page, layout, loading and not-found file lives inside a group. `features/` holds `registry.ts` and domain folders; a domain holds modules and an optional `_shared/`; a module root holds `index.ts` (required), `nav.ts` (optional) and feature folders; a feature holds only `components/`, `server/`, `forms/`, `hooks/` and `ai/`, with no loose files. `server/` holds only `actions.ts`, opening with the `"use server"` directive, and `queries.ts`, importing `"server-only"`; `forms/` holds `<name>.schema.ts` files and their tests, `hooks/` `use-<name>.ts(x)` files and their tests, `ai/` only `<capability>/` folders. Names under `features/` and route segments are kebab-case, dynamic segment names camelCase. The root of `shared/` holds only concern folders. `hooks/` stays in the set because ADR-0007 includes it; `forms/`, `hooks/` and `ai/` are created with their first real file (the forms kit, the first AI capability behind its own flag), never as empty placeholders.
- **Experimental file conventions are refused until an ADR adopts them.** `forbidden`, `unauthorized` and `global-not-found` fail the structure check; the authentication phase adopts one by amending this rule in its own change.
- **Routing-only means compose-only.** A file in `app/` renders components and never an HTML element; the root `layout.tsx` and `global-error.tsx` render only `<html>` and `<body>`. It imports only `next`, `next/*`, `react`, `@/shared/**`, `@/features/registry` and a module's public surface `@/features/<domain>/<module>`, always through the alias and never by a relative path; the root layout also imports `@dewiride/erp-ui/*` and `geist/*`, because the global stylesheet, fonts and providers belong in the root layout. The UI that lived in `app/` moves unchanged, keeping every `data-testid` and ARIA attribute: the skeletons to `SystemInfoOverviewSkeleton` and `AttachmentsOverviewSkeleton` in their modules' `components/`, exported through `index.ts` and rendered by `loading.tsx`; the sign-in frame to `shared/layout/auth-shell.tsx` (`AuthShell`); the error content to `shared/layout/error-page.tsx` (`ErrorPage({ digest, onRetry })`); the global-error content to `shared/layout/application-failure.tsx` (`ApplicationFailure({ onReload })`), rendered inside the `<html>`/`<body>` that `global-error.tsx` keeps; the root not-found `<main>` to `shared/layout/not-found-page.tsx` (`NotFoundPage`).
- **`shared/` never imports `features/`.** Neither does any file outside `app/`, `features/` and `shared/` (`proxy.ts`, `instrumentation.ts`, `instrumentation.node.ts`). The `NavigationEntry` type lives in `shared/layout/navigation-entry.ts`; `AppShell` takes a `navigation` prop, which `app/(app)/layout.tsx` passes from `@/features/registry`. `features/registry.ts` is imported only from `app/`, and nothing outside `app/` imports `app/`.
- **Two enforcers, one rule register.** `scripts/checks/feature-boundaries.ts` (with `scripts/checks/lib/web-structure.ts` and `web-imports.ts`) is the authority: it walks every file under `frontend/apps/web/src` (non-code files included, so a stray asset in `app/` is seen), resolves `@/` and relative specifiers to normalised paths with case ignored, reads static imports, re-exports, `export *`, side-effect imports, `import()` and `typeof import()`, and fails naming the file, the rule id (S1–S6 for the structure, I1–I6 for the imports) and the reason. It keeps its name, so the "Feature boundaries" step of `ci-frontend.yml` and `scripts/verify/verify.ts` run it unchanged. ESLint gives the same feedback in the editor and fails `pnpm lint`, with core rules only (`no-restricted-imports`, `no-restricted-syntax`, `no-restricted-globals`, `no-restricted-properties`) and no new package: `featureBoundaryConfigs()` in `packages/config/eslint/feature-boundaries.mjs`, composed into the `next` preset after its base rules, and one `no-restricted-imports` entry in the `react-library` preset. Because ESLint sees only the literal text of an import, its rules are a stricter subset where text is all it has (a module reaches its own files and its domain's `_shared/` by relative path only, never through the alias; no `..` detours; one config object per folder depth 0 to 8 below a module root refuses a relative path that climbs out of the module), and it adds what needs package names or the syntax tree: the package allow-list of `app/`, HTTP confinement, HTML elements in `app/`, object `href`s and `packages/ui` importing `apps/web`. One builder produces the complete option lists of every scope, including the type-role restrictions of ADR-0023, because a later flat-config object replaces a rule's options. The register in `docs/architecture/dependency-rules.md` lists every rule with its enforcer; `scripts/checks/tests/web-structure.test.ts` and `web-imports.test.ts` prove the script's rules and `packages/config/eslint/feature-boundaries.test.mjs` proves the ESLint rules, each with an allowed and a refused case per rule, the latter through ESLint's `Linter` and the full presets, so the order of the config objects is tested too.
- **HTTP confinement.** Outside `src/shared/api/**`, `@dewiride/erp-api-client` is imported for types only (`allowTypeImports`), and `fetch`, `XMLHttpRequest` and `EventSource` are refused as globals and as properties of `globalThis`, `window` and `self`, so `shared/api/client.ts` and `shared/api/upload.ts` stay the only code that talks to the API (ADR-0017).
- **Route types are generated before the compiler runs.** The web app's `typecheck` script is `next typegen && tsc --noEmit`, so a link, `redirect()` or `router.push()` naming a route `app/` does not define fails on a clean checkout. `next typegen` loads `next.config.ts` in the production build phase, which needs no environment variable because `readPublicEnv` applies its defaults. An `href` is a route string, a template literal over a known route included (`` `/platform/attachments?page=${page}` ``); an object `href` fails lint; a path only `proxy.ts` serves (`/api/...`) is cast with `as Route`. A page or layout that reads `params` or `searchParams` types its props with the generated global `PageProps<"/route">` or `LayoutProps<"/route">`.
- **The pure parts of `proxy.ts` are unit-tested.** The policy string and the https test move to `shared/security/content-security-policy.ts` (`contentSecurityPolicy({ nonce, secure, development })`, `isSecureRequest(url, headers)`) and the stripping of `x-forwarded-*` and `forwarded` from rewritten API requests to `withoutForwardedHeaders` in `shared/api/forwarded-headers.ts`; `node --test` covers both. `next/experimental/testing/server` is not used, because it is experimental. The matcher and the flow of `proxy.ts` do not change.
- **Earlier decisions this changes.** ADR-0007: its sentence "Import boundaries are enforced by `scripts/checks/feature-boundaries.ts`" becomes "the structure and import boundaries are enforced by `scripts/checks/feature-boundaries.ts` and the ESLint rules of `@dewiride/erp-config`, per the register in `dependency-rules.md`", and "`src/app/` is routing only" takes the checkable meaning above; "every page imports one component from `src/features/<domain>/<module>/index.ts`" still holds. ADR-0017 has already superseded ADR-0007's `shared/api/http.ts` with `shared/api/client.ts`. The sub-phase scope's `proxy.ts` scaffold and fetch wrapper skeleton were delivered in full by earlier sub-phases; this decision adds their tests, and leaves field-error mapping to `web-foundation-forms-and-validation-kit`, the `X-XSRF-TOKEN` header to `authentication-antiforgery-for-json-endpoints` and the session redirect to `authentication-web-login-page-and-session-integration`.

## Consequences

- A misplaced file, a folder outside the allowed set, a missing directive or a boundary break fails CI, naming the file and the rule; most boundary breaks are flagged in the editor as they are typed. A new module's shape is checked by `node scripts/checks/feature-boundaries.ts` and `pnpm lint` instead of by review.
- Nothing a person sees changes: the moved markup renders the same pages, and the existing Playwright specs for sign-in, navigation, system information, attachments and the kitchen sink pass unchanged.
- Widening an allow-list (`forms/` may need more than `*.schema.ts` for the forms kit; the authentication phase may want `unauthorized.tsx`) changes the register, the check and its test table in one change, with an ADR when it is a decision.
- The two layers can drift apart; one register, test tables that follow it and the script as the authority keep them aligned. ESLint's depth objects stop at eight folders below a module root (the deepest today is three); a deeper file gets only the alias rules in the editor, and the script still fails it in CI.
- The script reads imports with regular expressions: an import inside a comment or string, or two statements on one line, can mislead it. Prettier's one-statement-per-line layout keeps that unlikely.
- `pnpm typecheck` loads `next.config.ts`; a configuration that required an environment variable at load time would break it. `tsc` run without `next typegen` fails on the `PageProps` global. `tsconfig.json` also includes `.next/dev/types`, so stale output of an old `next dev` can keep a deleted route valid on a developer machine; CI starts clean.
- Later sub-phases build on the moved files: `web-foundation-feedback-motion-and-accessibility-baseline` restyles `ErrorPage`, `ApplicationFailure` and the skeletons and adds the `(app)`-level `error.tsx` and `loading.tsx`; `authentication-web-login-page-and-session-integration` owns `AuthShell`; `authentication-authenticated-application-shell` owns `AppShell` and the navigation it receives.
