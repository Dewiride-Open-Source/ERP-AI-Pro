# ADR-0017: HTTP conventions, the committed OpenAPI document and the generated TypeScript client

Status: accepted
Date: 2026-09-25

## Context

ADR-0007 deferred the choice of a generated API client and let the web app read the API through one hand-written `fetch` wrapper (`shared/api/http.ts`) with hand-written response types. With hundreds of modules ahead, a hand-written type per response drifts from the API the first time a member is renamed, and nothing fails when it does. The client must be generated from the contract the API actually serves, and a pull request that changes one without the other must fail in CI.

A generated client is only as good as the document it reads. The document must describe the error bodies (a client generator throws away a body whose shape it does not know), must be reproducible byte for byte on any machine, and must avoid the schema constructs the generator mishandles. Producing it at build time with the MSBuild `GetDocument` target boots the real `Program.Main` inside `dotnet build`, which connects to App Configuration and SQL Server and starts hosted services, with no switch to avoid it.

Three further conventions were open: how a request is correlated across the web server, the API and the logs; what every error body carries; and how endpoint input is validated and documented. .NET 10 ships built-in minimal-API validation (`Microsoft.Extensions.Validation`) whose source generator fails silently when it cannot see a type.

## Decision

- Correlation. `CorrelationIdMiddleware` runs first in `UseErpEndpointPipeline`. It keeps a caller's `X-Correlation-ID` when it is one value of at most 64 characters from `[A-Za-z0-9._-]`, otherwise uses the W3C trace id of the request activity, otherwise a version 7 GUID in `N` format. The value is stored as `ICorrelationIdFeature`, tagged on the activity as `erp.correlation_id`, written back as the `X-Correlation-ID` response header on every response, and held as the `CorrelationId` logger scope for the whole downstream pipeline.
- Problem contract. Every non-2xx body is RFC 9457 ProblemDetails written through `IProblemDetailsService`, which in ASP.NET Core 10 also covers `TypedResults.Problem` returned by endpoints (verified by a host test). `ProblemDetailsCustomizer` sets `type` to `/problems/<code>`, adds the `code` extension (the error's own code, or the status default from `ProblemTypes.DefaultCode`: a named code for 400, 401, 403, 404, 405, 413, 415, 429, 499 and 503, `request.rejected` for any other 4xx and `server.error` for any other 5xx, so a client mistake is never reported as a server fault), sets `instance` to the request path and `traceId` to the correlation id. `GlobalExceptionHandler` answers a `BadHttpRequestException` with its own status and `request.malformed` (or `request.too-large`), logged at warning, instead of a 500, and `RouteHandlerOptions.ThrowOnBadRequest` is on in every environment (the framework default throws only in Development and otherwise writes a bare 400), so Production gives the same answer as the tests; this piece of the transport-security sub-phase lands here because the first request record exposed it. The health endpoints write a 503 `service.unavailable` problem when readiness fails, naming no check. An idempotent replay of a stored problem rewrites its `traceId` to the replay's correlation id and logs the original id, so the header and the body always agree.
- Validation. `Microsoft.Extensions.Validation` comes from the ASP.NET Core shared framework, generator included, so no package reference is added. Its generator emits metadata only for public types reachable from endpoints in the assembly whose code calls `AddValidation()`, and silently skips anything else, so every module's `AddServices` calls `builder.Services.AddValidation()`, and request records are `public sealed record` types in `<Feature>/Endpoints/Requests/` with every attribute targeted at the property: `[property: Range(…)]` (validation reads parameter and property, the document only the property), `[property: FromQuery(Name = "take")]` for the camelCase wire name and `[property: Description("…")]` for the text the document shows. `RequestRecordTests` fails when a record is not public, sealed and a record, when an attribute sits on the constructor parameter, or when a record with rules is unknown to the running `ValidationOptions`. A failure answers 400 `HttpValidationProblemDetails` whose `errors` keys are camelCase through `DictionaryKeyPolicy`; JSON numbers are strict (`JsonNumberHandling.Strict`) so each member has one type on the wire and in the document.
- The document. `Hosts/Api` calls `AddOpenApi("erp", ErpOpenApiOptions.Configure)` with a literal name, because the XML documentation generator intercepts only literal calls and only this host references every module. The document is OpenAPI 3.1 with a fixed title, version `1.0` and the MIT licence, and no `servers` entry (the browser calls `/api` on its own origin). Schema ids must be unique across types (a collision throws at document build time). The `ProblemDetails` and `HttpValidationProblemDetails` schemas carry `code` and `traceId`, and `title` is marked `x-ms-primary-error-message` so the generated client fills the thrown error's `message`. Each module route group declares the 400 validation problem and the 404 and 500 problems.
- The snapshot. `docs/openapi/erp.json` is serialised from the hermetic test host through the `IOpenApiDocumentProvider` keyed `erp` and normalised (two-space indentation, relaxed escaping, LF endings). `OpenApiSnapshotTests` fails when the running API differs from the file and rewrites it when `ERP_OPENAPI_SNAPSHOT=update`. `OpenApiSchemaShapeTests` rejects `oneOf`, `anyOf`, `allOf`, `not`, `discriminator`, `patternProperties` and conditional keywords, schema ids that are not PascalCase identifiers, and any non-2xx response not described as `application/problem+json`.
- The generator. Microsoft Kiota (the owner's choice over openapi-typescript, a third-party package): the CLI `Microsoft.OpenApi.Kiota` 1.35.0 as a local tool in `backend/.config/dotnet-tools.json`, generating TypeScript with JSON serialisation only, `--exclude-backward-compatible`, `--clean-output`, the `NoServerEntry` rule disabled and the additional-data bag kept (the validation `errors` member is a map, which Kiota can only carry there). The serializer names are passed as `--serializer=@…` because System.CommandLine reads a token that starts with `@` as a response file. Output and `kiota-lock.json` are committed under `frontend/packages/api-client/src/generated`.
- The runtime. `@microsoft/kiota-abstractions`, `@microsoft/kiota-http-fetchlibrary` and `@microsoft/kiota-serialization-json` are pinned exactly at `1.0.0-preview.108` (published 2026-09-21). This is the prerelease exception to the package policy: no stable 1.0 exists, the npm `latest` tag itself is a preview, and kiota 1.35.0 reports its TypeScript support as preview. Preview.108 is newer than the preview.100 the 1.35.0 CLI recommends; the generated output compiles and runs against it (proved by the build and the Playwright suite). The transitive runtime is tslib 2.8.1 (0BSD, Microsoft, already in the lockfile), @opentelemetry/api 1.9.1 (Apache-2.0, already a direct dependency), tinyduration 3.4.1 (MIT) and @std-uritemplate/std-uritemplate 2.0.12 (Apache-2.0); the owner approved the last two when this sub-phase started. The three Kiota packages are added to the approved list of ADR-0009.
- The package. `@dewiride/erp-api-client` is a built workspace package (`tsc` to `dist`, ESM with declarations, one `exports` entry), because the generated deserializers do not compile under `exactOptionalPropertyTypes`: the package compiles with that flag off and the web app consumes its declarations with the flag on. Its `connect()` hides the Kiota runtime and builds an explicit middleware chain (user agent, then the caller's fetch) without the default retry and redirect handlers, so a failing call fails once and at once. The workspace `build` builds it topologically before the web app; `dev`, `lint` and `typecheck` build it first.
- The web client. `shared/api/client.ts` is the web app's only HTTP client: one connection per request (`React.cache`) forwarding `cookie`, `traceparent`, `tracestate` and `x-correlation-id`, fetching with `cache: "no-store"` and `redirect: "error"` (the API never redirects, so a redirect must not carry the cookie anywhere). `toApiError` maps what the client throws into `ApiError`, including field errors. This supersedes the `shared/api/http.ts` sentence of ADR-0007 and settles its deferred client choice; the antiforgery header for Server Functions arrives with antiforgery in the authentication phase.
- Drift. `scripts/api-client/generate.ts` refreshes the snapshot through the test host (it needs `ERP_TEST_SQL_CONNECTION`) and regenerates the client. `scripts/api-client/drift.ts` generates twice into temporary folders, reports a difference between the two as non-deterministic generation (microsoft/kiota#7997), then compares with the committed tree, ignoring only the lock file's folder-relative `descriptionLocation`. `ci-frontend.yml` and `verify.ts` run it; `ci-backend.yml` runs the snapshot test with the rest of the suite.

## Consequences

- An API change is one pull request: change the endpoint, refresh the snapshot, regenerate the client, adapt the web app. Forgetting a step fails the backend snapshot test or the frontend drift check.
- Generated models make every member optional and deliver JSON `null` as `undefined`, so web code reads members with `??` and shows a placeholder; the API contract itself is guarded by the backend tests.
- A problem thrown by the client is a plain object, not an `Error`; only `toApiError` knows how to narrow it, and `instanceof Error` checks on raw client errors are wrong.
- The runtime is a prerelease line with source-breaking changes announced for the TypeScript generator. Dependabot moves the three runtime packages together (npm group `kiota`) and the CLI in the NuGet `tooling` group; a CLI bump changes the generated output, which the drift check forces into the same pull request.
- The fix for microsoft/kiota#8177 (composed types that fail to compile) is not in 1.35.0. The schema-shape test keeps composed types out of the document, so that generator path is never reached.
- Response records stay internal to their module, so their XML documentation does not reach the document (the generator indexes public types only); operations carry `WithSummary` and request members `[Description]`.
- A validation error key is the CLR member path with only its first letter lowered by `DictionaryKeyPolicy`, so a top-level member reads `take` but a nested one would read `customer.ShippingAddress.Street`; revisit when the first nested request body arrives.
