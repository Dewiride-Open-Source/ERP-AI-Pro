# ADR-0022: Attachments in Azure Blob Storage behind an application encryption envelope

Status: accepted
Date: 2026-09-26

## Context

The `backend-platform-attachments-building-block` sub-phase gives every business module a way to store real files from day one (vendor bills, signed contracts, identity and bank documents); the `documents` phase extends it later. Its scope planned an encrypted, content-addressed Docker volume on the on-premises server. Facts that shape the decision:

- CLAUDE.md §9 (DPDP Act 2023) requires PAN, Aadhaar and bank documents to be encrypted at rest and every read of them to be audited. Attachments will carry exactly those scans.
- ADR-0005 allows exactly four Azure services: App Configuration, Key Vault, Microsoft Entra ID and, in production, Azure SQL; ADR-0010 repeats the list. Another Azure service needs the owner's decision.
- Production is one Ubuntu server on a home connection running Docker Compose with read-only root filesystems. A Docker volume lives on that one disk with no redundancy, no soft delete and no second copy, so its backup and restore would be ours to build, and developer machines and CI could never share it.
- Central India retail prices per GB-month, compared by the owner on 2026-09-26: Blob Storage Hot LRS 1.91 INR; Azure Files Hot LRS 2.87 INR, transaction-optimised 6.31 INR, Premium Files 16.82 INR provisioned.
- A block blob's staged blocks stay invisible until `Put Block List` commits them, the commit accepts `If-None-Match: *`, and the service discards blocks still uncommitted after seven days. An upload can therefore be written, hashed and scanned before anything becomes readable.
- `EfUnitOfWork.RunAsync` opens a transaction before the handler runs, inside the execution strategy that retries transient SQL failures (`Erp:Platform:Database:MaxRetryCount`), and `IdempotencyMiddleware` buffers and fingerprints the whole request body (ADR-0016). Neither fits a streamed upload of up to 100 MiB.
- Azurite, Microsoft's Blob Storage emulator, serves the same REST API locally and in CI without an Azure identity, but enforces neither role-based access nor the refusal of Shared Key.

## Decision

- **Azure Blob Storage, one Entra-only account per environment.** Attachments are stored in Azure Blob Storage, not in a Docker volume and not in Azure Files, which costs 1.5 to 8.8 times as much per GB-month and offers nothing the API uses: the API reads and writes whole objects through its own code, and the stage-then-commit upload below needs block blobs. Each environment has one `StorageV2` account created by `scripts/azure/bicep/modules/storage-account.bicep` (`Microsoft.Storage/storageAccounts@2026-04-01`): `allowSharedKeyAccess: false`, `defaultToOAuthAuthentication: true`, `allowBlobPublicAccess: false`, `allowCrossTenantReplication: false`, `minimumTlsVersion: TLS1_2`, HTTPS only; hierarchical namespace, SFTP, NFS v3 and local users off; public network access open with `defaultAction: Allow`, because no virtual network exists and developer addresses change; blob and container soft delete on, versioning and change feed off (blobs are never overwritten, so versions would only bill copies); one private container `attachments` (`publicAccess: None`); and a `CanNotDelete` lock `do-not-delete`, because soft delete does not cover deleting the account. The development account `sterpaiprodev` (`ERP_AZURE_STORAGE_DEV_NAME`) is `Standard_LRS`, Hot, in `centralindia` in `rg-erp-ai-pro`, with a 7-day retention (`developmentStorageDeleteRetentionDays`). Storage Blob Data Contributor (`ba92f5b4-2d11-453d-a403-e96b0029c9fe`) is assigned at container scope only, to the operator and the developers group; the templates grant no Storage Blob Delegator or Storage Account Contributor role, no account key is ever used, and the migrator receives no storage role. `provision.sh` checks the name with `az storage account check-name` before the account exists and writes `Erp:Platform:Attachments:BlobServiceUri` under `local-dev` from the deployment output, bumping the `local-dev` sentinel when the value changed; `verify.sh` asserts the account properties, the blob service properties, the private container, the lock, the container-scoped roles and a read-only blob listing signed in with Entra ID, and with `--labels` that the stored endpoint is the account's. The production account, its redundancy, its retention and the runtime service principal's role on its container belong to `first-deployment-production-attachments-storage`. Azure server-side encryption with Microsoft-managed keys stays on underneath everything below.
- **The Azure service list.** This supersedes the list of allowed Azure services in the context of ADR-0005 and its repetition in ADR-0010: Azure is used for App Configuration, Key Vault, Microsoft Entra ID, Blob Storage (attachments, one Entra-only account per environment) and, in production, Azure SQL.
- **An application encryption envelope over the stored bytes.** The API encrypts every file before it leaves the process, so the account holds only ciphertext and a storage data role, including one a subscription owner grants himself, reveals nothing. Per file, a random 32-byte data key encrypts the content in 64 KiB chunks with AES-256-GCM, and the data key is wrapped with AES-256-GCM under the key-encryption key. Format version 1 (`Encryption/EnvelopeHeader.cs`), integers big-endian, the key id `n` bytes of ASCII from `A-Z a-z 0-9 . _ -` with `n` from 1 to 32:

  | Offset | Bytes | Field |
  |---|---|---|
  | 0 | 4 | magic `ERPA` |
  | 4 | 1 | format version, `1` |
  | 5 | 1 | key id length `n` |
  | 6 | `n` | key id |
  | 6 + `n` | 16 | content id (the `StoredContentId` GUID, big-endian byte order) |
  | 22 + `n` | 4 | chunk size, 65 536 |
  | 26 + `n` | 7 | chunk nonce prefix, random per file |
  | 33 + `n` | 12 | wrap nonce, random |
  | 45 + `n` | 32 | wrapped data key |
  | 77 + `n` | 16 | wrap tag |

  The header is 93 + `n` bytes, and the wrap authenticates its first 33 + `n` bytes (everything before the wrap nonce) as associated data. The chunks follow the header: each is its ciphertext (65 536 bytes, the final one 1 to 65 536) followed by a 16-byte tag; chunk `i`'s 12-byte nonce is the prefix, `i` as a 32-bit big-endian integer, and one byte that is 1 for the final chunk and 0 otherwise; every chunk authenticates the whole header as associated data. `EnvelopeWriter` emits a full chunk only once more data arrives, so the chunk carrying the final flag is always the last. `EnvelopeReadStream.OpenAsync` checks the magic, the version, the key id, the chunk size and that the content id is the `StoredContent` it was asked for, finds the key among the configured keys, unwraps the data key and authenticates the first chunk before it returns a stream; it recognises the final chunk by reading one byte ahead and fails when the plaintext length differs from the recorded `Length`. An edited header, a chunk moved within or between files, a truncated or extended blob and a blob of another content all fail with `EnvelopeFormatException`. All cryptography comes from `System.Security.Cryptography` (`AesGcm`, `RandomNumberGenerator`, `IncrementalHash` and `SHA256` for the content and token hashes, `CryptographicOperations` to compare and zero key material); no package is added.
- **The key-encryption key and its rotation.** `Erp:Platform:Attachments:EncryptionKey` holds `<key id>:<32 random bytes in base64>`. It comes from the Key Vault secret `Erp--Platform--Attachments--EncryptionKey` of the environment's vault through an App Configuration Key Vault reference (the `local-dev` reference exists; the `production` reference and a separately generated production key in `first-deployment-production-attachments-storage`), from `dotnet user-secrets` for a store-less run (a copy of the development vault's key, written without display), from a generated, masked environment variable in `e2e.yml`, and from the compose secret file `infra/compose/secrets/Erp__Platform__Attachments__EncryptionKey` in the local containers (a separate key that never enters a vault; `docker-build.yml` generates one per run). `Erp:Platform:Attachments:RetiredEncryptionKeys` (`;`-separated entries of the same shape; secret `Erp--Platform--Attachments--RetiredEncryptionKeys`, referenced from the first rotation on) holds keys the API only decrypts with. `EncryptionKeys.TryParse` accepts an identical key in both settings, because a rotation copies the current key into the retired list before replacing it and the two settings refresh one after the other, and refuses one id naming two different keys; its messages name the setting and the key id, never the material. `KeyRing` parses the settings once per options instance of `IOptionsMonitor<AttachmentsOptions>`, so a rotated value delivered by the configuration refresh applies without a restart. `StoredContent.KeyId` (indexed) records which key wrapped each blob. Rotation adds keys and never re-encrypts: blobs are write-once, so re-wrapping would mean writing new blobs, which nothing does. The procedure is `docs/operations/runbooks/secrets.md`, section 5f. The API needs no Key Vault key operation; the key arrives as a secret like every other.
- **Storage layout.** One flat container. A blob's name is its `StoredContentId` (a version 7 GUID) in `N` format: 32 lowercase hexadecimal digits, no prefix, no extension. Names are random, never content hashes: names appear in storage logs and in the `url.full` of request spans, and a hash name would let anyone who sees them test whether a known document is stored; a hash is also known only after the whole upload, and a blob in an account without a hierarchical namespace cannot be renamed. Every blob is written once, committed with `If-None-Match: *`, carries `Content-Type: application/octet-stream` and has no metadata and no index tags (metadata comes back as response headers to every reader; tags need owner-level rights). Everything else lives in the SQL schema `files`, owned by the building block through `AttachmentsDbContext` (a `ModuleDbContext`, migration `InitialAttachments`): `Attachments` (the aggregate: file name, content type, scan status, `IAuditable`, `ISoftDeletable`, the foreign key to its content), `StoredContents` (`Sha256 binary(32)`, `Length`, `KeyId`, `StoredAt`), `UploadReservations`, `DownloadLinks` and `DownloadRedemptions`.
- **Deduplication by verified content, with a tolerated race.** Once the whole upload has been read, the uploader takes the newest three `StoredContents` rows with the same SHA-256 and length whose `KeyId` is the id of a configured key (a pre-filter only: the column compares without regard to case) and reuses the first one `StoredContentVerifier` can open. A row proves nothing about its blob: storage restored from another point in time can lack the blob, and a key id can come back carrying different material. So the verifier reads the envelope header with one ranged read of `EnvelopeHeader.MaxLength` (125) bytes (`IDocumentStore.OpenHeadAsync`) and unwraps its data key with `EnvelopeHeader.OpenDataKey`, which requires the header's content id to be the candidate's and matches the key id ordinally through `KeyRing.Find`; a missing blob or a header that does not open is logged at Error and the next candidate is tried. On a hit the new `Attachment` references that content and the staged blocks are deleted uncommitted; when no candidate opens, the blocks are committed and a `StoredContent` row is added, so an upload never depends on content that cannot be read. Three candidates bound the ranged reads an upload can cost. The `(Sha256, Length)` index is not unique: two identical uploads at the same moment both miss and both commit their own copy, and both rows stay valid and referenced. A unique index would turn that rare race into a failed upload; the cost is one extra copy. Identical content is therefore stored once except in that race, and per database: developers sharing the development account deduplicate within their own databases.
- **A streamed upload outside the unit of work.** `POST /api/platform/attachments` reads `Request.Body` with `MultipartReader`, never `IFormFile`, which buffers the file before any check runs; the first part with a file name is the upload, earlier parts are skipped and later parts are never read. `AttachmentUploader` checks the file name (`FileNames.Sanitize`), the declared type against `AllowedContentTypes`, that the name ends in an extension of that type (`ContentTypes.NameMatches`: `.pdf`, `.png`, `.jpg` or `.jpeg`, `.gif`, `.webp`, `.txt`, `.csv`, `.xlsx`, `.docx`, compared without regard to case; else 415 `attachment.extension-mismatch`), because a downloaded file is opened by whatever program its extension names and text saved as `.hta` or a ZIP saved as `.jar` would run as a program on the reader's computer, and the first 8 KiB against the type's signature (`ContentTypes.Matches`; text types must decode as UTF-8 and contain no NUL), then works in separate `SaveChangesAsync` steps: it saves an `UploadReservation` for a new content id; streams 64 KiB reads through the size limit, for `text/plain` and `text/csv` the `Utf8TextValidator` (every byte, not only the head, must decode as UTF-8 without NUL, else 415 `attachment.content-mismatch` before anything is committed), SHA-256, the scan hook and `EnvelopeWriter` into `BlockStagingStream`, which stages each full 4 MiB buffer as an uncommitted block (`StageBlockAsync` with an MD5 transfer checksum; block ids are the base64 of a 4-byte big-endian index, so all ids of a blob have one length) and publishes nothing on `Flush`; deduplicates; commits (`CommitBlockListAsync` with `If-None-Match: *`) only on a miss, treating `BlobAlreadyExists` or `ConditionNotMet` as success when the blob's committed block list equals its own (the client library retried a commit whose response was lost, and no other writer uses the random name); and saves the `Attachment`, any new `StoredContent` and the removal of the reservation in one `SaveChangesAsync`. No handler of the `Platform/Attachments` module runs inside `EfUnitOfWork`, because the unit-of-work step wraps only handlers whose assembly owns a catalogue context and that module owns none; so no SQL transaction stays open for up to `TransferTimeout`, and no execution-strategy retry re-runs a handler against a request body it already consumed. An upload holds one pooled 4 MiB block buffer and a few 64 KiB buffers. Rejected: `BlockBlobClient.OpenWriteAsync`, which creates a visible empty blob and commits on every flush and on dispose; `BlobClient.UploadAsync(Stream)`, a pull model that cannot interleave hashing and scanning and, for a stream of unknown length, can hold many 8 MiB blocks in memory with its default transfer options.
- **Reservations, unused links and the sweeper.** A reservation exists only while its content id names no `StoredContent`: the save that records the content removes it. A rejected, infected, failed or abandoned upload is cleaned up in a `finally` block under its own 30-second deadline rather than the request token, which is usually what was cancelled: the blob is deleted only when no `StoredContent` row references it (a save that failed on the client may still have committed on the server), then the reservation. When that cleanup itself fails, it is logged and left to `AttachmentsSweeper`, a `BackgroundService` that every `SweepInterval` (default 15 minutes; the first run one interval after start, so a short-lived test host never reaches it and the sweeper tests call `SweepReservationsAsync` and `PurgeUnusedLinksAsync` directly) runs two steps. `SweepReservationsAsync` takes up to 100 of the oldest reservations older than `UploadReservationLifetime` (default one hour; at least twice `TransferTimeout`, so an upload in progress is never swept, and below seven days, so it runs before the service discards uncommitted blocks itself), deletes the blob of each one without a `StoredContent` row, committed or not, and deletes the reservation. `PurgeUnusedLinksAsync` deletes, in one `ExecuteDelete` over the index `IX_DownloadLinks_ExpiresAt`, every `DownloadLinks` row whose `ExpiresAt` is more than `LinkGracePeriod` (one hour) ago and that has no redemption, so links nobody followed do not accumulate; a redeemed link stays, because its `DownloadRedemptions` rows, the record of who read the file, reference it, and the grace period covers a link followed in the moment before it expired whose redemption is saved just after. An exception is logged and the sweep runs again at the next interval. The sweeper works from its own database's rows, never from a blob listing, so developers sharing the development container never delete each other's files.
- **Downloads stream through the API; no shared access signature.** `POST /{id}/download-links` first checks with `StoredContentVerifier` that the attachment's stored content opens (blob present, header of this content, key configured) and answers 404 `attachment.not-found` otherwise, because a link to unreadable content would fail only after the person had followed it; then it saves a `DownloadLink` (attachment, actor, SHA-256 of the token in a unique `binary(32)` column, `CreatedAt`, `ExpiresAt = CreatedAt + DownloadLinkLifetime`) and returns `{ url, expiresAt }`, where `url` is the path of the named route `Platform.Attachments.Download` built with `LinkGenerator.GetPathByName`, `/api/platform/attachments/{id}/content?link=<token>`, and the token is 32 bytes from `RandomNumberGenerator` in Base64Url (43 characters). The token appears only in that response, so a copy of the database cannot be turned into working links. `GET /{id}/content?link=` binds `RedeemDownloadLinkRequest` and runs the command `RedeemDownloadLinkCommand` (a command, not a query, because it records a redemption), which hashes the token and matches it against the attachment, the current actor, `ExpiresAt > now` and an attachment that is not soft-deleted. A missing `link` or one over 64 characters fails request validation first (400 `request.invalid` naming `link`); after that, a token that does not decode to 32 bytes, no match, a missing blob and an envelope that fails authentication all answer the same 404 `attachment.not-found`, so a caller cannot tell the causes apart. On a match the blob's header and first chunk are authenticated, then a `DownloadRedemptions` row (link, attachment, actor, time) is saved, all before any byte is sent; the response is `Content-Disposition: attachment` with the stored file name, the stored content type and `Content-Length` set to the recorded size, without range requests because the decrypting stream cannot seek. A link may be redeemed again until it expires, each redemption recorded. The web app opens the returned path through a temporary same-origin `<a download>`, so the browser saves the file without leaving the page and a refused redemption never replaces the ERP with the problem body. A user-delegation SAS was rejected: the browser would receive ciphertext, so the envelope would have to go; issuing a SAS cannot be audited, and proving a read would need paid storage resource logs; a leaked SAS works from any address until it expires, and binding it to a person needs an Entra token in the browser, which CLAUDE.md §9 forbids; and it needs Storage Blob Delegator at account scope, CORS rules on the account and new CSP sources. A token from the ASP.NET Core Data Protection time-limited protector was not used either: its key ring arrives with the authentication phase, and a signed token can be neither revoked nor tied to redemption rows.
- **Virus scanning is a hook.** `IAttachmentScanner.StartAsync` returns an `IAttachmentScan` that receives the plaintext as it streams (`AppendAsync`) and returns `Clean` or `Infected` from `CompleteAsync` before anything is committed, because the stored bytes are ciphertext and cannot be scanned afterwards. With no scanner registered, attachments record `AttachmentScanStatus.NotScanned`; a clean verdict records `Clean`; an infected verdict answers 422 `attachment.infected` and leaves no blob and no reservation. The scanner is decided before go-live: Microsoft Defender for Storage malware scanning (about 935 INR per account-month plus about 14 INR per GB scanned) scans the blob in storage, where it would see only ciphertext, so it would require dropping the envelope; an on-server scanner needs a third-party approval under CLAUDE.md §6.
- **Credentials and clients.** `AddErpConfiguration` registers one `TokenCredential` in DI: with the App Configuration source, the `DefaultAzureCredential` instance the provider already uses, so the process keeps one token cache; otherwise a lazy factory over `AzureCredentialFactory` (`BuildingBlocks.Configuration/Credentials`), resolved only when a client that reaches Azure is built, so tests and emulator mode never need an identity. `AttachmentBlobClients` builds the container client from `BlobServiceUri` and that credential, plus a probe client for readiness with no retries and `HealthEndpoints.CheckTimeout` as its network timeout. Both are pinned to `BlobClientOptions.ServiceVersion.V2026_06_06`, which Azurite 3.37.0 supports, so a client library upgrade cannot send a service version the test emulator rejects; the pin and the Azurite digest move together. The client library keeps its own transport and retry policy: routing it through `IHttpClientFactory` would stack the retries of `AddErpHttpClientDefaults` on the library's own, and that handler's 30-second total timeout would cut off large transfers. `Microsoft.Extensions.Azure` is not used, because `AddAzureClients` builds its own credential and binds client options outside the repository's options validation. The package is `Azure.Storage.Blobs` 12.29.2 (MIT, pre-approved under `Azure.*`), and only `Dewiride.Erp.BuildingBlocks.Attachments.Storage.Blob` may use `Azure.Storage` types (`LayerTests.AzureStorage_IsReferencedOnlyByTheBlobStorageNamespace`).
- **Emulator mode.** `Erp:Platform:Attachments:EmulatorHost` is used instead of `BlobServiceUri`; exactly one of the two must be set, and a blank value counts as unset. The host is `127.0.0.1`, `localhost`, `host.docker.internal` or a single-label compose service name, and the client connects with `UseDevelopmentStorage=true;DevelopmentStorageProxyUri=http://<host>`, the emulator's well-known development account on port 10000, whose key the client library carries itself, so no storage key exists in configuration or in the repository. An emulator starts empty, so in emulator mode only `AttachmentStorageInitializer` creates the container at startup; against a real account the container comes from Bicep, and the API's identity holds its role on that one container only. Tests, CI and the local compose stack run in emulator mode against Azurite 3.37.0 (`mcr.microsoft.com/azure-storage/azurite:3.37.0@sha256:830430c1da1a2d537e08f3e6764dd1f5ae00cf0346bcaf625b968ec3f0971fd5`, blob service only, telemetry off, strict API-version checking); `dotnet run` and a locally started Playwright run use the real development account through the developer's `az login` session (`AzureCliCredential`), as the owner chose. `EmulatorHost` is host-local and never seeded. The validator does not refuse emulator mode in Production: the well-known key cannot authenticate to a real account, and every real account refuses Shared Key.
- **Validation when the API starts, not in every host.** `ErpHostComposition.AddErpPlatform` calls `AddErpAttachments()`, so the API, the test database host, the migrator and `dotnet ef` all see `AttachmentsDbContext` in the catalogue and the migrator creates the `files` schema. The options are bound with `ValidateDataAnnotations()` and `AttachmentsOptionsValidator` but without `ValidateOnStart()`, because the migrator validates options through `IStartupValidator` (ADR-0021) and needs neither the storage endpoint nor the key. `AttachmentStorageInitializer`, a hosted service, resolves the options, parses the key ring and prepares the emulator container when the API starts, so an invalid attachment setting fails API startup with a message naming the setting, while the migrator, which never starts its host, runs without any attachment setting.
- **The HTTP surface is the module `Platform/Attachments`.** Storage, encryption, metadata and links live in `BuildingBlocks.Attachments` behind `IAttachmentService`, so a business module attaches files without referencing another module. The module `Dewiride.Erp.Modules.Platform.Attachments` (descriptor schema `null`, flag `Erp.Modules.Platform.Attachments`, permissions `platform.attachments.files.upload`, `.read` and `.delete`) adds the seven routes, their handlers and the upload transport, so the feature gate, rate limiting, the catalogue checks and later the permission checks apply to them as to any module. Until the authentication phase the routes are anonymous and whitelisted in `ModuleCatalogTests`.
- **Transport for large bodies.** The upload endpoint carries `UploadSizeLimit`, an `IRequestSizeLimitMetadata` whose limit is `MaxSizeBytes` plus 64 KiB of multipart framing; routing applies it to the matched request before any middleware reads the body, so it overrides `Erp:Platform:Host:MaxRequestBodyBytes` (ADR-0018) for this endpoint only and follows `MaxSizeBytes` as it refreshes. `MaxSizeBytes` is at most `AttachmentsOptions.MaxSizeBytesCeiling` (100 MiB). Upload and download run under the named request-timeout policy `platform.attachments.transfer`, built from `TransferTimeout` (at most 10 minutes, below the 660-second `proxyTimeout` of the web app's rewrite). Every upload in flight holds a pooled 4 MiB staging block for its whole transfer, however slowly its body arrives, so the upload endpoint also requires the rate-limiter policy `platform.attachments.uploads`: a `ConcurrencyLimiter` with one partition for the whole process, `PermitLimit` from `MaxConcurrentUploads` (default 16, 1 to 1024) and `QueueLimit` 0, registered by `AttachmentsModule.AddServices`; the next upload answers 429 `rate-limit.exceeded` with `Retry-After` through the rejection writer of ADR-0019, before its body is read. The browser sends the file to `/api/platform/attachments` on the web origin with `XMLHttpRequest` (`frontend/apps/web/src/shared/api/upload.ts`), so progress is reported and no Server Function holds the file in the web server's memory. Next.js holds the body of every request `proxy.ts` matches, pages and Server Functions as well as the `/api` rewrite, in memory up to `experimental.proxyClientMaxBodySize` and silently cuts it off beyond it (10 MB by default). `next.config.ts` therefore exports a function of the phase and sets `"101mb"` (the 100 MiB ceiling plus framing) only for `next dev` and `next start` (`PHASE_DEVELOPMENT_SERVER`, `PHASE_PRODUCTION_SERVER`), the source-tree servers that load the file as they start and that local development, Playwright and CI use; the image's standalone `server.js` runs with the configuration `next build` recorded and keeps the 10 MB default, because in production the edge proxy sends `/api/*` straight to the API and no other request needs a larger buffer.
- **No idempotency key on the upload or on download links.** Both routes create something, but neither carries `.RequireIdempotencyKey()`; this narrows the convention of ADR-0016 for these two routes. For the upload, `IdempotencyMiddleware` would buffer and fingerprint the whole body, up to 100 MiB written to temporary storage (a tmpfs on the read-only production container) before the endpoint starts, while a repeated upload is harmless: identical bytes resolve to the same `StoredContent` and only add an `Attachment` row a person can delete, and the drop zone disables itself while an upload runs. For a download link the middleware would store the response body, which contains the token, in plain text in `platform_idempotency.IdempotencyKeys`, while a repeated request only creates a second short-lived link.
- **Wire conventions added with the first enum and the first paged route.** `AddErpEndpoints` registers `JsonStringEnumConverter(JsonNamingPolicy.CamelCase, allowIntegerValues: false)`, so every enum travels as its camelCase name and a number is refused; the OpenAPI document declares the names (`AttachmentScanStatus`: `notScanned`, `clean`) and the generated client carries them as constants. This extends the JSON rules of ADR-0017. `PagingParameters` binds `page`, `pageSize`, `sort` and `filter` through `FromQuery(Name = …)` with a `Description` each, so every paged route documents the same camelCase names. The Kernel gains `ErrorKind.TooLarge` (413) and `ErrorKind.UnsupportedType` (415), used by `attachment.too-large`, `attachment.unsupported-type`, `attachment.extension-mismatch`, `attachment.content-mismatch` and `attachment.multipart-required`.
- **Telemetry and health.** `AddErpAttachments` adds the tracing sources `Azure.Storage.Blobs.*` (the client library's logical operations such as `BlockBlobClient.StageBlock`; its HTTP requests already appear as `HttpClient` spans), the meter `Dewiride.Erp.Attachments` (collected through the `Dewiride.Erp.*` entry of `TelemetryMeters.Names`) and the readiness check `storage:attachments`, which reads the container's properties through the probe client and reports `Degraded`, not `Unhealthy`, because only the attachment routes depend on storage. The meter's instruments are `erp.attachments.uploads`, `erp.attachments.upload.size` (a histogram), `erp.attachments.downloads`, `erp.attachments.reservations.swept` and `erp.attachments.links.purged`. The download token travels in the query string: OpenTelemetry's ASP.NET Core instrumentation replaces every query value with `Redacted` by default, and `OTEL_DOTNET_EXPERIMENTAL_ASPNETCORE_DISABLE_URL_QUERY_REDACTION` is never set; the framework's request-start and request-finish log lines print the query string, so the category `Microsoft.AspNetCore.Hosting.Diagnostics` stays at `Warning` (all of `Microsoft.AspNetCore` in `appsettings.json`, that category explicitly in `appsettings.Development.json`); `TelemetryTests.Get_AttachmentContent_ExportsNoSpanOrLogCarryingTheLinkToken` proves that no exported span or log record carries the token. Logs name ids, lengths and key ids, never file names, tokens or content.
- **Tests.** Everything that passes through `BlobDocumentStore` or `ErpApiFactory` runs against Azurite, the storage counterpart of the rule that tests never use the EF Core in-memory or SQLite providers; test doubles of the store exist only in unit tests and as recording wrappers around the real store. `BlobTestContainer` (`Tests/Shared/Dewiride.Erp.Testing/Blob`), an xunit v3 assembly fixture declared beside `SqlTestDatabase`, reads `ERP_TEST_BLOB_EMULATOR_HOST`, deletes `erptest-` containers older than 24 hours, creates `erptest-<yyyyMMddHHmmss>-<8 hex>` per test process and deletes it at the end; `ErpApiFactory` points every test host at it, blanks `BlobServiceUri` and gives the test process one generated encryption key. The fixture builds its client with `AttachmentBlobClients.ServiceVersion` (visible to `Dewiride.Erp.Testing` through `InternalsVisibleTo`), so the fixture and the product send the same pinned service version. CI starts Azurite with the composite action `.github/actions/start-azurite` (`docker run`, like `start-sql-server` in ADR-0013, so Testcontainers is not needed); Dependabot bumps the image reference in `infra/compose/compose.override.yaml`, and `scripts/checks/tests/azurite-pin.test.ts` fails until the action and `docs/guides/local-development.md` carry the same reference. Because Azurite enforces neither role-based access nor the refusal of Shared Key, Entra-only access is proven against the development account by `verify.sh` and by a real round trip: on 2026-09-26 a file uploaded through the API to `sterpaiprodev` downloaded byte for byte, and the stored blob began with `ERPA` and contained no plaintext.
- **Earlier decisions this changes.** ADR-0005 and ADR-0010: the list of allowed Azure services gains Blob Storage (superseded as stated above; CLAUDE.md §1 carries the same list). ADR-0011: the runtime credential is also the one `TokenCredential` in DI that storage clients use. ADR-0013: SQL-backed test projects also declare the `BlobTestContainer` fixture, so integration tests need `ERP_TEST_BLOB_EMULATOR_HOST` beside `ERP_TEST_SQL_CONNECTION`, and CI starts Azurite with a composite action beside SQL Server. ADR-0016: a route that creates something carries `.RequireIdempotencyKey()` except the attachment upload and `download-links`. ADR-0017: enums travel as camelCase names, and paged routes document `page`, `pageSize`, `sort` and `filter`. ADR-0018: an endpoint may raise its body limit above `Erp:Platform:Host:MaxRequestBodyBytes` through `IRequestSizeLimitMetadata`, and the transfers run under their own named timeout policy. ADR-0019: readiness gains `storage:attachments`, which only degrades, and the upload route carries its own process-wide concurrency policy `platform.attachments.uploads` next to the global per-address and per-actor limiter. ADR-0021: the migrator composes the attachments building block and migrates `files` without any attachment setting. The sub-phase's planned "encrypted, content-addressed Docker volume" is replaced by this decision.

## Consequences

- Development storage costs 1.91 INR per GB-month plus transactions; production's price follows the redundancy chosen in `first-deployment-production-attachments-storage`. Every upload and download crosses the home connection on its way between Azure and the browser, so large transfers are bounded by the home uplink.
- The encryption key is the only way to read an attachment. Losing every copy of a key loses every file it wrapped (the vault's soft delete and purge protection guard against that), and an exposed key together with read access to the container exposes the files it wrapped. The key sits in the API's memory and is readable by every holder of Key Vault Secrets User on its vault. Rotation is manual (runbook section 5f), and a retired key stays listed until no `StoredContents.KeyId` names it. Content whose key is not configured, or whose key id names other material than the key that wrapped it, gets no download link (404 and an error log), and deduplication stores a new copy instead of reusing it.
- A refreshed attachment setting that fails validation makes `IOptionsMonitor<AttachmentsOptions>.CurrentValue` throw, so uploads, the upload policy, new download links and downloads fail with 500 until the value is corrected; the storage endpoint or emulator host, the container name, `TransferTimeout`, `UploadReservationLifetime`, `SweepInterval` and `MaxConcurrentUploads` are read once and change only at the next start (a sentinel bump after `provision.sh` changes `BlobServiceUri` therefore needs a restart as well).
- Deleting an attachment soft-deletes its row and stops its download links; its `StoredContent` and blob stay, because other attachments may share them. Purging unreferenced content and blobs (DPDP erasure, retention) belongs to `documents-document-model-and-permissions`; blob soft delete keeps a purged blob recoverable for the account's retention period.
- `DownloadRedemptions` is the record of who read which file until the audit trail of `user-management-audit-trail-building-block` exists. Until the authentication phase every caller is the anonymous actor, so the actor binding of links separates nobody and the routes serve anyone who reaches the API.
- Attachments record `notScanned` until the scanner is chosen before go-live; choosing Defender for Storage reopens the envelope decision.
- The development container is shared: a developer who drops their database leaves the blobs it referenced as unreferenced ciphertext, and uncommitted blocks the sweeper misses are discarded by the service after seven days. The developers group holds its first Azure write permission (blob data on the development container).
- A download token can remain in browser history and in any access log that records query strings; it expires after `DownloadLinkLifetime` and works only for the actor who created it. The edge proxy of the first-deployment phase must route `/api/*` straight to the API, which also keeps production uploads out of the web process, whose standalone server would cut them off beyond 10 MB. Until an edge proxy exists, the local containers (the web container rewrites `/api/*` itself) cut off an upload over 10 MB sent through their web origin; larger files go to the API's own port, or through `pnpm dev` or `next start`.
- One API process accepts at most `MaxConcurrentUploads` uploads at once, 64 MiB of staging blocks at the default of 16; the next upload answers 429 `rate-limit.exceeded` with `Retry-After`, whoever sends it, and the web app shows that problem in the upload panel like any other refusal. The cap applies even when `Erp:Platform:RateLimiting:Enabled` is `false`.
- Every `POST …/download-links` and every upload that finds a deduplication candidate costs a ranged blob read of at most 125 bytes per candidate checked; unredeemed links disappear an hour after they expire, so the database keeps no record of links that were created but never followed.
- A production API cannot start until `first-deployment-production-attachments-storage` writes `BlobServiceUri` and the key reference under `production`, as with the database reference.
- A client library upgrade that raises its default service version changes nothing while the version is pinned; raising the pin requires an Azurite image that supports it. The digest in `.github/actions/start-azurite` is bumped by hand, guarded by `azurite-pin.test.ts`.
- The first readiness answer after a developer starts `dotnet run` may be `Degraded` while `AzureCliCredential` obtains its first token within the 2-second check timeout.
- A business module attaches files through `IAttachmentService` and keeps the returned `AttachmentId`; `docs/architecture/attachments.md` describes the contract, the flows and the failure handling.
