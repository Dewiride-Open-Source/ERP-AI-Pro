# ADR-0029: Captures of a page at rest and the hydration marker

Status: accepted
Date: 2026-09-29

## Context

Every run of `e2e.yml` on `main` since the merge of `web-foundation-feedback-motion-and-accessibility` failed in the three WebKit projects (`webkit`, `mobile-ios` and, from ADR-0028, `tablet-ios`), while chromium, firefox and mobile-android passed. Pull requests run only chromium and mobile-android, so no pull request showed it. Three problems, reproduced with WebKit on Linux in the Playwright image `mcr.microsoft.com/playwright:v1.63.0-noble` limited to one or two processors (a remote browser server, `PW_TEST_CONNECT_WS_ENDPOINT`), none of them visible on a developer machine:

- **Scans of a page that had not come to rest (flaky).** The axe scan of ADR-0027 reported `color-contrast` on elements whose resting colours pass (the attachments list's "Type" filter trigger and column headers at 3.39:1 and 4.17:1, the in-shell not-found page, a hover card, the combobox's options) and once `document-title` after a refresh. A recording of the scan showed the cause: on a loaded runner the page hydrated four seconds into the scan, the controls that are disabled in the server's HTML (ADR-0025, ADR-0026) came alive and faded from 50 % opacity while axe measured them. `settleAnimations` had only checked that no finite animation ran when it was called: hydration came seconds after the load event with nothing moving in between, and a Radix popover mounts first and starts its entrance animation only once Floating UI has positioned it.
- **One test too long for a slow engine (every run).** "renders every primitive in its states" in the kitchen sink captured every primitive section in one test. Each capture is scanned first, and on a CI runner WebKit took about 5.4 s per capture (2.7 s of scan, 2.2 s of screenshot), so the test ran out of its 90 s after about 17 of its captures.
- **A motion test that needs frames (every run).** The feedback spec proved that a reminder moves by recording heights between closed and open. A loaded runner drew no frame inside the 200 ms of the animation, so the item went from closed to open with nothing between, although the animation ran for its full duration.

## Decision

- **The hydration marker.** A component whose server-rendered HTML differs from what it renders once hydrated calls `useHydrated()` (moved from the data table to `@dewiride/erp-ui/lib/use-hydrated`, and used by `useActionForm` instead of its own copy) and puts `data-hydrating` on its element until it has hydrated:
  - `DataTable` on its root, which covers the filters rendered inside it, because they hydrate in the same render;
  - `SubmitButton` from its own hydration, whatever its `ready` prop says, so the kitchen sink's specimen of the not-ready state never holds up a capture;
  - `ThemeToggle`, which checks no item until it has hydrated;
  - the kitchen sink's motion demo, which reads the preference and the durations only in the browser.
- **A capture waits for a page at rest.** `waitForRest` in `fixtures/test.ts` runs in the page and resolves when no element carries `data-hydrating` or `data-animating`, no finite animation or transition runs (`document.getAnimations()`; one that repeats for ever is left running), and the document has then stayed unchanged (a `MutationObserver` over the whole document) for three animation frames. It gives up after 10 s and fails the test, naming what was still busy or the last change and the number of frames it saw. `capture` waits for rest once, before the scan; the screenshot follows the scan while CSS motion is still held (next item).
- **The scan measures resting colours.** While axe and then the screenshot run, a style sets `animation-duration`, `animation-delay`, `transition-duration` and `transition-delay` to `0s !important` on every element and pseudo-element, and is removed afterwards. A change that starts meanwhile, such as a toast leaving, is then scanned and shown at its end, and an animation that repeats for ever shows its base style. One wait per capture matters: on a CI runner WebKit takes about two seconds per action on the kitchen sink, and a second wait before each screenshot pushed "dialogs, confirmations and sheets" past its 90 s, so that test is also split into "dialogs and confirmations" and "sheets". The failure message now carries axe's `failureSummary` for each element (for contrast: the ratio, both colours and the font).
- **The kitchen sink captures each primitive section in its own test** ("captures every primitive section", one test per section in each theme), with the same screenshot names. "renders every primitive in its states" keeps its assertions, focus and hover captures and the overflow check.
- **The motion test measures time.** It records the time of each click with the inline heights. Without the reduced-motion preference, the item's last height comes at least 90 % of the normal duration after the click, because an animation ends only once its duration has passed since it started, however few frames the runner draws. With the preference, no height between closed and open is ever written.
- **The offline system-information test waits for its refresh.** It waits for the page's React Server Components response before checking that Refresh is enabled, as the online test already did, so the capture never overlaps a refresh.
- **A change to the Playwright harness runs the full matrix before it merges.** `e2e.yml` already accepts `workflow_dispatch`, which runs all six projects on the branch; the run of `e2e.yml` on `main` after a merge is watched as well.

## Consequences

- A capture always shows a page that works: its controls are live, its popovers placed and its entrances finished, on every engine and runner speed. A page that never comes to rest fails with the reason, instead of producing a flaky scan.
- A new component that renders differently before hydration must mark itself with `data-hydrating`, or a capture may catch it mid-change. The form-kit and data-table specs prove the marker with JavaScript switched off and its absence once hydrated.
- The kitchen sink spec gains eleven tests per theme and project, one per primitive section, each loading the page; "renders every primitive in its states" stays and no longer captures the sections, so no single test holds every capture.
- **Earlier decisions this changes.** ADR-0027 says the scan waits until finite animations have finished and no element carries `data-animating`; that wait is now the rest described here, and the scan holds CSS motion at its end. ADR-0026's `useHydrated` for the data table's controls now lives in `@dewiride/erp-ui/lib/use-hydrated` and is shared with the form kit, the submit button, the theme toggle and the kitchen sink's motion demo.
