# ADR-0016: The application pipeline, the unit of work, query contracts and idempotency keys

Status: accepted
Date: 2026-09-22

## Context

ADR-0009 bans MediatR, so the hand-written `ICommandHandler`/`IQueryHandler` abstractions of the foundation phase have no pipeline: a handler is resolved and called directly, it saves its own changes, and nothing validates the request, logs the outcome, makes the write atomic with the reactions to its domain events, or stops a repeated POST from acting twice. Hundreds of modules will write these handlers, so the cross-cutting behaviour has to be automatic and identical everywhere, and a module author must not be able to disable it by forgetting a call.

Three further decisions were open. How a list endpoint accepts paging, sorting and filtering without letting a caller reach a column the module did not offer or inject SQL. How a failed validation reaches the client as RFC 9457 ProblemDetails with one message list per field. And how a client that retries a POST after a timeout avoids creating a second invoice, before authentication exists to identify the caller.

## Decision

- Pipeline by wrapping, not by convention. `AddHandlersFromAssembly` registers each handler as itself and its closed interface as `CommandHandlerPipeline<TCommand, TResult>` or `QueryHandlerPipeline<TQuery, TResult>`, built by `ActivatorUtilities` with a `HandlerDescriptor(HandlerType, RequestType, HandlerKind)`. Resolving `ICommandHandler<…>` therefore always yields the pipeline; the bare handler is reachable only by its concrete type, which only the pipeline asks for.
- Steps are ordered by `PipelineStage` (`Logging`, `Validation`, `UnitOfWork`), never by registration order, and are added with `TryAddEnumerable`, so calling `AddHandlersFromAssembly` for each of a hundred modules leaves exactly one of each step. A step sees the request, the descriptor and the continuation, and may short-circuit.
- `ValidationStep` uses `System.ComponentModel.DataAnnotations` (`Validator.TryValidateObject` with `validateAllProperties: true`, including `IValidatableObject`) and turns failures into `Error.Validation("request.invalid", …)` with a new `Error.Fields` dictionary of member → messages. `ResultExtensions.ToProblem` renders such an error as `HttpValidationProblemDetails`, so the response body carries `errors` per field alongside the `code` extension; validation errors without fields (the query-grammar ones) stay plain ProblemDetails. `ToCreatedResult(location)` adds the 201 case.
- `LoggingStep` starts an activity on `Dewiride.Erp.Application` per request and logs the outcome with `[LoggerMessage]`: commands at information, queries at debug, a failed result with its error code, an exception at warning before rethrowing. Cancellation is not logged.
- `UnitOfWorkStep` (in `BuildingBlocks.Persistence`, because the Application layer knows nothing of EF Core) applies to commands whose handler assembly owns a context in the `DbContextCatalog`. `EfUnitOfWork.RunAsync` joins an ambient transaction when one exists, otherwise runs the execution strategy with `ChangeTracker.Clear()` per attempt, a transaction, the handler, then alternating `SaveChangesAsync` and domain-event dispatch until a round finds no event (at most ten, then it throws naming the cycling event types); the events are taken off the aggregates before each save, so an aggregate the handler removed still raises them after EF detaches its entry. A failed `Result` rolls back; a `DbUpdateConcurrencyException` becomes `Error.Conflict("concurrency.conflict", …)`. Handlers never call `SaveChangesAsync`; `IHasDomainEvents` on the Kernel's `AggregateRoot<TId>` is what the loop walks.
- Query contracts are allow-list first. `PageRequest` (1-based page, size 1 to 200, default 50), `SortRequest` (`field:asc|desc`, `,`-separated, at most 5) and `FilterRequest` (`field:operator:value`, `;`-separated, `in` values `|`-separated, at most 10 terms of 100 values, percent-encoded values so separators may appear inside them) parse the wire text into terms, and `Resolve` maps them against the handler's `SortableFields<T>`/`FilterableFields<T>`. A field outside the list, an operator the field's type does not allow, or a value that does not parse answers 400 with `query.invalid-field`, `query.invalid-operator` or `query.invalid-value` naming what is allowed. The predicate is built from the registered selector expressions with values boxed in a closure so EF Core parameterises them; no user text ever reaches SQL. `ApplySort` always appends the caller's tie-breaker, and `ToPagedResultAsync` counts once and skips the row query when the page is past the end.
- Idempotency is middleware, not an endpoint filter, driven by `.RequireIdempotencyKey()` metadata: a filter runs after model binding has consumed the body and cannot capture the bytes the result executor writes. `IdempotencyMiddleware` runs after the feature gate, fingerprints method, path, query, actor id and buffered body with SHA-256, and claims (actor id, key) in `platform_idempotency.IdempotencyKeys` with an insert-first store that treats a unique-violation as "someone else holds it". In progress → 409 `idempotency.in-progress`; a different fingerprint → 422 `idempotency.key-reused`; completed → the stored status, content type, `Location` and body replayed with `Idempotency-Replayed: true`. The response is captured through a `BoundedCaptureStream` capped by `Erp:Platform:Idempotency:MaxStoredResponseBytes`; a larger response is still delivered to the first caller but a replay answers 409 `idempotency.replay-unavailable`. A 5xx or an exception releases the key so the client may retry with it, unless the unit of work already committed: `UnitOfWorkSignal` records the commit, the claim then stands and a retry answers 409, because a client that times out while the 201 is being written must not create a second invoice. `IdempotencyCleanupService` deletes expired rows on a `PeriodicTimer` driven by `TimeProvider`.
- `BuildingBlocks.Idempotency` owns the schema `platform_idempotency` through `AddModuleDbContext`, so the migrator and the test database host migrate it like any module context; `AddErpIdempotency` is part of `ErpHostComposition.AddErpPlatform`.

## Consequences

- A module author writes a handler and a request record with data annotations; logging, validation, the transaction, the domain-event dispatch and the concurrency mapping happen without any further call, and a handler that saves by itself is the exception worth reviewing.
- The container returns a pipeline, so a test that wants the bare handler resolves the concrete type. Handler constructors stay injectable because the pipeline resolves the handler from the same scope.
- Every command of a module with a context runs in a transaction, so a handler that only reads pays a transaction it does not need; queries do not, and a read-only use case belongs in a query handler.
- Domain events are dispatched inside the transaction: a handler that must not roll back the aggregate (sending mail, calling another system) belongs behind an integration event, not a domain event.
- The filter grammar is fixed in the wire format; adding an operator later is an additive change to `FilterOperators` and the field defaults, but changing a separator would break every stored URL, so the separators are part of this decision.
- Until authentication lands, an anonymous caller is `ActorIds.Anonymous`, so the idempotency key space is shared between anonymous callers: two clients choosing the same UUID would see each other's replay. The keys are UUIDs, the window is a day, and from the authentication phase each Entra identity has its own space; the interim is stated in the pull request rather than worked around.
- Storing response bodies means a reply may live in the database for a day. The store holds what the endpoint already returned to the caller and is dropped by the cleanup service; endpoints that must not have their body stored simply do not opt in.
