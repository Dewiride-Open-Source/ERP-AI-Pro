# ADR-0033: Antiforgery for requests the session cookie signs in

Status: accepted
Date: 2026-10-02

## Context

ADR-0004 decided that state-changing requests carry an antiforgery token in the `X-XSRF-TOKEN` header with a readable token cookie, ADR-0018 reserved the place of antiforgery in the request pipeline after authorization, and ADR-0017 and ADR-0025 left the header on the web app's API calls and on the browser upload to sub-phase `authentication-antiforgery-for-json-endpoints`. Since ADR-0031 the browser holds the session cookie `__Host-erp-session` and sends it with every request to the API, whether the page or another site caused it; `SameSite=Lax` keeps it off cross-site POSTs, but not off requests from a sibling site of the same registrable domain. Facts that shape the design, read from the ASP.NET Core 10.0.12 source and checked in browsers:

- The framework's antiforgery middleware (`UseAntiforgery`) validates only endpoints whose metadata requires it, which minimal APIs add for form binding; it records the result in `IAntiforgeryValidationFeature` and never answers the request itself, so it protects no JSON endpoint. With an explicit `UseRouting`, `WebApplication` inserts it ahead of the whole pipeline unless the app calls it.
- `DefaultAntiforgery` refuses every call, validation included, on a request it does not see as HTTPS when `AntiforgeryOptions.Cookie.SecurePolicy` is `Always`. The web server calls the API over plain HTTP inside the host, and local development is plain HTTP throughout.
- `DefaultAntiforgeryTokenStore` reads the request token from the header and, only when the header is absent and the body is a form, reads the whole form; once the framework middleware has recorded a failed validation, reading the form throws.
- A request token embeds the cookie token's security token and the user it was issued to: a hash of `sub`, which the Entra id token carries, or of every claim of an identity that has none. The cookie token names nobody. A token issued to an anonymous caller is refused once the caller is signed in, and a token issued to one person is refused for another.
- Next.js aborts a Server Function call whose `Origin` differs from `Host` (or `X-Forwarded-Host`); Server Functions call the API from the web server with the browser's cookies forwarded (`shared/api/client.ts`).
- Playwright's WebKit (1.63, on Windows) keeps a `Secure` cookie set over `http://localhost` but neither sends it back nor shows it to scripts; Chromium and Firefox treat `localhost` as secure.

The sub-phase is Community edition (ADR-0030, confirmed 2026-09-29).

## Decision

- **Only requests the session cookie signs in are checked.** `AntiforgeryValidationMiddleware` (`BuildingBlocks.Authentication/Antiforgery`) refuses a POST, PUT, PATCH or DELETE for which `AuthenticateAsync("Cookies")` succeeds (the cookie handler's cached result, so no second session check) unless it carries a valid token. GET, HEAD, OPTIONS and TRACE, anonymous requests and requests authenticated by another scheme (the test header today, a bearer token from `authentication-session-endpoints-openapi-security-and-bearer`) pass unchecked, because only the session cookie reaches the API without the page asking for it. An endpoint whose metadata disables validation (`DisableAntiforgery()`) is skipped; `ModuleCatalogTests.Endpoints_NeverDisableTheAntiforgeryCheck` fails on any product endpoint that does, and only the test sign-in route carries it, because it stands in for the Entra callback, which `UseAuthentication` answers before the check.
- **The token travels in the header.** The request token is the value of the readable cookie `__Host-erp-xsrf`, sent back in `X-XSRF-TOKEN`; the cookie token is the HttpOnly cookie `__Host-erp-antiforgery` (`AntiforgeryOptions.Cookie.Name`; names in `AntiforgeryTokens`). The body is never read for the token, so an upload without the header is refused before a byte of it is read. Only an endpoint whose metadata requires validation also takes it from the form field `__RequestVerificationToken`: `POST /api/auth/logout` carries `RequireAntiforgeryTokenAttribute`, because the page signs out with a form it posts as a top-level navigation, the one way that request can end in the Entra end-session redirect.
- **A refusal is 400.** `antiforgery.token-missing` when the cookie token or the request token is absent, `antiforgery.token-invalid` when the token does not deserialize, belongs to another cookie token or names another person (`AntiforgeryProblems`); the title is "The request could not be confirmed as coming from this site.", the `detail` is for developers, and a `[LoggerMessage]` warning records the method, the path and the code, never a token. The check runs after authorization, so a request without a session still answers 401, and before the feature gate and idempotency, so a refused request reaches no module and claims no key, and may be sent again.
- **Two middlewares, ours first.** `UseErpAntiforgery()` adds `AntiforgeryValidationMiddleware` and then the framework's `UseAntiforgery()`, called explicitly after `UseAuthorization` so `WebApplication` does not insert it before routing, and kept so an endpoint that binds a form keeps working: the framework validates such endpoints for every caller. Ours runs first because the framework's refusal would make its read of the form throw.
- **The API writes both cookies itself.** `AntiforgeryCookies.Issue` calls `IAntiforgery.GetTokens`, which writes nothing, with the request's user set to the person, and appends `__Host-erp-antiforgery` (HttpOnly, Secure, SameSite=Strict, Path=/) when a new cookie token was generated and `__Host-erp-xsrf` (Secure, SameSite=Strict, Path=/, readable by scripts) always, both without Expires, so they end with the browser session like the session cookie. `AntiforgeryOptions.Cookie.SecurePolicy` stays `None`; the framework never writes the cookie. The `__Host-` prefix keeps sibling hosts from setting or shadowing either cookie. Both are SameSite=Strict because only a request that one of this site's pages sends needs them: the API reads the request token only from the header or the form field, never from its cookie, and the web app reads that cookie only when a page sends a change, a same-site request that carries Strict cookies.
- **The pair lives with the session.** `SessionCookieEvents.SignedIn` issues it for the person on every sign-in, the Entra callback and the test sign-in alike; `SessionCookieEvents.SigningOut` clears both, so a sign-out and a session cookie the check refuses remove them. `IAntiforgery.GetTokens` reuses a valid cookie token only when the request carries one, which is safe because the cookie token names nobody and the request token names the person: the web app's same-origin calls to `GET /api/auth/antiforgery` keep it, and so does the test sign-in. The Entra callback is a cross-site `form_post` from Entra's own site and carries no SameSite=Strict cookie, so every Entra sign-in writes a new cookie token with the request token, and a request token issued before that sign-in, such as one a page captured earlier, is refused afterwards. A sign-in on a request whose session cookie the check refused, and whose pair `SigningOut` therefore cleared, writes the reused cookie token again, so the clearing cannot win.
- **Only this site's scripts renew the pair.** `GET /api/auth/antiforgery` (`Auth.Antiforgery`, signed in only; 204, or 401 without a session) issues the pair again only when `Sec-Fetch-Site` is absent (the web server's own calls) or exactly `same-origin` (the web app's scripts); otherwise it answers 400 `request.invalid` and sets nothing. A navigation another site starts carries the SameSite=Lax session cookie without the SameSite=Strict cookie token, so `IAntiforgery.GetTokens` would generate a new cookie token, `AntiforgeryCookies.Issue` would write it, and every request token a page of this site already holds would be refused; images and frames of another site carry no session cookie and answer 401 before the endpoint runs. A sibling site (`same-site`) and the address bar (`none`) are refused too, because the web app never sends either value. It is the same absent-or-exact rule that `GET /api/auth/login` applies to `Sec-Fetch-Mode` and `Sec-Fetch-Dest`.
- **Anonymous callers get no tokens.** The note that `GET /api/auth/antiforgery` had to be anonymous while the transitional platform routes are assumed that anonymous requests would be checked; they are not, so the endpoint requires a session and neither anonymous route list changes.
- **Tokens survive restarts.** They are Data Protection payloads under the persisted key ring and the fixed application name of ADR-0032, which `AddAntiforgery` reuses.
- **The web app sends the token.** `frontend/apps/web/src/shared/api/antiforgery.ts` holds the names and the rule, `sendWithAntiforgery`: a call that changes data carries `X-XSRF-TOKEN` with the value of `__Host-erp-xsrf`; after a refusal with an `antiforgery.` code it fetches a new pair from `GET /api/auth/antiforgery` once and sends the request once more, a 401 from that renewal means the session has ended, and a request whose body was a stream is never sent again. Server Functions follow it in `shared/api/client.ts` with the value from the forwarded cookie header, relaying the renewed cookies to the browser with `cookies().set`; the browser upload follows it in `shared/api/upload.ts` with the value from `document.cookie`. A refusal that survives the retry reaches people as a plain sentence, never as the API's `detail`: "The form could not be sent. Try again." in forms (`problemToFormState`) and "This could not be sent. Try again." wherever `apiErrorMessage` describes an `ApiError`.
- **Earlier decisions this changes.** ADR-0004: the readable cookie is `__Host-erp-xsrf`, not `XSRF-TOKEN`, and the check covers the requests the session cookie signs in. ADR-0018: antiforgery takes its reserved place after authorization, as two middlewares. ADR-0031: `POST /api/auth/logout` also answers 400 for a missing or invalid token. ADR-0017 and ADR-0025: the header the web app's API client and browser upload were to send is in place.

## Consequences

- No other site, a sibling site of the domain included, can make a signed-in person's browser change anything through the API: its form cannot set the header, its scripts cannot send the header to the API without CORS, and it cannot read the token. Server Functions are protected first by Next.js's origin check; the token on their API calls keeps one rule for every request that carries the cookie.
- Every request that changes data with the session cookie costs two Data Protection unprotects more; a refusal costs no database round trip beyond the session check.
- A browser that holds a session without the pair, signed in before this change or with some cookies cleared, has its first call that changes data refused once and accepted on the automatic retry.
- WebKit over `http://localhost` neither sends nor shows the Secure cookies, so a signed-in Playwright run on WebKit needs the e2e web origin over HTTPS; `authentication-test-authentication-infrastructure`, which brings the signed-in fixture, decides it and adds the signed-in browser proofs of the header.
- `authentication-session-endpoints-openapi-security-and-bearer` describes the header in the OpenAPI document and keeps bearer requests unchecked; a request that carries both a bearer token and the session cookie is checked, against `HttpContext.User`.
- `authentication-web-login-page-and-session-integration` builds the sign-out form: `<form method="post" action="/api/auth/logout">` with a hidden `__RequestVerificationToken` filled from `__Host-erp-xsrf` when the form is submitted, never when the page renders, because a sign-in in another tab replaces the pair.
- A sign-in that completes on a request carrying the browser's session cookie (the test sign-in, the e2e sign-in of `authentication-test-authentication-infrastructure`) keeps the cookie token; only the Entra callback always writes a new one.
