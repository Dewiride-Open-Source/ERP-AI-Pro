# ADR-0026: Server-driven lists: the view in the address and the data table

Status: accepted
Date: 2026-09-28

## Context

The `web-foundation-data-table-kit-core` sub-phase asks for a server-driven table "TanStack Table + TanStack Query over the generated API client" with sorting, filtering, pagination, column visibility, row selection and a mobile card layout, backed by the paginated-query contract of `backend-platform-application-layer-primitives`. Facts that shape the decision (web paths relative to `frontend/apps/web/src/`):

- **Reads.** ADR-0017 makes `shared/api/client.ts` the web app's only HTTP client: it is `server-only`, forwards the visitor's cookie and trace headers, and the browser sends no API request from script except the upload of `shared/api/upload.ts` (ADR-0022). TanStack Query, approved in ADR-0009, is a browser-side cache whose query functions run in the browser; using it for lists would need either the generated client in the browser or Server Functions as read calls, which React and Next.js document for mutations only.
- **The list contract** (ADR-0016, `docs/architecture/application-pipeline.md`): `page` from 1, `pageSize` 1 to 200, `sort` as up to five `field[:asc|desc]` terms, `filter` as up to ten `field:operator:value` terms joined by `;` (operators `eq`, `ne`, `gt`, `gte`, `lt`, `lte`, `contains`, `in` with `|` between values), each value percent-encoded and decoded by the API with `Uri.UnescapeDataString`; a field outside an endpoint's allow-list answers 400. `GET /api/platform/attachments` sorts by `fileName`, `contentType`, `sizeBytes` and `createdAt` (default `createdAt` descending) and filters `fileName` and `contentType` as text and `createdAt` as an instant.
- **TanStack Table.** The latest release on 2026-09-28 is `@tanstack/react-table` 9.2.4 (published 2026-08-28), a rewrite of v8: `useTable` with `tableFeatures({...})` registering only the features a table uses, state held in TanStack Store atoms, `table.FlexRender`, and per-table column meta through a phantom `columnMeta` slot. Its runtime dependencies are `@tanstack/table-core` 9.2.4 and `@tanstack/react-store` 0.11.1, which brings `@tanstack/store` 0.11.1 and `use-sync-external-store` 1.7.0; all four are MIT (the first three from the TanStack organisation, maintainer `tannerlinsley`; the last from Meta's React repository); the peer is `react >=18`. Server-side operation is `manualSorting`, `manualPagination` and `manualFiltering`, with `data` holding the current page.
- **Next.js 16.3.6.** Every page is rendered at request time (the nonce content security policy). A navigation that changes only search parameters runs in a transition and keeps the current page on screen until the new one is ready; `window.history.pushState` and `replaceState` integrate with `useSearchParams` without a server request; `next/link` calls `onNavigate`, which may cancel the router's navigation; `next/form` with a string `action` submits as a native GET form before hydration and as a client navigation after it; typed routes accept a route, or `?${string}` alone, as an `href`. `redirect()` inside a page streamed behind `loading.tsx` answers 200 and redirects in the browser.
- **The owner's decision (2026-09-28)**: when someone pages, sorts or filters a list, the server fetches just that page and the page address records the view (page, sorting, filters and hidden columns), so a link, a bookmark or the Back button brings the same view back, and the old rows stay visible, dimmed, until the new ones arrive; the browser never reads ERP data directly. TanStack Query is not used.
- **Time.** India observes no daylight saving, so every India Standard Time midnight is a fixed UTC+05:30 instant; `createdAt` is a UTC `DateTimeOffset`.

## Decision

- **Owner decision, recorded.** Lists read on the server through `client.ts`; the view lives in the address; no browser-side read path and no TanStack Query (it stays approved under ADR-0009 for a later list that needs live updates, which would come with its own ADR).
- **Packages.** `@tanstack/react-table` 9.2.4 (ADR-0009 approval) is pinned in the `catalog` of `pnpm-workspace.yaml` and is a dependency of `@dewiride/erp-ui` only; nothing outside `packages/ui/src/components/data-table/` imports it, so `apps/web` works with the kit's own types. `@tanstack/table-core`, `@tanstack/react-store`, `@tanstack/store` and `use-sync-external-store` are approved with it, stay transitive and are declared nowhere. The Dependabot `ui` group gains `@tanstack/*`. The GitHub Advisory Database listed no advisory for any of the five on 2026-09-28.
- **The data table** (`packages/ui/src/components/data-table/`, contract in `docs/architecture/design-system.md`, section "Data table"). `DataTable<TRow>` renders one page it is given; it is controlled and knows nothing of addresses. A column is `DataTableColumn<TRow>`: `id` (for a sortable column, the API field name), `header`, `cell(row)`, `sort` (`text`, `number` or `date`; present means sortable), `hideable`, `align`, `role` (`title` or `actions`) and a cell `className`. TanStack Table (`rowSortingFeature`, `columnVisibilityFeature`, `rowSelectionFeature`, `manualSorting`, one sort term) holds the column model, visibility and selection:
  - **Sorting.** A sortable header is a button inside a `th` carrying `aria-sort`. A column sorts first ascending when it is text and descending when it is a number or a date, and each further press flips the order; a list is never unsorted, because every list has a default order. Below the container breakpoint the headers are hidden, so a "Sort by" select lists each visible sortable column in both orders, worded for its kind ("A to Z", "highest first", "earliest first").
  - **Rows.** The `title` column renders as the row header (`th scope="row"`); the `actions` column has a visually hidden header and cannot be hidden or sorted.
  - **Column visibility.** A "Columns" menu of checkbox items shows each hideable column; the last visible data column cannot be hidden.
  - **Selection.** An optional checkbox per row ("Select <row label>") and a select-all checkbox for the page (checked, mixed or clear) select by row id, so a selection survives paging and sorting; a live status says how many rows are selected, and "Clear selection" empties it and moves focus to the list.
  - **Paging.** The page bar shows a live status ("Showing 21–40 of 132 bills.", with the order read out to screen readers), the rows-per-page select and first, previous, next and last links rendered by a link component the caller supplies. A link that leads nowhere on the first or last page stays the same element with `aria-disabled`, so keyboard focus never falls to the page.
  - **Pending and empty.** While a new page is on its way the status says "Loading…", the table or card list carries `aria-busy` and dims; a list without rows shows the caller's empty state and no page controls.
  - **Cards.** Below the `@2xl/data-table` container width (42rem) the same rows render as a list of cards: the title, then each visible column as a term and definition, then the actions. Both layouts are in the page and one is shown by a container query, so the server's HTML is right at every width without measuring the screen.
  - **Before hydration.** Controls that work only through React (sort buttons, the sort select, the column menu, the checkboxes, the rows-per-page select and the choice filter) render disabled in the server's HTML and enable on hydration (`useHydrated`, `useSyncExternalStore` with a server snapshot of `false`), as the form kit's submit button does; page links and the filter form work before hydration.
- **Filter controls** (`components/data-table/filters/`): `DataTableTextFilter` (a search box), `DataTableOptionsFilter` (a menu of checkbox items that writes one hidden input per chosen value) and `DataTableDateRangeFilter` (the kit's `DateRangeInput` writing `<name>From` and `<name>To` hidden inputs, which hold only real calendar dates). A date that is not a real date, or an end before the start, sets the text box's custom validity and shows its message once the box loses focus or the form is sent.
- **The view in the address** (`shared/lists/`). A list is described by a `ListDefinition` in `<feature>/lists/<name>.list.ts`, built with `defineList`, which refuses at import a definition the API contract cannot serve (page sizes outside 1 to 200 or out of order, a default page size or sort that is not offered, field names the API grammar refuses, filters that could send more than ten terms, colliding parameter names, hideable columns that do not exist). The address holds, in this order: each filter (`<param>=<text>`, `<param>=<value>` once per chosen option, `<param>From` and `<param>To`), `sort=<field>:<asc|desc>`, `size=<page size>`, `page=<n>` and `hide=<column>,<column>`; a value equal to its default is left out, so the first page in the default order is the bare path. `readListQuery` reads Next.js's `searchParams` into a `ListQuery` (unknown parameters, malformed or repeated values, options outside a fixed list, impossible dates and reversed ranges, sizes that are not offered, pages the API cannot reach and unknown or all columns hidden are dropped) and reports whether the address was already canonical; a page redirects a non-canonical address to `listHref` and a page past the last one to the last page. `listApiParameters` maps a query onto the API: the sort always explicitly, a text filter to its operator (`contains` or `eq`), options to `in`, a date range on an instant to `gte` its first day's IST midnight and `lt` the IST midnight after its last day (no upper bound for 9999-12-31), and a date range on a calendar date to `gte` and `lte`; every value is encoded with `encodeURIComponent`, so `;`, `:`, `|` and `%` in a value survive.
- **Navigation.** `ListTable` (`shared/lists/list-table.tsx`) binds the data table to the address inside one `ListNavigationProvider`: sorting, the page size and the filter form call `navigate(href)`, which runs `router.push(href, { scroll: false })` in one transition whose pending flag dims the list; page links are `next/link` elements (`prefetch={false}`, `scroll={false}`) whose `onNavigate` cancels the router's own navigation and calls the same `navigate`. In-page links are relative (`?page=2`, or the base path for the canonical first page); server redirects use the absolute `listHref`. Hiding or showing a column rewrites the address with `window.history.replaceState` and no server request; the server reads `hide` too, so the first render already leaves those columns out. Changing the sort, the page size or a filter returns to the first page; a new set of filters clears the selection.
- **The filter form** (`shared/lists/list-filter-form.tsx`) is `next/form` with the list's path as its string `action`, `role="search"` and an "Apply filters" button; its hidden inputs carry the sort, the page size and the hidden columns, so a submission before hydration keeps them and the server canonicalises it. After hydration `onSubmit` checks validity (focusing the first invalid field instead of sending), builds the canonical address from the form's fields and navigates through the list's transition. The form keeps its fields, and the focus in them, when the address changes because it applied the filters; any other change (Clear filters, Back, a link) remounts it with the new values, and after "Clear filters" focus moves to the first filter. When filters match nothing the list shows "No <things> match these filters." with its own "Clear filters" link.
- **Working examples.** `/design/data-table` (`features/platform/design/data-table`) lists 64 fixed example purchase bills that its `server/queries.ts` sorts, filters and pages on the server, and is the harness of the component tests; the kitchen sink shows the data table on local state, while loading and without rows; `/platform/attachments` lists stored files through the kit against the API, and its hand-written table and pagination are deleted.

## Consequences

- Every list view has an address: links, bookmarks and Back restore it, and a saved view (`business-building-blocks-web-shared-kit-extensions`) can be stored as one. Bulk actions receive the selected row ids from the selection the kit keeps; a CSV export can send the same `listApiParameters`.
- Each change of page, sort or filter is one server render and one API call; returning to a page seen a moment ago fetches it again, and no browser cache can serve stale rows. A list that needs live updates or virtualised scrolling of thousands of rows needs a client-driven variant and its own ADR.
- Each page renders its rows twice (table and cards); with the API's cap of 200 rows per page the cost is small.
- `apps/web` never imports TanStack Table; replacing it touches `packages/ui/src/components/data-table/` only.
- **Earlier decisions this changes.** ADR-0024: a feature may hold `lists/` with `<name>.list.ts` definitions and their `<name>.list.test.ts` tests (rules S4 and S5), and a module's `index.ts` exports nothing from `lists/` (rule I7). ADR-0025: its GET forms are specified here for lists: the filter form is `next/form` with a string `action`, and after hydration its `onSubmit` sends the canonical address through the list's transition. ADR-0009: the approvals gain TanStack Table's four transitive packages; TanStack Query stays approved and unused.
