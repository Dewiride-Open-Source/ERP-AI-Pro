# ADR-0059: Background jobs: a persistent queue, leases, IST schedules and the nightly account check

Status: accepted
Date: 2026-11-01

## Context

- **What existed.**
  - Background work ran as hosted services on a `PeriodicTimer` (`AttachmentsSweeper`, `IdempotencyCleanupService`): every API instance runs its own, nothing records a run or retries a failed one, and a tick that falls in a restart is lost.
  - Every deletion past a retention period ran in the migrator alone (`IRetentionSweep`, `RetentionRunner`), on `migrate` and on the nightly `retain` at 01:00 India time ([ADR-0043](0043-change-records-and-the-append-only-audit-schema.md), [ADR-0049](0049-the-production-host-a-deploy-account-keys-from-the-home-network-and-nightly-updates.md)).
  - The account check (`DirectoryAccountCheck.RunAsync(IDirectoryAccounts, CancellationToken)` of `Identity/Users`, [ADR-0047](0047-user-lifecycle-the-account-check-and-the-team-handover.md)) ran only when an administrator pressed "Check Microsoft accounts". ADR-0047 named its nightly run, as the system actor, as this item's first recurring job. `IDirectoryAccounts` is registered by `AddErpAuthentication`, which the API host alone composes, so the migrator and the test database host compose the users module without it.
  - A scope created outside a request already resolves the system: `HttpActorContext` answers `(ActorIds.System, false)` when there is no `HttpContext`, and `HttpRequestOrigin` falls back to `SystemRequestOrigin`, whose correlation id is the current activity's trace id ([persistence](../architecture/persistence.md), section "Actors").
  - The compose `api` service set no `stop_grace_period`.
- **Facts that shaped the design** (official sources, read 2026-11-01).
  - Hosting (learn.microsoft.com, "Background tasks with hosted services in ASP.NET Core", ".NET Generic Host in ASP.NET Core", ".NET Generic Host"): `HostOptions.ShutdownTimeout` defaults to 30 seconds and bounds the whole stop, after which the remaining services "stop even if they're still processing"; the token a hosted service's `StopAsync` receives carries that timeout "to indicate that the shutdown process should no longer be graceful"; hosted services stop in the reverse order of their registration, and the host waits in `BackgroundService.StopAsync` for `ExecuteAsync` to complete; `ConsoleLifetime` handles SIGTERM, "sent by other apps, such as `docker stop`"; and "If the app shuts down unexpectedly (for example, the app's process fails), `StopAsync` might not be called."
  - Docker (docs.docker.com, the Compose file reference and `docker container stop`; github.com/docker/compose, `pkg/compose/create.go`): `stop_grace_period` is how long Compose waits after the stop signal before it sends SIGKILL, and the "Default value is 10 seconds"; `docker stop` without `--timeout` waits the container's own stop timeout, which Compose sets from `stop_grace_period` when it creates the container (`StopTimeout`), so the same period bounds `erp-ai-pro.service`'s `docker compose stop` and `heal.sh`'s `docker restart` ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)).
  - SQL Server (learn.microsoft.com, "Transaction locking and row versioning guide", "Optimized locking"): `READ_COMMITTED_SNAPSHOT` is on by default in Azure SQL Database and off in SQL Server. Without optimized locking, a `READ COMMITTED` update selects its rows "using a blocking scan where an update (`U`) lock is acquired on the data row as data values are read", and only one transaction can hold a `U` lock on a resource at a time. Azure SQL Database always runs optimized locking (SQL Server 2025 has it off by default), whose lock after qualification checks the predicate on the latest committed version of the row: "If the row has changed after the predicate was evaluated previously, the database engine reevaluates (requalifies) the predicate again before modifying the row." A statement with an `OUTPUT` clause or a variable assignment does not use lock after qualification. So a single-row `UPDATE` whose `WHERE` repeats the values a runner read changes the row for exactly one of two racing runners, on the owner's SQL Server and on Azure SQL alike.
  - Microsoft.Identity.Web (learn.microsoft.com, "Call custom APIs"): "Use `CreateAuthorizationHeaderForAppAsync` to obtain an app-only token for background or daemon scenarios", the call `GraphDirectoryAccounts` already makes.
  - crontab(5) of Ubuntu's `cron` package, Vixie cron 3.0pl1 (manpages.ubuntu.com, the page of Ubuntu 22.04, `cron` 3.0pl1-137ubuntu3): the fields are minute 0–59, hour 0–23, day of month 1–31, month 1–12 and day of week 0–7, where 0 or 7 is Sunday; "If both fields are restricted (i.e., don't start with *), the command will be run when either field matches the current time"; "this implementation only checks if the first character is a *", which is why `0 0 */2 * sun` runs on every Sunday that is an odd date, where POSIX would run it every Sunday and on every odd date. Ubuntu 26.04, the server's release, ships the same package (`cron` 3.0pl1-200ubuntu1, packages.ubuntu.com); the site's crontab(5) pages for 24.04 and 26.04 come from the `cronie` and `systemd-cron` packages, which word the restriction "do not contain the "*" character" and "aren't *".
  - Microsoft Entra's provisioning service (learn.microsoft.com, "Enable accidental deletions prevention in the Microsoft Entra provisioning service"): a deletion threshold, evaluated in each provisioning cycle, above which the service "requires an admin to explicitly allow the processing of the deletions"; "the same functionality also works for disables".
- **Owner decisions of 2026-11-01.** The Community edition; the nightly account check at 00:30 India time; finished runs kept 400 days; no deactivation threshold while the owner is the ERP's only user (section "Consequences").

## Decision

- **A building block with an HTTP-surface module, as for attachments** ([ADR-0022](0022-attachments-in-azure-blob-storage.md)). `BuildingBlocks.Jobs` owns `JobsDbContext` (schema `platform_jobs`, `ef.ts` key `jobs`), the queue, the runner, the scheduler, the cron parser, the administration service and the retention sweep, so any module uses jobs by referencing the building block. `Modules/Platform/Jobs` (schema `null`, routes `/api/platform/jobs`, flag `Erp.Modules.Platform.Jobs`, after `AuditModule` in `Modules.All`) is only its HTTP surface.
- **Three tables, none of them audited.** `JobRuns` (`JobRun : Entity<JobRunId>`), `JobRunEvents` (`JobRunEvent`, `IAppendOnly`) and `JobSchedules` (`JobSchedule`).
  - A run changes at every claim, every lease renewal (every 40 seconds while it runs), every outcome, re-run and cancel. As `IAuditable`, each change would add a change record to the books' trail of eight financial years, which nothing switches off and only the migrator deletes, and its claim and renewal must be `ExecuteUpdate` statements, which the bulk guard refuses on auditable types. So a run is neither auditable nor append-only, and no aggregate root, because `AggregateTests` checks the aggregate roots of every assembly.
  - Its history is its events: one is inserted per enqueue, attempt start, attempt outcome, re-run, cancel request and cancel, never updated, and deleted only with its run, by the cascade of its foreign key.
  - A schedule is neither, because its next occurrence moves every night; its definition lives in code and App Configuration, whose own revision history the store keeps.
  - The business changes a job makes are recorded by their own contexts, with the system as their actor.
- **A claim is a compare-and-set with a fencing lease token.**
  - A runner reads its candidates without tracking: `Status` pending or failed, `DueAt` reached and `JobName` among the jobs its process defines, by `DueAt` then `Id`, as many as it has free slots.
  - It claims each with one `ExecuteUpdateAsync` whose `WHERE` repeats what it read (`Id`, `Status` pending or failed, `DueAt` reached, the `AttemptCount` it saw). The statement sets `Running`, a new `LeaseToken` (`Guid.CreateVersion7()`), `LeaseHolder` (`<machine>:<pid>`), `LeaseExpiresAt` (now plus `LeaseDuration`), `StartedAt` and `AttemptCount + 1`, and the `Started` event is inserted in the same transaction, under the execution strategy. One row changed is a claim; none means another runner won.
  - Every later write of the attempt also requires its `LeaseToken` and `Status` `Running`, so a runner that lost its lease never overwrites another's outcome.
  - Claiming only the names its process defines leaves a run of a job another release defines to an instance that knows it.
  - Every state change is a statement of `Persistence/JobRunTransitions.cs`.
- **Leases and their recovery.** `LeaseDuration` (2 minutes) is renewed every third of it while the job runs. Each poll recovers the runs of the jobs its process defines whose lease expired, by the same compare-and-set on the `LeaseToken` it read: a `LeaseExpired` event and the failure `job.lease-expired`, retried or dead-lettered as below, or `Cancelled` when a cancel was requested. A renewal that finds another token in the row cancels the job's token and discards the outcome, logged at Warning. Lease times come from each process's `TimeProvider`, so the instances' clocks must agree within seconds; production runs one instance on one server.
- **One claim per attempt, at least once across crashes.** A process that dies after the job did its work and before its outcome was recorded leaves the run to recovery and a retry: exactly once would need the job's own transaction, its calls outside the database (Microsoft Graph) and the outcome in one transaction. So every job is idempotent and safe to run twice at once. The account check is: it takes the organisation lock and reads only active records, so a second run changes nothing.
- **Every run executes as the system actor.** The runner creates each run's scope from the root `IServiceScopeFactory` on its own loop, started with the host and outside any request, so `HttpActorContext` gives `ActorIds.System` and `HttpRequestOrigin` gives `SystemRequestOrigin`, whose correlation id is then the attempt's trace id: the runner starts an `Activity` per attempt, creating one itself when no listener samples it. Before it invokes the job, the runner reads `IActorContext.ActorId` in the run's scope, and any other actor fails the attempt permanently with `job.actor-not-system`, because the books' trail must never credit a person with the ERP's own changes. Who enqueued, re-ran or cancelled a run is recorded on its events, never as the actor of the job's changes.
- **Retries with doubling delays, then the dead letter.**
  - Each `JobDefinition` declares a `JobRetryPolicy(MaxAttempts, FirstDelay, MaxDelay)`, by default (5, 1 minute, 1 hour).
  - A retryable failure adds one to `FailureCount`. Below `MaxAttempts` the run is `Failed`, due again after `min(MaxDelay, FirstDelay × 2^(FailureCount − 1))`; otherwise it is `DeadLettered`.
  - Retried: the error kinds `Unavailable` and `Conflict`, an exception (`job.exception`), the attempt timeout (`job.timed-out`) and an expired lease. Dead-lettered at once: every other kind (`Validation`, `NotFound`, `Forbidden`, `Failure`, `TooLarge`, `UnsupportedType`), `job.payload-unreadable` and `job.actor-not-system`, because retrying a refusal that cannot change only delays the dead letter that tells an administrator to act, such as `directory.access-denied` while `User.Read.All` is not granted.
  - The delay has no jitter: runs are few and claimed one by one, so retries that fall due together overload nothing, and the page shows the exact time of the next attempt.
  - `AttemptCount` counts the attempts of the run's whole life and numbers them; `FailureCount` counts the failures since the enqueue or the last re-run and drives the policy.
- **The attempt timeout and cooperative cancellation.** `JobDefinition.AttemptTimeout` (10 minutes) cancels the job's token and fails the attempt with `job.timed-out`. A job's token is linked from four sources: the host's abort, the attempt timeout, a cancel request and a lost lease. .NET cannot stop code that ignores its token, so such a job keeps its slot and its lease until it returns, logged at Warning.
- **A graceful shutdown.**
  - `JobRunnerService : BackgroundService` starts claiming only after `IHostApplicationLifetime.ApplicationStarted`, so a host whose start fails (an invalid setting, the key ring's check) never claims a run.
  - On stop, the stopping token ends the loop, so nothing more is claimed, and the overridden `StopAsync` awaits the attempts in flight. When its token fires at the host's `ShutdownTimeout`, 30 seconds and left at that default, it cancels the runner's abort source, which fires every job's token, and gives the attempts 5 more seconds to record their outcome, on a token of their own.
  - An attempt cancelled by the shutdown is `Interrupted`: its run returns to `Pending`, due at once, with `FailureCount` unchanged, because a restart is no failure.
  - The compose `api` service gets `stop_grace_period: 45s`: the 30 seconds, the recording and a margin. Without it Docker kills the container after 10 seconds. A SIGKILL, an exit for lack of memory or a power cut leaves the run to lease recovery.
- **Administrators re-run and cancel runs.**
  - A re-run (`POST /api/platform/jobs/runs/{id}/rerun`) of a `failed`, `deadLettered` or `cancelled` run returns it in place to `Pending`, due at once, with `FailureCount` 0 and `FinishedAt`, the last error and the cancel columns cleared, inserts a `Rerun` event with the administrator's object id and wakes the local runner. A cancelled run is included so that a mistaken cancel can be undone. A `succeeded` run is refused with 409 `job.run-not-rerunnable`, because running it again could repeat its effects, and the run of a job this release does not define with 409 `job.not-defined`. The run keeps its id and its key, so an occurrence stays one run.
  - A cancel (`POST /api/platform/jobs/runs/{id}/cancel`) ends a `pending` or `failed` run at once, with an event. A `running` run gets `CancelRequestedAt`, `CancelRequestedBy` and a `CancelRequested` event; the holding runner sees the request at its next renewal, within about 40 seconds, cancels the job's token and records `Cancelled` when the job returns, or `Succeeded` when the job succeeded first. A running run whose lease expired is cancelled at once. A finished run answers 409 `job.run-finished`.
- **Idempotency keys.**
  - `(JobName, IdempotencyKey)` is unique. A key is 1 to 200 characters of `A-Z a-z 0-9 . _ : + -`, without spaces or `@`, so no email address fits, and is built from ids and dates, never names. The prefix `occurrence:` belongs to the scheduler, and `IJobQueue` refuses it.
  - An enqueue whose key exists returns that run's id, whatever its state, when the payload's JSON is identical, and throws `InvalidOperationException` when it differs: a programming error, as the HTTP idempotency fingerprint's mismatch is. A key deduplicates for as long as its run is kept.
  - The enqueue commits on its own, through `JobsDbContext`'s connection, outside the caller's unit of work. Until `business-building-blocks-transactional-outbox-and-integration-events` exists, a module enqueues with a key derived from its change, so a retried or rolled-back unit of work cannot run a job twice, and the job reads the current state when it runs.
- **Recurring schedules.**
  - A module configures one schedule per recurring job (`AddRecurringJob<TJob, TOptions>(definition, options => options.<Schedule>)`), which the scheduler reads through `IOptionsMonitor<TOptions>` at every poll on every instance, so a refreshed value applies without a restart.
  - `JobSchedules` keeps the state. On first sight the row is inserted with the next occurrence after now, and a duplicate-key insert means another instance won; so a newly scheduled job never runs a past occurrence. A changed expression moves the row, by compare-and-set, to the next occurrence under the new expression, without a run.
  - A due row (`NextOccurrenceAt` reached) takes the latest occurrence not after now. In one transaction the scheduler moves the row on, by compare-and-set on the `NextOccurrenceAt` and `Expression` it read (no row changed: another scheduler took the occurrence, and the transaction rolls back), and, unless the run that `LastRunId` names is unfinished (`pending`, `running` or `failed`, a skip it logs), inserts the run `occurrence:<the occurrence in India time as yyyy-MM-ddTHH:mm+05:30>` due at the occurrence with its `Enqueued` event, whose actor is the system, and sets `LastRunId`. The row's lock serialises the schedulers, and the unique key is the last guard.
  - Of the occurrences missed while the API was down, only the latest runs, at the first poll after it is back. The check, like any job that brings state up to date, needs only today's state, and seven queued nightly checks would repeat one piece of work; running none would leave a night unchecked whenever a deployment or the 03:00 update restart spans 00:30. The latest missed occurrence is at most one period old.
  - An occurrence is skipped while the schedule's previous run is unfinished, so a stuck or retrying run never piles up. An administrator's re-run can still overlap one, which every job allows.
  - An invalid expression stops only its own job: it is logged at Error once per distinct value, the job is not scheduled until the value is fixed, and the jobs page shows the reason. The schedule's options get no `ValidateOnStart`, because nothing alerts anyone ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)): a start refused at the 03:00 restart over a typo would keep the whole ERP down until someone looked, while the check can still be run by hand.
- **The cron grammar and its meaning.** An in-house parser, `CronSchedule`, internal to the building block.
  - Five fields separated by spaces, at most 200 characters: minute 0–59, hour 0–23, day of month 1–31, month 1–12 and day of week 0–7, where 0 and 7 are Sunday. A field is `*`, or a list of items, each a number, a range `n-m`, a range with a step `n-m/s`, or `*/s`; numbers have one or two ASCII digits. There are no names, no `n/s`, no `?`, `L`, `W` or `#`, and no seconds field.
  - Times are India Standard Time, the fixed offset +05:30 of `Kernel.Time.IndianStandardTime`.
  - The day fields follow Ubuntu's crontab(5): a day field is restricted unless its text starts with `*`; when both are restricted a day matches when either matches, and otherwise when both do, an unrestricted field matching every day. So `*/2` filters and still counts as unrestricted: `0 0 */2 * 1` runs on the odd-numbered Mondays, while `0 0 1-31/2 * 1` runs on every odd day and every Monday.
  - An expression whose day of month exists in none of the months it names (`0 0 30 2 *`) never runs and is refused. Every refusal is `job.schedule-invalid`, with a message the jobs page shows.
- **The runner is composed by the API alone.**
  - `ErpHostComposition.AddErpPlatform` calls `AddErpJobs()` for every host, after `AddErpAttachments()`: the context (readiness `database:platform_jobs`), `JobCatalog`, `IJobQueue`, `IJobAdministration`, `JobSignal`, `JobsOptions` (validated on start, which the migrator's retention needs) and the retention sweep.
  - Only the API's `Program.cs` calls `AddErpJobRunner()`: `JobRunnerOptions` (validated on start), `JobRunner`, `JobScheduler`, `JobRunnerInstance`, `JobsMetrics`, the activity source and the hosted `JobRunnerService`. `LayerTests.JobRunner_IsComposedByTheApiHostAlone` pins it.
  - `ErpApiFactory` removes the hosted `JobRunnerService` unless a test calls `WithJobRunner()`, and keeps the engine's singletons for a test to drive. Every factory host of a test process shares one test database, so a loop in each would claim other tests' runs and fire the nightly check at 00:30 India time; and the end-to-end API host runs none, so no Playwright run fires the check while the account-check specs take turns.
- **Jobs are created per run**, with `ActivatorUtilities.CreateFactory` in the run's scope, and are never registered as services. So `DirectoryAccountCheckJob(DirectoryAccountCheck check, IDirectoryAccounts directory, ILogger<DirectoryAccountCheckJob> logger)` takes the directory that only the API composes, and the migrator and the test database host still compose the module and pass `ValidateOnBuild`. `JobTests.Jobs_CanEveryOneBeActivatedInTheApiHost` resolves every job's constructor in a scope of the API host.
- **Payloads and error text.**
  - A payload is serialised by `System.Text.Json` with the Web defaults, strict numbers and enums as camelCase names, and stored in a `json` column, at most 16 KiB of UTF-8 (`ArgumentException` above that). It holds identifiers only, and the job reads the data when it runs: never a secret, a token, a credential or a connection string, nor personal data (names, emails, phone numbers, PAN, Aadhaar, bank details, salary). The API never returns it, the page never shows it, and no log or span carries it. A run whose payload does not deserialise fails permanently with `job.payload-unreadable`.
  - A failed `Result` stores its `Error.Code` (at most 128 ASCII characters, else `job.failed`) and its `Error.Message` cut to 512 characters, a message the code writes for an administrator that names no person, value or secret.
  - An exception stores `job.exception` and the exception's type name alone, never its message or stack trace, which can quote values (SQL Server's messages, [ADR-0054](0054-failed-sql-spans-rely-on-the-sqlclient-instrumentation.md)) or addresses that carry tokens; the exception itself goes only to the log, as `GlobalExceptionHandler` logs a request's. No answer of the API echoes a payload or an exception's text.
- **Retention in the migrator's retention step.** `JobRunRetentionSweep : IRetentionSweep`, which `migrate` runs after the seeders and `retain` runs alone, deletes the runs that `Succeeded`, were `DeadLettered` or were `Cancelled` and whose `FinishedAt` is older than `Erp:Platform:Jobs:FinishedRunRetention`, oldest first, in batches of 1,000 by the filtered `FinishedAt` index, as `AuditRetentionSweep` deletes; their events go by the cascade. It also deletes the `JobSchedules` rows of jobs this release does not schedule. Pending, running and failed runs are never deleted. One place and one timer serve every deletion past a retention period; this is a choice of placement, not of rights, because the API's database user could delete in `platform_jobs`. A failed sweep is logged at Error and `retain` exits 1. The API has no purge loop and no job that purges runs.
- **The test aids live in the testing library**, `Tests/Shared/Dewiride.Erp.Testing/Jobs`, because test code never ships in a product assembly (`LayerTests.ProductAssemblies_NeverReferenceTheTestingLibrary`) and the library already sees the internals it needs. `InProcessJobQueue` (`ErpApiFactory.WithInProcessJobQueue()`) is an `IJobQueue` that validates as the real one, records and deduplicates each enqueue and runs nothing until `RunAllAsync`, which runs each recorded run once through the building block's `JobInvoker`, in its own scope, as the system. `JobRunnerDriver` drives the real engine of a factory host one run at a time, by its id, because every host of the process shares the test database. `JobRunSeeder` and `JobRunSeed` insert a run in a chosen state with consistent events. Module unit tests keep hand-rolled recording fakes, as they do for `IAttachmentService`.
- **Observability.** `[LoggerMessage]` records inside an attempt's scope (`JobRunId`, `JobName`, `Attempt`, and `CorrelationId`, the attempt's trace id), never with the payload, the idempotency key or an actor id; the meter `Dewiride.Erp.Jobs` (`erp.jobs.*`) and the activity source `Dewiride.Erp.Jobs` (one span `job <name>` per attempt, parent of the handler and SQL spans), both under the `Dewiride.Erp.*` wildcard ([observability](../guides/observability.md), section "Background jobs"). Readiness gains `database:platform_jobs` and nothing else.
- **The HTTP surface.** Five routes under `/api/platform/jobs` and three permissions, `platform.jobs.runs.read`, `platform.jobs.runs.rerun` and `platform.jobs.runs.cancel` (`JobsPermissions`), held by Administrator alone, and the pages `/platform/jobs` and `/platform/jobs/runs/[runId]` ([routing register](../routing.md)). The module flag gates the surface only: the runner, the scheduler and the nightly check run while it is off.
- **The first recurring job.** `identity.users.directory-account-check` (`People/Hosting/DirectoryAccountCheckJob` of `Identity/Users`, in the `Hosting` layer, which may use Application, `BuildingBlocks.*` and `Microsoft.Extensions.*`) runs `DirectoryAccountCheck.RunAsync` with the directory and logs counts only. `Erp:Identity:Users:AccountCheckSchedule` (`AccountCheckOptions`, bound without validation) schedules it, seeded `30 0 * * *`. Its retry policy is (6, 5 minutes, 1 hour), so a night's attempts start at 00:30, 00:35, 00:45, 01:05, 01:45 and 02:45, and a run that fails them all is dead-lettered before the 03:00 update restart; its `AttemptTimeout` is 10 minutes. `directory.unavailable` (the directory unreachable, or an answer without one enabled account) and the organisation lock's `concurrency.conflict` are retried; `directory.access-denied` dead-letters at once.
- **Throughput.** `MaxConcurrentRuns` 2 and `PollInterval` 30 seconds. A singleton `JobSignal` (a `TaskCompletionSource` created with `RunContinuationsAsynchronously`) wakes the local loop after an enqueue, a re-run, an enqueued occurrence or a freed slot. Every wait is `Task.Delay(…, TimeProvider, …)`, so `FakeTimeProvider` drives the waits in tests.

## Options rejected

- **Hangfire or Quartz.NET.** Third-party packages the owner would have to approve, each with a schema and a dashboard of its own outside the ERP's sign-in, permissions, flags and trail.
- **Azure Functions, WebJobs or Container Apps jobs.** Azure serves the ERP App Configuration, Key Vault, Entra ID, Blob Storage and Azure SQL alone, and the check needs the API's sign-in services.
- **A systemd timer, as for `retain`.** The check needs the sign-in certificate and the Graph client, which the migrator must not hold ([ADR-0050](0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md)), and a timer that called the API would need an anonymous or token-bearing internal route.
- **A `PeriodicTimer` without persistence, as `AttachmentsSweeper` is.** No record of a run, no retry, a run per instance, and an occurrence that falls in a restart is lost.
- **A module that owns the tables.** Other modules could use it only by referencing a module's implementation.
- **Auditable runs**: noise in the legal trail, a record for every lease renewal, and claims the bulk guard refuses. **One table without events**: who re-ran or cancelled a run would be lost. **An attempts table with "last re-run by" columns**: a history that overwrites itself.
- **Row-version concurrency through tracked entities** (driven by exceptions, two round trips, a read again before every renewal), **`sp_getapplock` per run** (a lock owned by a session or a transaction for the whole attempt, which pins a connection or an open transaction for minutes) and **`UPDATE TOP(n) … WITH (UPDLOCK, READPAST) OUTPUT inserted.*`** (raw SQL naming columns outside the EF Core model, and claims in batches that a few runs a night do not need).
- **Running a job as the administrator who asked**: ADR-0047 already chose the system for the nightly run. **An actor set per scope**: dependency injection cannot replace one registration per scope.
- **A new run for each re-run**: chains of keys, and two rows for one piece of work; Hangfire and Sidekiq also requeue in place. **Refusing to cancel a running run**: a stuck job could then be stopped only by restarting the API, while the renewal that sees the request runs anyway.
- **Catching up every missed occurrence, catching up none, and refusing to start over an invalid schedule** (the reasons under "Recurring schedules"). **Schedules edited on the jobs page**: a schedule is a setting, kept with its history in App Configuration.
- **NCrontab or Cronos**, packages the owner would have to approve; **month and day names**, because implementations disagree on lists and ranges of names, and numbers give each value one spelling; **a seconds field**; **the `?`, `L`, `W` and `#` extensions**; **`TimeZoneInfo`**, because India Standard Time is a fixed offset.
- **The runner in every host, trusting that the migrator never starts its host**: the migrator would compose and validate the runner's settings and dependencies for nothing. **A production setting that switches the runner off**: only tests would use it.
- **Service location through the job's context**, **a "directory unavailable" stand-in in every host** (stub logic) and **registering each job in the API host** (hosts hold no logic).
- **A health check of the runner**: it would tell nobody anything ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)), and `Degraded` restarts no container.
- **A feature or a permission of its own for schedules**, and **"Run now" for a scheduled job**: outside the item's scope.

## Consequences

- **The nightly check runs at 00:30 India time** (owner decision of 2026-11-01), so a leaver's access ends the same night, before the 01:00 `retain`, the 02:00 backup and the 03:00 update restart.
- **Finished runs are kept 400 days** (owner decision of 2026-11-01), as long as the server's journal keeps the same runs' log lines ([ADR-0058](0058-records-kept-a-year-inside-india.md)), so each run on the page can be traced in the journal by its trace id. The history also names the administrators who re-ran or cancelled a run. A deleted run frees its idempotency key, so an enqueue that reuses a key after that period runs again.
- **No deactivation threshold** (owner decision of 2026-11-01). The nightly run keeps the account check's own guard, "an answer without one enabled account changes nothing", and gets no other:
  - While the owner is the ERP's only user, the check can never deactivate them: the answer either lists their account as enabled or holds no enabled account at all.
  - With more people, a wrong answer of the directory about one administrator could deactivate them; when they are the only administrator, nobody in the ERP can reactivate them. Recovery then needs a database edit, or someone who manages Microsoft Entra giving `Erp.Admin` to an account without a record, whose first sign-in starts an active administrator ([threat model](../security/auth-threat-model.md), residual risk 11).
  - Microsoft Entra's provisioning service guards its own disables and deletes with an "accidental deletions prevention" threshold, above which an administrator must allow them (learn.microsoft.com/entra/identity/app-provisioning/accidental-deletions).
  - The owner chose not to add one while they are the ERP's only user.
- **At least once.** A crash after a job's work and before its outcome is recorded runs the job again, so every job must be idempotent and safe to run twice at once ([background jobs](../architecture/background-jobs.md), section "Rules for every job").
- **Nobody is told when a job fails** ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)). A dead-lettered run, and an invalid schedule, which silently stops its job, show only on the jobs page and in the server's journal.
- **The shutdown depends on `stop_grace_period`.** `erp-ai-pro.service`'s `docker compose stop` (within its `TimeoutStopSec` of 3 minutes), a deployment's rollout and `heal.sh`'s restart wait up to 45 seconds for the api to stop, instead of 10, and `heal.sh` holds the deployment lock meanwhile. A kill, an exit for lack of memory or a power cut falls back to lease recovery: the run is recovered once its lease expires, up to 2 minutes later, and is retried after its delay, counted as a failure.
- **Application tokens outside a request are proven against `TestTokenEndpoint` alone.** The first production night proves them, with the seeded schedule and the server's clock, on the jobs page: the item's last acceptance criterion.
- **Leases trust each process's clock.** Two instances with clocks apart, or a rolling deployment whose releases schedule a job differently, could recover leases early or move a schedule row back and forth.
- **The day rule surprises people.** `0 0 13 * 5` runs on every 13th and every Friday, and `0 0 */2 * 1` only on odd-numbered Mondays. The architecture document gives examples, and the parser's tests pin them.
- **No browser test sees a run execute**, because the end-to-end API host runs no runner; the integration tests prove that path.
- **Cancelling a running job is cooperative**: it takes effect within about 40 seconds, and only when the job honours its token.
- **Earlier decisions this changes.**
  - [ADR-0043](0043-change-records-and-the-append-only-audit-schema.md): the migrator's retention step runs a second sweep and is the one place for every deletion past a retention period, not only for what the API's database user may not delete.
  - [ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md): an api that freezes is killed 45 seconds after the heal service asks it to stop, instead of 10.
