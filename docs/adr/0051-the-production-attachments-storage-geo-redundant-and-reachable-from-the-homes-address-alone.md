# ADR-0051: The production attachments storage: geo-redundant, reachable from the home's address alone

Status: accepted
Date: 2026-10-19

## Context

- **What existed.**
  - Attachments live in Azure Blob Storage, one Entra-only `StorageV2` account per environment made by `scripts/azure/bicep/modules/storage-account.bicep`: Shared Key off, public network access open with `defaultAction: Allow`, blob and container soft delete, versioning and the change feed off, one private container `attachments` and a `CanNotDelete` lock. The development account `sterpaiprodev` is `Standard_LRS` with 7 days of soft delete. The production account, its redundancy, its retention and the runtime service principal's role on its container were left to this decision, and a production API cannot start without `Erp:Platform:Attachments:BlobServiceUri` and the `Erp:Platform:Attachments:EncryptionKey` reference under `production` (ADR-0022).
  - The API encrypts every file before it leaves the process, so an account holds only ciphertext, and the key-encryption key lives in Key Vault (ADR-0022).
  - The production database admits only the home's public IPv4 address, through its one firewall rule `home`, which `database.sh --allow-current-address` or `--allow-address <IPv4>` moved; the owner moves it by hand when the address changes (owner decision of 2026-10-18), and its backups are geo-redundant to South India (ADR-0050).
  - The api container signs in as the runtime service principal with its certificate from `kv-erp-ai-pro-ops`, and that identity holds Key Vault Secrets User on `kv-erp-ai-pro-prod` (ADR-0050).
  - The server reaches the internet through the home connection, whose public IPv4 address the provider changes from time to time (ADR-0048), and holds a global IPv6 address that no published port listens on (ADR-0049).
  - `/healthz/ready` answers one word, `Healthy` or `Degraded`, or a 503 problem that names no check; `storage:attachments` only degrades it, the `database:*` checks fail it, and the failing check is named in the api's log (`docs/routing.md`, `docs/guides/observability.md`).
- **Owner decisions (2026-10-19).**
  - Geo-redundant storage, a second copy in South India, as recommended.
  - 90 days of blob and container soft delete, as recommended.
  - The account reachable only from the home's public address, not from every address as recommended; the command that moves the database's rule moves the storage account's rule with it.
  - The Azure changes behind a dry run, which listed exactly the approved set: the account with its container, soft delete and lock, Storage Blob Data Contributor on the container for the runtime service principal alone, the production encryption key, the two settings under `production`, one test upload read back as the runtime identity, and the rule for the home's address.
- **What the services document.**
  - Geo-redundant storage keeps three synchronous copies in the primary region and copies them asynchronously to the paired region, Central India's being South India, where they are again kept three times. The secondary copy cannot be read or written until the account fails over, which the owner can start (planned or unplanned) and Microsoft starts only after an extended regional outage. The copy runs behind the primary, typically by less than 15 minutes with no guarantee, and an unplanned failover leaves the account locally redundant in the new region until geo-redundancy is turned on again, which copies the data again at a charge (Azure Storage, "Azure Storage redundancy", "Azure storage disaster recovery planning and failover", "Azure Storage failover FAQ").
  - The Microsoft retail price list for block blobs in Central India (read 2026-10-19): Hot data stored ₹1.9198 per GB-month locally redundant, ₹2.3997 zone-redundant, ₹3.8396 geo-redundant, ₹4.7995 geo-redundant with read access to the secondary and ₹5.786 geo-zone-redundant; write operations ₹5.2794 per 10,000 locally redundant and ₹10.5588 geo-redundant; geo-replication data transfer ₹8.2551 per GB copied to the secondary.
  - Blob soft delete keeps a deleted or overwritten blob for 1 to 365 days and container soft delete a deleted container with its blobs; soft-deleted data is billed at the rate of live data (Azure Storage, "Soft delete for blobs", "Soft delete for containers").
  - Network rules take effect only when the default action is `Deny`. An IP rule (`ipRules`) admits a public IPv4 address or range; private ranges and `/31` and `/32` prefixes are refused, and IP rules cannot admit clients in the account's own region, which reach it from private Azure addresses and need a virtual network rule. Requests from trusted Azure services pass whatever the other rules say unless `bypass` is `None`. The rules guard the data plane only; account management through Azure Resource Manager stays reachable from anywhere ("Azure Storage firewall rules and network access control", "Guidelines and limitations for the Azure Storage firewall").
  - IPv6 addresses go into a list of their own, `networkAcls.ipv6Rules`, and an account publishes IPv6 endpoints, URIs of their own, only when `dualStackEndpointPreference.publishIpv6Endpoint` is set (Storage resource provider; the Azure CLI's `--ipv6-address` and `--publish-ipv6-endpoint` are previews, and the firewall's limitations page still speaks of IPv4 alone). `sterpaiproprod` has an empty IPv6 list and publishes no IPv6 endpoint, and its standard blob endpoint had no IPv6 address on 2026-10-19.
  - An association with a network security perimeter changes who reaches a storage account while its public network access stays `Enabled`: in the default Transition mode the perimeter's inbound rules apply besides the account's own, in Enforced mode instead of them ("Transition to a network security perimeter in Azure", "Network security perimeter for Azure Storage").
  - A private endpoint connection admits traffic once approved; a pending request admits nothing, and a rejected one stays listed (`az storage account private-endpoint-connection approve|reject|delete`).
  - The account's `dataCollaborationPolicyProperties` (`allowStorageDataShares`, `allowCrossTenantDataSharing`) decide whether data shares, a way to grant reading outside role assignments, may be made on it, and `allowSharedKeyAccessForServices` sets Shared Key per service (Storage resource provider); both are unset on both accounts.
  - A `CanNotDelete` lock lets authorized users modify a resource but not delete it (Azure Resource Manager, "Lock your resources"), and Storage Blob Data Contributor is the least privileged built-in role that restores a soft-deleted container ("Soft delete for containers").

## Decision

- **The account.** `provision.sh` deploys the production account `sterpaiproprod` (`ERP_AZURE_STORAGE_PROD_NAME`, which must differ from `ERP_AZURE_STORAGE_DEV_NAME`; a new name is checked with `az storage account check-name` before the what-if) from the same `storage-account.bicep` as the development account, in the resource group's region, Central India: `Standard_GRS` (`productionStorageAccount` in `main.bicep`), Hot, Shared Key off, a private container `attachments`, blob and container soft delete of 90 days (`productionStorageDeleteRetentionDays`), versioning and the change feed off, and the `CanNotDelete` lock `do-not-delete`. Both copies stay in India.
- **Its network.** The public endpoint stays on, because the server has no virtual network, behind `networkAcls` with `defaultAction: Deny`, `bypass: None`, one IP rule, the home's public IPv4 address, and empty IPv6, virtual network and resource instance rule lists (`restrictToAllowedAddresses` and `allowedAddresses` of `storage-account.bicep`; the development account keeps `defaultAction: Allow` with the trusted-service bypass, because developers work from changing addresses). `provision.sh` reads the address the database's rule `home` admits and passes it to the template as `productionStorageHomeAddress`, so a deployment keeps the account's rule equal to the database's. While that rule admits no single address (no server yet, no rule, or a range), a deployment keeps the account's own single public address, or none when it has none, and before the what-if `provision.sh` stops while the rule admits an address that is not public, or while it admits none and the account admits more than one public address (naming the rules to remove by hand), so a deployment never strips the account's address. The API reaches the account through its standard IPv4 endpoint, which `BlobServiceUri` names; no IPv6 endpoint is published.
- **Who reads it.** `provision.sh` grants the runtime service principal Storage Blob Data Contributor on the production `attachments` container, the only role on the account and in it: no person, group or the migrator holds a data role there, and nobody holds a Storage data role above it. Shared Key stays off for every service and data sharing stays off on both accounts, which only `verify.sh` guards: the template sets neither, and a `PATCH` of the account turns either off again (`docs/operations/azure-bootstrap.md` section 8).
- **The key and the settings.** `Erp--Platform--Attachments--EncryptionKey` exists in `kv-erp-ai-pro-prod` with a value of its own (id prefix `prod`), made by the block of `docs/operations/runbooks/secrets.md` section 5f with `user_secrets=false` and never displayed or copied anywhere else. `provision.sh` writes `Erp:Platform:Attachments:BlobServiceUri` under `production` (`https://sterpaiproprod.blob.core.windows.net/`) as it does under `local-dev`, bumping a label's sentinel only when its value changed (the API builds its storage clients when it starts, so a new endpoint needs a restart), and the `Erp:Platform:Attachments:EncryptionKey` reference in `infra/appconfig/key-vault-references.json` lists no labels, so `seed.sh` writes it under both, each resolving in that label's vault.
- **The home's address, one command.** `scripts/azure/home-address.sh` keeps both rules that admit the home: the database's firewall rule `home` (`ensure_firewall_rule`, `lib/sql.sh`) and the production account's IP rule (`ensure_production_storage_home_address`, `lib/storage.sh`).
  - Run from a computer on the home network without a VPN, it learns the address Azure sees: from `sys.dm_exec_connections` when the database answers, from error 40615 when its firewall refuses, and from the rule `home` itself when the database refuses the sign-in of an operator who is not its Microsoft Entra admin, which happens only after the firewall admitted this computer. `--address <IPv4>` takes the address from the operator instead; a private, shared or reserved address is refused (`is_public_ipv4`, `lib/common.sh`).
  - Before it changes anything, it fails while the server holds another firewall rule or the account admits more than one address: public network access other than `Enabled`, a default action other than `Deny`, a bypass, a virtual network, resource instance or IPv6 rule, a second IP rule or one that is not a public address (each converged by `provision.sh`), an approved private endpoint connection (rejected with `az storage account private-endpoint-connection reject`), or a network security perimeter association (removed on the perimeter's page). A pending private endpoint connection, which admits nothing, is only reported.
  - It moves the database's rule as ADR-0050 describes, compared at both ends so that a range is narrowed, and sets every field of the account's `networkAcls` in one `PATCH` (`az rest`, api-version 2026-04-01): `Deny`, no bypass, that address as the only IP rule and empty IPv6, virtual network and resource instance rule lists, so neither the old and the new address together nor no address is ever admitted between two calls. A move of either rule is announced. `--dry-run` prints both changes.
  - `database.sh` keeps only the users, still refusing to run while another server rule exists; the modes `--allow-current-address` and `--allow-address` are gone.
- **The checks.** `verify.sh` reads the production account back like the development one, with its own redundancy and retention, and checks that its public endpoint stays on behind `Deny`, no bypass and no virtual network, resource instance or IPv6 rule, that it publishes no IPv6 endpoint, has no private endpoint connection that is not rejected and belongs to no network security perimeter, with exactly one IP rule equal to the address the database's rule `home` admits; that the runtime service principal holds Storage Blob Data Contributor on its container among exactly its roles; and that nobody else holds a role on the account or in it, nor a Storage data role above it, a role whose definition cannot be read counting as one. On both accounts it checks that Shared Key is off for every service and that no data share may be made. `verify.sh --labels` compares `BlobServiceUri` under both labels with the accounts' endpoints and reads the key reference back under both.
- **The proof.** On 2026-10-19 the runtime service principal, signed in with its own certificate in a throwaway Azure CLI profile on the operator's computer, uploaded a random 64 KiB file to the production container, read it back with the same SHA-256 and deleted it; the soft-deleted test blob expires after the 90 days. The update request that `home-address.sh` sends when the address moves was sent against Azure by its function, `ensure_production_storage_home_address`, run with its comparison bypassed and the address the account already admitted, and the rules read back unchanged.
- **Earlier decisions this changes.**
  - ADR-0022: public network access with `defaultAction: Allow` now holds for the development account only; the production account, its redundancy, its retention and the runtime service principal's role follow this record.
  - ADR-0050: the firewall rule `home` is kept by `home-address.sh`, together with the storage account's rule, instead of by `database.sh --allow-current-address` and `--allow-address`; the owner still moves it by hand.

## Options rejected

- **Locally redundant storage**, half the price. One region would hold every file while the database's backups sit in South India too, so a regional disaster could leave records whose attachments are lost.
- **Zone-redundant storage** (three zones in Central India) and **geo-zone-redundant storage** (₹5.786 per GB-month). The first survives a zone but not the region; the second pays half as much again for zones on top of the second region, which the outages this project plans for do not need.
- **Read access to the secondary region** (RA-GRS, ₹4.7995 per GB-month). The API has no use for a read-only copy, and a failover makes the secondary writable when it is needed.
- **Every address, as the development account allows**, recommended because every request needs a token of the runtime service principal and the files are ciphertext. The owner chose the home's address alone; the cost is a second rule to move, which the same command moves.
- **The trusted-service bypass.** No Azure service reads the account, and the bypass takes precedence over every other rule.
- **A private endpoint or a virtual network.** The server is on premises with no virtual network, and a site-to-site VPN costs more than the storage.
- **An automatic updater of the rules.** Declined for the database by the owner (2026-10-18); Azure reports the new address in error 40615, and one command moves both rules.
- **A confirmation before `home-address.sh` moves the rules.** The runbook runs `--dry-run` first, which names the address, every move is announced, and a move from the wrong computer is undone by running the script again from home; the scripts take no interactive input.
- **`az storage account network-rule add` and `remove`.** Two calls leave either both addresses or none admitted between them, and they change nothing else that may have been added; the one `PATCH` sets the whole rule set after the checks found nothing but the home's rule.
- **Moving the storage rule only through `provision.sh`.** A full deployment for an address change is slower, and between the database's move and the next deployment the files would stay unreachable.
- **Turning the IPv6 endpoint off in the template.** An IPv6 endpoint behind `Deny` with an empty IPv6 list admits nobody; the template keeps the list empty and `verify.sh` reports a published endpoint, instead of the template setting a preview property the account has never carried.
- **A data role for the operator on the production container**, as on the development one. No person needs to read production files, which are ciphertext without the key; a restore grants a temporary role (`docs/operations/azure-bootstrap.md` section 8).
- **Blob versioning or point-in-time restore.** Blobs are written once under a new name and never overwritten (ADR-0022), and soft delete covers deletion for 90 days.

## Consequences

- Storage costs ₹3.84 per GB-month, writes ₹10.56 per 10,000 and each GB written ₹8.26 once for its copy to South India; deleted files are billed at the same rate for the 90 days they stay recoverable.
- Only the address both rules name reaches the files, the server's API and the operator's computer at home alike. When the home's address changes, uploads and downloads answer 500 `server.error` and the api's log shows `storage:attachments` failing with 403 `AuthorizationFailure`, while the database refuses the same address with error 40615, so `/healthz/ready` answers 503; `home-address.sh` restores both (`docs/operations/runbooks/home-address.md`). Until it runs, the rules still admit the previous address, which the provider may already have given to another customer, who would still need a token of the runtime service principal and would read only ciphertext. From anywhere else, the operator included, the account answers 403.
- The firewall guards the files, not the account: Azure Resource Manager, and with it the account's settings, its locks and its role assignments, stays reachable from anywhere for whoever holds the rights.
- Restoring a deleted blob or container needs a data role, which nobody holds: the operator grants themselves one for the restore, from the home's address, and removes it afterwards with the lock lifted (`docs/operations/azure-bootstrap.md` section 8).
- The server reaches the account over IPv4 only, from the home's IPv4 address, though the home network has IPv6: the account takes no IPv6 rule and publishes no IPv6 endpoint.
- A private endpoint connection that someone else requests fails `verify.sh` while it is pending or approved, and stops `home-address.sh` once approved; rejecting it, an update the lock allows, ends both.
- In a regional outage the copy in South India serves once the account fails over, possibly missing the last minutes of writes; an unplanned failover leaves the account locally redundant there until geo-redundancy is turned on again, at a charge. The procedure, and whether to rehearse a planned failover, belong to `first-deployment-backups-and-restore-drill`, which also decides any Azure-side backup, since a backup service would need a trusted-service exception or a virtual network and reopens this record.
- Account names are global: changing `ERP_AZURE_STORAGE_PROD_NAME` after the account exists creates a new, empty account and points `BlobServiceUri [production]` at it, while the old one keeps its files and its lock.
- The round trip proves the runtime identity's role and the home's rule from the operator's computer; the API's own round trip on the server belongs to `first-deployment-go-live-checklist-and-production-smoke`.
