# ADR-0025: Forms: typed submissions, one schema, field-error mapping and the form composites

Status: accepted
Date: 2026-09-27

## Context

The `web-foundation-forms-and-validation-kit` sub-phase asks for form primitives (a field, a select and a combobox, `dd-MM-yyyy` date and date-range pickers, an INR amount input with lakh and crore grouping, GSTIN, PAN and IFSC inputs, the attachments drop zone) driven by Zod schemas shared between Server Functions and the browser, the `useActionState` submission pattern, the mapping of ProblemDetails onto form fields, and component tests. Facts that shape the decision (web paths relative to `frontend/apps/web/src/`):

- **Packages.** ADR-0009 approved `react-hook-form` and `zod`, and ADR-0007 left their introduction to the web foundation phase with an ADR of its own. `react-hook-form` 7.89.0 has no schema integration: its `resolver` option is a plain function type, and it exports the path helpers `get` and `set`; the documented adapter, `@hookform/resolvers` 5.9.1, is not approved and would bring `@standard-schema/utils` with it. `radix-ui` 1.6.7 exports no calendar, combobox or listbox (its `Select` is the WAI-ARIA select-only combobox). The `radix-nova` `combobox` item imports `@base-ui/react`, which ADR-0023 keeps out of the lockfile; `cmdk` 1.1.1, behind the `command` item, was last released on 2025-03-14, hard-codes `aria-expanded="true"` on its input and has an open issue (#413) about an `aria-activedescendant` that is missing at mount and stale after filtering. The `calendar` item installs `react-day-picker@latest`, 10.0.1, whose compiled output imports its runtime dependencies `date-fns` and `@date-fns/tz`; `date-picker` is not a registry item but a recipe (`calendar` inside `popover`), and `form` is an empty item. The registry `calendar.tsx` fails to compile once under `exactOptionalPropertyTypes` (TS2375: `Calendar` renders `<CalendarDayButton locale={locale}>` with a `locale` that may be `undefined`, while the prop is declared `locale?: Partial<Locale>`), and `catalogMode: strict` refuses the CLI's install of `react-day-picker@latest`.
- **Submitting.** The Next.js, React and shadcn examples post `FormData` through `<form action={serverFunction}>` so a form works before hydration. The schema then has to parse the FormData encoding (`"on"`, repeated keys, dotted names) while react-hook-form holds booleans, arrays and nested objects; React resets uncontrolled fields after every run of such an action, including a run that returned errors; and a submission made before hydration reaches the action as raw FormData without the browser-side `onSubmit` ever running (react-dom 19.3.0). react.dev requires a `useActionState` dispatch to run inside a transition and logs an error in development otherwise. Every ERP page is for signed-in people, and the composite controls (Radix select, popovers, the calendar) need JavaScript anyway.
- **Error keys.** ASP.NET Core validation names a nested member by its CLR path (`Customer.ShippingAddress.Street`, `OrderItems[0].Description`, Microsoft Learn "Validation in ASP.NET Core"), `ValidationStep` names DataAnnotations members in PascalCase, and the serializer's `DictionaryKeyPolicy` converts only the first character of a dictionary key, so a nested key reached the web app as `customer.ShippingAddress.Street` although `http-conventions.md` promised camelCase member names. The generated client maps a problem body only for statuses the OpenAPI document declares; a 409 or 422 that an endpoint does not declare with `ProducesProblem` arrives with its status only.
- **Idempotency** (ADR-0016). A create endpoint requires an `Idempotency-Key` UUID. A completed key replays the stored answer, 4xx answers included; the same key with another body answers 422 `idempotency.key-reused`; a key whose request is still running, or whose unit of work committed before a 5xx, answers 409 `idempotency.in-progress`; a completed key whose answer was too large to store answers 409 `idempotency.replay-unavailable`; any other 5xx or exception releases the key.
- **Indian identifiers.** The GST Council flyer "Registration under GST Law" and CBIC's "GST System Project: FAQs: Registration" (Q2.1) describe a 15-character GSTIN: two digits of State code, the 10-character PAN, a two-character entity code and a check character. No allow-listed source publishes the check-character algorithm; the stricter patterns for the 13th and 14th characters appear only on blogs and would refuse real registrations such as TDS deductors and UIN holders; the State codes form an effective-dated list, which belongs to `business-building-blocks-statutory-parameter-store-and-gst-datasets` (root `CLAUDE.md` §5). The Income Tax Department's ITR-3 AY 2026-27 JSON schema V1.1 on incometax.gov.in gives the PAN pattern `[A-Z]{5}[0-9]{4}[A-Z]` and the IFSC pattern `[A-Z]{4}[0][A-Z0-9]{6}`.
- **Formats.** `Intl.NumberFormat("en-IN")` groups in lakhs and crores but takes a number, exact only up to 2^53; `Intl.DateTimeFormat("en-IN")` writes `27/09/2026`, not `27-09-2026`; the API carries a `DateOnly` as `yyyy-MM-dd` and an amount as a `decimal(19,4)` value.
- **Component tests.** `@playwright/experimental-ct-react` stops at 1.62.1 and the Playwright 1.63 release notes end its updates; a DOM runner (Vitest with Testing Library on jsdom or happy-dom) needs seven to nine unapproved packages, adds a third test runner and renders neither Radix positioning, themes, real drag and drop nor ARIA snapshots; the kitchen-sink rule already requires a Playwright spec for every primitive (ADR-0023). `node --test` loads `.ts` but not `.tsx`, adds no extension to a relative ESM specifier and cannot resolve the web app's `@/` alias, which rules L1 and L2 of ADR-0024 make feature code use for `shared/`.
- **The content security policy.** The nonce policy of `proxy.ts` allows no `eval` outside development. Zod 4.6.5 probes `new Function` the first time it builds an object schema, to compile a faster parser, unless `jitless` is set in its global configuration (`globalThis.__zod_globalConfig`, `v4/core/core.js`); Firefox reports the refused probe as a console error. `instrumentation-client.ts` (stable since Next.js 15.3) runs in the browser before hydration and is bundled into every page.
- **react-hook-form 7.89.** When a field changes, react-hook-form re-validates it by its own name and keeps only an error found at that name, so a `Controller` whose value is an object loses errors reported on its members while the person types.

## Decision

- **Owner approvals (2026-09-27), appended to the ADR-0009 list.** `react-day-picker` 10.0.1 (MIT, "Copyright (c) 2014-2026 Giampaolo Bellavite and contributors"; maintainer `gpbl`, `github.com/gpbl/react-day-picker`; npm provenance attested; peer `react >=16.8.0`) is the calendar grid of the shadcn `calendar` primitive, which the design system takes from the registry, and `radix-ui` has no calendar. `date-fns` 4.4.0 (MIT, "Copyright (c) 2021 Sasha Koss and Lesha Koss", `pkgs/core/LICENSE.md`; organisation `date-fns`, maintainer `kossnocorp`) is its runtime dependency and a dependency the registry item names; `@date-fns/tz` 1.5.0 (MIT, "Copyright © 2024 Sasha Koss", same organisation) enters the lockfile only through `react-day-picker`. No Microsoft package offers either. All three had no advisory in the GitHub Advisory Database on 2026-09-27. They are pinned in the `catalog` of `pnpm-workspace.yaml`, `react-day-picker` and `date-fns` are dependencies of `@dewiride/erp-ui` only (no code outside `packages/ui` imports them; the kit's own date helpers are plain code over ISO strings, and nothing in the repository imports `date-fns` directly today), and both join the Dependabot `ui` group; `react-hook-form` 7.89.0 is pinned under its ADR-0009 approval as a dependency of `@dewiride/erp-web` and joins the `validation` group with `zod`. `@hookform/resolvers` and `cmdk` are not approved.
- **The combobox is built in-house** on Radix `Popover` and `PopoverAnchor`, following the WAI-ARIA APG editable combobox with a listbox popup and list autocomplete: DOM focus stays on the input (`role="combobox"`, `aria-autocomplete="list"`; `aria-expanded` is `true`, and `aria-controls` set, only while options are listed, and an empty or loading result shows its message and announces it through a live region instead; `aria-activedescendant` names the active option and is reset whenever the filter changes), options carry `role="option"` and `aria-selected`, disabled options are skipped, the popover is non-modal with its auto-focus on open and close prevented, and the value is chosen only from the list (leaving the input restores the chosen option's label). No `cmdk`.
- **GSTIN is checked for its shape only**: upper-cased, stripped of everything outside `[0-9A-Z]`, then `^[0-9]{2}[0-9A-Z]{13}$`. No check-character validation and no State-code list in the web app. PAN is `^[A-Z]{5}[0-9]{4}[A-Z]$` and IFSC `^[A-Z]{4}0[A-Z0-9]{6}$`, each citing the ITR-3 schema in a comment beside its schema in `shared/forms/schemas/indian-identifiers.ts`.
- **Mutation forms are not sent before the page is interactive, and they send typed values.** A mutation form has `noValidate`, `method="post"` and `onSubmit`, never an `action` prop and never `FormData`. Its submit button renders disabled on the server and until hydration (`ready` from `useSyncExternalStore` with a server snapshot of `false`), so pressing Enter before then sends nothing. On submit, react-hook-form validates, then `startTransition(() => dispatch({ values: form.getValues(), idempotencyKey }))` sends the raw input values, the same shape the schema parses in the browser, to a Server Function through `useActionState`; no reset follows, so values never travel back in an answer. GET forms (list filters, search) are a separate kind: `next/form` with a string `action` and URL search parameters.
- **One schema per form, isomorphic, in `<feature>/forms/<name>.schema.ts`** (rule S5 of ADR-0024): the `z.object` schema, `<Name>Values = z.input<…>`, `<Name> = z.output<…>`, the default values, the named limits, the `<name>FieldAliases` map (API key → form path) and the `<name>ProblemMessages` map (problem code → sentence) when the form needs them; no `server-only`, no value import from `@/shared/api`, no asynchronous refinement. Messages are plain English written for the person. Composite inputs keep canonical strings in form state: an amount as a decimal string (`"1234567.50"`, `""` when empty), a calendar date as `yyyy-MM-dd` (or the trimmed text a person typed that is not a real date, so the schema can refuse it), an identifier upper-cased; lakh and crore grouping and `dd-MM-yyyy` exist only inside the inputs.
- **The resolver is in-house.** `schemaResolver(schema)` (`shared/forms/schemas/schema-resolver.ts`) runs Zod's `safeParseAsync` and turns issues into react-hook-form's error tree with its exported `get` and `set`, keeping the first issue per field (`criteriaMode: "firstError"`), putting an issue about a list itself at `<list>.root` and a path-less issue at `root`; the issue path is built by `issuePath`, which the server-side mapping shares. `useActionForm` (`shared/forms/client/use-action-form.ts`) sets `mode: "onTouched"` and `shouldFocusError: true`, so a browser-side failure focuses the first invalid field; it never calls `watch()` (the `react-hooks/incompatible-library` rule warns on it), and components read values with `useWatch`.
- **One controller per leaf field.** A composite input bound to several values (a date range) gets one `useController` per value (`validity.from`, `validity.to`), and a rule reported on one value because of another names the other in `deps` (`validity.from` re-checks `validity.to`), so an error on a member survives while the person types; `DateRangeInput` accepts `toId` and `toRef` for that purpose.
- **The `FormState` contract** (`shared/forms/state/form-state.ts`, serialisable, the only thing a Server Function returns to a form): `{ status: "idle" }`, `{ status: "invalid"; fieldErrors: Readonly<Record<string, readonly string[]>>; formErrors: readonly string[] }`, `{ status: "failed"; message; code?; reference? }` and `{ status: "succeeded"; message? }`, all members `readonly`, built with `idleFormState`, `formInvalid`, `formFailed` (which leaves out an undefined `code` or `reference`) and `formSucceeded`. It never echoes values, so PAN, bank and salary values never travel back in an answer. `reference` is the problem's `traceId`, shown as "Reference: …" so a person can quote it to support.
- **The submission envelope.** A Server Function receives `{ values, idempotencyKey? }` and re-parses it with `parseSubmission(schema, submission, { idempotent })` (`shared/forms/schemas/parse-submission.ts`, asynchronous): `values` must be an object and, for an idempotent form, `idempotencyKey` a UUID (`z.uuid()`); a malformed envelope answers `failed` "The form could not be sent. Try again.", a schema failure answers `invalid` with the issues as field and form errors, and success yields `{ ok: true, data }` plus `idempotencyKey` for an idempotent form.
- **The Server Function shape** (`<feature>/server/actions.ts`, `"use server"`, async exports only): `export async function <verb><Thing>(previous: FormState, submission: unknown): Promise<FormState>`, whose first statement today is `parseSubmission`; the command is then mapped explicitly, in a non-exported synchronous function of the same file, to the generated client's request model, so no key the schema does not name can reach the API; the call goes through `callApi` with `Idempotency-Key: parsed.idempotencyKey` for a create; a caught error becomes `problemToFormState(error, { aliases, messages })`; a `redirect()` stays outside the `try`, and an edit that stays on the page calls `refresh()` from `next/cache` and returns `formSucceeded(…)`. Server Functions never receive files: a form that attaches one uploads it from the browser through `shared/api/upload.ts` (ADR-0022) and holds the returned attachment id. Every endpoint a form posts to declares its 409 and 422 answers with `ProducesProblem`, or their codes never reach the form.
- **What the authentication phase adds to every Server Function**: the session check as the first statement, before `parseSubmission` (`authentication-web-login-page-and-session-integration`, with the session-expired return path), joined by the permission check once permissions exist (`user-management-roles-and-permissions`), and the `X-XSRF-TOKEN` header on its API call and on the browser upload (`authentication-antiforgery-for-json-endpoints`). Until then the kit writes no stub for them, a 401 maps to "Your session has ended. Sign in again.", and every anonymous caller shares one idempotency key space.
- **The error-key grammar.** Every key of a validation problem's `errors` is a camelCase JSON member path: member names joined by `.`, a collection element as its zero-based index in brackets (`customer.shippingAddress.street`, `orderItems[0].description`), and `""` for a rule about the request as a whole. `ProblemDetailsCustomizer` rewrites every key of every `HttpValidationProblemDetails`, from the built-in validation filter and from `ResultExtensions.ToProblem` alike, converting each member name with `JsonNamingPolicy.CamelCase` and keeping indices; keys that meet after conversion keep every message. The web app's `apiKeyToFormPath(key, aliases)` (`shared/forms/errors/field-paths.ts`) turns a key into a react-hook-form path (`orderItems[0].description` → `orderItems.0.description`), converting a member name the API left in PascalCase with the exact .NET rule (`camelCaseMemberName`), then applies the form's aliases (the longest alias whose key, written in any spelling of the grammar, is a prefix at a segment boundary; an alias to `""` makes the message a form error); `""`, a malformed key and a path through a name react-hook-form reserves (`root`, `type`, `types`, `ref`, `message`, `form`) become form errors. A form names its fields after the API request's JSON members so most keys need no alias.
- **Problems become form states** through `problemToFormState(error, { aliases, messages })` (`shared/forms/errors/problem-to-form-state.ts`). Its own messages are written for the person; it shows a problem's `detail` only where the table says so, meant for a module's own codes, whose details are written for the person, and never for a 400 that means the web app built the request wrongly (its detail names request types and parameters) or for an idempotency code. A form maps any other platform code it can meet, such as `concurrency.conflict`, in its `messages`:

  | Input | Result |
  |---|---|
  | `TypeError` (the API did not answer; `callApi` lets it through) or an `ApiError` with status 0 | `failed` "The ERP service did not respond. Try again." |
  | 5xx, 504 `request.timeout` included | `failed` "The server could not finish this. Try again." with the reference and no code |
  | 400 with `fields` | `invalid`: each key mapped as above, duplicate messages dropped |
  | a problem code the form maps in `messages` | `failed` with that sentence, the code and the reference |
  | 409 `idempotency.in-progress` | `failed` "Still being saved. Wait a moment, then check the list before trying again." |
  | 422 `idempotency.key-reused` | `failed` "The details changed since the last attempt. Send the form again." |
  | 409 `idempotency.replay-unavailable` | `failed` "This was already saved. Check the list before sending it again." |
  | 404 `feature.disabled` | `failed` "This part of the ERP is switched off." |
  | 400 without fields and without a code, or with `request.invalid`, `request.malformed`, `idempotency.key-missing`, `idempotency.key-invalid` or a `query.*` code | `failed` "The form could not be sent. Try again." (the web app built the request wrongly; the detail is for the server log) |
  | 400 without fields with another code | `failed` with the problem's `detail` |
  | 401, 403, 404, 429 | `failed` "Your session has ended. Sign in again.", "You do not have permission to do this.", "This record no longer exists.", "Too many requests. Wait a minute and try again." |
  | any other 4xx (a module's 409 or 422) | `failed` with the problem's `detail`, else "This could not be saved." |
  | anything else | rethrown, so `error.tsx` renders |

  Every `failed` from a 4xx keeps the problem's code, every `failed` built from a problem carries its `traceId` as the reference, and an `invalid` carries neither.
- **Showing server errors.** `useActionForm` applies an `invalid` answer with `setError(path, { type: "server", message })` per field and sets `root.server` for every `invalid` and `failed` answer; the error summary (`FormAlert`) renders while `root.server` is set (react-hook-form clears it on the next submit) and takes focus once rendered. For `invalid` it lists the form errors and every field error still standing, each linked to its field's id (`formFieldId(formId, path)`, from `useId`), so an error on a field that is not rendered is never lost; for `failed` its title is the message with the reference beneath. A field's own server error clears when the field revalidates.
- **The idempotency rule.** A form created with `idempotent: true` mints a key with `crypto.randomUUID()` at its first dispatch and sends the same key with every dispatch until an answer decides the attempt. `keepsIdempotencyKey(state)` (`shared/forms/state/idempotency-key.ts`) keeps it after a `failed` answer without a code (the API was unreachable, answered 5xx, or answered a 4xx without a code, where the safe side is to keep it) or with `idempotency.in-progress` or `idempotency.replay-unavailable` (the create already ran under the key, so a new key could create a second record); every other answer (`invalid`, `succeeded`, every other coded `failed`, `idempotency.key-reused` included) clears it, and the next dispatch mints a fresh one. `useActionState` runs dispatches one at a time, and the form ignores a submit while one is pending. Edit forms carry the entity's row version instead of a key: a stale one answers 409 `concurrency.conflict` (`EfUnitOfWork`), whose detail names entity types, so an edit form maps that code in its `messages`.
- **The form composites live in `@dewiride/erp-ui`** and stay presentational: they never import `zod`, `react-hook-form` or `apps/web` (rule L6), and they take and emit the canonical strings above. `components/forms/`: `FormField` (label, description, errors, the `*` for a required field hidden from assistive technology, `data-invalid` and `data-disabled`, and the control's `id`, `aria-invalid`, `aria-describedby` and `aria-required` handed to a render function; the label carries `<id>-label`, `formFieldLabelId`), `FormAlert` (the destructive `Alert`, `role="alert"`, `tabIndex={-1}`, a link per message with a field id that focuses the field, "Reference: …") and `SubmitButton` (disabled while not `ready` or `pending`, `aria-busy` with an `aria-hidden` spinner while pending, its label unchanged). `components/inputs/`: `AmountInput` (a leading "₹", `inputMode="decimal"`, at most 15 integer digits and `scale` decimals, the canonical value emitted on every keystroke, lakh and crore grouping when not focused) and `IdentifierInput` (monospace, upper-cases and strips everything outside `[0-9A-Z]` while typing and pasting, cut at `maxLength`, left alone while an input method composes). `components/pickers/`: `DateInput` and `DateRangeInput` over `DateTextInput` (typed `dd-MM-yyyy` with `-`, `/` or `.`, one- or two-digit day and month, eight digits or an ISO date; shown as `dd-MM-yyyy` when not focused) with a modal calendar popover in the APG date-picker dialog model (focus moves into the grid and returns to the button, days outside `min`/`max` disabled, month and year dropdowns, a range calendar with two months from `md` that commits only when both ends are chosen; the two text boxes of a range are never reordered, and the schema reports an end before the start). `components/combobox/`: `Combobox`. Their pure logic sits in `.ts` siblings (`replace-input-text`, `calendar-limits`, `combobox-options`) and in `src/lib/` (`indian-number`, `identifiers`, `calendar-date`, and `calendar-defaults`, the `en-IN` locale with weeks starting on Monday, which `apps/web` spreads into a standalone `Calendar` because it cannot import `react-day-picker` itself). The calendar primitive is `components/ui/calendar.tsx` from the registry with one registered patch (`CalendarDayButton`'s `locale?: Partial<Locale> | undefined`), written from `shadcn add calendar --view` because the CLI's install is refused by `catalogMode: strict`.
- **The kit in `apps/web`** is the concern folder `shared/forms/` with `state/`, `errors/`, `schemas/` (`schemaResolver`, `parseSubmission`, `gstinSchema`, `panSchema`, `ifscSchema` with `identifierLengths`, and the builders `requiredText`, `optionalInput`, `amountSchema`, `calendarDateSchema` and `dateRangeSchema`, which reports an end before the start on `to`) and `client/` (`useActionForm`, `form-feedback.ts`). Its modules import each other and `shared/api/problem-details.ts` by relative path with the `.ts` extension (`allowImportingTsExtensions`), which Node needs.
- **`instrumentation-client.ts` sets Zod's `jitless` switch** with `import { config } from "zod"; config({ jitless: true });` before hydration, so no form page reports a policy violation; `config` is imported by name because the `z` namespace would put all of Zod into the root bundle every page loads, and the named import reaches the one global configuration the form pages' copy of Zod reads. The file imports nothing from `features/` (rule I5 covers every file outside `app/`, `features/` and `shared/`).
- **Component tests.** A component test is a Playwright spec that drives one component or one scenario on a harness page of the production build, on every Playwright project, in light and dark (`forEachTheme`) where the rendering is theme-specific, with ARIA snapshots, the keyboard path, one validation failure and the console-error guard; the component's pure logic is covered by `node --test` beside it. No DOM runner and no experimental component-testing package. The harness pages are `/design/kitchen-sink`, whose Forms section shows every composite in every state, and `/design/form-kit`, the example form "Register a supplier (example)" (`features/platform/design/form-kit`), whose Server Function `registerSupplierExample` re-parses the submission and answers as its "Server answer" field chooses (accept, a field error, a validation problem with nested keys through aliases, a 409 with a module code, a 500, an unreachable API) by mapping a fixed `ApiError` or `TypeError` with `problemToFormState`, without calling the API or storing anything, while its drop zone uploads for real. Both pages ship in every environment, like the kitchen sink (ADR-0023). The unit-test runner `erp-unit-tests` starts `node --test` with `--import` of `packages/config/cli/resolve-source-alias.mjs`, a `module.registerHooks` resolve hook that maps `@/…` to `src/…` of the package under test (the path, then `.ts`, then `/index.ts`), so a feature schema that imports `@/shared/forms/**` is testable; the tests themselves import `./<name>.ts`.
- **Earlier decisions this changes.** ADR-0009: the approved list gains `react-day-picker`, `date-fns` and the transitive `@date-fns/tz`. ADR-0023: `combobox` is resolved in-house and stays uninstalled from the registry, `calendar` is installed with a register entry, `date-picker` is built as its recipe, and `form` is built from `field` and `react-hook-form`; the kitchen sink gains the Forms section. ADR-0007: "mutations are Server Functions that re-check the session and validate with Zod" takes the shape above (re-parse the envelope with the shared schema, map problems to a `FormState`), and the frontend rule "return `{ errors }` for `useActionState`" becomes "return a `FormState`". ADR-0024: `forms/` exists from this change (`platform/design/form-kit/forms/supplier-example.schema.ts`), and `instrumentation-client.ts` joins `proxy.ts`, `instrumentation.ts` and `instrumentation.node.ts` among the files outside `app/`, `features/` and `shared/`.

## Consequences

- Every mutation form is built the same way (`useActionForm`, `FormField`, one schema, one Server Function), and a validation rule is written once and checked in the browser and again on the server; an API answer lands on the field it concerns, including a nested one, or in the focused summary.
- A mutation form cannot be sent before its page has hydrated, and a person with JavaScript switched off cannot send one; the Save button says so by staying disabled. The `javaScriptEnabled: false` test of `form-kit.spec.ts` proves that pressing Enter then sends no Server Function request.
- A retry after an unknown outcome replays or completes the same create instead of creating a second record; a decided answer always starts the next attempt with a fresh key.
- The combobox, the date inputs and the amount and identifier inputs are ours to keep accessible: their ARIA and keyboard behaviour is proven by the kitchen-sink and form-kit specs on every project, and their pure logic by `node --test`. `react-day-picker` is a single-maintainer package; a calendar regression fails the calendar tests of both specs.
- `ProblemDetailsCustomizer` changes a nested validation key on the wire (`customer.ShippingAddress.Street` → `customer.shippingAddress.street`); no existing endpoint had a nested key, so `docs/openapi/erp.json` and the generated client do not change.
- Losing the `calendar.tsx` patch on a refresh fails `pnpm typecheck`. Removing `config({ jitless: true })` makes the form-kit spec fail on Firefox through the console-error guard; importing `z` there instead puts Zod's full library into the root bundle, which only a bundle review catches.
- The agreement document of `/design/form-kit` is a real attachment: it is stored encrypted and listed at `/platform/attachments` like any other, `form-kit.spec.ts` deletes the one it uploads, and a person who uploads one there and leaves keeps a stored file until it is deleted from that list.
- Statutory datasets stay out of the web app: GSTIN State codes, and any check character, arrive with `business-building-blocks-statutory-parameter-store-and-gst-datasets` and are enforced by the API.
- Revisit: server search in the combobox (`onInputValueChange`, `loading`) gets its first real caller with the first master-data picker; the authentication phase inserts the session, permission and antiforgery pieces above into every Server Function; `/design/form-kit` becomes signed-in only with the rest of the `(app)` shell.
