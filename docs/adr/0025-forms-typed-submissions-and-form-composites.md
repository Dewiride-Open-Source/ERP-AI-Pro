# ADR-0025: Forms: typed submissions, one schema, field-error mapping and the form composites

Status: accepted
Date: 2026-09-27

## Context

The `web-foundation-forms-and-validation-kit` sub-phase asks for form primitives (a field, a select and a combobox, `dd-MM-yyyy` date and date-range pickers, an INR amount input with lakh and crore grouping, GSTIN, PAN and IFSC inputs, the attachments drop zone) driven by Zod schemas shared between Server Functions and the browser, the `useActionState` submission pattern, the mapping of ProblemDetails onto form fields, and component tests. Facts that shape the decision (web paths relative to `frontend/apps/web/src/`):

- **Packages.** ADR-0009 approved `react-hook-form` and `zod`, and ADR-0007 left their introduction to the web foundation phase with an ADR of its own. `react-hook-form` 7.89.0 has no schema integration: its `resolver` option is a plain function type, and it exports the path helpers `get` and `set`; the documented adapter, `@hookform/resolvers` 5.9.1, is not approved and would bring `@standard-schema/utils` with it. `radix-ui` 1.6.7 exports no calendar, combobox or listbox (its `Select` is the WAI-ARIA select-only combobox). The `radix-nova` `combobox` item imports `@base-ui/react`, which ADR-0023 keeps out of the lockfile; `cmdk` 1.1.1, behind the `command` item, was last released on 2025-03-14, hard-codes `aria-expanded="true"` on its input and has an open issue (#413) about an `aria-activedescendant` that is missing at mount and stale after filtering. The `calendar` item installs `react-day-picker@latest`, 10.0.1, whose compiled output imports its runtime dependencies `date-fns` and `@date-fns/tz`; `date-picker` is not a registry item but a recipe (`calendar` inside `popover`), and `form` is an empty item. The registry `calendar.tsx` fails to compile once under `exactOptionalPropertyTypes` (TS2375: `Calendar` renders `<CalendarDayButton locale={locale}>` with a `locale` that may be `undefined`, while the prop is declared `locale?: Partial<Locale>`), and `catalogMode: strict` refuses the CLI's install of `react-day-picker@latest`. It also declares its `Root`, `Chevron`, `DayButton` and `WeekNumber` components inside `Calendar`'s render, so every re-render of a calendar hands `DayPicker` new component types and React remounts the whole grid, which drops the focus of a month or year dropdown (react.dev, "Preserving and Resetting State").
- **Submitting.** The Next.js, React and shadcn examples post `FormData` through `<form action={serverFunction}>` so a form works before hydration. The schema then has to parse the FormData encoding (`"on"`, repeated keys, dotted names) while react-hook-form holds booleans, arrays and nested objects; React resets uncontrolled fields after every run of such an action, including a run that returned errors; and a submission made before hydration reaches the action as raw FormData without the browser-side `onSubmit` ever running (react-dom 19.3.0). react.dev requires a `useActionState` dispatch to run inside a transition and logs an error in development otherwise. Every ERP page is for signed-in people, and the composite controls (Radix select, popovers, the calendar) need JavaScript anyway.
- **Error keys.** ASP.NET Core validation names a nested member by its CLR path (`Customer.ShippingAddress.Street`, `OrderItems[0].Description`, Microsoft Learn "Validation in ASP.NET Core"), `ValidationStep` names DataAnnotations members in PascalCase, and the serializer's `DictionaryKeyPolicy` converts only the first character of a dictionary key, so a nested key reached the web app as `customer.ShippingAddress.Street` although `http-conventions.md` promised camelCase member names. The generated client maps a problem body only for statuses the OpenAPI document declares; a 409 or 422 that an endpoint does not declare with `ProducesProblem` arrives with its status only.
- **Idempotency** (ADR-0016). A create endpoint requires an `Idempotency-Key` UUID. A completed key replays the stored answer, 4xx answers included; the same key with another body answers 422 `idempotency.key-reused`; a key whose request is still running, or whose unit of work committed before a 5xx, answers 409 `idempotency.in-progress`; a completed key whose answer was too large to store answers 409 `idempotency.replay-unavailable`; any other 5xx or exception releases the key.
- **Indian identifiers.** The GST Council flyer "Registration under GST Law" and CBIC's "GST System Project: FAQs: Registration" (Q2.1) describe a 15-character GSTIN: two digits of State code, the 10-character PAN, a two-character entity code and a check character. No allow-listed source publishes the check-character algorithm; the stricter patterns for the 13th and 14th characters appear only on blogs and would refuse real registrations such as TDS deductors and UIN holders; the State codes form an effective-dated list, which belongs to `business-building-blocks-statutory-parameter-store-and-gst-datasets` (root `CLAUDE.md` §5). The Income Tax Department's ITR-3 AY 2026-27 JSON schema V1.1 on incometax.gov.in gives the PAN pattern `[A-Z]{5}[0-9]{4}[A-Z]` and the IFSC pattern `[A-Z]{4}[0][A-Z0-9]{6}`.
- **Formats.** `Intl.NumberFormat("en-IN")` groups in lakhs and crores but takes a number, exact only up to 2^53; `Intl.DateTimeFormat("en-IN")` writes `27/09/2026`, not `27-09-2026`; the API carries a `DateOnly` as `yyyy-MM-dd` and an amount as a `decimal(19,4)` value.
- **Component tests.** `@playwright/experimental-ct-react` stops at 1.62.1 and the Playwright 1.63 release notes end its updates; a DOM runner (Vitest with Testing Library on jsdom or happy-dom) needs seven to nine unapproved packages, adds a third test runner and renders neither Radix positioning, themes, real drag and drop nor ARIA snapshots; the kitchen-sink rule already requires a Playwright spec for every primitive (ADR-0023). `node --test` loads `.ts` but not `.tsx`, adds no extension to a relative ESM specifier and cannot resolve the web app's `@/` alias, which rules L1 and L2 of ADR-0024 make feature code use for `shared/`.
- **The content security policy.** The nonce policy of `proxy.ts` allows no `eval` outside development. Zod 4.6.5 probes `new Function` the first time it builds an object schema, to compile a faster parser, unless `jitless` is set in its global configuration (`globalThis.__zod_globalConfig`, `v4/core/core.js`); Firefox reports the refused probe as a console error. `instrumentation-client.ts` (stable since Next.js 15.3) runs in the browser before hydration and is bundled into every page.
- **react-hook-form 7.89.** When a field changes, react-hook-form re-validates it by its own name and keeps only an error found at that name, so a `Controller` whose value is an object loses errors reported on its members while the person types.

## Decision

- **Owner approvals (2026-09-27), appended to the ADR-0009 list.** `react-day-picker` 10.0.1 (MIT, "Copyright (c) 2014-2026 Giampaolo Bellavite and contributors"; maintainer `gpbl`, `github.com/gpbl/react-day-picker`; npm provenance attested; peer `react >=16.8.0`) is the calendar grid of the shadcn `calendar` primitive, which the design system takes from the registry, and `radix-ui` has no calendar. `date-fns` 4.4.0 (MIT, "Copyright (c) 2021 Sasha Koss and Lesha Koss", `pkgs/core/LICENSE.md`; organisation `date-fns`, maintainer `kossnocorp`) is its runtime dependency and a dependency the registry item names, and `@date-fns/tz` 1.5.0 (MIT, "Copyright © 2024 Sasha Koss", same organisation) its other one. No Microsoft package offers any of them. All three had no advisory in the GitHub Advisory Database on 2026-09-27. `react-day-picker` is pinned in the `catalog` of `pnpm-workspace.yaml`, is a dependency of `@dewiride/erp-ui` only (no code outside `packages/ui` imports it) and joins the Dependabot `ui` group; `date-fns` and `@date-fns/tz` are declared nowhere and enter the lockfile only as dependencies of `react-day-picker`, because nothing in the repository imports either (the kit's own date helpers are plain code over ISO strings), and a direct declaration would pin a copy nothing loads while the calendar keeps the one `react-day-picker` resolved; `react-hook-form` 7.89.0 is pinned under its ADR-0009 approval as a dependency of `@dewiride/erp-web` and joins the `validation` group with `zod`. `@hookform/resolvers` and `cmdk` are not approved.
- **The combobox is built in-house** on Radix `Popover` and `PopoverAnchor`, following the WAI-ARIA APG editable combobox with a listbox popup and list autocomplete: DOM focus stays on the input (`role="combobox"`, `aria-autocomplete="list"`; `aria-expanded` is `true`, and `aria-controls` set, only while options are listed, and an empty or loading result shows its message and announces it through a live region instead; `aria-activedescendant` names the active option and is reset whenever the filter changes), options carry `role="option"` and `aria-selected`, disabled options are skipped, the popover is non-modal with its auto-focus on open and close prevented, and the value is chosen only from the list (leaving the input restores the chosen option's label, which the component remembers from any `options` list that contained it, so a server search whose results leave the chosen option out does not lose it). No `cmdk`.
- **GSTIN is checked for its shape only**: upper-cased, stripped of everything outside `[0-9A-Z]`, then `^[0-9]{2}[0-9A-Z]{13}$`. No check-character validation and no State-code list in the web app. PAN is `^[A-Z]{5}[0-9]{4}[A-Z]$` and IFSC `^[A-Z]{4}0[A-Z0-9]{6}$`, each citing the ITR-3 schema in a comment beside its schema in `shared/forms/schemas/indian-identifiers.ts`.
- **Mutation forms are not sent before the page is interactive, and they send typed values.** A mutation form has `noValidate`, `method="post"` and `onSubmit`, never an `action` prop and never `FormData`. Its submit button renders disabled on the server and until hydration (`ready` from `useSyncExternalStore` with a server snapshot of `false`), so pressing Enter before then sends nothing; while a submission is pending it keeps focus and refuses clicks and implicit submission with `aria-disabled` instead of the native `disabled`, which would drop focus to the page. On submit, react-hook-form validates, then `startTransition(() => dispatch({ values: form.getValues(), idempotencyKey }))` sends the raw input values, the same shape the schema parses in the browser, to a Server Function through `useActionState`; no reset follows, so values never travel back in an answer. GET forms (list filters, search) are a separate kind: `next/form` with a string `action` and URL search parameters.
- **One schema per form, isomorphic, in `<feature>/forms/<name>.schema.ts`** (rule S5 of ADR-0024): the `z.object` schema, `<Name>Values = z.input<…>`, `<Name> = z.output<…>`, the default values, the named limits, the `<name>FieldAliases` map (API key → form path) and the `<name>ProblemMessages` map (problem code → sentence) when the form needs them; no `server-only`, no value import from `@/shared/api`, no asynchronous refinement. Messages are plain English written for the person. Composite inputs keep canonical strings in form state: an amount as a decimal string (`"1234567.50"`, `""` when empty), a calendar date as `yyyy-MM-dd` (or the trimmed text a person typed that is not a real date, so the schema can refuse it), an identifier upper-cased; lakh and crore grouping and `dd-MM-yyyy` exist only inside the inputs.
- **The resolver is in-house.** `schemaResolver(schema)` (`shared/forms/schemas/schema-resolver.ts`) runs Zod's `safeParseAsync` and turns issues into react-hook-form's error tree with its exported `get` and `set`, keeping the first issue per field (`criteriaMode: "firstError"`), putting an issue about a list itself at `<list>.root` and a path-less issue at `root`; the issue path is built by `issuePath`, which the server-side mapping shares. `useActionForm` (`shared/forms/client/use-action-form.ts`) sets `mode: "onTouched"` and `shouldFocusError: true`, so a browser-side failure focuses the first invalid field; a path-less issue (a rule about the form as a whole, such as the form kit's check that characters 3 to 12 of the GSTIN are the PAN) is listed in the error summary under "Some details need attention." (`formErrorAlertContent`), and when the refused submit found no field error (`hasFieldErrors`) the summary takes focus, because no field would otherwise explain why nothing was sent; it never calls `watch()` (the `react-hooks/incompatible-library` rule warns on it), and components read values with `useWatch`.
- **One controller per leaf field.** A composite input bound to several values (a date range) gets one `useController` per value (`validity.from`, `validity.to`), and a rule reported on one value because of another names the other in `deps` (`validity.from` re-checks `validity.to`), so an error on a member survives while the person types; `DateRangeInput` accepts `toId` and `toRef` for that purpose, and `ends` so each text box is marked invalid and described by the error region only when its own value has a message (the form kit's `rangeEndState`). A date field counts as visited, and `onTouched` checks it, only when focus leaves its text boxes, its button and the calendar that button controls together (the form kit's `leavesGroup` follows the button's `aria-controls` into the portalled popover), so moving through the calendar or its month and year dropdowns never shows an error while the person is still choosing.
- **The `FormState` contract** (`shared/forms/state/form-state.ts`, serialisable, the only thing a Server Function returns to a form): `{ status: "idle" }`, `{ status: "invalid"; fieldErrors: Readonly<Record<string, readonly string[]>>; formErrors: readonly string[] }`, `{ status: "failed"; message; code?; reference? }` and `{ status: "succeeded"; message? }`, all members `readonly`, built with `idleFormState`, `formInvalid`, `formFailed` (which leaves out an undefined `code` or `reference`) and `formSucceeded`. It never echoes values, so PAN, bank and salary values never travel back in an answer. `reference` is the problem's `traceId`, shown as "Reference: …" so a person can quote it to support.
- **The submission envelope.** A Server Function receives `{ values, idempotencyKey? }` and re-parses it with `parseSubmission(schema, submission, { idempotent })` (`shared/forms/schemas/parse-submission.ts`, asynchronous): `values` must be an object and, for an idempotent form, `idempotencyKey` a UUID (`z.uuid()`); a malformed envelope answers `failed` "The form could not be sent. Try again.", a schema failure answers `invalid` with the issues as field and form errors, and success yields `{ ok: true, data }` plus `idempotencyKey` for an idempotent form.
- **The Server Function shape** (`<feature>/server/actions.ts`, `"use server"`, async exports only): `export async function <verb><Thing>(previous: FormState, submission: unknown): Promise<FormState>`, whose first statement today is `parseSubmission`; the command is then mapped explicitly, in a non-exported synchronous function of the same file, to the generated client's request model, so no key the schema does not name can reach the API; the call goes through `callApi` with `Idempotency-Key: parsed.idempotencyKey` for a create; a caught error becomes `problemToFormState(error, { aliases, messages })`; a `redirect()` stays outside the `try`, and an edit that stays on the page calls `refresh()` from `next/cache` and returns `formSucceeded(…)`. Server Functions never receive files: a form that attaches one uploads it from the browser through `shared/api/upload.ts` (ADR-0022) and holds the returned attachment id. Every endpoint a form posts to declares its 409 and 422 answers with `ProducesProblem`, or their codes never reach the form.
- **What the authentication phase adds to every Server Function**: the session check as the first statement, before `parseSubmission` (`authentication-web-login-page-and-session-integration`, with the session-expired return path), joined by the permission check once permissions exist (`user-management-roles-and-permissions`), and the `X-XSRF-TOKEN` header on its API call and on the browser upload (`authentication-antiforgery-for-json-endpoints`). Until then the kit writes no stub for them, a 401 maps to "Your session has ended. Sign in again.", and every anonymous caller shares one idempotency key space.
- **The error-key grammar.** Every key of a validation problem's `errors` is a camelCase JSON member path: member names joined by `.`, a collection element as its zero-based index in brackets (`customer.shippingAddress.street`, `orderItems[0].description`), and `""` for a result that names no member: every `IValidatableObject` result without a member at any depth, and a class-level attribute result on the request record itself. The built-in validation keys a class-level attribute result on a nested object or collection element by that object's path (`customer`, `orderItems[1]`), and `ValidationStep` validates top-level properties only; the table in `http-conventions.md` is exact. `ProblemDetailsCustomizer` rewrites every key of every `HttpValidationProblemDetails`, from the built-in validation filter and from `ResultExtensions.ToProblem` alike, converting each member name with `JsonNamingPolicy.CamelCase` and keeping indices, in one ordinal lookup per key so a body failing once per collection element costs time in proportion to its keys; keys that meet after conversion keep every message, and the keys keep the order validation reported them in. The web app's `apiKeyToFormPath(key, aliases)` (`shared/forms/errors/field-paths.ts`) turns a key into a react-hook-form path (`orderItems[0].description` → `orderItems.0.description`), converting a member name the API left in PascalCase with the exact .NET rule (`camelCaseMemberName`), then applies the form's aliases (the longest alias whose key, written in any spelling of the grammar, is a prefix at a segment boundary; an alias to `""` makes the message a form error); `""`, a malformed key and a path through a name react-hook-form reserves (`root`, `type`, `types`, `ref`, `message`, `form`) become form errors. A form names its fields after the API request's JSON members so most keys need no alias. A key that names an object rather than a field (`customer`, `orderItems[1]`) becomes that object's path (`orderItems.1`), which no field carries, so its message is listed in the summary without a link (next items); an alias to `""` would move it to the form errors but would take every key below that object with it.
- **Problems become form states** through `problemToFormState(error, { aliases, messages })` (`shared/forms/errors/problem-to-form-state.ts`). Its own messages are written for the person; it shows a problem's `detail` only where the table says so, meant for a module's own codes, whose details are written for the person, and never for a 400 that means the web app built the request wrongly (its detail names request types and parameters) or for an idempotency code. A form maps any other platform code it can meet, such as `concurrency.conflict`, in its `messages`:

  | Input | Result |
  |---|---|
  | a `TypeError` with the message `fetch failed` or `terminated` whose `cause` is an `Error` other than `unexpected redirect` (Node's fetch could not reach the API or lost the answer; `callApi` lets it through), or an `ApiError` with status 0 | `failed` "The ERP service did not respond. Try again." |
  | 5xx, 504 `request.timeout` included | `failed` "The server could not finish this. Try again." with the reference and no code |
  | 400 with `fields` | `invalid`: each key mapped as above, duplicate messages dropped |
  | a problem code the form maps in `messages` | `failed` with that sentence, the code and the reference |
  | 409 `idempotency.in-progress` | `failed` "Still being saved. Wait a moment, then check the list before trying again." |
  | 422 `idempotency.key-reused` | `failed` "The details changed since the last attempt. Send the form again." |
  | 409 `idempotency.replay-unavailable` | `failed` "This was already saved. Check the list before sending it again." |
  | 404 `feature.disabled` | `failed` "This part of the ERP is switched off." |
  | 400 without fields and without a code, or with `request.invalid`, `request.malformed`, `idempotency.key-missing`, `idempotency.key-invalid` or a `query.*` code | `failed` "The form could not be sent. Try again." (the web app built the request wrongly; the detail is for the server log) |
  | 400 without fields with another code | `failed` with the problem's `detail` |
  | 401, 403, 404, 429 | `failed` "Your session has ended. Sign in again.", "You do not have permission to do this.", "This record no longer exists.", "Too many requests. Wait a minute and try again." |
  | any other 4xx (a module's 409 or 422) | `failed` with the problem's `detail`, else "This could not be saved." |
  | anything else (any other `TypeError`, such as a programming error, an API address fetch cannot parse or a redirect `redirect: "error"` refused) | rethrown: the Server Function throws, and the form shows it as a rejected call (next item) |

  Every `failed` from a 4xx keeps the problem's code, every `failed` built from a problem carries its `traceId` as the reference, and an `invalid` carries neither.
- **Showing server errors.** A field's id is `formFieldId(formId, path)` (`formId` from `useId`). As a submit starts, `useActionForm` records the ids of the form's controls (`form.elements`, a fieldset included) and keeps them with the answer to that submission; a path belongs to a rendered field when its field's id is among them (`renderedField`); the path of a key on an object or a collection element (`customer`, `orderItems.1`), or on a member no control carries, never does. The hook applies an `invalid` answer with `setError(path, { type: "server", message })` for every path of a rendered field only (`renderedFieldErrors`), so a key on an object never replaces the errors of the fields below it, and sets `root.server` for every `invalid` and `failed` answer; the error summary (`FormAlert`) renders while `root.server` is set (react-hook-form clears it on the next submit) and takes focus once rendered. For `invalid` it lists, in the answer's order after the form errors, every message of a rendered field still standing, linked to its field's id, and every message of any other path without a link, which stays until the next submit because no field can show or clear it; for `failed` its title is the message with the reference beneath. A field's own server error clears when the field revalidates. A Server Function call that rejects (the web server refused it, its request or its answer never arrived, or the function threw) never reaches `error.tsx`: the action `useActionForm` hands to `useActionState` catches the rejection, passes Next.js's own redirect and not-found errors on with `unstable_rethrow`, and turns anything else into a `FormState` with `rejectedActionState(error, unstable_isUnrecognizedActionError)` (`shared/forms/client/rejected-action.ts`): an `UnrecognizedActionError`, which Next.js raises when the web server answers `x-nextjs-action-not-found` because the page came from an earlier deployment whose Server Function ids the new build no longer has (Next.js 16.3 guide "Server Actions", Deployment considerations), becomes `failed` "This page is out of date. Reload the page, then send the form again.", since sending again can never succeed; an error carrying a `digest`, which is how a Server Function that threw reaches the browser, becomes `failed` "The server could not finish this. Try again." with the digest as reference; and any other rejection `failed` "The ERP service did not respond. Try again.". None has a code, so the form keeps its values and its idempotency key.
- **The idempotency rule.** A form created with `idempotent: true` mints a key with `crypto.randomUUID()` at its first dispatch and sends the same key with every dispatch until an answer decides the attempt. The key is chosen as each dispatch is sent, by `idempotencyKeyToSend(last, answer, mint)` (`shared/forms/state/idempotency-key.ts`), which records the answer each key was sent after (`SentIdempotencyKey`): a dispatch with no new answer since the last one reuses its key, and so does one after an answer `keepsIdempotencyKey(state)` keeps; any other answer mints a fresh key. `keepsIdempotencyKey` keeps it after a `failed` answer without a code (the web server or the API did not answer, the API answered 5xx or a 4xx whose problem the generated client could not read, or the Server Function threw, so the create may have run; keeping a key the API never saw is harmless, as after a call the web server refused from an out-of-date page, which ran nothing) or with `idempotency.in-progress` or `idempotency.replay-unavailable` (the create already ran under the key, so a new key could create a second record); every other answer (`invalid`, `succeeded`, every other coded `failed`, `idempotency.key-reused` included) ends the attempt. `useActionState` runs dispatches one at a time, and the form ignores a submit while one is pending. Edit forms carry the entity's row version instead of a key: a stale one answers 409 `concurrency.conflict` (`EfUnitOfWork`), whose detail names entity types, so an edit form maps that code in its `messages`.
- **The form composites live in `@dewiride/erp-ui`** and stay presentational: they never import `zod`, `react-hook-form` or `apps/web` (rule L6), and they take and emit the canonical strings above. `components/forms/`: `FormField` (label, description, errors, a visible "(required)" after the label of a required field, hidden from assistive technology, which hears `aria-required` instead, so no page needs a legend for a symbol, `data-invalid` and `data-disabled`, and the control's `id`, `aria-invalid`, `aria-describedby` and `aria-required` handed to a render function; the label carries `<id>-label`, `formFieldLabelId`), `FormAlert` (the destructive `Alert`, `role="alert"`, `tabIndex={-1}`, a link per message with a field id that focuses the field, "Reference: …") and `SubmitButton` (natively disabled while `disabled` or not `ready`; while `pending` it stays focusable with `aria-disabled`, `aria-busy` and an `aria-hidden` spinner, and cancels every click, which also stops the implicit submission of Enter in a field; its label unchanged). `components/inputs/`: `AmountInput` (a leading "₹", `inputMode="decimal"`; typing and pasting keep digits, one decimal point with at most `scale` decimals after it (scale 0 keeps the point and drops what follows) and a leading minus written as `-`, U+2212, U+2013, U+FE63, U+FF0D or an opening parenthesis; integer digits are never cut and the minus is kept without `allowNegative`, so an amount the field refuses, such as 16 integer digits or a negative, is emitted as typed for the schema to refuse, and any other as its canonical value on every keystroke; lakh and crore grouping when not focused, replaced on focus by the plain digits with the caret or selection on the same digits, once the press ends (its release, or the context menu that takes it) when a primary-button click or a tap gave the focus; losing focus first ends that wait, so the next focus swaps again) and `IdentifierInput` (monospace, upper-cases and strips everything outside `[0-9A-Z]` while typing and pasting, cut at `maxLength`, left alone while an input method composes). `components/pickers/`: `DateInput` and `DateRangeInput` over `DateTextInput` (typed `dd-MM-yyyy` with `-`, `/` or `.`, one- or two-digit day and month, eight digits or an ISO date; shown as `dd-MM-yyyy` when not focused) with a modal calendar popover in the APG date-picker dialog model (focus moves into the grid and returns to the button, days outside `min`/`max` disabled, month and year dropdowns, a range calendar with two months from `md` that commits only when both ends are chosen; the two text boxes of a range sit side by side while each can be at least 8rem wide and stack otherwise, are never reordered, and take their own invalid state through `ends`, and the schema reports an end before the start). `components/combobox/`: `Combobox` (Left, Right, Home and End return to the text; its clear and toggle buttons are named with the field's label). Their pure logic sits in `.ts` siblings (`replace-input-text`, `press-watch`, `calendar-limits`, `combobox-options`) and in `src/lib/` (`indian-number`, `identifiers`, `calendar-date`, and `calendar-defaults`, the `en-IN` locale with weeks starting on Monday, which `apps/web` spreads into a standalone `Calendar` because it cannot import `react-day-picker` itself). The calendar primitive is `components/ui/calendar.tsx` from the registry with two registered patches (`CalendarDayButton`'s `locale?: Partial<Locale> | undefined`, and its `Root`, `Chevron`, `DayButton` and `WeekNumber` components declared at module level, the day button reading the locale through `useDayPicker`, so a re-render keeps the grid and its focus), written from `shadcn add calendar --view` because the CLI's install is refused by `catalogMode: strict`.
- **The kit in `apps/web`** is the concern folder `shared/forms/` with `state/`, `errors/`, `schemas/` (`schemaResolver`, `parseSubmission`, `gstinSchema`, `panSchema`, `ifscSchema` with `identifierLengths`, and the builders `requiredText`, `optionalInput`, `amountSchema`, `calendarDateSchema` and `dateRangeSchema`, which reports an end before the start on `to`) and `client/` (`useActionForm`, `form-feedback.ts`, `rejected-action.ts`). The schemas check with the same helpers the inputs use (`normaliseAmount`, `groupIndian`, `maxAmountIntegerDigits`, `maxAmountScale`, `isIsoDate`, `compareIsoDates`, `formatDisplayDate` and `normaliseIdentifier` from `@dewiride/erp-ui/lib/*`), so the inputs and the schemas share one definition of an amount's limits, a real date and an identifier's characters; the optional builders treat an absent value (`undefined` or `null`) like empty text. Its modules import each other and `shared/api/problem-details.ts` by relative path with the `.ts` extension (`allowImportingTsExtensions`), which Node needs.
- **`instrumentation-client.ts` sets Zod's `jitless` switch** with `import { config } from "zod"; config({ jitless: true });` before hydration, so no form page reports a policy violation; `config` is imported by name because the `z` namespace would put all of Zod into the root bundle every page loads, and the named import reaches the one global configuration the form pages' copy of Zod reads. The file imports nothing from `features/` (rule I5 covers every file outside `app/`, `features/` and `shared/`).
- **A page bundles only the client code of what it imports.** `features/platform/design/index.ts` exports two page components (`KitchenSink` and `FormKit`), and `features/registry.ts` imports every module's `index.ts` for its `nav`, so each page's server graph reached every re-exported page and Turbopack kept their client components: both design pages loaded the other one's client modules, and every `(app)` page the client components of every registered module. Turbopack's own inference can only mark a module as free of side effects in its evaluation, which "may still have side effects based on its imports", so it keeps a re-export whose target imports client or package code; only a declared side-effect-free module can be skipped whole. `apps/web/package.json` therefore declares `"sideEffects": ["./src/instrumentation-client.ts", "*.css"]`: every other web source file is free of side effects, so Turbopack follows a re-export in `index.ts` to the file that defines the imported name and drops the rest, and a page or `features/registry.ts` bundles only what it uses. `instrumentation-client.ts` is listed because its module-level `config({ jitless: true })` is its whole purpose, and `*.css` because a stylesheet is imported for its effect; a file whose evaluation does more than define exports joins the list in the same change. ESLint enforces the declaration (rule X3 of `docs/architecture/dependency-rules.md`): outside the listed files and the unit tests, which are never bundled, a web source file has no statement at module level other than imports, exports, declarations and directives, and imports a local file (a relative or `@/` specifier other than a stylesheet) only by name, never bare; the listed files are `sideEffectFiles` in `frontend/packages/config/eslint/feature-boundaries.mjs`, and `feature-boundaries.test.mjs` fails when they differ from the declaration. `tests/smoke/web-bundles.spec.ts` reads each route's HTML with the `request` fixture, fetches every script chunk it references, and checks that each route carries its own module's client test ids and none of another module's.
- **Component tests.** A component test is a Playwright spec that drives one component or one scenario on a harness page of the production build, on every Playwright project, in light and dark (`forEachTheme`) where the rendering is theme-specific, with ARIA snapshots, the keyboard path, one validation failure and the console-error guard; the component's pure logic is covered by `node --test` beside it. No DOM runner and no experimental component-testing package. The harness pages are `/design/kitchen-sink`, whose Forms section shows every composite in every state, and `/design/form-kit`, the example form "Register a supplier (example)" (`features/platform/design/form-kit`), whose Server Function `registerSupplierExample` re-parses the submission and answers as its "Server answer" field chooses (accept, a field error, a validation problem with nested keys through aliases and keys on an object and a collection element that no field carries, a 409 with a module code, a 500, an unreachable API) by mapping a fixed `ApiError`, or the `TypeError` Node's fetch throws for a refused connection, with `problemToFormState`, without calling the API or storing anything, while its drop zone uploads for real; its schema also carries a rule that names no field (the GST Council's "Registration under GST Law": characters 3 to 12 of a GSTIN are the PAN), checked only once GSTIN and PAN are each well formed. Both pages ship in every environment, like the kitchen sink (ADR-0023). The unit-test runner `erp-unit-tests` starts `node --test` with `--import` of `packages/config/cli/resolve-source-alias.mjs`, a `module.registerHooks` resolve hook that maps `@/…` to `src/…` of the package under test (the path, then `.ts`, then `/index.ts`), so a feature schema that imports `@/shared/forms/**` is testable; the tests themselves import `./<name>.ts`.
- **Earlier decisions this changes.** ADR-0009: the approved list gains `react-day-picker` and its dependencies `date-fns` and `@date-fns/tz`, both transitive only. ADR-0017: its decision that validation `errors` keys are camelCase through `DictionaryKeyPolicy`, and its consequence that a nested key would read `customer.ShippingAddress.Street` ("revisit when the first nested request body arrives"), are reversed: `DictionaryKeyPolicy` lowers only the first character of a key, so `ProblemDetailsCustomizer` now camel-cases every member name of every key (`customer.shippingAddress.street`), and the key grammar above, with its table in `http-conventions.md`, replaces the single-policy rule. ADR-0023: `combobox` is resolved in-house and stays uninstalled from the registry, `calendar` is installed with two register entries, `date-picker` is built as its recipe, and `form` is built from `field` and `react-hook-form`; the kitchen sink gains the Forms section. ADR-0007: "mutations are Server Functions that re-check the session and validate with Zod" takes the shape above (re-parse the envelope with the shared schema, map problems to a `FormState`), and the frontend rule "return `{ errors }` for `useActionState`" becomes "return a `FormState`". ADR-0024: `forms/` exists from this change (`platform/design/form-kit/forms/supplier-example.schema.ts`), and `instrumentation-client.ts` joins `proxy.ts`, `instrumentation.ts` and `instrumentation.node.ts` among the files outside `app/`, `features/` and `shared/`; its rules stay as written, its register gains X3 (above), and the `sideEffects` declaration above makes a module `index.ts` that re-exports several page components, and the registry that imports every `index.ts`, put into a page only the client code of the names it imports.

## Consequences

- Every mutation form is built the same way (`useActionForm`, `FormField`, one schema, one Server Function), and a validation rule is written once and checked in the browser and again on the server; an API answer lands on the field it concerns, including a nested one, or in the focused summary.
- A mutation form cannot be sent before its page has hydrated, and a person with JavaScript switched off cannot send one; the Save button says so by staying disabled. The `javaScriptEnabled: false` test of `form-kit.spec.ts` proves that pressing Enter then sends no Server Function request.
- A retry after an unknown outcome replays or completes the same create instead of creating a second record; a decided answer always starts the next attempt with a fresh key. A Server Function call that fails on the way leaves the form, its values and its key in place.
- A page ships no other module's client components (`web-bundles.spec.ts`); a module-level effect in a web source file missing from `sideEffects` would be dropped from any page that imports none of that file's exports, so `pnpm lint` refuses a module-level statement or a bare local import in any web source file that is not listed (X3). A module-level declaration whose initialiser has an effect (`const registered = register()`) passes the rule and is caught only by review.
- The combobox, the date inputs and the amount and identifier inputs are ours to keep accessible: their ARIA and keyboard behaviour is proven by the kitchen-sink and form-kit specs on every project, and their pure logic by `node --test`. `react-day-picker` is a single-maintainer package; a calendar regression fails the calendar tests of both specs.
- `ProblemDetailsCustomizer` changes a nested validation key on the wire (`customer.ShippingAddress.Street` → `customer.shippingAddress.street`); no existing endpoint had a nested key, so `docs/openapi/erp.json` and the generated client do not change.
- Losing the `calendar.tsx` patch on a refresh fails `pnpm typecheck`. Removing `config({ jitless: true })` makes the form-kit spec fail on Firefox through the console-error guard; importing `z` there instead puts Zod's full library into the root bundle, which only a bundle review catches.
- The agreement document of `/design/form-kit` is a real attachment: it is stored encrypted and listed at `/platform/attachments` like any other, `form-kit.spec.ts` deletes the one it uploads, and a person who uploads one there and leaves keeps a stored file until it is deleted from that list.
- Statutory datasets stay out of the web app: GSTIN State codes, and any check character, arrive with `business-building-blocks-statutory-parameter-store-and-gst-datasets` and are enforced by the API.
- Revisit: server search in the combobox (`onInputValueChange`, `loading`) gets its first real caller with the first master-data picker; the authentication phase inserts the session, permission and antiforgery pieces above into every Server Function; `/design/form-kit` becomes signed-in only with the rest of the `(app)` shell; the first request record with a class-level rule on a nested object decides whether a message keyed by an object path, listed today without a link and without saying which object it concerns, needs a label or an alias.
