# ADR-0060: Integration events: per-module outboxes, deliveries as job runs and no order

Status: accepted
Date: 2026-11-06

## Context

- **What existed.**
  - A module reaches another only through its Contracts, and writes across modules go through integration events ([ADR-0002](0002-modular-monolith-module-anatomy.md)), but nothing carried one: `Kernel.Events.IIntegrationEvent` (`Guid EventId`, `DateTimeOffset OccurredOn`) had no implementation and no caller.
  - Domain events stay inside their module: `EfUnitOfWork` dispatches them to the module's own `IDomainEventHandler`s round by round inside the command's transaction, saving what each round's handlers changed, for at most `MaxDispatchRounds` (10) rounds, and a reaction that must not roll back with the aggregate "belongs behind an integration event, not a domain event" ([ADR-0016](0016-application-pipeline-and-idempotency.md)).
  - `BuildingBlocks.Jobs` runs the ERP's own work as persisted runs under idempotency keys, claimed under leases by the API's runner, retried with doubling delays, dead-lettered, re-run and cancelled from the jobs page, always as the system actor ([ADR-0059](0059-background-jobs-a-persistent-queue-leases-ist-schedules-and-the-nightly-account-check.md)). Its enqueue commits on a connection of its own, so ADR-0059 had a module enqueue with a key derived from its change "until `business-building-blocks-transactional-outbox-and-integration-events` exists" (its decision "Idempotency keys"). `JobPayloads` read a payload with the Web defaults, which fill a missing constructor parameter with its default, so a payload that lacked a member still ran, although the architecture document says that a run whose payload type changed since it was enqueued fails with `job.payload-unreadable`.
  - `UnitOfWorkSignal` recorded only that the outermost unit committed (`Committed`, which the idempotency middleware reads). `JobSignal`, which wakes the runner, was internal to the jobs building block, and the runner's poll ran the scheduler, the lease recovery and the claims alone. `UnitOfWorkStep` took the first catalogue context of a command handler's assembly.
  - [ADR-0047](0047-user-lifecycle-the-account-check-and-the-team-handover.md) left the users module's cross-module messages to this item: the deactivation of a person, and the invitation of a directory person with ERP roles and the recording of a position, for `hr-core-onboarding-and-offboarding` and `integrations-entra-group-onboarding-and-sync`.
- **Facts that shaped the design** (official sources, read 2026-11-02 and 2026-11-06).
  - EF Core (learn.microsoft.com, "Creating and Configuring a Model" and "What's New in EF Core 6.0"): with `EntityTypeConfigurationAttribute` on an entity type, EF Core "will use the specified `IEntityTypeConfiguration` implementation whenever the … entity type is included in a model", for example "by creating a `DbSet<TEntity>` property", and such types "will not be automatically discovered in an assembly". So one configuration in a building block shapes a table in exactly the contexts that declare its set.
  - SQL Server (learn.microsoft.com, "uniqueidentifier (Transact-SQL)" and "Comparing GUID and uniqueidentifier values"): for `uniqueidentifier`, "ordering is not implemented by comparing the bit patterns of the two values", and `SqlGuid.CompareTo` treats "the last six bytes of a value" as the most significant. A version 7 `Guid` therefore does not sort by its time in SQL Server.
  - SQL Server's `json` type (learn.microsoft.com, "JSON data type", section "Numeric precision"): when text is converted to `json`, "JSON text containing a JSON number can be rounded based on the number format".
  - SQL Server (learn.microsoft.com, "Transaction locking and row versioning guide" and "SET TRANSACTION ISOLATION LEVEL"): `READ_COMMITTED_SNAPSHOT` is on by default in Azure SQL Database and off in SQL Server, where `READ COMMITTED` takes shared locks that "also block the statement from reading rows modified by other transactions until the other transaction is completed".
  - EF Core (learn.microsoft.com, "Connection Resiliency", section "Transaction commit failure and the idempotency issue"): "if the connection is dropped while the transaction is being committed the resulting state of the transaction is unknown", and the execution strategy "will retry the operation as if the transaction was rolled back".
  - EF Core (learn.microsoft.com, "Applying Migrations", section "Migration locking", "SQLite EF Core Database Provider Limitations", section "Concurrent migrations protection", and "Breaking changes in EF Core 9"): since EF Core 9, `Migrate`, `MigrateAsync` and `dotnet ef database update` "automatically acquire a database-wide lock before applying any migrations", on SQL Server "a session-level application lock (`sp_getapplock`) that is automatically released when the connection closes", and EF Core 10 runs each migration in its own transaction again. So test fixtures that migrate contexts of their own into the one test database, as `SampleDatabase` does, take turns when they start together.
  - System.Text.Json (learn.microsoft.com, "What's new in .NET libraries for .NET 9", the reference pages of `JsonSerializerOptions.RespectRequiredConstructorParameters` and `RespectNullableAnnotations`, and "Handle unmapped members during deserialization"): constructor-based deserialization "treats all constructor parameters as optional by default, filling missing parameters with default values"; `RespectRequiredConstructorParameters` refuses a payload without a non-optional parameter and `RespectNullableAnnotations` a null for a non-nullable property or constructor parameter, though not for collection elements or generic parameters, and Microsoft recommends both for new applications; a JSON property that maps to no member is skipped by default (`JsonUnmappedMemberHandling.Skip`).
  - C# (learn.microsoft.com, "interface (C# Reference)", section "Static abstract and virtual members", and "Static abstract and virtual interface member errors and warnings"): the compiler resolves a `static abstract` interface member at compile time, the member "can be accessed only on a type parameter" (CS8926), and an interface whose static member has no most specific implementation "cannot be used as type argument" (CS8920).
- **Owner decisions of 2026-11-02.** The Community edition (confirmed 2026-11-01). An event that has been passed on is kept 400 days (`Erp:Platform:IntegrationEvents:PublishedEventRetention`), as long as job history and the server's journal. This item builds and proves the delivery alone, with no product event; the first, a person deactivated, comes with `hr-core-onboarding-and-offboarding`.
- **Owner decision of 2026-11-06.** The item's work is committed on `main` and pushed with the owner's approval, without pull requests.

## Decision

- **A building block that owns no schema.** `BuildingBlocks.IntegrationEvents` (`backend/BuildingBlocks/IntegrationEvents/Dewiride.Erp.BuildingBlocks.IntegrationEvents`, referencing `BuildingBlocks.Application`, `BuildingBlocks.Kernel`, `BuildingBlocks.Persistence` and `BuildingBlocks.Jobs`) holds the publisher, the subscription contract, the types of the two tables, the relay and the retention sweep. `ErpHostComposition.AddErpPlatform` calls `AddErpIntegrationEvents()` for every host right after `AddErpJobs()`; it binds `IntegrationEventsOptions` (`Erp:Platform:IntegrationEvents`), validated on start in every host. The tables live in the schemas of the modules that use them, so the building block registers no context and the catalogue's order does not change.
- **An event is a Contracts record that names itself.**
  - `Kernel.Events.IIntegrationEvent` declares one member, `static abstract string Name { get; }`. An event without a name does not compile, the publisher and the delivery read `TEvent.Name` without reflection, and the event's id and time belong to its outbox row, not to its type.
  - An event is a public sealed record in a Contracts `<…>.Events` namespace. Its name is three lower-case kebab-case segments of at most 128 characters (`IntegrationEventNames`), unique, the first two the permission prefix of the module whose Contracts declare it, and never a version (`v<n>`).
  - Its members are `Guid`, `bool`, `int`, `DateOnly`, `DateTimeOffset`, enums of a Contracts assembly or of the Kernel, their nullable forms and `IReadOnlyList<T>` of them: identifiers, flags, counts, dates and states, and nothing else. A subscriber reads anything more through the publisher's Contracts when it runs.
  - `IntegrationEventSerializer` writes and reads with the rules of `JobPayloads` (the Web defaults, strict numbers, enums as camelCase names and never numbers) plus `RespectRequiredConstructorParameters` and `RespectNullableAnnotations`, so a missing member, a null for a member that cannot be null or a value of the wrong type makes an event unreadable instead of filling it with a default. A member the type does not know is skipped, so an event published by a release is still read by the release before it after a rollback. An event's JSON is at most 15 KiB, so the delivery's payload fits the 16 KiB of a job payload.
  - Evolution: a name never changes; a member is added only as a constructor parameter with a default; any other change is a new event with a name for its meaning, and the old event is retired in two releases: the first stops publishing it, and a later one deletes it and its subscribers once no outbox holds a row of it waiting.
- **Publishing writes the module's own outbox inside the unit of work.**
  - A module publishes from a domain-event handler in `<Module>.Integration.Publishers`, an `IDomainEventHandler<TDomainEvent>` that `AddHandlersFromAssembly` registers like any other: `IIntegrationEventPublisher.Publish<TEvent>(ModuleDbContext context, TEvent integrationEvent)` (`where TEvent : class, IIntegrationEvent`) answers the event's `IntegrationEventId`, a version 7 strongly-typed id.
  - `OutboxPublisher` (scoped) throws `InvalidOperationException` for a context without an open transaction, so a publication outside a unit of work fails, and for a context that does not map `OutboxMessage`. It adds the row to the context, and the unit of work's next round saves it in the same transaction: a unit that fails, throws or rolls back leaves no row, a committed unit exactly one per publication. At every publication it registers `UnitOfWorkSignal.AfterCommit` with `OutboxRelay.Announce`, which makes the relay due and wakes the local runner through `IJobRunnerSignal`.
- **Three extension points.**
  - `UnitOfWorkSignal.AfterCommit(Action)`: `EfUnitOfWork` runs the callbacks once the outermost unit has committed, after the execution strategy returned, so a callback can never turn a committed command into a retry or a failure. `MarkRolledBack()` drops the callbacks of a unit that failed, threw or is being retried, and a unit that joins an ambient transaction leaves its callbacks to the outer unit's commit.
  - `IJobRunnerSignal` (`Jobs/Queue`, public), implemented by `JobSignal` and composed by `AddErpJobs` for every host, lets code outside the building block wake the local runner; a host without a runner, such as the migrator, wakes nothing.
  - `IJobRunSource` (`Jobs/Running`) with `AddJobRunSource<TSource>()`, which registers the source once as a singleton of its own type, so the building block that owns it reaches it (the publisher announces to the relay), and as an `IJobRunSource`: at each poll the runner runs the scheduler, then every source, each in its own `try`/`catch` with its own failure streak, then the lease recovery and the claims, so a run a source enqueues is claimed in the same poll and a failing source costs the poll only its own work.
- **Two tables per module, opted into with a set and a migration.**
  - `OutboxMessage` (table `OutboxMessages`): `Id` (`IntegrationEventId`, set in code), `EventName varchar(128)`, `Payload json`, `OccurredAt`, `CorrelationId varchar(64) NULL` (the publishing request's, from `IRequestOrigin`) and `RelayedAt NULL`, indexed by `(OccurredAt, Id)` where `RelayedAt IS NULL`, for the relay, and by `RelayedAt` where it is set, for retention. It is neither `IAuditable` nor `IAppendOnly`: the relay marks a row with `ExecuteUpdate`, which the bulk guard refuses on both, and a change record per mark would fill the books' trail with the ERP's bookkeeping, as a job run would.
  - `ProcessedMessage` (table `ProcessedMessages`): the primary key `(EventId, Subscriber varchar(128))`, the subscriber being its delivery job's name, and `ProcessedAt`, indexed; `IAppendOnly`.
  - Each type carries `[EntityTypeConfiguration]`, whose configuration names the table and no schema, so the context's default schema applies. A module that publishes declares `public DbSet<OutboxMessage> OutboxMessages => Set<OutboxMessage>();`, a module that subscribes the `ProcessedMessage` set, and each adds the tables with a migration of its own. No product context maps either table yet.
  - A module context maps, besides its own types, only `ChangeRecord`, `OutboxMessage` and `ProcessedMessage`, and a context that maps either table maps it as the configuration does: in its own schema under the configured table name, the outbox's `Payload` a `json` column with its two filtered indexes, the processed records keyed by `(EventId, Subscriber)`.
- **One relay in the runner's poll, reading when a pass is due.** `OutboxRelay`, one singleton `IJobRunSource`, reads the outboxes of the catalogue contexts that map `OutboxMessage`, which `IntegrationEventTables` finds once from their models.
  - A pass is due after an announcement (a commit of the relay's own process that published), at the first poll after the API starts, after a pass in which an event could not be passed on, and once `FullPassInterval` (one hour) has gone by since the last pass, which also finds an event whose process stopped between its commit and its announcement, or one another process committed. At any other poll the relay reads nothing, because every read writes a command line of a module's context at `Information`.
  - A pass reads each outbox's rows not yet relayed in pages of 100, ordered by `(OccurredAt, Id)` because a version 7 id does not sort by time in SQL Server, until a page holds fewer. Each row is passed on in its own `try`/`catch`: for each subscriber of its name the relay enqueues that subscriber's delivery under the key `event:<the event id in D format>`, then marks the row with an `ExecuteUpdate` that sets `RelayedAt` where `Id` is the row's and `RelayedAt IS NULL`; an event without subscribers is marked without a run.
  - A row that fails is logged at `Error` the first time only, left out of the rest of the pass and tried again at the next pass, which the failure makes due, so an event the relay cannot pass on never holds back the others.
  - `RelayOneAsync(Type contextType, IntegrationEventId id, CancellationToken cancellationToken)` passes one event on, for tests.
- **Deliveries are job runs, one per event and subscriber.**
  - A subscriber implements `IIntegrationEventHandler<in TEvent>` (`Task<Result> HandleAsync(TEvent integrationEvent, IntegrationEventContext context, CancellationToken cancellationToken)`, with `IntegrationEventContext(IntegrationEventId EventId, DateTimeOffset OccurredAt, JobContext Job)`), is sealed and lives in `<Module>.Integration.Consumers`. Its module registers it from `AddServices` with `AddIntegrationEventHandler<TEvent, THandler>(JobDefinition definition)`: the subscriber is the job `definition.Name`, under the consuming module's prefix, with the definition's title, description, retry policy and attempt timeout. `IntegrationEventCatalog` holds the registrations (`IntegrationEventSubscription`).
  - A delivery's payload is `IntegrationEventDelivery(Guid EventId, string EventName, string Source, DateTimeOffset OccurredAt, string? CorrelationId, JsonElement Event)`, the event itself included, so a delivery never reads the outbox and a re-run works after the row was deleted. A change to this record needs new subscriber job names, because runs already queued carry its old shape.
  - `IntegrationEventDeliveryJob<TEvent, THandler>` reads the event strictly (unreadable: `integration-event.unreadable`, a `Failure`, dead-lettered at once), creates the subscriber with `ActivatorUtilities` in the run's scope, as a job is created, and runs it inside `EfUnitOfWork` on the context its assembly owns (`DbContextCatalog.OwnedBy(typeof(THandler).Assembly)`), which in the same transaction inserts its `ProcessedMessage`. A processed record already there means the event was handled, and the delivery succeeds without running the subscriber again. It logs inside `IntegrationEventScope`: the event's id, name and outbox schema, and the correlation id of the request whose change published it.
  - `DbContextCatalog.OwnedBy(Assembly)` throws when an assembly owns more than one catalogue context, and `UnitOfWorkStep` uses it too, so a module's commands and its deliveries commit through its one context.
  - The jobs building block supplies the rest: the retry policy of the subscriber's definition (a `Conflict` or `Unavailable` result, an exception, a timeout or an expired lease retried with doubling delays, any other failure dead-lettered at once), the jobs page with Run again and Cancel, the metrics, the span per attempt and the retention of finished runs.
- **Every delivery runs as the system.** The runner creates its scope outside any request, so its change records carry `ActorIds.System` and the attempt's trace id as their correlation id. `ICallerPermissions` throws outside a request, so a subscriber checks nothing of a person: the module that publishes authorises the person who acts for everything the event will cause, before it publishes.
- **Job payloads are read strictly too.** `JobPayloads` adds `RespectRequiredConstructorParameters` and `RespectNullableAnnotations`, so a payload that lacks a member, or holds a null for a member that cannot be null, does not deserialise, and its run dead-letters with `job.payload-unreadable` instead of running on values nobody wrote.
- **Retention in the migrator's retention step.** `IntegrationEventRetentionSweep`, one `IRetentionSweep` walking every catalogue context that maps either table, which `migrate` runs after the seeders and `retain` runs alone, deletes the rows relayed longer ago than `PublishedEventRetention` (400 days; 1 to 3650 days), never a row not yet relayed, and the processed records older than `Erp:Platform:Jobs:FinishedRunRetention`, as long as a delivery run is kept and can run again, both in statements of 100 rows, as `JobRunRetentionSweep` deletes runs.
- **No meter and no test driver yet.** The jobs meter already counts the relay's enqueues (`erp.jobs.enqueued`, a key already used counted `existing`) and each delivery's attempts by subscriber (`erp.jobs.attempts`), and production exports no OTLP and alerts nobody ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)). The testing library gains a driver with the first module that publishes; until then only the building block's own tests drive a delivery, by the event's id.
- **Architecture tests** (`IntegrationEventTests`). No product module publishes yet, so each rule runs over the product's types, where it finds nothing, and over probe types, accepting the one that keeps it and refusing each that breaks it: the event rules above (a public sealed record of a module's Contracts in an `.Events` namespace, a well-formed and unique name under the module's prefix without a version, the members); publishers, the types whose constructor takes `IIntegrationEventPublisher`, only in `<Module>.Integration.Publishers`; subscribers sealed, in `<Module>.Integration.Consumers`, in a module whose context maps `ProcessedMessage`, with delivery jobs named under the module's prefix (`JobTests`, reading a delivery job's module from its subscriber); and the mapping rules of the two tables.

## Options rejected

- **One outbox for the whole ERP**, mapped by every context as `audit.ChangeRecords` is: a module's events would leave its schema, and one table would hold every module's waiting and kept events; the roadmap scope asks for a table per module, and a module's events and processed records stay in its schema, made by its migrations.
- **The jobs table as the outbox**: enqueuing the deliveries inside the publisher's transaction would make every unit of work that publishes span `JobsDbContext` as well (a shared connection and `UseTransaction`), so the jobs store would join every module's transaction.
- **Deleting an event once passed on**: the admin console (`operations-hardening-admin-console`) shows the outbox, and the owner chose to keep passed-on events 400 days, which also keeps the way from a delivery back to the request that caused it.
- **A cursor or watermark for the relay**: an id and `OccurredAt` are taken when a row is added, and rows commit in another order, so a cursor past a row that commits later would skip it for good. The filtered index on the rows not yet relayed keeps every read small instead.
- **Reading every outbox at every poll**: an idle API would write a command line of every publishing module's context every `PollInterval`, as the jobs store would if `AddErpJobs` did not log its commands at `Debug` ([background jobs](../architecture/background-jobs.md), section "Observability"), while the announcement after a commit, the first poll after a start and the hourly pass already find every event.
- **A recurring relay job**: a run every minute would put 1,440 runs a day on the jobs page and wait up to a minute, and a job is named under a module's prefix (`JobTests`), which a building block has none of. **Relaying in the request after the commit**: the person would wait for it, and the poll would still be needed for whatever a failure left. **A loop of its own**: a second poll beside the runner's, with its own wake and its own failure handling.
- **One run per event that fans out to every subscriber**: one subscriber's failure would retry or dead-letter the work of the others. **A delivery engine of its own**: retries, dead letters, re-runs, cancels, the page and retention already exist in the jobs. **The subscriber as the job itself**: every subscriber would repeat reading the event, the processed record and the unit of work.
- **An attribute that names the event**: a missing attribute shows only in a test or at run time, and reading it needs reflection; a `static abstract` member is checked by the compiler.
- **Lenient reading**, the serializer's defaults: a missing member would be filled with a default, and the subscriber would act on a value nobody published.
- **Strings, `long`, `decimal` and `Money` in events**: the `json` column can round a large or precise number, and a string can carry a name or free text, which neither a job payload nor a row kept 400 days may hold. **Versioned names** (`…-v2`): a name says what happened; another meaning is another event, and the old one is deleted in the same change.
- **An order**: delivering the events of one key one at a time would hold every later event behind a failing one, and a subscriber that reads the current state when it runs needs no order.
- **Exactly once**: a commit can succeed while its acknowledgement is lost, which the execution strategy retries as a rollback, and a subscriber's call outside the database cannot join its transaction.
- **A meter of its own**: nothing reads it in production, and the jobs meter counts the enqueues and the attempts. **A testing driver now**: no module publishes yet, and the first one that does adds it with its tests.
- **Processed records kept for ever, or deleted with their event**: a processed record matters while its delivery can run again, which ends when the run is deleted after `FinishedRunRetention`.

## Consequences

- **At least once, so every subscriber is idempotent.** Two relays at once, or a failure between an enqueue and the mark, enqueue under the same key and find the same run. Two runners executing one delivery after a lost lease, and an administrator's re-run of a delivery that failed after its change committed, meet the processed record: the second insert hits the primary key, its unit of work rolls back with `concurrency.conflict`, which is retried, and the retry finds the record and succeeds. The processed record does not cover:
  - a publication repeated after a lost commit acknowledgement: the execution strategy runs the command again as if it had rolled back, and the second event has a new id, so a subscriber's change also holds against a second event with the same meaning, by its business key;
  - an effect outside the database (Microsoft Graph, mail), which can happen twice when the delivery's transaction fails after it, so such a subscriber makes the effect idempotent itself, for instance through a job enqueued under a key built from the event's id.
- **No order.** The relay reads by `(OccurredAt, Id)`, but each delivery is a run of its own, claimed two at a time (`MaxConcurrentRuns`) and retried after delays, so a subscriber may see a later event first. It reads the current state when it runs, as a job does, and the architecture document says that no order is promised.
- **An event that was not announced waits for a pass.** The process that commits an event announces it and passes it on at once; an event whose process stopped between its commit and its announcement is passed on at the first poll after the API starts again, and one another process committed, the migrator or a second instance, within `FullPassInterval`.
- **A subscriber added in a release receives only the events relayed after that release starts**; nothing replays earlier ones. A subscriber removed in a release leaves its unfinished runs pending, under a job the release does not define, until an administrator cancels them on the jobs page.
- **Retiring an event takes two releases.** A row of an event whose subscribers a release removed finds no subscriber and is marked without a run, so the release that stops publishing an event keeps its subscribers, and a later release, once no outbox holds a row of it waiting, deletes the event and its subscribers.
- **The trail across a delivery.** A subscriber's change records name the ERP and carry the attempt's trace id, which the run's `Started` event keeps; the run's key names the event, and the event's outbox row keeps the publishing request's correlation id, under which the publisher's change records name the person, as the delivery's lines in the journal do (`PublishedCorrelationId`). The run and the row are kept 400 days, as the journal keeps its lines, while change records are kept 8 financial years ([ADR-0043](0043-change-records-and-the-append-only-audit-schema.md)): after 400 days a subscriber's records still say that the ERP made the change, but no longer lead to the person whose change caused it.
- **Authorisation belongs to the publisher.** A subscriber acts as the system on what an event says, so a module checks, before it publishes, every permission the subscribers' effects need of the person who acts: an event that asks the users module to invite a person with ERP roles needs the asker's `identity.users.people.assign-roles`.
- **The owner's SQL Server waits where Azure SQL does not.** With `READ_COMMITTED_SNAPSHOT` off, the relay's read of a module's outbox waits behind a transaction that added a row and has not committed, at most the command timeout, after which the poll logs the source's failure and the next poll reads again; Azure SQL Database reads the last committed rows and never waits.
- **Building blocks do not subscribe.** A subscriber lives in a module's `Integration.Consumers`, is named under the module's prefix and records its processed record in the module's context, so `notifications-notification-core` and `reporting-reporting-infrastructure`, whose scopes have building blocks subscribe to events, need a module that subscribes and calls them.
- **Nobody is told when a delivery fails** ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)). A dead-lettered delivery shows on the jobs page, under its subscriber's name and the key `event:<id>`, and in the server's journal; an event the relay cannot pass on shows only in the journal, at `Error`, and stays in the outbox, where retention never deletes it.
- **A module's first publication or subscription needs a migration of its own**, and a change to the configuration of either table needs one in every module that maps it.
- **An integration event is never a type argument as `IIntegrationEvent`** (CS8920): code that handles events in general works through `Type` or a type parameter constrained to the interface.
- **Earlier decisions this changes.**
  - [ADR-0059](0059-background-jobs-a-persistent-queue-leases-ist-schedules-and-the-nightly-account-check.md): work a module wants done only once its change commits is an integration event the module publishes and subscribes to itself, which answers its "until `business-building-blocks-transactional-outbox-and-integration-events` exists" (an accepted ADR is not edited, so the architecture document carries the rule); a payload that lacks a member or holds a null for one that cannot be null does not deserialise, so its run dead-letters with `job.payload-unreadable`; the poll also asks the run sources; and code outside the building block wakes the runner through `IJobRunnerSignal`.
  - [ADR-0043](0043-change-records-and-the-append-only-audit-schema.md): a module context also maps `OutboxMessage`, which is neither `IAuditable` nor `IAppendOnly`, and the `IAppendOnly` `ProcessedMessage`, besides `ChangeRecord`.
  - [ADR-0016](0016-application-pipeline-and-idempotency.md): the unit of work runs callbacks after its commit, and a command handler's assembly owns at most one catalogue context.
