# ADR-0050: The production database: Azure SQL Basic with Microsoft Entra-only users

Status: accepted
Date: 2026-10-19

## Context

- **What existed.**
  - Production uses Azure SQL with `Authentication="Active Directory Default"` and contained Microsoft Entra users, the API's with data roles and the migrator's with schema rights; the tier was left to the first deployment (ADR-0008).
  - The migrator runs as an identity of its own: `compose.production.yaml` gives the `migrator` service `MIGRATOR_AZURE_CLIENT_ID` and the file secret `erp-migrator-client.pem`, and `Erp:Platform:Database:MigratorConnectionString` replaces the API's connection string for it (ADR-0021).
  - The migration `AddChangeRecords` creates the role `erp_audit_append_only` and denies it `UPDATE`, `DELETE` and `ALTER` on the schema `audit`. The API's user joins it, so the running API may only insert there. The migrator needs `CREATE ROLE` and `CONTROL` on `audit`, never `db_owner`, and a user-defined role is visible only to holders of `ALTER ANY ROLE` and to its members, so the migrator should create the role itself (ADR-0043).
  - The logs of every ICT system stay in India for 180 days (CERT-In Directions of 28.04.2022, direction (iv); ADR-0038), and the home connection's public address changes (ADR-0048).
  - `scripts/azure` held one app registration per server identity only for the API (`ERP-AI-Pro Runtime (production)`), its certificate `Erp--Platform--Identity--RuntimeClientCertificate` in `kv-erp-ai-pro-prod` and exported by `export-runtime-certificate.sh`.
  - The runtime holds Key Vault Secrets User on the whole production vault, because it reads most of what the vault holds: the production sign-in certificate, the attachments key and the connection string.
  - `AppConfigurationSetup.Configure` selects every key of the unlabelled and the environment's label and resolves every Key Vault reference among them while the store loads, and `AddErpConfiguration` adds the store with `optional: false`, so a reference the host may not read stops it starting.
- **Owner decisions.**
  - 2026-10-18: Azure SQL at the Basic tier, chosen over SQL Server Express on the server and over the free offer. When the home's public address changes, the owner updates the firewall rule by hand; no updater.
  - 2026-10-19: the Azure changes are made behind a dry run; the Microsoft Entra admin's SQL runs through the Go sqlcmd signed in with the Azure CLI; no alert on the database's size.
  - 2026-10-19, after the review: the client certificates of the runtime and the migrator move to a third vault that only the operator reads, made new there and removed from the production vault, and the migrator reads only its two connection strings.
- **What the services document.**
  - A Basic database has 5 DTU, at most 2 GB, 30 concurrent workers and 300 sessions, on standard storage, and a restore may need a larger tier for the time it runs (Azure SQL, "Resource limits for single databases using the DTU purchasing model").
  - The Microsoft retail price list gives Basic in Central India ₹17.6716 a day (read 2026-10-19), about ₹540 a month.
  - "In the DTU model ... there's no extra charge for PITR backup storage for default retention of seven days"; Basic keeps 1 to 7 days. New databases store backups geo-redundantly, replicated to the paired region (Azure SQL, "Automated backups"), and Central India's pair is South India.
  - A deleted database is restored "to the deletion time, or an earlier point in time, on the same server", while deleting the server deletes "all of its databases and their PITR backups" (Azure SQL, "Restore a database from a backup"). In Azure SQL Database only the server-level principal or a member of `dbmanager` may `DROP DATABASE` (`DROP DATABASE`). The subscription feature `block-tsql-crud` blocks `CREATE DATABASE`, `DROP DATABASE` and `ALTER DATABASE` in T-SQL for every logical server of the subscription (Azure SQL, "How to block T-SQL CRUD").
  - Server-level IP firewall rules take up to five minutes to apply, and "Allow Azure services and resources to access this server" admits connections from any Azure resource, other customers' included (Azure SQL, "IP firewall rules"). A refused client gets error 40615, which names its address, and an admitted one reads its address from `sys.dm_exec_connections.client_net_address`.
  - The Microsoft Entra admin is "the only user who can initially create other Microsoft Entra users"; `CREATE USER [name] FROM EXTERNAL PROVIDER` resolves the display name, the SID of a service principal's user is its application (client) id, and `WITH OBJECT_ID` is "a troubleshooting repair item" for display names that repeat (Azure SQL, "Microsoft Entra service principals with Azure SQL" and its tutorial; `CREATE USER`).
  - The ODBC sqlcmd that SQL Server installs signs in to Microsoft Entra ID interactively only through a window of its own; the Go sqlcmd's `--authentication-method ActiveDirectoryAzCli` reuses the Azure CLI's sign-in ("Authenticate with Microsoft Entra ID in sqlcmd").
  - The `administrators` block of a server sets Entra-only authentication when the server is created; later updates of that property go through `servers/azureADOnlyAuthentications`. `isIPv6Enabled` turns the server's IPv6 support on or off (template reference `Microsoft.Sql/servers` 2025-01-01).
  - A `CanNotDelete` lock lets authorized users "read and modify a resource, but they can't delete it", and child resources inherit it (Azure Resource Manager, "Lock your resources").
  - Key Vault Secrets User reads "secret contents including secret portion of a certificate with private key". Microsoft recommends "a vault per application per environment ... with roles assigned at the key vault scope", and roles on individual secrets only where "individual secrets must be shared between multiple applications" (Key Vault, "Provide access to Key Vault keys, certificates, and secrets with Azure role-based access control").
  - The App Configuration provider's `Map` transforms each setting before the provider processes it; a Key Vault reference it rewrites into a plain value is never resolved (`AzureAppConfigurationOptions.Map`, proven by `AppConfigurationSetupTests`).
  - A deleted application registration stays restorable for 30 days, and restoring it in the Microsoft Entra admin center restores its service principal too (Microsoft Entra, "Deletion and recovery of applications FAQ" and "Restore a soft deleted enterprise application").

## Decision

- **The server and the database.** `scripts/azure/bicep/modules/sql-database.bicep`, deployed by `provision.sh` in the resource group's region, Central India:
  - the server `sql-erp-ai-pro` (`ERP_AZURE_SQL_SERVER_NAME`): Microsoft Entra-only authentication, set by `administrators` and converged by `azureADOnlyAuthentications/Default`; the operator who runs the script, a member user of the tenant, as its Microsoft Entra admin; TLS 1.2 at least; the public endpoint on and IPv6 off; a `CanNotDelete` lock `do-not-delete` on the server, which covers its database;
  - the database `ErpAiPro` (`ERP_AZURE_SQL_DATABASE_NAME`): Basic, 5 DTU, 2 GB, collation `SQL_Latin1_General_CP1_CI_AS`, geo-redundant backups (South India, still in India), 7 days of point-in-time restore;
  - `provision.sh` checks that a new server name is free before the what-if, and stops when the server's Microsoft Entra admin is not the signed-in operator, because the template's `administrators` block would hand the server to whoever deploys it.
- **The firewall.** The template creates no rule, so a deployment never resets the address. `database.sh` keeps the server's one rule, `home`, admitting one public IPv4 address:
  - `--allow-current-address`, run only from a computer on the home connection without a VPN: when the server answers, it reads this computer's address from `sys.dm_exec_connections`, and when the firewall refuses, from error 40615; `--allow-address <IPv4>` takes the address from the operator; a private, shared or reserved address is refused;
  - the rule is compared at both ends, so a rule widened to a range is narrowed, and moving it to another address is announced, because the server at home then reaches the database only if that is the home's address;
  - every mode of `database.sh` refuses to run, before it changes anything, while a server-level rule besides `home` exists, and its users script refuses a database-level rule (`sys.database_firewall_rules`); there is never a rule for Azure services or a range, and the lock keeps another rule until it is removed by hand;
  - a refusal of the address `home` already admits is waited out for the five minutes a rule takes to apply; a refusal of any other address fails at once;
  - the owner moves the rule when the home's address changes (`docs/operations/runbooks/database.md`).
- **The vaults.** `provision.sh` deploys a third vault, `kv-erp-ai-pro-ops` (`ERP_AZURE_KEYVAULT_OPS_NAME`), from the same `key-vault.bicep` as the other two (RBAC, soft delete, purge protection) without a data-protection key. Only the operator holds a role on it, Key Vault Secrets Officer and Certificates Officer, and no application ever reads it.
  - `entra.sh` keeps the client certificates of the server identities there: `Erp--Platform--Identity--RuntimeClientCertificate` and `Erp--Platform--Identity--MigratorClientCertificate`, self-signed PEM certificates of 12 months, each its registration's only credential. `export-client-certificate.sh <runtime|migrator>` downloads one for the server.
  - Why a vault of their own: the runtime reads the whole production vault, so a client certificate there would let a compromised API sign in as the migrator, whose user owns `audit` and `erp_audit_append_only` and could delete what ADR-0043 keeps append-only; the runtime's own certificate is of no use in a vault it can open only after signing in with it.
  - On 2026-10-19 the certificates of the first setup, made in the production vault, were replaced by new ones in the operations vault; the old key credentials were pruned and the old certificates deleted from the production vault, which keeps them recoverable for its 90 days of soft delete.
- **The migrator's identity.**
  - `entra.sh` converges `ERP-AI-Pro Migrator (production)` (`ERP_AZURE_APP_MIGRATOR_NAME`) like the runtime registration: single tenant, no redirect URI, no secret, its client certificate in the operations vault as its only credential.
  - `provision.sh` grants it App Configuration Data Reader on the store and Key Vault Secrets User on exactly the two secrets `Erp--Platform--Database--ConnectionString` and `Erp--Platform--Database--MigratorConnectionString` of the production vault, the runtime's vault, whose first secret the API reads too: role assignments at secret scope, the exception Microsoft documents for secrets shared between applications. It holds no role on the vault as a whole and no crypto role, because it never opens the key ring. The secrets it may read are `ERP_AZURE_MIGRATOR_SECRETS` (`scripts/azure/lib/common.sh`), a list of their own beside the connection strings `provision.sh` writes; a secret is granted on the run after the one that writes it, and `provision.sh` removes a Key Vault Secrets User the migrator holds on the whole production vault.
  - The migrator host passes `MigratorApplication.KeyVaultReferences`, the two connection-string keys, to `AddErpPlatform`. `AppConfigurationSetup.WithoutUnnamedReference`, applied through the provider's `Map`, loads every other Key Vault reference of the store as an empty value without contacting Key Vault, so the migrator starts with nothing else to read. The API passes no list and resolves every reference.
  - `--rotate-client-certificate <runtime|migrator>` and `--prune-old-credentials <local-dev|production|runtime|migrator>` serve both server identities.
- **The connection strings.** `provision.sh` writes `Server=tcp:<server host>,1433;Database=ErpAiPro;Authentication="Active Directory Default";Encrypt=True;TrustServerCertificate=False;Connect Timeout=30` into both `Erp--Platform--Database--ConnectionString` and `Erp--Platform--Database--MigratorConnectionString` of the production vault when they differ, through a file, since `az` under Git Bash runs through a batch file that would mangle the double quotes. The string holds no credential: each container signs in as the identity its environment names. `infra/appconfig/key-vault-references.json` references the first under both labels and the second under `production` only.
- **The users.** `database.sh` runs `scripts/azure/sql/database-users.sql` as the Microsoft Entra admin through the Go sqlcmd (`ERP_AZURE_SQLCMD`, else the one on `PATH`, else `C:\Program Files\SqlCmd`), with `--authentication-method ActiveDirectoryAzCli`:
  - before any change it refuses a database DDL trigger, which would run as the admin when the script's statements fire it, and a database-level firewall rule;
  - it creates each contained user `FROM EXTERNAL PROVIDER` by its registration's display name and refuses one whose type is not `E` or whose SID is not its app's client id;
  - the migrator's user gets `db_ddladmin`, `db_datareader`, `db_datawriter` and `CREATE ROLE`;
  - it refuses, and removes nothing itself, whenever the users hold more than that: the runtime's user in a role besides `db_datareader`, `db_datawriter` and `erp_audit_append_only`, holding a permission besides `CONNECT` or owning a role or a schema; the migrator's user in a role besides its three or holding a permission besides `CONNECT`, `CREATE ROLE` and `CONTROL` on `audit`; `db_owner`, `db_securityadmin` or `db_accessadmin` with a member besides `dbo`; `db_ddladmin` with a member besides the migrator's user;
  - the runtime's user gets no role until the migrations have created `audit` and `erp_audit_append_only`; then, in one run, `CONTROL` on `audit` for the migrator unless it owns the schema, the runtime's user into the role first and only then into `db_datareader` and `db_datawriter`, so it never writes to `audit` without the denial, and, under `EXECUTE AS USER`, the proof that the runtime's user may insert into `audit` and may not update, delete, alter, control or take ownership of it, alter `erp_audit_append_only`, any role or any user, control the database or impersonate the migrator's user or `dbo`, whether a right is its own or reaches it through `public` or a role (a right a role holds on itself is no right at all), and that the migrator's holds `CONTROL` on `audit` and `CREATE ROLE`;
  - `--dry-run` prints every change and still checks what exists.
- **The first migration.** The operator runs the migrator once from their computer as the migrator's own identity, with its exported certificate, so the migrator creates every schema and the role and owns them; then `database.sh` again. Later migrations run on the server (`docs/operations/runbooks/migrations.md`).
- **The checks.**
  - `verify.sh --database` reads back the server, its Microsoft Entra admin (`az sql server ad-admin list`), the firewall, the absence of a virtual network rule, a private endpoint and an IPv6 rule, the database, its restore policy, both secrets (without showing a differing value) and, through a dry run of the users script, the users and their rights.
  - The default run checks that the runtime and the migrator hold exactly their roles across the subscription, directly or through a group, and that only the operator holds a role on or in the operations vault and nobody else a Key Vault data role above it.
  - `--entra` checks that every registration signs in with its current certificate alone (no other key credential, no federated credential, no credential on its service principal) and that the production vault holds no client certificate. A key credential is identified by the SHA-1 of the certificate Microsoft Graph returns for it, which `entra.sh` uses too when it adds or prunes one, never by its `customKeyIdentifier`, which whoever adds a credential chooses.
- **No size alert** (owner decision of 2026-10-19). The database runbook measures the size against the 2 GB cap whenever the database is worked on.

## Options rejected

- **The free serverless offer.** A serverless database consumes compute while connected, and the API's pool, health checks and nightly work keep it connected, so the monthly free amount would run out within days.
- **SQL Server Express in a container on the server.** Recommended as cheaper and closer, and declined by the owner (2026-10-18). It would also go against the rule that no SQL Server container runs outside CI, so it would need a decision of its own; the database runbook keeps it as the fallback.
- **The rule "Allow Azure services".** It admits every Azure resource of every customer.
- **An automatic updater of the firewall rule.** Declined by the owner; Azure reports the new address, and the runbook moves the rule in one command.
- **The ODBC sqlcmd's interactive sign-in, and SQL pasted into the portal's query editor.** A window to complete on every run, or steps outside any script; the owner chose the Go sqlcmd.
- **`CREATE USER ... WITH OBJECT_ID`.** Meant for repeated display names; the SID check already tells a stale user apart.
- **A lock on the database alone.** Whether a lock on a child resource stops the deletion of its parent is undocumented, while a lock on the server covers both and still lets the firewall rule be updated.
- **Pre-creating `erp_audit_append_only` as the admin.** The migrator could then miss the role in its existence check (ADR-0043).
- **An alert at 80 % of the 2 GB.** Declined by the owner (about ₹9 a month).
- **The client certificates in the production vault**, as the first setup made them. The runtime could read the migrator's private key there.
- **Roles on single secrets for the runtime.** The runtime reads nearly every secret of its vault, which is the vault-scope case Microsoft recommends.
- **A vault for the migrator alone.** It would hold copies of the two connection strings, two homes for one value, for no secret the roles on the two secrets do not already keep from the migrator.
- **The connection strings as plain configuration values**, which would leave the migrator no Key Vault role at all. The production strings carry no credential, but a connection string can (the local containers' does), so the key keeps one shape, a Key Vault reference, in every environment.
- **Denying the runtime's user writes to the `__EFMigrationsHistory` tables** (a note of ADR-0043). A forged or deleted history row cannot change data or rights by itself: it makes the migrator skip or repeat a migration of its image. A repeated migration fails on the objects it finds and is rolled back, and a skipped one leaves the schema behind the model, which fails at the API's first use of it. A skipped migration that only tightens rights fails nothing, so every migration that changes the rights of a database user ships with its `EXECUTE AS USER` proof in `database-users.sql`, which `verify.sh --database` runs, as `AddChangeRecords` does. A denial would be one more step for each module's history table, while the runtime's user can already change every business row.

## Consequences

- The database costs ₹17.67 a day; backups within the 7 days add nothing.
- The data is capped at 2 GB and the work at 30 concurrent workers; a restore may need a larger tier while it runs, and moving up is one command (`docs/operations/runbooks/database.md`).
- Only the home's current public address reaches the database. When it changes, the API's readiness fails until the owner moves the rule, and error 40615 in the API's log names the new address. The firewall is the second gate: an internet provider may give one public address to many customers, so every connection also needs a token of a user the database knows.
- The lock stops the deletion of the server, which would take every backup with it, and of the database through Azure. It does not stop `DROP DATABASE` in T-SQL, which only the Microsoft Entra admin may run here and which no script issues; a dropped database is restored on the same server within the 7 days. `block-tsql-crud` would block that statement for every logical server of the subscription and is not registered.
- The operator is the only Microsoft Entra admin; a second admin, or a group as admin, needs a decision of its own. Changing the admin is deliberate (`az sql server ad-admin create`), and from then on `provision.sh` runs only for that admin.
- The users are created by display name and the resources by their parameter names. Renaming a registration (`ERP_AZURE_APP_RUNTIME_NAME`, `ERP_AZURE_APP_MIGRATOR_NAME`) after the database has users, or changing `ERP_AZURE_SQL_SERVER_NAME` or `ERP_AZURE_SQL_DATABASE_NAME`, creates a new registration or a new, empty server or database and points the connection strings at it; the names stay as they are.
- A deleted registration is restored, with its client id, from the Microsoft Entra recycle bin within 30 days (`docs/operations/runbooks/database.md`, "Recovery"). After that a new runtime registration gets a new user once the old one is dropped, while a new migrator registration cannot take over the schemas its predecessor's user owns without their permissions being reset, which needs a decision of its own.
- The client certificates leave the operations vault only through the operator's export for the server; a compromised API reads no certificate but the production sign-in certificate it signs people in with, and the migrator's certificate reads two secrets.
- The migrator's certificate reaches the server only together with the deployment's images, because from then on `erp-ai-pro-retain.timer` runs `retain` every night (ADR-0049).
- `database.sh` and `verify.sh --database` need the Go sqlcmd and a computer the firewall admits; the operator's computer and the server share the home's public address.
