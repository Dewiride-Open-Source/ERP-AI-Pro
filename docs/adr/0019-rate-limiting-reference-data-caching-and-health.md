# ADR-0019: Rate limiting, reference-data caching and health checks

Status: accepted
Date: 2026-09-26

## Context

The roadmap asks for a global per-IP limiter chained to a per-user sliding-window policy returning 429 with `Retry-After`, output caching restricted to tagged reference-data endpoints, and `/healthz/live` plus `/healthz/ready` covering SQL Server and App Configuration. ADR-0018 fixed the request pipeline order and reserved a place for the rate limiter ahead of authentication. Facts that shape the decision:

- ASP.NET Core's `RateLimitingMiddleware` evaluates one `GlobalLimiter` per request and skips every limiter for an endpoint carrying `DisableRateLimitingAttribute`. A partition keyed by the signed-in user can only see that user once authentication has run: `HttpContext.User` is empty before it.
- Dewiride's staff often share one office internet connection, so a limit per address that also applied to signed-in people would make colleagues share one allowance.
- In production the edge proxy routes `/api/*` straight to the API with the browser's address in `X-Forwarded-For`, but a page rendered by the web container calls the API as `http://api:8080` from the web container's own address. Next.js keeps an incoming `X-Forwarded-For` and sets it to the socket address only when it is absent.
- Every `/api` route is cookie-authenticated from the authentication phase, so a shared output cache would have to vary by user; the browser calls the API on the web origin, so an HTTP cache lifetime on a response is honoured by the browser.
- `HealthCheckRegistration.Timeout` defaults to infinite and `AddDbContextCheck` takes no timeout; against an unreachable SQL Server the readiness check waited for the full connect timeout (30 seconds in the test), longer than the container probe's 3-second client timeout. The App Configuration provider keeps the configuration it last loaded when the store is unreachable.
- `backend-platform-http-and-openapi-conventions` decided that the anonymous readiness endpoint names no check in its 503 problem.

## Decision

- **One global limiter, partitioned by who is calling.** `GlobalRateLimiter` (`BuildingBlocks.Endpoints/RateLimiting`) gives an anonymous request a fixed-window partition per client address (`address:<address>`; an IPv4-mapped address as IPv4, an IPv6 address by its /64 prefix so one client cannot mint partitions, no address as `unknown`) and a signed-in request (`IActorContext.IsAuthenticated`) a sliding-window partition per actor (`actor:<id>`) across every address. A signed-in person is never limited by address. This replaces the roadmap's chain of a per-IP limiter in front of a per-user limiter, which would have throttled an office as one caller. Queueing is off (`QueueLimit` 0). `Erp:Platform:RateLimiting:{Enabled, AnonymousPermitLimit, AnonymousWindow, ActorPermitLimit, ActorWindow, ActorSegmentsPerWindow}` bind `RateLimitingOptions`, validated at startup; `Enabled=false` sets no global limiter. No named policy is registered until an endpoint needs one (the authentication phase's sign-in endpoints).
- **Rejection.** 429 with `Retry-After` in whole seconds (at least 1) and a problem written through `IProblemDetailsService.TryWriteAsync`, so its code is the status default `rate-limit.exceeded`. The wait comes from the rejected lease's `RetryAfter` metadata when it has one (the fixed-window anonymous limiter reports the window); a rejected sliding-window lease in .NET 10 carries none (`SlidingWindowRateLimiter` returns a shared failed lease), so the actor limiter's segment length, `ActorWindow / ActorSegmentsPerWindow`, the earliest a permit can free up, stands in for it. Every module route group declares the 429 problem, so the generated client maps it.
- **Order.** `UseErpRateLimiting()` runs after `UseErpEndpointPipeline()` (forwarded headers, routing, request timeouts and database cancellation already ran) and before the feature gate and idempotency. Authentication, when it arrives, is called explicitly before the rate limiter, and authorization and antiforgery after it. This supersedes ADR-0018's placement of the rate limiter ahead of authentication.
- **The web app forwards the visitor's address.** `forwardedHeaders` (`frontend/apps/web/src/shared/api/forwarded-headers.ts`) sends the last `X-Forwarded-For` entry it received, the one the edge proxy appended, on every server-side API call. The API honours it only because the web container sits inside `Erp:Platform:Host:KnownNetworks`; the web container must stay reachable only through the edge proxy.
- **Health.** `AddErpHealthChecks` gives every check without its own timeout `HealthEndpoints.CheckTimeout` (2 seconds) through a `PostConfigure<HealthCheckServiceOptions>`, so every check is covered whether it was registered before `AddErpHealthChecks` (the per-context `database:<schema>` checks from `AddErpPlatform`) or after it (a check a host or test adds). The App Configuration check fails as `Degraded`, which keeps readiness at 200. The readiness report keeps its shape: a status word for healthy or degraded, and a 503 `service.unavailable` problem naming no check when unhealthy. The per-context database checks are the SQL Server check; no separate server-level check is added because every context shares one connection string. Both health endpoints carry `DisableRateLimiting()` and `DisableHttpMetrics()`.
- **No output caching.** `AddOutputCache` and `UseOutputCache` are not used. A GET endpoint that serves reference data identical for every caller opts in with `.WithReferenceDataCaching(maxAge)` (1 second to 1 day); `SecurityHeadersMiddleware` then answers its successful responses with `Cache-Control: private, max-age=<seconds>`, and every other response keeps `no-store`.
- **HybridCache on the server.** A new building block, `BuildingBlocks.Caching`, registers `HybridCache` (`Microsoft.Extensions.Caching.Hybrid` 10.10.0, MIT, dotnet/extensions) from `Erp:Platform:Caching:{DefaultExpiration, MaximumPayloadBytes}` for every host through `AddErpPlatform`, so the API, the test hosts and the migrator resolve the same services. No `IDistributedCache` is registered, so the cache lives in process only, which suits the single API process; handlers inject the abstract `HybridCache` from `Microsoft.Extensions.Caching.Abstractions`.

## Consequences

- Before the authentication phase every caller is anonymous, so only the per-address limit applies. Without `KnownNetworks` (local development) every caller is the loopback peer and shares one anonymous allowance; the browser suite made about 120 API calls in a 47-second run against the default 600 per minute. If the suite approaches the limit, raise `AnonymousPermitLimit` under the `local-dev` label.
- Limits, the enabled switch and the partitions are built once at startup; a changed setting takes effect at the next start.
- Partitioning by client address is exposed to address spoofing only where forwarded headers are trusted, which is limited to `KnownNetworks`.
- The first-deployment phase must have the edge proxy append the client address to `X-Forwarded-For` for requests it passes to both the API and the web container, and must list the compose network in `KnownNetworks`.
- A readiness answer arrives within about 2 seconds even when a dependency hangs, provided the check observes its cancellation token.
- Reference data may be marked for browser caching only when it contains nothing personal or caller-specific, because a private browser cache survives sign-out.
