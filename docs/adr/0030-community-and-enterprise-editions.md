# ADR-0030: Community and Enterprise editions, the LGPL-3.0-only licence and the contributor licence agreement

Status: accepted
Date: 2026-09-29

## Context

The repository was published under the MIT licence, which lets anyone take the code into a closed product without giving anything back. The owner decided on the model Odoo uses: an open-source edition that is a complete ERP core, and a paid edition that is that core plus proprietary modules. Odoo publishes its Community edition under LGPLv3 (its `LICENSE` file carries the LGPL text and, because the LGPL is a set of additional permissions on top of the GPL, the GPL text as well) and its Enterprise edition under a proprietary licence that allows use only with a valid subscription. Odoo accepts outside contributions only after a contributor licence agreement, signed by committing a file under `doc/cla/`.

The owner's decisions of 2026-09-29:

- This repository is the **Community edition**, licensed **LGPL-3.0-only**; the copyright holder is **Dewiride Technologies Private Limited**.
- The **Enterprise edition** is the Community core plus proprietary Enterprise modules, developed in the private repository **`Dewiride-Enterprise/ERP-AI-Pro-Enterprise`**.
- Outside contributors sign an Odoo-style **contributor licence agreement**; the owner and Dependabot are exempt.
- **One public roadmap** marks every sub-phase Community or Enterprise, and Claude recommends an edition and asks the owner before any sub-phase starts or is added.
- The **AI foundation** (the one `IChatClient` pipeline, the prompt library and tool registry, evaluation and safety) is Community; **every AI feature** is Enterprise. **Payroll** is Enterprise. The sign-in phase is Community.

Facts that shape the implementation:

- Git history holds only the owner's commits and Dependabot's, so no other author's consent is needed to relicense. Versions already published under MIT stay available under MIT to whoever obtained them.
- GitHub's licence detection (licensee) reports LGPL only when the root holds exactly the GPL text and the LGPL text, conventionally `COPYING` and `COPYING.LESSER` (GNU's "How to use GNU licenses" and choosealicense.com's LGPL-3.0 page); a third licence file makes it report "other".
- The FSF recommends a notice in every source file but does not require one; this repository's comment policy bans licence headers.
- Microsoft.OpenApi 2.12.0 (the version `Microsoft.AspNetCore.OpenApi` 10.0.12 resolves) has `OpenApiLicense.Identifier`, and OpenAPI 3.1 makes `identifier` and `url` mutually exclusive.
- `actions/dependency-review-action` v5.0.0 still accepts `deny-licenses` but its README marks it deprecated for removal; `allow-licenses` is the supported form. GitHub's dependency graph for this repository lists npm packages only as `pkg:npm/<name>@catalog:` without licences or transitive packages, so dependency review cannot see what the web workspace actually installs.
- The Harmony contributor agreements (HA-CLA-I, HA-CLA-E v1.0) are published for reuse under CC BY 3.0, and their outbound-licence "Option Five" lets the recipient license a contribution under any licence, including a proprietary one, on condition that it is also licensed under the licence the project uses. The Apache ICLA states no reuse terms and grants to the Apache Software Foundation with no outbound clause.

## Decision

- **Two editions, two repositories.** `Dewiride-Open-Source/ERP-AI-Pro` holds the Community edition. `Dewiride-Enterprise/ERP-AI-Pro-Enterprise` (private) holds the Enterprise modules and, from `business-building-blocks-enterprise-edition-composition`, the Enterprise hosts, which pin this repository as a git submodule and compose both module sets. The private repository is never made public, forked or mirrored, and nothing is copied from it into this repository. Its settings: private visibility; forking refused (the organisation forbids forks of private repositories); squash merges only, with the pull request title and body as the commit message, and head branches deleted after merge; no wiki or projects; Dependabot alerts and automated security fixes on; workflows get a read-only token and cannot approve pull requests; a ruleset on `main` refuses deletion and force pushes, requires linear history and a pull request, and allows only squash merges; `CODEOWNERS` assigns every path to the owner. Secret scanning with push protection and code scanning need GitHub's paid security licences for a private repository and are switched on by the owner.
- **The licence is stated once.** `COPYING` (GPL-3.0) and `COPYING.LESSER` (LGPL-3.0), verbatim from gnu.org, replace `LICENSE`, and no other licence file sits at the root. The README carries the copyright line (`Copyright (c) 2026 Dewiride Technologies Private Limited`) and the GNU notice for version 3 only; `backend/Directory.Build.props` sets `PackageLicenseExpression` `LGPL-3.0-only` and the legal name as `Authors`, `Company` and `Copyright`; every `package.json` declares `"license": "LGPL-3.0-only"`; the OpenAPI document's licence object is `name` "GNU Lesser General Public License v3.0 only" with `identifier` `LGPL-3.0-only` and no `url`. Source files carry no licence notice. "Version 3 only" keeps the choice of any later licence version with the copyright holder, which the contributor agreement already covers.
- **The Enterprise licence.** The private repository's `LICENSE` is the "ERP-AI-Pro Enterprise Edition Licence v1.0" of Dewiride Technologies Private Limited, written in its own words on the structure of Odoo's Enterprise licence: use for the licensee's own business only while a subscription or written agreement is valid; modifications for the licensee's own use; no publication, distribution, sublicensing or hosting for third parties unless the agreement allows it; the Community components stay under LGPL-3.0-only and nothing in it restricts the rights that licence grants; no warranty; limited liability; termination; the laws of India. It awaits review by a lawyer before the first customer.
- **The contributor licence agreement.** `docs/cla/individual-cla-1.0.md` and `docs/cla/corporate-cla-1.0.md` adapt the Harmony HA-CLA-I and HA-CLA-E v1.0 (CC BY 3.0, attributed in each file) with Dewiride Technologies Private Limited as the recipient, outbound Option Five naming LGPL-3.0-only, and Indian law with the courts of the company's registered office. A contributor signs by committing `docs/cla/individual/<lowercase-login>.md` or `docs/cla/corporate/<company-slug>.md` in the Odoo format described in `docs/cla/sign-cla.md`. The workflow `cla` (job "Contributor licence agreement") runs on `pull_request_target`: the workflow file comes from the default branch and `scripts/checks/cla.ts` and `docs/cla/exempt.json` from the pull request's base commit, while the pull request's commits and signature files are only read as git objects, never checked out or run. The commits checked are those of the head that are not on the base branch as it is when the check runs, each read on its own so that no byte of a commit message can hide a trailer; the signatures that cover them are those of the base branch as it is when the check runs, with the signature files the pull request adds or edits on top. Every commit author and `Co-authored-by` email must be covered: an exempt email counts as a commit author only in a pull request opened by an exempt login (the owner, or Dependabot, whose branches the owner adds adaptations to) and as a `Co-authored-by` address in every pull request (the trailer a review suggestion adds), and any other email only when a well-formed signature in the head lists it; a trailer that does not hold exactly one `<name> <email>` is reported whole as uncovered. A pull request opened by a login that is not exempt also fails unless a signature names that login (an individual signature's file name, or a corporate contributor line). An individual signature is added or edited only by its own login; a corporate signature is added only by the signatory it names and edited only by the signatory named on the base branch; an exempt login may add or edit any signature; no signature is deleted or renamed. A GitHub no-reply address must belong to the login on its line, and a company signatory's email counts in the exempt-email and duplicate-email checks. The individual agreement is signed only by a person at least eighteen years old. The agreements await review by a lawyer before the first outside contribution.
- **Dependency direction.** The Enterprise edition depends on the Community edition, never the reverse: nothing in this repository names, imports, stubs, feature-flags, hides or reserves room for Enterprise work. An extension point exists here only for a Community reason, with a Community implementation and test; a Community item that an Enterprise item builds on publishes the contracts, integration events or extension points that item needs.
- **Enterprise modules.** An Enterprise capability is its own module with the standard four projects, rooted at `Dewiride.Erp.Enterprise.Modules.<Domain>.<Module>`, referencing only Community `*.Contracts`, `BuildingBlocks.*` and Enterprise `*.Contracts`; its schema, route group, feature flag and permissions are unique across both editions. An Enterprise capability that extends a Community module is a companion module in the same domain; an AI capability is the companion `<Domain>/<Module>Ai` (for example `Finance/SalesAi`), so `Ai/` feature folders and the web's `ai/` folders exist only in Enterprise modules.
- **Placement.** Community is the platform and building blocks, identity and user management, master data, the books with their statutory documents and registers, timesheets, the projects core, HR core and recruitment, the procurement and assets core, notifications, generated documents, the integration framework and public API, operations and hardening, the installable web app, security, privacy (DPDP) and accessibility, and the AI foundation. Enterprise is every AI feature, payroll, the configurable workflow engine, filing packs and reconciliation workbenches, analytics, dashboards and forecasting, and connectors to outside services (government portals, banks, payment gateways, Microsoft 365, engineering tools, messaging channels). A security or privacy fix is never Enterprise-only. Anything not covered is recommended by analogy with the nearest decided item and confirmed by the owner.
- **Roadmap editions.** Every sub-phase carries `edition` (`community` or `enterprise`) and, once the owner has confirmed it, `editionConfirmedOn`. `node scripts/roadmap/roadmap.ts edition <community|enterprise> <id…> [--confirm]` records a recommendation or a confirmation (a phase id applies to all its sub-phases), `start` and `done` refuse a sub-phase whose edition is not confirmed, and `add-sub-phase` requires `--edition`. `depends-on <id…> --on a,b` replaces an item's dependencies, and the validator refuses Community work that depends on Enterprise-only work. A dependency is judged by the edition of the sub-phase that waits on it: a sub-phase dependency is met when that sub-phase is done; a phase dependency is met for Enterprise work when every sub-phase of that phase that is not deferred is done, and for Community work when its Community sub-phases that are not deferred are all done, so the Enterprise sub-phases of a Mixed phase never hold Community work back. `next` offers a planned sub-phase once its own and its phase's dependencies are met for its edition, the validator reports a done phase whose dependency is not met for the edition of any of its done sub-phases, and it refuses every dependency cycle, including one that runs through a phase and its own sub-phases (the graph gives each phase, per edition, a start node waiting for its dependencies and a done node waiting for the sub-phases that edition waits for). `ROADMAP.md` shows the edition of every phase (Community, Enterprise or Mixed) and sub-phase, marked "recommended" until confirmed. The owner confirmed the done phases and the sign-in phase on 2026-09-29; everything later carries Claude's recommendation. An Enterprise item's code and pull request live in the private repository, while its roadmap changes are committed here.
- **Reading roadmap scopes written before this decision.** Scope text cannot be edited, so a Community scope that names an Enterprise item is read through its "Edition split (ADR-0030)" note: a Community item publishes a contract or integration event that the Enterprise item consumes, and never names it in code. A Community scope that sends approvals "through `approvals-workflow`" means the Community minimal approvals building block, which stays the permanent Community approval path. A scope that names a `<Domain>/<Module>/Ai` folder means the Enterprise companion module `<Domain>/<Module>Ai`.
- **The composition work.** `business-building-blocks-edition-extension-points` (Community) makes the hosts, the API pipeline, the OpenAPI registration, the web navigation registry and the architecture and structure checks accept a module set assembled outside this repository, and puts the minimal approvals building block behind a replaceable approval-routing contract. `business-building-blocks-enterprise-edition-composition` (Enterprise) builds the private repository's solution, workspace, hosts, checks over both trees, OpenAPI snapshot, generated client and images, and moves production to the Enterprise images. Enterprise items whose phases would otherwise be eligible earlier depend on it.
- **Dependency licences.** Every dependency of either edition carries a licence on the allow list in `scripts/checks/lib/licence-policy.ts`: permissive licences, MPL-2.0, LGPL-2.1 and LGPL-3.0, OFL-1.1, and CC-BY-4.0 or CC0-1.0 for data. GPL, AGPL, SSPL, source-available and non-commercial licences are refused in both editions, because the Enterprise edition could not ship them. A package whose licence is not an SPDX expression is listed as reviewed only after its licence has been read, and the review pins the evidence that was read: the declared licence text of an npm package, the SHA-256 of the licence file inside a NuGet package, or the exact licence URL of a NuGet package that links outside licenses.nuget.org; a version whose evidence differs fails until its licence is read again. Dependency review reads the same list from `.github/dependency-review-config.yml` (by package name), and `scripts/checks/licences.ts` checks every installed npm package, every NuGet package in the restore graph of any project of the solution (the `libraries` of every `backend/artifacts/obj/*/project.assets.json`, test packages included) and every local tool of `backend/.config/dotnet-tools.json`, in CI and in `verify.ts`, because the dependency graph does not see the web workspace's packages and dependency review only notes a package without a licence. `System.Security.Cryptography.ProtectedData`, which `Microsoft.Identity.Client.Extensions.Msal` resolves to 4.5.0 (licensed by a corefx URL) in some graphs, is pinned centrally to its current MIT release.
- **Distribution obligations.** Publishing an image conveys LGPL-3.0-only object code, so `first-deployment-release-and-deploy-pipeline` puts the licence texts and a third-party notices file into both images, labels them `org.opencontainers.image.licenses=LGPL-3.0-only` with their source and revision, and names each release's tagged commit as the corresponding source. Running the images on Dewiride's own server conveys nothing.
- **Earlier decisions this changes.** ADR-0017: the OpenAPI document's licence is LGPL-3.0-only by SPDX identifier, without a URL. ADR-0009: an approved package must also carry a licence on the allow list. ADR-0002, ADR-0007 and ADR-0024: the `Ai/` and `ai/` folders they describe exist only in Enterprise modules. ADR-0012: every Enterprise AI capability keeps its own feature flag, now declared in its Enterprise module.

## Consequences

- A company may run, study, change and share the Community edition; a change to the Community code that it distributes must be shared under LGPL-3.0-only, while its own separate modules may stay closed. Hosting a changed copy as a service for others does not oblige it to publish the change.
- Dewiride can ship outside contributions in the Enterprise edition because the contributor agreement grants that right, while each contribution also stays available under LGPL-3.0-only. The agreements and the Enterprise licence are drafts adapted by the maintainers and are relied on only after a lawyer has reviewed them. Dewiride Technologies Private Limited must hold the copyright in the owner's own commits (through employment or a written assignment) to license them under the Enterprise terms.
- An outside pull request fails the "Contributor licence agreement" check until its authors sign; the owner adds that check to the ruleset's required checks once the workflow is on `main`, and requires Code Owners' review, with the Repository admin role as a bypass for pull requests only (an author cannot approve their own pull request), so that an outside pull request adding a workflow with a job of the same name waits for the owner. A `pull_request_target` workflow runs only from the default branch, so it does not run on the pull request that introduces it. A maintainer's own commit pushed into an outside contributor's pull request is not covered by the exemption (the maintainer opens a separate pull request instead), while a maintainer's `Co-authored-by` trailer is.
- Every sub-phase now needs the owner's confirmation of its edition before `start`. Enterprise work cannot begin before `business-building-blocks-enterprise-edition-composition`, and `hr-core` and `compliance` no longer wait for payroll. Every Community item whose scope touches Enterprise work carries an "Edition split (ADR-0030)" note that says which part is Community and which is built with the Enterprise item: the HR leave, attendance and exit feeds, generated documents, reimbursement settlement, recurring expenses, recruitment and requisition approvals, the approval bridges of reimbursements and timesheets, the scaffolders, the TDS, banking, procurement and compliance web items, the TDS receivable, the minimal approvals building block and its consumer migration, the payroll registers, and the recruitment screens. The notes on the timesheet billing feed, web push and recruitment's calendar scheduling leave the split to the owner when those items are planned.
- A new dependency whose licence is not on the allow list fails CI in either ecosystem, even as a development dependency; `Microsoft.Testing.Extensions.CodeCoverage` (Microsoft licence terms, test tooling that never ships) is listed as reviewed.
- `Microsoft.Identity.Client.NativeInterop` (the MSAL native runtime, `libmsalruntime.so` in the API image, brought in by `Microsoft.Data.SqlClient.Extensions.Azure` through `Microsoft.Identity.Client.Broker`) is under Microsoft Software License Terms whose section 3(e) forbids distributing it. It is listed as reviewed because running the image on Dewiride's own server conveys nothing, but no image that contains it may be published or given to a customer; `first-deployment-release-and-deploy-pipeline` removes it from the published images (or the dependency that brings it) before the first release.
- Adding any other licence file at the repository root makes GitHub report the licence as "other".
