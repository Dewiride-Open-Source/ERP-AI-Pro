# ADR-0061: A module scaffolder that registers what it writes, proven on every push

Status: accepted
Date: 2026-11-07

## Context

- **What existed.** Adding a module was a manual list in `docs/architecture/adding-a-module.md`: four projects and a README, the descriptor, the context and its first migration, the feature folders, then registrations in `Modules.All`, `backend/Dewiride.Erp.slnx`, a domain's solution filter, `docs/routing.md`, `docs/configuration.md`, the web registry and the domain's area, and the page objects and specs. It left out what a module also needs: the composition project's reference, the host lock files, the flag seed `infra/appconfig/feature-flags.json`, the gated Playwright pair and the OpenAPI contract with its generated client. The document promised "a scaffolder (`scripts/new-module`)" with the business building blocks phase. Several tests listed the modules by hand (`FeatureEndpointsTests`, `ConfigurationSourceTests` and the shell's Playwright specs for the sidebar, the page search, the start page and the employee's navigation), so every new module also meant editing tests that did not concern it.
- **The roadmap's scope** named a `dotnet new erp-module` template package (`templates/erp-module`) with folders the current anatomy no longer has (`Infrastructure`, a design-time factory, `Ai` in a Community module) and a separate `pnpm scaffold:feature` for the web half.
- **Two modules of one name.** The roadmap plans five `Core` modules (`Clients/Core` first, then `Vendors`, `Finance`, `Timesheets` and `Projects`). `Modules.cs` imported every module namespace, so two `CoreModule` classes would be ambiguous (CS0104), and `scripts/ef/lib/contexts.ts` keyed a context by its class name alone, so two `CoreDbContext` classes would make every `ef.ts` command throw.
- **Research (Microsoft Learn, read 2026-11-06).** "Custom templates for dotnet new", "Create a project template" and "Create a template package": a template is a folder with `.template.config/template.json`, installed with `dotnet new install` into each user's template registry, and "templates can run MSBuild tasks and arbitrary code during project creation"; a template renders files but edits no existing file.
- **Owner decisions.** 2026-11-06: a zero-dependency Node script in `scripts/` that also registers the module, not a `dotnet new` template. 2026-11-07: the generated slice lists, opens and adds one kind of record; GitHub proves the scaffolder on every push to `main`, never on a pull request (the repository is public, so the runner minutes cost nothing, and the proof finishes before the slowest Playwright shard). Later that day, declining a download of Playwright's Firefox to the owner's computer, the owner chose to have that proof also run the generated specs on Firefox.

## Decision

- **One command writes and registers a Community module.** `node scripts/scaffold/new-module.ts <Domain>/<Module> --entity <Entity> --title … --description … --read-permission … --create-permission …` (with `--entities`, `--singular`, `--plural`, `--area-title` for a new domain, `--icon` and `--files-only`) validates every input first and refuses, listing every problem and writing nothing (a clash that depends on a name once the name is well formed), a malformed or reserved name, a name the compiler or the build would misread, a planned file git ignores, prose holding a word the comment policy refuses, a module, schema, route, flag, context key or API model name already in use, a permission sentence or navigation title already used, a target file with uncommitted changes and a missing anchor. It then writes every file and registration in one change set, which restores the edited files and removes the created ones when a write fails, each on its own, naming any it could not put back, and runs the completion: `dotnet restore` (the host lock files), `dotnet format` over the C# it wrote, `ef.ts add Initial<Entities>`, `scripts/api-client/generate.ts` (the OpenAPI contract and the Kiota client) and Prettier over the web files. `--files-only` stops after writing and prints the commands that remain. It ends by printing the `git restore` and `git clean` lines that undo it and the owner-consented seed of the new flag.
- **The slice is real, small and rule-free.** One aggregate with one `Name` (required, trimmed, at most 100 characters), `IAuditable` and recorded under `<domain>.<module>.<entities>`; list (paged, sorted and filtered by name), get and create endpoints under two permissions whose one-sentence descriptions the owner approves before the command runs, held by administrators alone; a web module with a list, a record page with its change history and an add form behind the module flag; unit, integration and Playwright tests (gated and API-unavailable included). No edit, delete, uniqueness or soft delete: they differ between master data and financial documents, so each module adds its own.
- **Names the compiler would misread are refused.** The entity is refused when a namespace that a generated file naming it imports, implicitly or by a using directive, holds a public non-generic type of its name (CS0104), or when a generated type whose file names the entity declares a member, or a positional record parameter, of its name, which C# reads in the entity's place (CS0542 in the entity, CS0119 where a member access follows); the domain, the module and the plural become namespaces, so each is refused when it would hide a type of the implicit namespaces or of `Xunit` from the code beneath its parent (CS0234). The .NET types come from `scripts/scaffold/lib/dotnet-type-names.json`, which `scripts/scaffold/type-names.ts` writes from the documentation files of the SDK's reference packs and of the restored packages, for exactly the namespaces the templates import (a scaffold test refuses a template that imports one the file lacks); the building blocks' types are read from their sources on every run. A domain or module containing `Tests` is refused, because the architecture tests skip every assembly whose name holds `Tests` (`ErpAssemblies`) and `backend/build/Layers.props` makes a project whose name ends in it a test project; so is a domain, module or plural named `Bin`, `Obj` or `Migrations`, folders that git or the repository checks treat as generated.
- **Templates are the files they render.** `scripts/scaffold/templates/{backend,web/feature,web/routes,web/area,e2e,registrations}` hold `.tmpl` files that `renderTree` (`lib/templates.ts`) maps to their output roots, replacing a fixed vocabulary of tokens (`__Domain__`, `__module-kebab__`, `__entities_snake__`, `__Entity-words__`, `__Title__`, …) in paths and contents and refusing an unknown one. The comment policy reads a template as the language it renders and the folder cap counts its `.cs`, `.ts` and `.tsx` templates, so a template obeys the rules of the file it becomes.
- **Edits find an anchor or refuse.** Each registration is a pure function of the file's text that inserts the module's line after an anchor and refuses when the module is present or the anchor missing, keeping the file's line endings, byte order mark and path separators. A new domain also gets its solution filter (every project outside `Modules/` plus its own, the rule `Identity.slnf` now follows too), its row in `backend/solutions/README.md` and its area file.
- **Two modules of one name work.** `Modules.cs` reaches every module through one alias (`using ErpModules = Dewiride.Erp.Modules;`, entries `new ErpModules.<D>.<M>.<M>Module()`); a module context's key in `scripts/ef` is `<domain>-<module>` from its path and `dotnet ef` receives its fully qualified class name; a web module's navigation export is named after its feature. Schemas, routes, flags and API model names stay unique, and the command refuses a clash.
- **Nothing lists the modules by hand any more.** `FeatureEndpointsTests` and `ConfigurationSourceTests` derive the module flags and readiness checks from `Modules.All`, still exactly; the shell's Playwright specs build every expectation from the one list `registeredNavigation` of `frontend/e2e/fixtures/navigation.ts`, still asserting it whole, with an oracle of their own for the page search; the gated pair's flags come from `infra/appconfig/feature-flags.json`.
- **The proof.** `node scripts/scaffold/prove.ts` generates the throwaway module `ScaffoldProof/Jobs` (a new domain, multi-word, under a module name a building block already uses) in a worktree of HEAD beside the repository, naming the changes of the checkout it leaves out, and runs the scaffolder's tests, the registration audit over the generated module, the locked restore, the build with warnings as errors, the pending-model and format checks, the module's own tests and coverage gate (`coverage-gate.ts --module`), the architecture tests, the API host's OpenAPI, feature-list and readiness tests, the folder, comment and secret scans and the web lint, typecheck, unit tests, Prettier, build and feature boundaries; `--e2e` adds the generated specs, on Chromium unless `--all-projects` or `--project` names others, and refuses while another server holds Playwright's ports, which it would otherwise test instead. ci-backend's `Build, analyse and test` runs it in place with the generated specs on Firefox (`--in-place --e2e --project=firefox`, `--in-place` refused outside GitHub Actions, Firefox installed with its system packages first) on every push to `main`, after the job's own steps, so no job is added and the release gate's required list is unchanged; when the proof fails or is cut off, the job uploads the proof's own TRX and coverage files (`scaffold-proof-*`), the generated sources and Playwright's failure evidence; `verify.ts` and every ci-backend run add only the scaffolder's own tests.

## Options rejected

- **A `dotnet new` template package**, the scope's wording: it installs into each developer's and runner's template registry, runs arbitrary code at creation, and edits no existing file, so a script would still do every registration; one script does both.
- **Two entry points** (`new-module` and `pnpm scaffold:feature`): one half could ship without the other (root `CLAUDE.md` §3.7, ship the pair together).
- **A journal on disk for the rollback**: the originals stay in memory and the command refuses a target with uncommitted changes, so `git restore` and `git clean` always undo it whole.
- **Edit and delete in the slice**: an invoice must never be deleted while a master record may be, so the generator would invent a rule many modules must take back out.
- **Unique module names across domains**: five planned `Core` modules.
- **A separate proof job, path filters, or the proof inside `verify.ts`**: a job pays checkout, restore, SQL Server, Azurite and the build again and adds a release-gate entry; a path filter would miss the shared code the templates call; a local proof would add a quarter of an hour to every push and check Windows alone.

## Consequences

- A new module starts complete and registered, and a broken template shows on the push that broke it; ci-backend runs about 8 to 10 minutes longer on `main`, still shorter than the slowest Playwright shard.
- The generated Playwright specs ran on five projects in this item, Firefox aside, and run on Firefox in the proof on every push to `main`; a real module generated with them runs them on all six projects in the full matrix.
- Module context keys changed (`platform-system-info`, `identity-users`, …): `node scripts/ef/ef.ts list` shows them, and the migration guides use them.
- **Earlier decisions this changes.** [ADR-0021](0021-migrator-program-and-seeding.md) keyed every context by its kebab-case class name (`system-info`, `idempotency`); a module context is now keyed `<domain>-<module>`, a building block's as before, and `dotnet ef` receives the fully qualified class name. [ADR-0002](0002-modular-monolith-module-anatomy.md)'s manual steps for a new module become what the command automates.
- A template obeys the same rules as code, so a rule that changes for modules changes the templates in the same change; the proof refuses the push otherwise.
