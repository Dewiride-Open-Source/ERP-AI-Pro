# ADR-0031: Sign-in through Microsoft Entra ID in the API

Status: accepted
Date: 2026-09-29

## Context

ADR-0004 made the API the confidential OpenID Connect client of Microsoft Entra ID, with `AddMicrosoftIdentityWebApp`, callbacks under `/api/auth/`, a session cookie the browser holds and 401 ProblemDetails instead of redirects. Sub-phase `authentication-oidc-bff-in-the-api` builds that sign-in. The owner's decisions of 2026-09-29:

- The sub-phase is Community edition (ADR-0030).
- A session ends after 30 minutes without a request and 12 hours after sign-in, whatever happens in between.
- The platform routes that exist today (system information, attachments, the feature list) stay reachable without signing in until `authentication-web-login-page-and-session-integration` makes the web app sign people in; permission checks and permission-filtered navigation belong to `user-management-roles-and-permissions`.
- Every new setting lives in Azure App Configuration, never in a local file (`appsettings*.json`, `launchSettings.json`, user secrets or any git-ignored settings file). A run that cannot reach the store gets throwaway values generated for that run.
- The Entra and App Configuration changes of the scripts run only after a dry run, by the lead.

Facts that shape the design:

- The registrations have certificates only and no client secret (ADR-0010). Microsoft.Identity.Web hands the plain ASP.NET Core OpenID Connect handler a client secret and nothing else; a certificate reaches Entra only through its token acquisition, which redeems the code with MSAL's `AcquireTokenByAuthorizationCode(...).WithPkceCodeVerifier(...)` and a client assertion signed with the certificate (AzureAD/microsoft-identity-web at commit 2f227c6: `MicrosoftIdentityWebAppAuthenticationBuilder.cs`, `TokenAcquisition.cs`). Enabling it sets the response type to `code` and adds `offline_access` to the requested scopes.
- The registrations disable the implicit grant (`scripts/azure/lib/graph.sh`), so the handler default `ResponseType=id_token` cannot work. .NET 9 and later use pushed authorization when the discovery document advertises it; Entra's does not today.
- The browser reaches the API only through the web app's rewrite, and Next.js's rewrite proxy (`proxy-request.js` in `next`) sets `changeOrigin`, so the API sees `Host: localhost:5080` or `api:8080`; ADR-0018 ignores `X-Forwarded-Host`; and MSAL keeps the redirect URI built for the first request it served. A redirect URI built from the request would therefore name the API, not the origin the person opened.
- In .NET 10 the cookie handler answers an API endpoint's challenge with 401 or 403 but keeps the `Location` header, and still redirects for a request that matches no endpoint and for an endpoint that is not an API endpoint. The fallback authorization policy also applies to a request that matches no endpoint.
- `RedirectHttpResult.IsLocalUrl` refuses `//`, `/\` and control characters but accepts the virtual-path form `~/`.
- Microsoft.Identity.Web merges its client credentials once and caches the certificate it loaded, and binds every identity option once, so a changed certificate or identity setting reaches a running API only through a restart. Setting `EventsType` on the OpenID Connect options would bypass its event handlers; it chains the handlers set on `MicrosoftIdentityOptions.Events` into multicast delegates that await only the last task. It forces the name claim `preferred_username` for non-B2C sign-ins. `MsalMemoryTokenCacheOptions` in 4.15.0 has an absolute expiry only. Its sign-out hook removes the person's account from MSAL's token cache (`RemoveAccountAsync`), but a session cookie issued earlier stays valid unless the cookie handler looks the account up: Microsoft Learn's troubleshooting article "No account or login hint was passed to the AcquireTokenSilent" (solution 2, "Reject the authentication cookie") rejects a cookie whose account `GetAccountAsync` does not find; its `RejectSessionCookieWhenAccountNotInCacheEvents` is sample code, not a type of the 4.15.0 packages.
- The cookie handler renews a sliding cookie by default only once more than half of its lifetime has passed, so a person active 14 minutes after sign-in and idle for the next 17 would be signed out after a 30-minute idle timeout.
- Both Microsoft.Identity.Web and the OpenID Connect handler write the error description Entra returns, which can quote the person's account, into their own log records.
- Every challenge writes a correlation and a nonce cookie, so a page on another site that made the browser request the sign-in route again and again through images or frames could fill the person's cookies for this site. Browsers mark a page they open themselves with `Sec-Fetch-Mode: navigate` and `Sec-Fetch-Dest: document`.
- Packages, all MIT and the latest stable releases on nuget.org on 2026-09-29: `Microsoft.Identity.Web` 4.15.0 (with its `.TokenAcquisition`, `.TokenCache`, `.Certificate`, `.Certificateless` and `.Diagnostics` 4.15.0 and `Microsoft.Identity.Abstractions` 12.7.0); pinned centrally because transitive pinning is on and mixed versions of one family fail at run time: `Microsoft.Identity.Client`, `.Broker` and `.Extensions.Msal` 4.90.1, the `Microsoft.IdentityModel.*` family and `System.IdentityModel.Tokens.Jwt` 8.23.0, `Microsoft.AspNetCore.Authentication.OpenIdConnect` and `.JwtBearer` 10.0.12 (the shared framework's version).

## Decision

- **A building block, composed by the API only.** `Dewiride.Erp.BuildingBlocks.Authentication` (`backend/BuildingBlocks/Authentication`) holds the sign-in, because a module cannot own `/api/auth` (the descriptor naming rules would put its routes under `/api/identity/authentication`; `/api/platform/features` in `BuildingBlocks.Modules` is the precedent). `Program.cs` calls `builder.AddErpAuthentication()` and `app.MapErpAuthEndpoints()`; `ErpHostComposition.AddErpPlatform` does not, so the migrator and the test database host never compose it. `dotnet ef` builds the API host, which registers the building block, but never starts it, so the identity settings are neither read nor validated at design time and migrations need none of them. It has no schema and no feature flag, and it is the only product assembly that references `Microsoft.Identity.Web` (`LayerTests.MicrosoftIdentityWeb_IsReferencedOnlyByTheAuthenticationBuildingBlock`).
- **Two schemes; the cookie answers every challenge.** `AddAuthentication` makes `Cookies` the default, challenge, sign-in, sign-out and forbid scheme; `AddMicrosoftIdentityWebApp(_ => { }, cookieScheme: Cookies)` adds the `OpenIdConnect` scheme, which only `GET /api/auth/login` challenges and `POST /api/auth/logout` signs out. `SessionCookieEvents` answers the cookie handler's redirects with problems written through `IProblemDetailsService.TryWriteAsync` and no `Location`: 401 `request.unauthenticated` titled "Sign in to use this API." and 403 `request.forbidden` titled "The signed-in person may not do this."; a caller that accepts no JSON gets the status code pages plain-text body with the same status.
- **The certificate redeems the code.** `.EnableTokenAcquisitionToCallDownstreamApi()` with no scope and `.AddInMemoryTokenCaches()` make Microsoft.Identity.Web redeem the code through MSAL with the credential `CredentialSource.Base64Encoded` built from `Erp:Platform:Identity:ClientCertificate`, the Key Vault certificate; no client secret exists anywhere. Tokens are never saved in the cookie (`SaveTokens=false`); MSAL's in-memory cache keeps them for at most `SessionLifetime` (`MsalMemoryTokenCacheOptions.AbsoluteExpirationRelativeToNow`), until `authentication-token-cache-and-data-protection-key` moves them to SQL Server.
- **Handler settings.** `MicrosoftIdentityOptionsSetup` configures `MicrosoftIdentityOptions` for the `OpenIdConnect` scheme, which Microsoft.Identity.Web copies onto the handler options (the handler options are never configured directly): `Instance`, `TenantId`, `ClientId`, the credential above; `ResponseType=code`, `ResponseMode=form_post`, `UsePkce=true`, `PushedAuthorizationBehavior=Disable`, `SaveTokens=false`, `MapInboundClaims=false`, role claim `roles` (the name claim is `preferred_username`); the paths of `AuthPaths`: `CallbackPath` `/api/auth/signin-oidc`, `SignedOutCallbackPath` `/api/auth/signout-callback-oidc` and `SignedOutRedirectUri` `/login`; `RemoteSignOutPath` is empty (`PathString.Empty`). The correlation and nonce cookies are HttpOnly, Secure and `SameSite=None`, because Entra posts the callback from its own site. The event handlers are set on `MicrosoftIdentityOptions.Events` and complete synchronously (`SignInEvents`).
- **Redirect URIs come from `Erp:Platform:Identity:WebOrigin`, never from the request.** `SignInEvents` sets `redirect_uri` to `WebOrigin` + `/api/auth/signin-oidc` on every authorization request and `post_logout_redirect_uri` to `WebOrigin` + `/api/auth/signout-callback-oidc` on every end-session request, and `ConfidentialClientOptionsSetup` gives MSAL the same redirect URI, which Entra requires the redemption to repeat. Entra registers exactly the two callback paths on each origin (`REDIRECT_PATHS` in `graph.sh`, which `RedirectPathsTests` compares with `AuthPaths`).
- **No front-channel sign-out.** No registration sets a front-channel logout URL (`RedirectPathsTests.Registration_DeclaresNoFrontChannelLogoutUrl`: `graph.sh` never names `logoutUrl`), and the handler answers no remote sign-out path, because a path left to answer would let any site sign a person out by pointing the browser at it. `/api/auth/signout-oidc` is therefore an unknown path: 401 `request.unauthenticated` to an anonymous caller, 404 `resource.not-found` to a signed-in one, whose session stays (`LogoutEndpointTests.Get_RemoteSignOutPathOfTheHandlerWithASession_LeavesThePersonSignedIn`). Only `POST /api/auth/logout` signs a person out. A front-channel logout, which the scope of `authentication-web-login-page-and-session-integration` names, would register the logout URL and set the handler path in one change, by a decision of its own.
- **One settings section, every value in the store.** `EntraSignInOptions` binds `Erp:Platform:Identity` (not an `AzureAd` section) with `ValidateDataAnnotations`, `ValidateOnStart` and `EntraSignInOptionsValidator`:

  | Key | Default | Rule | Where the value lives |
  |---|---|---|---|
  | `TenantId` | — | a GUID written as 8-4-4-4-12 hexadecimal digits without braces (`Guid.TryParseExact` with format `D`), other than the empty GUID, so `common`, `organizations`, `consumers` and the braced, parenthesised and hyphenless forms are refused | per label, written by `entra.sh` |
  | `ClientId` | — | the same GUID form, other than the empty GUID | per label, written by `entra.sh` |
  | `Instance` | `https://login.microsoftonline.com/` | absolute https, path `/`, no query, fragment or user info | seeded unlabelled |
  | `WebOrigin` | — | an https origin (host and optional port); http only for `localhost` or `127.0.0.1` outside Production; the rule of `require_origin` in `graph.sh` | per label, written by `entra.sh` from `ERP_AZURE_LOCAL_WEB_ORIGIN` and `ERP_AZURE_PRODUCTION_WEB_ORIGIN` |
  | `ClientCertificate` | — | base64 PKCS#12 that opens without a password (`X509CertificateLoader.LoadPkcs12`, `EphemeralKeySet`), carries an RSA private key and is valid now by `TimeProvider` | Key Vault reference per label |
  | `SessionIdleTimeout` | `00:30:00` | 1 minute to 1 day | seeded unlabelled |
  | `SessionLifetime` | `12:00:00` | 1 minute to 7 days, and at least `SessionIdleTimeout` | seeded unlabelled |

  A missing or invalid value stops the API at startup with a message naming the setting (`IdentitySettingsStartupTests`). Every value is read once, when the API starts. Tests, CI, the local containers and the store-less API Playwright starts use throwaway values made for that run (Consequences).
- **The session.** The cookie `__Host-erp-session` is HttpOnly, always Secure, `SameSite=Lax`, path `/`, without `Domain` and without `Expires`, so it ends with the browser session; it lives `SessionIdleTimeout` and slides. `SessionCookieEvents.CheckSlidingExpiration` issues it again on the first request more than one minute after it was last issued, so a session ends only after `SessionIdleTimeout` without a request, at most a minute sooner. Signing in stamps the time from `TimeProvider` in the authentication property `erp.signed-in-at`, which sliding renewal keeps. On every request that carries the cookie, `ValidatePrincipal` rejects the cookie and signs it out (clearing it with an expiry in 1970, then 401 `request.unauthenticated`) once `SessionLifetime` has passed since that time, and also when the person's account is missing from MSAL's token cache: the account id `<uid>.<utid>` comes from Microsoft.Identity.Web's `GetMsalAccountId()`, the id its sign-out removes, and is looked up with `GetAccountAsync` on the confidential client application of the `OpenIdConnect` scheme (`IConfidentialClientApplicationProvider`), a cache read without any network call; a principal missing `uid` or `utid` is refused. Signing out therefore revokes every copy of the session cookie at once, and a restart of the API, which empties the in-memory cache, signs everyone out. The check does not call `GetAccessTokenForUserAsync`, which could refresh a token over the network on every request.
- **Endpoints.** The group `/api/auth` (tag `Auth`) documents 429, 500 and 504, which the rate limiter, the exception handler and the request timeout can answer there (the first challenge fetches Entra's discovery document under the request's timeout). `GET /api/auth/login` (`Auth.Login`, anonymous) binds the request record `LoginRequest`: `returnUrl` of at most 2048 characters that starts with `/`, passes `RedirectHttpResult.IsLocalUrl` and holds only visible ASCII (`!` to `~`), which also refuses `~/`; `/` when absent; otherwise 400 `request.invalid` with `errors.returnUrl`. A valid request is then refused when `Sec-Fetch-Mode` is present and not exactly `navigate`, or `Sec-Fetch-Dest` is present and not exactly `document` (case-sensitive, a single value each): 400 `request.invalid` with the `detail` "The sign-in starts only from a page the browser opens itself, never from an image, a frame or a script.", no `errors`, no `Location` and no cookie, for a signed-in caller too, so no other site can make the browser collect correlation and nonce cookies through an image, a frame or a script; a request carrying neither header (a script, `curl`, Playwright's request client) is served normally. A signed-in caller is redirected to the path; anyone else is challenged with it as the return address. `POST /api/auth/logout` (`Auth.Logout`) is protected by the fallback policy, so a cross-site post, which carries no Lax cookie, is refused with 401 before anything is signed out; for a signed-in caller the cookie is cleared, Microsoft.Identity.Web removes the account from the token cache, so every copy of that cookie is refused from then on, and the answer redirects to Entra's end-session endpoint, which returns through the signed-out callback to `/login`. A failed callback (declined consent, forged or missing state, a missing correlation cookie, a token or redemption failure) redirects to `/login?error=sign-in-failed` and logs the `SignInEvents` warning "A sign-in did not complete: {Failure} failure with OAuth error {OAuthError}" with only a failure category and an OAuth error code of the RFC 6749 grammar (`unrecognised` for any other value), never the error description, the query or the form; the sign-in page then shows a fixed message and never the query value. `AddErpAuthentication` adds two logging filters in code, `Microsoft.Identity.Web` at `Warning` and `Microsoft.AspNetCore.Authentication.OpenIdConnect.OpenIdConnectHandler` at `Critical`, so no log category records the error description either (`SignInCallbackTests.Post_FailedCallbacks_WriteNoErrorDescriptionEvenWhenConfigurationLogsEveryLevelOfTheIdentityLibraries` sets both categories to `Trace` in configuration). The filters are registered after the configured `Logging:LogLevel` rules, so they win over a configured rule for the same or a shorter category; a longer category or a `Logging:<Provider>:LogLevel` section would override them for that provider, so neither is ever configured for these libraries.
- **Authorization.** The fallback policy requires an authenticated user and names no scheme, so the test scheme and a later bearer scheme satisfy it. A route is anonymous only with `IAllowAnonymous` metadata: permanently the health routes, `/api/auth/login` and, in Development, the OpenAPI document and the Scalar reference; transitionally the ten platform routes (the two system-information routes, the seven attachment routes and `/api/platform/features`), until `authentication-web-login-page-and-session-integration`. `ModuleCatalogTests` fails on an anonymous route on neither list and on a list entry that is not a mapped anonymous route. An anonymous request that matches no route answers 401, a signed-in one 404; a wrong method answers 405 only to a signed-in caller.
- **Pipeline.** `UseForwardedHeaders → UseErpConfigurationRefresh → UseErpEndpointPipeline → UseAuthentication → UseErpRateLimiting → UseAuthorization → UseFeatureGate → UseErpIdempotency`, both calls explicit. The callbacks are answered inside `UseAuthentication`, before the rate limiter; `/api/auth/login` falls under the anonymous per-address limit; no named rate-limit policy exists for sign-in. `UseAntiforgery` belongs to `authentication-antiforgery-for-json-endpoints`.
- **Tests never reach Entra.** Every test host registers the scheme `Test` (`TestAuthHandler`) as the default authenticate scheme: a request carrying `X-Test-User` with the object id of a persona in `TestUsers` is that person, and any other request falls through to the real session cookie. Every test host also registers `TestTokenEndpoint` as MSAL's `IMsalHttpClientFactory` (Microsoft.Identity.Web's token acquisition takes a registered one before it adds its own): it answers instance discovery and the tenant's token endpoint, records every token request, redeems a code from `TestTokenEndpoint.CodeFor(user)` with tokens and `client_info` shaped like Entra's, refuses any other code with 400 `invalid_grant`, and fails any other request. `TestSignIn` redeems such a code through MSAL, which puts the person's account (`TestUser.AccountId`) in the token cache, and then mints the real cookie through the product scheme; `TestIdentityProvider` gives the handler a fixed discovery document, and `TestSignInCertificate` a self-signed certificate per test process. `SignInCallbackTests` proves the redemption request MSAL sends for a callback: `grant_type=authorization_code`, the posted code, the client id and no `client_secret`, a `code_verifier` whose S256 hash is the `code_challenge` of the authorize redirect, `redirect_uri` `WebOrigin` + `/api/auth/signin-oidc`, and a `client_assertion` of type `urn:ietf:params:oauth:client-assertion-type:jwt-bearer` signed with the sign-in certificate (`iss` and `sub` the client id, `aud` the token endpoint). `LayerTests.ProductAssemblies_NeverReferenceTheTestingLibrary` keeps the test scheme out of every product assembly, and `RequestRecordTests.RequestRecords_OfModulesAndBuildingBlocks_AreFound` extends the request-record rules to the building blocks, so `LoginRequest` is checked like a module's record. No Playwright spec performs an Entra round trip; a real sign-in is proven by hand, through `dotnet run` and `pnpm dev`, which read every setting from the store.
- **Earlier decisions this changes.** ADR-0004: token acquisition is enabled from the first sign-in, because it is the only path that redeems a code with a certificate, with an in-memory cache until `authentication-token-cache-and-data-protection-key`; the Playwright sign-in strategy is the one above, and the signed-in fixture belongs to `authentication-test-authentication-infrastructure`. ADR-0005: a change to the sign-in certificate, or to any other `Erp:Platform:Identity` value, reaches the API through a restart, not a sentinel bump. ADR-0018: authentication and authorization have their places in the order above; antiforgery keeps its reserved place. ADR-0019: the sign-in endpoints get no named rate-limit policy, and the transitional platform routes stay anonymous rather than cookie-authenticated. ADR-0022: a download link now works only for the signed-in person who created it, while anonymous callers of the transitional routes still share the anonymous actor; the attachment permissions are enforced by `user-management-roles-and-permissions`, not by this phase.

## Consequences

- Nothing about sign-in is configured on a developer machine: `dotnet run` reads every identity value from the store. A store-less API starts only with throwaway identity values in its environment and can never complete a Microsoft sign-in: `ErpApiFactory` injects fixed test ids, `https://erp.example.com` and a per-process certificate unless a test supplies its own; `e2e.yml` gives both API hosts the placeholder ids `11111111-1111-1111-1111-111111111111` and `22222222-2222-2222-2222-222222222222`, a certificate generated and masked in the job and their own web origin; `docker-build.yml` writes a generated certificate into the compose file secret; the local compose stack has the placeholder ids and `http://localhost:3000` in `compose.override.yaml` and a self-signed certificate in the git-ignored file secret `infra/compose/secrets/Erp__Platform__Identity__ClientCertificate`, made once with openssl and reused until it expires after 365 days, because it is test data that no registration knows and that never signs anyone in, not a setting; the gated API Playwright starts locally gets the placeholder ids, `http://localhost:3002` and a certificate that `throwawaySignInCertificate()` makes with openssl for the run.
- A completed callback cannot be automated, because it needs a code and a signed id token from Entra; the tests prove the redemption request and the session that follows it, and the owner's manual sign-in against the local-dev registration is the proof of the whole path, recorded in the pull request. The account check reads the `uid` and `utid` claims, which outside the tests (whose personas carry them by construction) come only from Entra's answer to a real sign-in, so it is proven by signing in again by hand. The Playwright check of the redirect to Microsoft first reads `GET /api/platform/system-info` through the web origin and runs only when its `applicationName` ends with ` (local-dev)`, which only the store's `local-dev` label sets; against any other API it is skipped, because a store-less API has the placeholder tenant and answers the challenge with a 500.
- A restart of the API signs everyone out while the token cache is in memory, every local `dotnet run` restart included; each person signs in again.
- Rotating the sign-in certificate is: new version, restart every API that reads it, sign in, prune the old credential ([secrets runbook](../operations/runbooks/secrets.md), section 5b).
- Re-running `entra.sh` adds `offline_access` to each sign-in registration's Graph permissions and re-issues the tenant-wide grant with four scopes, and writes `Erp:Platform:Identity:WebOrigin` per label.
- Every host test that calls a protected route signs in with `AsUser`, and a test endpoint mapped with `WithTestEndpoints` falls under the fallback policy unless it carries `.AllowAnonymous()`.
- Known limits, revisited by the named sub-phases: the token cache is in memory, so a restart empties it and every session ends with it, and the Data Protection key ring that protects the session, state, nonce and correlation cookies keeps the framework's default storage until `authentication-token-cache-and-data-protection-key` persists it and protects it with the Key Vault key; a cookie 401 carries no `WWW-Authenticate` header (`authentication-session-endpoints-openapi-security-and-bearer`); no `id_token_hint` is sent at logout, because tokens are not saved, so Entra may ask which account to sign out; the callbacks are not rate limited; the sign-in start refuses only what the browser marks as something other than a page it opens, so a browser that sends no fetch metadata headers is served like a script; whether WebKit keeps a Secure `__Host-` cookie over `http://localhost` is unverified (`authentication-test-authentication-infrastructure`); the certificate check loads the PKCS#12 with `EphemeralKeySet`, which macOS does not support, so the API does not start on macOS (it runs on Windows and in the Linux containers).
