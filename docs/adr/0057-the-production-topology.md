# ADR-0057: The production topology

Status: accepted
Date: 2026-10-31

## Context

The first deployment's decisions are spread over nine records, one per part ([ADR-0048](0048-the-edge-proxy-caddy-on-the-servers-local-address.md) to [ADR-0056](0056-the-servers-own-files-backed-up-nightly-sealed-to-an-operator-key-and-the-restore-drill.md)). The go-live puts them into use together, and this record states the whole as it runs, so a reader learns where each part lives, who reaches it, and what keeps it, without reading every record first.

## Decision

- **Where people reach it.** One server in the owner's home, bare metal Ubuntu LTS, wired, at an address the router reserves, reachable on the home network alone: there is no public name, the home's public address changes, and no port of the router is forwarded. People open `https://<address>`; every device trusts the proxy's own root once ([ADR-0048](0048-the-edge-proxy-caddy-on-the-servers-local-address.md), [ADR-0052](0052-the-edge-proxys-tls-policy-limits-timeouts-headers-and-access-log.md)). The proxy publishes 80 and 443 on IPv4 alone, so the server's global IPv6 address reaches no port ([ADR-0049](0049-the-production-host-a-deploy-account-keys-from-the-home-network-and-nightly-updates.md)).
- **What runs on the server.** Docker Compose with four services from the release's public images, run by digest: the one-shot `migrator`, `api`, `web` and the Caddy `proxy`, which alone publishes ports and sends `/api/*` to the api and everything else to the web server. The deploy account `erp-ai-pro` owns the deployment checkout and runs every compose command; `erp-ai-pro.service` brings the stack back at boot, `erp-ai-pro-retain.timer` runs the retention sweeps nightly, `erp-ai-pro-heal.timer` restarts a container that stays unhealthy, and `erp-ai-pro-backup.timer` seals the server's own files to Azure every night ([ADR-0049](0049-the-production-host-a-deploy-account-keys-from-the-home-network-and-nightly-updates.md), [ADR-0053](0053-the-release-public-images-a-dependabot-gate-attestations-verified-on-the-server-and-the-deployment-scripts.md), [ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md), [ADR-0056](0056-the-servers-own-files-backed-up-nightly-sealed-to-an-operator-key-and-the-restore-drill.md)).
- **What runs in Azure, all in Central India.**
  - App Configuration (Free), the one store with the `production` label, which the api reads at startup and every 30 minutes for its sentinel.
  - Key Vault: `kv-erp-ai-pro-prod` for the production secrets and the data-protection key, which the api reads; `kv-erp-ai-pro-ops` for the server identities' certificates and the backup encryption certificate, which only the operator reads ([ADR-0050](0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md)).
  - Azure SQL Basic `ErpAiPro` on `sql-erp-ai-pro`, Microsoft Entra-only, with its backups geo-redundant to South India: 7 days of point-in-time restore, weekly copies for 5 weeks and monthly copies for 12 months.
  - Blob Storage: `sterpaiproprod` for the attachments, which the api encrypts itself before they leave it ([ADR-0051](0051-the-production-attachments-storage-geo-redundant-and-reachable-from-the-homes-address-alone.md)), and `sterpaiprobackup` for the server's own sealed files, both geo-redundant to South India.
  - Microsoft Entra ID: the production sign-in registration, which people sign in through, and the server identities runtime (the api), migrator and backup, each with a certificate as its only credential.
- **Who reaches what.** The database's firewall and both storage accounts admit the home's public IPv4 address alone, and `home-address.sh` moves the three rules together when that address changes; nothing else reaches them, Azure's own services included. Each server identity holds only its own roles: the runtime the store, its secrets, the data-protection key and the attachments container; the migrator the database's two connection strings; the backup its one container ([ADR-0050](0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md), [ADR-0051](0051-the-production-attachments-storage-geo-redundant-and-reachable-from-the-homes-address-alone.md), [ADR-0056](0056-the-servers-own-files-backed-up-nightly-sealed-to-an-operator-key-and-the-restore-drill.md)).
- **The address.** The server's address is the host of `ERP_AZURE_PRODUCTION_WEB_ORIGIN` in the git-ignored `scripts/azure/params.env`, from which `entra.sh` writes the production registration's redirect URIs and front-channel logout URL, `Erp:Platform:Identity:WebOrigin` and `Erp:Platform:Host:AllowedHosts` (`<address>;api;127.0.0.1`) under the `production` label, and `ERP_SITE_ADDRESS` in the server's git-ignored `.env`, from which the proxy serves it. It is in no file of this repository.
- **How a release reaches it.** A tag on main's newest commit, refused while a check, a Dependabot alert or a Dependabot pull request is open, builds the three images once and attests them; `deploy.sh` on the server verifies each image's provenance and SBOM against that tag before it migrates and rolls the stack ([ADR-0053](0053-the-release-public-images-a-dependabot-gate-attestations-verified-on-the-server-and-the-deployment-scripts.md)).
- **How the server stays current.** Ubuntu's security and regular updates install every day, the GitHub CLI's with them, and the server restarts at 03:00 India time when one needs it (owner decision of 2026-10-31, which adds the regular updates to the security updates of [ADR-0049](0049-the-production-host-a-deploy-account-keys-from-the-home-network-and-nightly-updates.md)). Docker's packages stay a monthly step by hand, for the reason ADR-0049 gives: Docker's repository has no security pocket, so its minor releases would install unattended in the middle of the day ([host setup runbook](../operations/runbooks/host-setup.md), "Upkeep"). What runs inside the containers is kept current by each release ([ADR-0053](0053-the-release-public-images-a-dependabot-gate-attestations-verified-on-the-server-and-the-deployment-scripts.md)).
- **What nobody watches.** Nothing alerts anyone whether the server is up or failing, nor about a failed backup; the server's journal and the containers' logs hold what happened ([ADR-0055](0055-the-production-host-restarts-an-unhealthy-container-and-alerts-nobody.md)).
- **The go-live** follows the [go-live checklist](../operations/runbooks/go-live.md), which ends with the first restore rehearsal and the lock of the backups' write-once policy.

## Consequences

- **The ERP serves the home network alone.** A person away from home cannot reach it; a public name, through a tunnel or a forwarded port with Let's Encrypt, is a later decision that changes the proxy's certificate and the sign-in registration's addresses ([proxy runbook](../operations/runbooks/proxy.md), "Moving to a public name").
- **A change of the home's public address** stops the database and storage calls until `home-address.sh` runs ([home address runbook](../operations/runbooks/home-address.md)).
- **An outage of Central India** stops the ERP, because the store and the vaults live there; the data stays in India in both regions.
