# ADR-0036: Web sign-in, the session in the browser and single sign-out

Status: accepted
Date: 2026-10-08

## Context

- Until now the API locked only new routes: the system information, attachments and features routes stayed anonymous on `ModuleCatalogTests.TransitionalAnonymousRoutes`, and every page of the web app opened without a session (owner decision of 2026-09-29, ADR-0031). `authentication-web-login-page-and-session-integration` locks the pages and those routes together.
- The session cookie `__Host-erp-session` is HttpOnly and protected by the API's key ring (ADR-0032), so the web server can tell only whether the browser sent one; whether it still names a session only the API knows. Layouts do not render again on a client-side navigation, so a check in the `(app)` layout alone does not see a session that ended while the person moved between pages (Next.js 16, "Layouts and auth checks").
- The session slides: the API renews the cookie on the first request more than a minute after it was issued (`SessionCookieEvents.CheckSlidingExpiration`). The web server's calls carry the browser's cookie, so the API renews it for them, but the renewed `Set-Cookie` reaches the web server, never the browser. A person who only moves between server-rendered pages keeps a cookie that expires `SessionIdleTimeout` after the browser last received one.
- `GET /api/auth/session` and `POST /api/auth/session` exist for a page to watch the session and to renew it when the person chooses to stay (ADR-0034). The sign-out is a form the page posts with the request token in `__RequestVerificationToken`, filled when it is sent (ADR-0033).
- Microsoft Entra ID's end-session page asks which account to sign out of unless the request carries a `logout_hint`, the value of the ID token's optional claim `login_hint` (Microsoft identity platform, "Send a sign-out request"). Chrome checks every redirect a form submission follows against the page's `form-action`, and the sign-out's answer redirects to `login.microsoftonline.com`.
- Single sign-out: when a person signs out of any app of the tenant, Entra loads each other app's front-channel logout URL in a hidden cross-site iframe with the query parameters `iss` and `sid` (OpenID Connect Front-Channel Logout 1.0; MSAL.js, "Front-channel logout"). The SameSite=Lax session cookie never travels in that iframe. Entra accepts only an https front-channel logout URL, `https://localhost` included and `http://localhost` refused (Microsoft identity platform, "Validation differences by supported account types"), and the local-dev web origin is `http://localhost:3000`. ADR-0031 left front-channel sign-out to "a decision of its own".
- Owner decisions of 2026-10-08: single sign-out on, so a sign-out from another Microsoft app signs the person out of the ERP everywhere, as the ERP's own Sign out does; Microsoft's account question skipped; a start page at `/` that greets the person and shows a card per area.

## Decision

- **The routes lock.** The ten transitional endpoints lose `AllowAnonymous`; `TransitionalAnonymousRoutes` is deleted, and `PermanentAnonymousRoutes` gains `/api/auth/signout-oidc`. Every module route group and the features route declare 401 in the OpenAPI document. The compose smoke test, whose stack has no persona sign-in, expects 401 `request.unauthenticated` from them.
- **The pages lock: proxy.ts checks presence only.** A `GET` or `HEAD` of any page except `/login` without the session cookie answers 307 to `/login?returnUrl=<path and query>` (`signInRedirectFor` in `shared/auth/page-access.ts`; `/` goes to plain `/login`, and so does an address the API would refuse to return to); framework paths (`/_next/`, `/__nextjs`) and Server Function calls (a POST) pass. A `/login` address whose `returnUrl` the API would refuse loses that parameter and keeps the others (`loginAddressWithoutForeignReturn`). `localReturnPath` (`shared/auth/sign-in-addresses.ts`) is the rule of the API's `LoginRequest`: a path starting with `/` but not `//` or `/\`, visible ASCII only, at most 2048 characters, a repeated parameter counting as absent; a value that fails is dropped, never repaired. `proxy.ts` writes the page's path and query into the request header `x-erp-page-path`, replacing whatever the browser sent, for the redirects below.
- **The API decides, during the render.** `shared/auth/session.ts` (server-only): `readSession` (per request through React `cache`) reads `GET /api/auth/me` through `callApiAllowingSignedOut` and answers `signed-in` with the person, `signed-out` on a 401, `unavailable` on anything else; `requireSession` redirects a signed-out visitor to `/login?returnUrl=<x-erp-page-path>&reason=session-ended` and returns the rest, so a page whose API cannot be reached still shows what it can. It is the first statement of every Server Function (`createDownloadLink`, `deleteAttachment` and the design harnesses' functions) and runs on every full page load through the shell's `AccountArea`. `callApi` and `sendApi` (`shared/api/client.ts`) turn any 401 into the same redirect, the data-access check Next.js recommends, so a client-side navigation whose session ended goes to the sign-in page as well; `redirect()` throws, so every caller that catches API errors (`AttachmentsOverview`'s `Promise.allSettled`, `SystemInfoCard`, `RecentStartupsTable`, `getFeatureFlags`, the attachment Server Functions) passes it on with `unstable_rethrow`.
- **The sign-in page.** `LoginCard` sends a visitor whose session still holds straight to `returnUrl` (or `/`), asking the API only when the browser sent a session cookie. The sign-in link carries the validated `returnUrl`. `?error=sign-in-failed` keeps its alert; `?reason=session-ended` and `?reason=signed-out` show a polite status. On wide screens a panel beside the card states three facts about the ERP, entering one after the other with `animate-fade-up` and the motion tokens as delays.
- **The start page.** `/` is `app/(app)/page.tsx`, `StartPage` of the web-only module `features/platform/home`: "Welcome, <name>" and a card for every navigation entry whose module flag is on, each with the entry's new `description`; `app/page.tsx` is gone and structure rule S3 refuses a page at the root of `app/`. The wordmark and the not-found page lead home.
- **The shell shows the person.** `AccountArea` (`features/identity/auth`) renders the name ("Signed in as …", visible from `md`), `SignOutButton` and `SessionKeeper`; the `(app)` layout passes it to `AppShell` as `account`.
- **Sign-out.** `SignOutButton` posts a form to `/api/auth/logout` as a top-level navigation. When it is sent it reads `GET /api/auth/session` first: a session that already ended goes to `/login?reason=signed-out` instead of a refusal; otherwise it fills `__RequestVerificationToken` from `__Host-erp-xsrf`, fetching the pair again when the cookie is missing. The API sends `logout_hint` from the principal's `login_hint` claim (`SignInEvents.RedirectToIdentityProviderForSignOut`), and both the logout and the signed-out callback land on `/login?reason=signed-out` (`AuthPaths.SignedOutPage`). The web app's `form-action` names `https://login.microsoftonline.com`, the public cloud every registration uses.
- **The session in the browser.** `shared/api/session/session-watch.ts` reads (`GET`) and renews (`POST`, with `X-XSRF-TOKEN` and one renewal of the pair after an `antiforgery.*` refusal) `/api/auth/session` from the browser, the third kind of API request the browser sends itself after uploads and the antiforgery renewal, because only an answer the browser receives carries the renewed cookie. `sessionAnswer` turns an answer into the times on the API's clock and the offset to the browser's from the `Date` header. `SessionKeeper` renews on a page load, a navigation, a pointer press or a key press, at most once a minute (`renewalDue`); it reads the session again before warning and at the end, because another tab of the browser renews the same cookie; two minutes before the idle timeout it asks "Are you still there?" (Stay signed in, also Escape, or Sign out); five minutes before the lifetime ends, when renewing no longer helps, it says once "Your session ends soon"; once the API answers 401, it shows "Your session has ended", which cannot be dismissed, with Sign in again to `/api/auth/login?returnUrl=<this page>`. Both leads are minutes, well over the 20 seconds WCAG 2.2.1 asks for.
- **Single sign-out.** `GET /api/auth/signout-oidc?iss=&sid=` (`AuthEndpoints`, `Auth.FrontChannelSignOut`, anonymous, `FrontChannelSignOutRequest`, not in the OpenAPI document) ends the sessions of the person whose Entra session `sid` names. Every cookie sign-in records the principal's `sid` with its `iss` and MSAL account id (`EntraSessions`, key `entra-session:<sid>` in the distributed cache table, kept `SessionLifetime` plus five minutes), from `SessionCookieEvents.SigningIn`, which the cookie handler awaits; a record that cannot be written fails the sign-in. A request whose `sid` has a record with the same issuer revokes the person as the logout does (`SessionRevocations`, then the account in the token cache) and removes the record; any other request changes nothing; every well-formed request answers 200 with no body. A site that sends a browser there signs nobody out without the `sid`, which never leaves the API. The handler's own `RemoteSignOutPath` stays empty, because it could only sign out the cookie of the request. `entra.sh` sets `web.logoutUrl` to the web origin plus `/api/auth/signout-oidc` on a sign-in registration whose web origin is https, and none otherwise, and sets the optional claim `login_hint` on the ID tokens of both registrations (`scripts/azure/entra/optional-claims.json`).
- **Playwright.** `persona` defaults to `"accountant"`; `null` visits as nobody. `signIn` returns the person and their Entra session (`PersonaSignInResponse` adds `entraSessionId` and `issuer`). The origin without an API gets a session cookie no API would accept (`addUnverifiedSessionCookie`), enough for `proxy.ts`. `api` (`signedInApi`) sends the context's session to the API with the request token on every change.

## Earlier decisions this changes

- ADR-0031: the transitional anonymous routes are gone; the API answers a front-channel sign-out at `/api/auth/signout-oidc`, and the registrations of https origins name it; the sign-out lands on `/login?reason=signed-out` and carries `logout_hint`.
- ADR-0024: the root of `app/` holds no page (S3), and `shared/api/session/session-watch.ts` joins `shared/api/upload.ts` as browser code that calls the API.
- ADR-0033 and ADR-0034: the sign-out form and the session watch they describe now exist.
- ADR-0035: every spec signs in unless it opts out, and the origin without an API carries an unverified cookie.

## Consequences

- Every full page load costs the API one `GET /api/auth/me` and one `POST /api/auth/session` from the browser; an active person renews at most once a minute.
- Single sign-out works only where the web origin is https: in production once the first deployment sets the production web origin, never on the local-dev registration. Locally it is proven against the test identity provider, not against Entra.
- A session signed in before this change has no Entra session record, so a sign-out elsewhere cannot end it; it ends by itself within `SessionLifetime`.
- A visitor whose cookie the API refuses keeps it until the next sign-in replaces it, because a page render cannot change cookies; `proxy.ts` therefore lets such a visitor reach a page, whose render sends them to the sign-in page.
- `authentication-authenticated-application-shell` turns the account area into the user menu; `user-management-roles-and-permissions` filters the start page's cards with the navigation; `authentication-login-hardening` limits and audits the front-channel route with the other sign-in routes.
