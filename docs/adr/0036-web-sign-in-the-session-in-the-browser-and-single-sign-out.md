# ADR-0036: Web sign-in, the session in the browser and single sign-out

Status: accepted
Date: 2026-10-08

## Context

- Until now the API locked only new routes: the system information, attachments and features routes stayed anonymous on `ModuleCatalogTests.TransitionalAnonymousRoutes`, and every page of the web app opened without a session (owner decision of 2026-09-29, ADR-0031). `authentication-web-login-page-and-session-integration` locks the pages and those routes together.
- The session cookie `__Host-erp-session` is HttpOnly and protected by the API's key ring (ADR-0032), so the web server can tell only whether the browser sent one; whether it still names a session only the API knows. Layouts do not render again on a client-side navigation, so a check in the `(app)` layout alone does not see a session that ended while the person moved between pages (Next.js 16, "Layouts and auth checks").
- The session slides: the API renews the cookie on the first request more than a minute after it was issued (`SessionCookieEvents.CheckSlidingExpiration`). The web server's calls carry the browser's cookie, so the API renews it for them, but the renewed `Set-Cookie` reaches the web server, never the browser. A person who only moves between server-rendered pages keeps a cookie that expires `SessionIdleTimeout` after the browser last received one.
- `GET /api/auth/session` and `POST /api/auth/session` exist for a page to watch the session and to renew it when the person chooses to stay (ADR-0034). The sign-out is a form the page posts with the request token in `__RequestVerificationToken`, filled when it is sent (ADR-0033).
- Microsoft Entra ID's end-session page asks which account to sign out of unless the request carries a `logout_hint`, the value of the ID token's optional claim `login_hint`, and without the sign-out redirect "the user may remain authenticated" in that browser (Microsoft identity platform, "Send a sign-out request"). Chrome checks every redirect a form submission follows against the page's `form-action`, and the sign-out's answer redirects to `login.microsoftonline.com`; CSP Level 3 ignores a source expression's path once a request has been redirected (section 7.6, "Paths and Redirects").
- Single sign-out: when a person signs out of any app of the tenant, Entra loads each other app's front-channel logout URL in a hidden cross-site iframe with the query parameters `iss` and `sid` (OpenID Connect Front-Channel Logout 1.0; MSAL.js, "Front-channel logout"). The SameSite=Lax session cookie never travels in that iframe. Microsoft documents that the request carries `iss` and `sid`, not which of the tenant's two issuer forms (`https://login.microsoftonline.com/<tenant id>/v2.0` or `https://sts.windows.net/<tenant id>/`) it sends. The `sid` claim identifies the Entra sign-in session, and every token issued from that session, to any app, carries the same `sid` (Microsoft identity platform, "ID token claims reference" and "Linkable identifiers"; MSAL.js passes it between apps for single sign-on), so it is no secret: every app the person uses in that Entra session holds it. Entra accepts only an https front-channel logout URL, `https://localhost` included and `http://localhost` refused (Microsoft identity platform, "Validation differences by supported account types"), and the local-dev web origin is `http://localhost:3000`. ADR-0031 left front-channel sign-out to "a decision of its own".
- Owner decisions of 2026-10-08: single sign-out on, ending the ERP sessions of the Entra session the sign-out names (that browser), as Microsoft's own apps behave; Microsoft's account question skipped; a start page at `/` that greets the person and shows a card per area.

## Decision

- **The routes lock.** The ten transitional endpoints lose `AllowAnonymous`; `TransitionalAnonymousRoutes` is deleted, and `PermanentAnonymousRoutes` gains `GET /api/auth/signout-oidc` and `POST /api/auth/logout`. Every module route group and the features route declare 401 in the OpenAPI document. The compose smoke test, whose stack has no persona sign-in, expects 401 `request.unauthenticated` from the system information, attachments and features routes.
- **The pages lock: proxy.ts checks presence only.** A `GET` or `HEAD` of any page except `/login` without the session cookie answers 307 to `/login?returnUrl=<path and query>` (`signInRedirectFor` in `shared/auth/page-access.ts`; `/` goes to plain `/login`, and so does an address the API would refuse to return to); framework paths (`/_next/`, `/__nextjs`) and Server Function calls (a POST) pass, and the matcher leaves out `robots.txt` beside the static assets, so crawlers read its rules. A `/login` address whose `returnUrl` the API would refuse loses that parameter and keeps the others (`loginAddressWithoutForeignReturn`). `localReturnPath` (`shared/auth/sign-in-addresses.ts`) is the rule of the API's `LoginRequest`: a path starting with `/` but not `//` or `/\`, visible ASCII only, at most 2048 characters, a repeated parameter counting as absent; a value that fails is dropped, never repaired. `proxy.ts` writes the page's path and query into the request header `x-erp-page-path`, replacing whatever the browser sent, for the redirects below.
- **The API decides, during the render and in every Server Function.** `shared/auth/session.ts` (server-only): `readSession` (per request through React `cache`) reads `GET /api/auth/me` through `callApiAllowingSignedOut` and answers `signed-in` with the person, `signed-out` on a 401, `unavailable` on anything else. A render calls `requireSession`, which redirects a signed-out visitor to `/login?returnUrl=<x-erp-page-path>&reason=session-ended` and returns the rest, so a page whose API cannot be reached still shows what it can, every read it makes being refused without a session; it runs on every full page load through the shell's `AccountArea`. A Server Function changes something, so its first statement is `requireSignedInPerson`, which redirects alike and refuses the call when the session cannot be read (an outage, or an anonymous caller who exhausted its rate-limit partition, which the API would otherwise turn into a call for nobody); the forms kit and the list kit show the refusal as a failure. `pnpm lint` refuses a `"use server"` file whose exported functions do not start with `await requireSignedInPerson()` or that exports anything but function declarations and types. `callApi` and `sendApi` (`shared/api/client.ts`) turn any 401 into the same redirect, the data-access check Next.js recommends, so a client-side navigation whose session ended goes to the sign-in page as well; `redirect()` throws, so every caller that catches API errors (`AttachmentsOverview`'s `Promise.allSettled`, `SystemInfoCard`, `RecentStartupsTable`, `getFeatureFlags`, the attachment Server Functions) passes it on with `unstable_rethrow`.
- **The sign-in page.** `LoginCard` sends a visitor whose session still holds straight to `returnUrl` (or `/`), asking the API only when the browser sent a session cookie. The sign-in link carries the validated `returnUrl` and names the notice in `aria-describedby`, and the page title follows the state ("Sign-in failed", "Session ended", "Signed out", "Sign in"). `?error=sign-in-failed` keeps its alert; `?reason=session-ended` and `?reason=signed-out` show a status. On wide screens a panel beside the card, headed by its tagline, states three facts about the ERP, entering one after the other with `animate-fade-up` and the motion tokens as delays.
- **The start page.** `/` is `app/(app)/page.tsx`, `StartPage` of the web-only module `features/platform/home`: "Welcome, <name>" and a card for every navigation entry whose module flag is on, each with the entry's new `description`; `app/page.tsx` is gone and structure rule S3 refuses a page at the root of `app/`. The wordmark and the not-found page lead home.
- **The shell shows the person.** `AccountArea` (`features/identity/auth`) renders `SignOutButton` and `SessionKeeper` on every page of the `(app)` group, and the name ("Signed in as …", visible from `md`, truncated) when the session was read, so a page loaded while the API could not answer still keeps the session alive and offers Sign out; the `(app)` layout passes it to `AppShell` as `account`.
- **Sign-out.** `SignOutButton` posts a form to `/api/auth/logout` as a top-level navigation, filling `__RequestVerificationToken` from `__Host-erp-xsrf` when it is sent and fetching the pair first when the cookie is missing; it is a `SubmitButton`, so focus stays on it while the browser leaves. The route is anonymous too, because a page whose session already ended must still end the Microsoft sign-in of its browser, or the next person at a shared computer would be signed in as this one: a request the session cookie signs in records the sign-out (`SessionRevocations`), forgets the Entra session record of the sign-in and signs out both schemes, the end-session request carrying `logout_hint` from the principal's `login_hint` claim (`SignInEvents.RedirectToIdentityProviderForSignOut`); an anonymous request whose `Sec-Fetch-Site` is absent or `same-origin` signs out only the OpenID Connect scheme, so it touches no cookie and Entra asks which account to sign out; an anonymous request from another site answers 401 `request.unauthenticated`, as every route does without a session. Both the logout and the signed-out callback land on `/login?reason=signed-out` (`AuthPaths.SignedOutPage`). The web app's `form-action` is `'self' https://login.microsoftonline.com/common/oauth2/v2.0/logout`: the path lets no form of the page post to another Microsoft address, while the redirect to the tenant's end-session endpoint passes because a redirected request is matched on its origin only.
- **The session in the browser.** `shared/api/session/session-watch.ts` reads (`GET`) and renews (`POST`, with `X-XSRF-TOKEN` and one renewal of the pair after an `antiforgery.*` refusal) `/api/auth/session` from the browser, the third kind of API request the browser sends itself after uploads and the antiforgery renewal, because only an answer the browser receives carries the renewed cookie. `sessionAnswer` turns an answer into the times on the API's clock and the offset to the browser's from the `Date` header. `SessionKeeper` renews on a page load, a navigation, a pointer press or a key press, at most once a minute (`renewalDue`); its decisions live in the pure `session-keeper-state.ts`: one exchange at a time, a renewal asked for while a check runs sent right after it (making the check's answer stale), one next check (the warning time, the end plus a second, or 30 seconds after an answer that said nothing), and nothing once the keeper is gone. It reads the session again before warning and at the end, because another tab of the browser renews the same cookie; two minutes before the idle timeout it asks "Are you still there?" (Stay signed in, also Escape, or Sign out); five minutes before the lifetime ends, when renewing no longer helps, it says once "Your session ends soon", focusing the notice's text so a key press cannot dismiss it unread; closing either returns focus where it was. Once the API answers 401 it shows "Your session has ended", which cannot be dismissed, with Sign in again to `/api/auth/login?returnUrl=<this page>` and Sign out. The times are on the browser's clock in IST ("5:44 pm IST"). Both leads are minutes, well over the 20 seconds WCAG 2.2.1 asks for.
- **Single sign-out ends the sessions of one Entra session.** `GET /api/auth/signout-oidc?iss=&sid=` (`AuthEndpoints`, `Auth.FrontChannelSignOut`, anonymous, `FrontChannelSignOutRequest`, not in the OpenAPI document). Every cookie sign-in records the principal's MSAL account id under its `sid` (`EntraSessions`, key `entra-session:<sid>` in the distributed cache table, kept `SessionLifetime` plus five minutes) from `SessionCookieEvents.SigningIn`, and the session check refuses a cookie whose principal carries a `sid` without a record, or with a record of another account, between the sign-out record and the token cache entry. A request whose `iss` is the tenant's issuer in either form and whose `sid` has a record forgets that record (`FrontChannelSignOut`), so every session signed in from that Entra session is refused from then on, while the person's sessions from other Entra sessions, on other devices, stay signed in; any other request changes nothing; every well-formed request answers 200 with no body, unless the record cannot be read or forgotten (500). Both store calls run without the request's cancellation, so a frame Entra tears down mid-request still ends the session. Since the `sid` is no secret, a request naming one can end at most the sessions of that one Entra session and never signs anyone in; the logout forgets the record of its own sign-in, so a `sid` another app keeps ends nothing afterwards. Ending every session of the person, as the ERP's own Sign out does, was rejected: any app of the tenant could then sign a person out of the ERP everywhere, again and again. The handler's own `RemoteSignOutPath` stays empty, because it could only sign out the cookie of the request. `entra.sh` sets `web.logoutUrl` to the web origin plus `/api/auth/signout-oidc` on a sign-in registration whose web origin is https, and none otherwise, and sets the optional claim `login_hint` on the ID tokens of both registrations (`scripts/azure/entra/optional-claims.json`).
- **A sign-in that cannot start a session lands on the sign-in page.** The remote handler issues the cookie after its own failure handling, so a failure there, such as the Entra session record that cannot be written, would end in the exception handler on Entra's form post. `SignInEvents.TicketReceived` issues the cookie itself (Microsoft.Identity.Web chains it only after the event's default handler, which does nothing, so its task is the one awaited) and on a failure signs out again whatever the cookie handler wrote, logs the category `session` at `Error` with the exception (none of the store's, Data Protection's or the antiforgery tokens' exceptions names a token or the account) and redirects to `/login?error=sign-in-failed`; a callback the browser abandoned is left to the request pipeline.
- **Playwright.** `persona` defaults to `"accountant"`; `null` visits as nobody. `signIn` returns the person and their Entra session (`PersonaSignInResponse` adds `entraSessionId` and `issuer`). The origin without an API gets a session cookie no API would accept (`addUnverifiedSessionCookie`), enough for `proxy.ts`. `api` (`signedInApi`) sends the context's session to the API with the request token on every change. The `context` fixture aborts every request a page sends to `login.microsoftonline.com`; Chromium and Firefox route only the first request of a redirect, so a spec that starts a sign-in or a sign-out answers that first request itself with a document that moves on (Playwright cannot fulfil a redirect in WebKit), and no spec reaches Microsoft.
- **Earlier decisions this changes.**
  - ADR-0031: the transitional anonymous routes are gone; the API answers a front-channel sign-out at `/api/auth/signout-oidc`, and the registrations of https origins name it; the sign-out is anonymous-capable, lands on `/login?reason=signed-out` and carries `logout_hint`.
  - ADR-0024: the root of `app/` holds no page (S3), and `shared/api/session/session-watch.ts` joins `shared/api/upload.ts` as browser code that calls the API.
  - ADR-0033 and ADR-0034: the sign-out form and the session watch they describe now exist.
  - ADR-0035: every spec signs in unless it opts out, and the origin without an API carries an unverified cookie.

## Consequences

- Every full page load costs the API one `GET /api/auth/me` and one `POST /api/auth/session` from the browser; an active person renews at most once a minute. Every request the session cookie signs in reads one more row of the distributed cache table, the Entra session record, beside the sign-out record and the token cache entry.
- A person who signs out of another Microsoft app on one device stays signed in to the ERP on the others; the ERP's own Sign out still ends every session of the person.
- A Server Function called while the API cannot answer is refused rather than run, even one that would not have called the API.
- Single sign-out works only where the web origin is https: in production once the first deployment sets the production web origin, never on the local-dev registration. Locally it is proven against the test identity provider, not against Entra, and which issuer form Entra sends is confirmed by the first deployment's manual check.
- A session signed in before this change carries a `sid` without a record, so the session check refuses it once and the person signs in again.
- A visitor whose cookie the API refuses keeps it until the next sign-in replaces it, because a page render cannot change cookies; `proxy.ts` therefore lets such a visitor reach a page, whose render sends them to the sign-in page.
- `authentication-authenticated-application-shell` turns the account area into the user menu; `user-management-roles-and-permissions` filters the start page's cards with the navigation and re-checks permissions beside `requireSignedInPerson`; `authentication-login-hardening` limits and audits the front-channel and sign-out routes with the other sign-in routes.
