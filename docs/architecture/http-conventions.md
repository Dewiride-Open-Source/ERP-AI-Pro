# HTTP conventions

How every API route behaves on the wire, how its contract is published and how the web app consumes it. The decision and its reasons are in [ADR-0017](../adr/0017-http-conventions-openapi-snapshot-and-generated-client.md), extended for enums, paging parameters and files by [ADR-0022](../adr/0022-attachments-in-azure-blob-storage.md) and for sign-in and the session by [ADR-0031](../adr/0031-sign-in-through-entra-in-the-api.md); the middleware order, the body limit and the request timeout are in [request pipeline](request-pipeline.md).

## Correlation id

| Rule | Detail |
|---|---|
| Header | `X-Correlation-ID`, on every response of the API |
| Accepted from the caller | one value, at most 64 characters of `[A-Za-z0-9._-]` (`CorrelationId.IsWellFormed`) |
| Otherwise | the W3C trace id of the request activity (32 lowercase hex characters), else a version 7 GUID in `N` format |
| Where it appears | `ICorrelationIdFeature` on the `HttpContext`, the activity tag `erp.correlation_id`, the logger scope `CorrelationId` for the whole request, and `traceId` in every problem body |
| Proved by | `CorrelationIdMiddlewareTests`, `CorrelationIdTests` (host), `api-problems.spec.ts` |

## Problem details

Every non-2xx body is `application/problem+json` (RFC 9457), health endpoints included, and carries:

| Member | Value |
|---|---|
| `type` | `/problems/<code>` |
| `code` | the error's code (`Error.Code` for a failed `Result`) or the default of the status |
| `status` | the HTTP status |
| `title` | a human-readable summary; the generated client copies it into the thrown error's `message` |
| `instance` | the request path |
| `traceId` | the correlation id of the request |
| `errors` | validation problems only: member path (camelCase, grammar below) → messages |

The keys of `errors` follow one grammar: camelCase JSON member names joined by `.`, a collection element written as its zero-based index in brackets after its member (`gstin`, `customer.shippingAddress.street`, `orderItems[0].description`), and the empty key `""`. Which key a result gets is decided by the validator that produced it; the two validators place results as follows (keys as they reach the wire):

| Result | Built-in validation (`Microsoft.Extensions.Validation`, the endpoint filter that `AddValidation()` enables; it descends into nested objects and collection elements) | `ValidationStep` of the application pipeline (`Validator.TryValidateObject` over the top-level properties of a command or query; nested objects are not validated) |
|---|---|---|
| A property attribute | the property's path below the request record, which adds no prefix of its own (`customer.shippingAddress.street`, `orderItems[0].description`) | the property's name (`text`) |
| A class-level attribute or `IValidatableObject` result that names members | the path of the object the rule belongs to, then each named member (`customer.email`, `orderItems[1].quantity`) | each named member (`to`) |
| A class-level attribute result that names no member | the path of the object the attribute is declared on: `""` for the request record itself, `customer` for a nested object, `orderItems[1]` for a collection element | `""` |
| An `IValidatableObject` result that names no member | `""`, however deep the object that returned it | `""` |

Both validators check an object's class-level attributes only when none of its properties failed (the built-in validation counts every failure inside the object, nested ones included) and call its `IValidatableObject.Validate` only when those attributes passed too, so a rule about a whole object is reported only once everything inside it is valid. The built-in validation leaves `ValidationContext.MemberName` at the last property it validated, and `ValidationAttribute.IsValid(object?, ValidationContext)` names that member in the result of a class-level attribute that overrides only `bool IsValid(object?)`: such a rule on the object at `nested` is reported under `nested.nestedItems`, its last property. A class-level attribute therefore overrides `IsValid(object?, ValidationContext)` and returns its own `ValidationResult`. `ProblemDetailsTests` proves the built-in column on the wire, row by row, and `ValidationStepTests` the `ValidationStep` column.

Validation reports the CLR path of a member (`Customer.ShippingAddress.Street`, `OrderItems[0].Description`) and the serializer's `DictionaryKeyPolicy` would convert only the start of the key, so `ProblemDetailsCustomizer` rewrites every key of every `HttpValidationProblemDetails`, from the built-in validation filter and from `ResultExtensions.ToProblem` alike: each member name is converted with `JsonNamingPolicy.CamelCase`, the policy of the JSON body (`GSTIN` → `gstin`, `IFSCCode` → `ifscCode`, `BankAccount.IFSCCode` → `bankAccount.ifscCode`), indices stay as they are, a problem whose keys are all in the grammar is left untouched, keys that meet after conversion keep every message, and the keys keep the order validation reported them in. The rewrite makes one ordinal hash lookup per key, so its cost grows in proportion to the number of keys, which a body failing once per collection element can push to hundreds of thousands (`ProblemDetailsCustomizerTests`, including 100,000 keys converted within a 5-second timeout, and `ProblemDetailsTests` on the wire). The web app turns a key into a form field path with `apiKeyToFormPath` in `frontend/apps/web/src/shared/forms/errors/field-paths.ts` (`orderItems[0].description` → `orderItems.0.description`, the object key `orderItems[1]` → `orderItems.1`) and shows the messages of `""` in the form's error summary.

Default codes, used when nothing more specific was set: `request.invalid` (400), `request.unauthenticated` (401), `request.forbidden` (403), `resource.not-found` (404), `request.method-not-allowed` (405), `request.too-large` (413), `request.unsupported-media-type` (415), `rate-limit.exceeded` (429), `service.unavailable` (503), `request.timeout` (504), `request.rejected` (any other 4xx) and `server.error` (any other 5xx). Codes raised by the platform: `request.host-not-allowed` (a `Host` outside `Erp:Platform:Host:AllowedHosts`), `request.malformed` (a value the binder cannot read, such as `?take=many` or a body that is not JSON; `RouteHandlerOptions.ThrowOnBadRequest` is on in every environment so these always reach `GlobalExceptionHandler`), `feature.disabled` (the module's flag is off), `antiforgery.token-missing` and `antiforgery.token-invalid` (400, a request that changes data with the session cookie and carries no valid antiforgery token; section "Antiforgery"), `idempotency.*` and `query.*` (see [application pipeline](application-pipeline.md)). A failing readiness check answers 503 `service.unavailable` and names no check, because `/healthz/ready` is anonymous; a healthy or degraded report stays a plain-text status word. A request without a valid session to a route that is not anonymous answers 401 `request.unauthenticated` with the title "Sign in to use this API.", and so does an anonymous request to a path no route matches or with a method the route does not allow, because the fallback policy also applies when routing found no endpoint or only the framework's method-mismatch endpoint, which carries no `AllowAnonymous`; a signed-in request to such a path answers 404 `resource.not-found` or 405 `request.method-not-allowed`. A signed-in request a policy refuses answers 403 `request.forbidden` with the title "The caller may not do this.". Neither refusal carries `Location`; on a route that takes bearer tokens both carry `WWW-Authenticate` while `Erp.Platform.Identity.BearerTokens` is on (section "Bearer tokens"), and on every other route neither does, because the session cookie is no HTTP authentication scheme (section "Sign-in and the session"). Platform problems are written with `IProblemDetailsService.TryWriteAsync`, so a caller whose `Accept` header admits no JSON keeps the status and receives the status code pages plain-text body instead of a 500.

A replayed idempotent response (`Idempotency-Replayed: true`) carries the stored body with its `traceId` rewritten to the replay's correlation id; the log line `Replayed the stored problem of request <original> as request <replay>` links the two. A module's own codes are `<aggregate>.<reason>` in kebab case, for example `invoice.already-issued`.

A failed `Result` takes its status from the error's `ErrorKind` (`ResultExtensions.ToProblem`): `Validation` 400, `Forbidden` 403, `NotFound` 404, `Conflict` 409, `TooLarge` 413, `UnsupportedType` 415, `Failure` 422, `Unavailable` 503. `Unavailable` (`Error.Unavailable`) is a dependency that cannot answer now, such as `directory.unavailable` when Microsoft Graph cannot be reached ([ADR-0040](../adr/0040-directory-invitations.md)). `TooLarge` and `UnsupportedType` (`Error.TooLarge`, `Error.UnsupportedType`) exist for content a handler refuses after reading it, such as `attachment.too-large` for a file over the configured limit, `attachment.extension-mismatch` for a file name whose extension contradicts the declared type and `attachment.content-mismatch` for bytes that contradict it; the transport's own refusals keep the default codes `request.too-large` and `request.unsupported-media-type`.

An update of a record carries the `version` the API last returned for it (the base64 of its row version), and answers 409 `concurrency.conflict` when the record changed since; so does a save that a unique index refuses because another request saved the same value at the same moment (`EfUnitOfWork`, [application pipeline](application-pipeline.md)). A version the API never issued answers 400 with the module's own code, such as `user.version-invalid` ([ADR-0039](../adr/0039-people-and-their-admission.md)).

## JSON on the wire

`AddErpEndpoints` configures `HttpJsonOptions` once for every endpoint, and the OpenAPI document describes exactly that shape:

| Rule | Setting | Effect |
|---|---|---|
| Numbers are JSON numbers | `NumberHandling = JsonNumberHandling.Strict` | `"5"` is refused where `5` is expected, so every member has one type in the document |
| Dictionary keys are camelCase | `DictionaryKeyPolicy = JsonNamingPolicy.CamelCase` | the policy converts the start of each key only; the keys of a validation problem's `errors` are already camelCase member paths when it runs, because `ProblemDetailsCustomizer` converts every member name of the key (section "Problem details") |
| Enums are camelCase names | `JsonStringEnumConverter(JsonNamingPolicy.CamelCase, allowIntegerValues: false)` | `AttachmentScanStatus.NotScanned` travels as `"notScanned"`; a number is refused on input. The document declares `enum: ["notScanned", "clean"]`, and the generated client exposes the names as the constant object `AttachmentScanStatusObject`, so the web app compares names, never numbers. Renaming an enum member is therefore a wire change and updates the web app in the same change |

## Request records and validation

A route that takes input binds it to a public request record and lets the built-in validation reject it before the handler runs:

```csharp
namespace Dewiride.Erp.Modules.Platform.SystemInfo.Startups.Endpoints.Requests;

public sealed record ListRecentStartupsRequest(
    [property: FromQuery(Name = "take")]
    [property: Description("How many starts to return, between 1 and 100; 20 when the caller does not ask.")]
    [property: Range(ListRecentStartupsQuery.MinimumCount, ListRecentStartupsQuery.MaximumCount)]
    int? Take);
```

- The record is `public sealed` and lives in `<Feature>/Endpoints/Requests/`; the validation generator skips non-public types without a warning.
- Every attribute uses the `property:` target. `FromQuery(Name = …)` gives the camelCase wire name, `Description` gives the text the OpenAPI document shows, the DataAnnotations attributes (or `IValidatableObject`) give the rules, and the document derives `minimum`, `maximum`, `maxLength`, `pattern` and `required` from them.
- Query values the handler treats as optional are nullable (`int?`), and the default is applied in code; a non-nullable value type would make the parameter mandatory.
- The module's `AddServices` calls `builder.Services.AddValidation()`; without that call the module's records are silently not validated. `RequestRecordTests` fails the build in that case.
- The endpoint takes the record with `[AsParameters]` for query strings or as the body parameter, and never re-validates it.

A list endpoint takes the shared request record `PagingParameters` (`BuildingBlocks.Endpoints/Paging`) with `[AsParameters]`. Its members carry the same attributes, so every paged route documents the same four query parameters: `page` ("Page number, from 1; the first page when absent."), `pageSize` ("Items per page, from 1 to 200; 50 when absent."), `sort` (comma-separated `field:asc` or `field:desc` terms over the endpoint's allow-list) and `filter` (semicolon-separated `field:operator:value` terms, values percent-encoded, an `in` list separated by `|`). `ToListRequest()` parses them and the handler resolves them against its allow-lists; the grammar and the `query.*` codes are in [application pipeline](application-pipeline.md). The answer is `PagedResponse<T>`: `{ items, page, pageSize, totalCount, totalPages }`.

## Files on the wire

Uploads and downloads are the two routes that do not exchange JSON; both belong to `Platform/Attachments` ([attachments](attachments.md)).

| | Upload: `POST /api/platform/attachments` | Download: `GET /api/platform/attachments/{id}/content?link=` |
|---|---|---|
| Body | `multipart/form-data`; the first part with a file name is the file, read as it arrives with `MultipartReader` over `Request.Body`; the endpoint never binds `IFormFile` and never buffers the file | the decrypted file, streamed with `TypedResults.Stream` |
| Headers | any `Content-Type` other than `multipart/form-data` with a boundary of at most 70 characters answers 415 `attachment.multipart-required`; signed in with the session cookie, `X-XSRF-TOKEN`, without which the upload is refused before its body is read (section "Antiforgery") | the stored content type, `Content-Disposition: attachment` with `filename` and `filename*` (UTF-8), `Content-Length` set explicitly from the recorded size because the decrypting stream cannot seek; no `Accept-Ranges` and no range requests |
| Limits | body `MaxSizeBytes` + 64 KiB through the endpoint's `IRequestSizeLimitMetadata` ([request pipeline](request-pipeline.md), "Transport limits"); timeout policy `platform.attachments.transfer`; rate-limiter policy `platform.attachments.uploads`, at most `MaxConcurrentUploads` uploads in flight per process ([request pipeline](request-pipeline.md), "Rate limits") | timeout policy `platform.attachments.transfer` |
| Answer | 201 with `Location` and the attachment; 400, 413, 415 and 422 problems (`attachment.*`, including 415 `attachment.extension-mismatch` for a file name without an extension of the declared type, plus 413 `request.too-large` when the body passes the endpoint's limit); 429 `rate-limit.exceeded` with `Retry-After` when the concurrency cap is reached | 200, or 404 `attachment.not-found` for every refusal after request validation; a missing or over-long `link` is the 400 validation problem `request.invalid` of the request record `RedeemDownloadLinkRequest` |
| Idempotency | no `Idempotency-Key` (ADR-0022) | a GET, handled by the command `RedeemDownloadLinkCommand` because it records a redemption |
| Document | an operation transformer declares the `multipart/form-data` request body (an object with the required binary member `file`); `ProducesProblem` adds 413, 415, 422 and 429 | `Produces<Stream>(200, "application/octet-stream")` |
| Web app | `uploadFile` in `frontend/apps/web/src/shared/api/upload.ts` posts a `FormData` with `XMLHttpRequest` from the browser to `/api` on the web origin, with `X-XSRF-TOKEN` from the cookie `__Host-erp-xsrf` (section "Antiforgery"), for progress and so no Server Function holds the file in the web server's memory (`next dev` and `next start` still hold the proxied body in memory up to `experimental.proxyClientMaxBodySize`, `"101mb"`, and the image's standalone server up to the 10 MB default; in production the edge proxy sends `/api/*` straight to the API); errors become `ApiError` through `problemFromBody` | the row opens the path that `POST …/download-links` returned (Server Function `createDownloadLink`) through a temporary same-origin `<a download>`, a same-origin request to `/api` that carries the person's session cookie, so a link opens only for the signed-in person who created it; the browser saves the file without leaving the page, and a refused redemption never replaces the page with the problem body |

A link that must be followed by a browser (a download) is a path the API builds with `LinkGenerator.GetPathByName` from a named route (`.WithName(…)`), never a string the handler assembles, so a path base or a route change cannot break it. A secret in a query string, like the download token, is safe from telemetry only because the ASP.NET Core instrumentation redacts query values and the framework's request lines (`Microsoft.AspNetCore.Hosting.Diagnostics`) stay at `Warning` ([observability](../guides/observability.md)); it still reaches browser history and any access log that records query strings, so such a token is single-purpose, short-lived and bound to the actor.

## Sign-in and the session

The browser signs in through the API and afterwards holds only a cookie ([ADR-0031](../adr/0031-sign-in-through-entra-in-the-api.md); the routes are in the [routing register](../routing.md)):

| Rule | Detail |
|---|---|
| Start | `GET /api/auth/login?returnUrl=<local path>` answers 302 to `<Instance><tenant id>/oauth2/v2.0/authorize` with `response_type=code`, `response_mode=form_post`, `code_challenge_method=S256`, the scopes `openid profile offline_access` and `redirect_uri` `Erp:Platform:Identity:WebOrigin` + `/api/auth/signin-oidc`, whatever `Host` the request carried; a signed-in caller gets a 302 straight to the path. Only a page the browser opens itself starts it: with `Sec-Fetch-Mode` present and not exactly `navigate`, or `Sec-Fetch-Dest` present and not exactly `document`, it answers 400 `request.invalid` with the `detail` "The sign-in starts only from a page the browser opens itself, never from an image, a frame or a script." and no `errors`, `Location` or cookie, signed in or not; a request with neither header is served normally |
| Return address | `returnUrl` (request record `LoginRequest`) is at most 2048 characters, starts with `/`, passes `RedirectHttpResult.IsLocalUrl` and holds only visible ASCII (`!` to `~`), so `https://…`, `//…`, `/\…`, `~/…`, control characters and spaces are refused with 400 `request.invalid` and `errors.returnUrl` "The return address must be a path on this site, such as /platform/attachments."; absent, it is `/` |
| Callback | Entra posts the code to `/api/auth/signin-oidc`; the API redeems it with the sign-in certificate, issues the session cookie and redirects to the return address. A failed callback redirects to `/login?error=sign-in-failed`, where the sign-in page shows "We could not sign you in. Try again, or ask your administrator for access." The session starts only for a person whose record admits them ([ADR-0039](../adr/0039-people-and-their-admission.md)): the sign-in creates the person's record in `identity_users.Users`, or links one registered beforehand and brings it up to date, and the callback of a person whose record is deactivated redirects to `/login?error=account-deactivated`, where the page shows "Your account has been deactivated, so you cannot sign in. Ask your administrator if you need access again.", and records `SignInRefused` |
| Session cookie | `__Host-erp-session`: HttpOnly, always `Secure`, `SameSite=Lax`, `Path=/`, no `Domain`, no `Expires` or `Max-Age` (it ends with the browser session); valid for `Erp:Platform:Identity:SessionIdleTimeout` (30 minutes) after the last request that renewed it, and never longer than `Erp:Platform:Identity:SessionLifetime` (12 hours) after sign-in, measured from the authentication property `erp.signed-in-at`; issued again on the first request more than the renewal interval after it was last issued, the renewal interval being one minute or half of `SessionIdleTimeout`, whichever is shorter, so a session ends after `SessionIdleTimeout` without a request, at most one renewal interval sooner, and slides at the shortest permitted `SessionIdleTimeout` (one minute) too, except that `GET /api/auth/session` never renews it and `POST /api/auth/session` always does; accepted only while the person's record admits them (neither deactivated nor deleted) and their account is in the API's token cache, otherwise cleared with a 401 `request.unauthenticated` |
| Sign-in cookies | `__Secure-erp-correlation.*` and `__Secure-erp-nonce.*` (`MicrosoftIdentityOptionsSetup.CorrelationCookiePrefix`, `NonceCookiePrefix`), set by the redirect to Entra: HttpOnly, `Secure`, `SameSite=None`, because Entra posts the callback from its own site; the `__Secure-` prefix makes the browser refuse one set without `Secure`, so a page served over plain HTTP cannot plant its own; path `/api/auth/signin-oidc`, expiring after the 15-minute remote authentication timeout (`web-security.spec.ts`) |
| Sign-out | `POST /api/auth/logout` clears the session cookie, records the person's sign-out time and removes their account from the token cache, so every copy of that cookie, and every other session of the person issued before the sign-out, is refused from then on, a later sign-in included (a failure to record it answers 500 and signs nothing out), and answers 302 to Entra's end-session endpoint with `post_logout_redirect_uri` `WebOrigin` + `/api/auth/signout-callback-oidc`, which redirects to `/login?reason=signed-out`, and with `logout_hint` the session's `login_hint` claim (the optional claim of the ID token, `SignInEvents.RedirectToIdentityProviderForSignOut`), so Entra signs that account out without asking which one; it also forgets the Entra session record of this sign-in (`EntraSessions`, below), so a `sid` another app holds ends nothing afterwards; without a valid antiforgery token, in `X-XSRF-TOKEN` or in the form field `__RequestVerificationToken` of a form the page posts, 400 `antiforgery.token-missing` or `antiforgery.token-invalid`, leaving the person signed in (section "Antiforgery"). The route is anonymous too, because a page whose session already ended must still end the Microsoft sign-in of its browser, or the next person at a shared computer would be signed in as this one: a request the session cookie does not sign in, and whose `Sec-Fetch-Site` is absent or exactly `same-origin`, signs nothing out here, touches no cookie and answers 302 to the end-session endpoint without `logout_hint`, where Entra asks which account to sign out; with any other `Sec-Fetch-Site` (another site's form post) it answers 401 `request.unauthenticated`, as every route does without a session. Signing out ends every session of that person, on every device and browser, because the token cache holds one entry per person: each other session's next request answers 401 `request.unauthenticated` and clears its cookie. A sign-out the person makes in another app of the tenant reaches the API as Entra's front-channel request `GET /api/auth/signout-oidc?iss=&sid=` (anonymous, from a hidden frame of Entra's site, without the session cookie): every cookie sign-in records the principal's `sid` with its account (`EntraSessions`, `entra-session:<sid>` in the distributed cache table, kept `SessionLifetime` plus five minutes; a record that cannot be written fails the sign-in, which lands on `/login?error=sign-in-failed`), the session check refuses a cookie whose `sid` has no record or a record of another account, and a request whose `iss` is the tenant's issuer (the v2.0 form or `https://sts.windows.net/<tenant id>/`) and whose `sid` names a recorded session forgets that record (`FrontChannelSignOut`), so every session signed in from that Entra session (that browser) is refused from then on while the person's sessions elsewhere stay signed in; the `sid` is no secret, since every app of the Entra session receives it, so a request naming one ends at most the sessions of that Entra session; any other request changes nothing, every well-formed one answers 200 with no body unless the record cannot be read or forgotten (500 `server.error`), and a missing or over-long `iss` or `sid` 400 `request.invalid` ([ADR-0036](../adr/0036-web-sign-in-the-session-in-the-browser-and-single-sign-out.md)) |
| Who is signed in | `GET /api/auth/me` answers `{ id, name, userName, roles }`: the person's Entra object id (`oid`), display name (`name`), sign-in name (`preferred_username`) and app roles (`roles`); the person's permissions join it with `user-management-roles-and-permissions` |
| Session times | `GET /api/auth/session` answers `{ expiresAt, lifetimeEndsAt }` without renewing the cookie, so a page can watch the time left without keeping an idle person signed in; `POST /api/auth/session` (with the antiforgery token) renews the cookie at once, however recently it was renewed, and answers the renewed times. `expiresAt` is when the session ends unless a request renews it first, never after `lifetimeEndsAt`, the end of `SessionLifetime` after sign-in; both are to the second and never later than the session really ends, so a renewed `expiresAt` is the expiry the renewed cookie carries or a second earlier. Both routes take the session cookie only, so a request the test header or a bearer token signs in answers 401 (ADR-0034) |
| Refusals | 401 `request.unauthenticated` and 403 `request.forbidden` as problems (section "Problem details"), never a redirect and never a `Location` header or a `WWW-Authenticate` header; a caller whose `Accept` admits no JSON gets the status code pages plain-text body with the same status |
| Tokens | never in the cookie, the browser, a log or a response: `SaveTokens` is off, and MSAL keeps them in the SQL Server table `platform_caching.DistributedCacheEntries`, protected with Data Protection, for at most `SessionIdleTimeout` after the last request and `SessionLifetime` after sign-in (each plus five minutes); a restart keeps every session (ADR-0032) |
| Proved by | `LoginEndpointTests`, `LogoutEndpointTests`, `SignInCallbackTests`, `SessionAdmissionTests`, `SessionCookieTests`, `CurrentUserEndpointTests`, `SessionEndpointTests`, `FallbackPolicyTests` (host), `LoginRequestTests`, `SignInEventsTests` (unit), `login.spec.ts` |

## Antiforgery

Another site can make the browser send the session cookie to the API, so a request that changes data with it must also prove it came from this site's pages ([ADR-0033](../adr/0033-antiforgery-for-requests-the-session-cookie-signs-in.md); the middleware is in [request pipeline](request-pipeline.md), section "Antiforgery"):

| Rule | Detail |
|---|---|
| Checked | every POST, PUT, PATCH and DELETE the session cookie signs in, which is every such request to a session route that carries the cookie, whatever else it carries; never GET, HEAD, OPTIONS or TRACE, an anonymous request, one the test header signed in, or a request to a route that takes bearer tokens, which ignores the cookie (ADR-0034) |
| Cookie token | `__Host-erp-antiforgery`: HttpOnly, always `Secure`, `SameSite=Strict`, `Path=/`, no `Domain`, no `Expires` |
| Request token | `__Host-erp-xsrf`: readable by the page's scripts, always `Secure`, `SameSite=Strict` (only a request a page of this site sends needs it), `Path=/`, no `Domain`, no `Expires`; its value goes back in the header `X-XSRF-TOKEN`, or, on an endpoint that reads a form (`POST /api/auth/logout`), in the form field `__RequestVerificationToken` |
| Lifetime | every sign-in issues the person's pair; sign-out and a session cookie the session check refuses clear both; `GET /api/auth/antiforgery` (signed in, 204) issues it again, a new cookie token only when the request carries none that is valid; the Entra callback, a form post from Entra's own site, never carries the SameSite=Strict cookie token, so every Entra sign-in writes a new one and a request token issued before it is refused, which is why a page reads `__Host-erp-xsrf` when it sends, never when it renders; a request token names the person it was issued to, so it is refused once another person signs in on that browser; tokens survive a restart of the API on the same key ring (ADR-0032) |
| Renewal | `GET /api/auth/antiforgery` answers 400 `request.invalid` with the `detail` "The antiforgery tokens are issued again only to a script of this site, never to a page, an image or a frame another site opens." and sets no cookie when `Sec-Fetch-Site` is present and not exactly `same-origin` (another site, a sibling site or the address bar): a navigation another site starts carries the Lax session cookie without the Strict cookie token, and would otherwise make the API write a new cookie token and refuse the request tokens pages hold, while images and frames of another site carry no session cookie and answer 401 first; the web app's scripts send `same-origin`, and its server sends no `Sec-Fetch-Site` (Node's `fetch` adds only `Sec-Fetch-Mode: cors`) |
| Refusal | 400 `antiforgery.token-missing` (the cookie token or the request token is absent) or `antiforgery.token-invalid` (a token that does not deserialize, belongs to another cookie token or names another person), title "The request could not be confirmed as coming from this site.", before the feature gate and idempotency, so nothing ran and the request may be sent again; a request without a session answers 401 first |
| Web app | `sendWithAntiforgery` in `frontend/apps/web/src/shared/api/antiforgery.ts` holds the rule: a call that changes data sends `X-XSRF-TOKEN` with the value of `__Host-erp-xsrf`, and after a refusal with an `antiforgery.` code fetches a new pair from `GET /api/auth/antiforgery` once and sends the request once more (never a request whose body was a stream); a 401 from that renewal means the session ended. Server Functions follow it in `shared/api/client.ts` with the value from the forwarded `cookie` header, relaying the renewed cookies to the browser with `cookies().set`; the browser upload (`shared/api/upload.ts`) and the session renewal (`renewSessionTimes`, `shared/api/session/session-watch.ts`) follow it with the value from `document.cookie`, renewing through `renewBrowserAntiforgeryTokens` (`shared/api/browser-antiforgery.ts`); the sign-out form fills `__RequestVerificationToken` from `__Host-erp-xsrf` when it is sent, fetching the pair first when that cookie is missing, and never resends. A refusal that survives the retry reaches people as "The form could not be sent. Try again." in forms and "This could not be sent. Try again." through `apiErrorMessage`, never as the problem's `detail` |
| Proved by | `AntiforgeryValidationTests`, `AntiforgeryCookieTests`, `SignInCallbackTests`, `ModuleCatalogTests.Endpoints_NeverDisableTheAntiforgeryCheck` (host and architecture), `antiforgery.test.ts` (web unit), `files.spec.ts` (the retried upload on every browser project) |

## Bearer tokens

A route that calls `RequireBearerToken(BearerTokenAccess)` takes a Microsoft Entra ID access token for the API's app registration instead of the session cookie ([ADR-0034](../adr/0034-session-endpoints-bearer-tokens-per-route-and-the-security-description.md)); no product route does yet, and every other route ignores a token:

| Rule | Detail |
|---|---|
| Switch | the platform flag `Erp.Platform.Identity.BearerTokens`, off by default and under both labels; while it is off no token signs anything in, and a bearer route answers 401 without `WWW-Authenticate` |
| Token | `Authorization: Bearer <token>`: a JWT signed with RS256 by a key of the tenant's v2.0 metadata, `iss` exactly `<tenant id>/v2.0` resolved against `Erp:Platform:Identity:Instance` (`https://login.microsoftonline.com/<tenant id>/v2.0` in the public cloud), `aud` exactly the client id (never `api://…`), `ver` `2.0`, `tid` the tenant, a GUID `oid`, within its lifetime; and either a person's token (`scp`, `idtyp` absent or `user`) or an application's (no `scp`; `idtyp` `app`, or no `idtyp` and `sub` equal to `oid`), so the id tokens of the same registration are refused |
| Access | a person's token reaches the route with one of the route's scopes in `scp`, an application's with one of its application roles in `roles`; a person's own app roles never grant application access; a route calls `RequireBearerToken` once, on its group or on itself, and a second call fails when the route is built, because both accesses would apply while the OpenAPI document could describe only one |
| Refusals | no token: 401 `request.unauthenticated` with `WWW-Authenticate: Bearer`; a refused token: 401 with `Bearer error="invalid_token"`, never the reason; a valid token without the access: 403 `request.forbidden` with `Bearer error="insufficient_scope"`; the session cookie alone: 401, because the route ignores it |
| Session | none: the caller is the person or application the token names (`oid`), rate-limited as that actor; `/api/auth/me` and `/api/auth/session` refuse a token, signing out does not reach it, and the cookie is neither read, renewed nor cleared on a bearer route |
| Proved by | `BearerTokenSignInTests`, `BearerTokenAccessTests`, `BearerTokenRouteTests`, `AuthenticationSchemeTests` (host), `BearerTokenClaimsTests`, `BearerTokenAccessHandlerTests`, `BearerTokenAccessTests`, `BearerTokenRouteExtensionsTests` (unit) |

## The OpenAPI document

- Built by `Hosts/Api/OpenApi/OpenApiSetup` with `ErpOpenApiOptions.Configure`: OpenAPI 3.1, title `ERP-AI-Pro API`, version `1.0`, no `servers` entry. Development serves it at `/openapi/erp.json` with the Scalar reference at `/scalar`; Production maps neither.
- Every module route group documents the 400 validation problem and the 401 (`request.unauthenticated`), 404, 429 (`rate-limit.exceeded`), 500 and 504 (`request.timeout`) problems, and `GET /api/platform/features` its 401; the `/api/auth` group (tag `Auth`) documents 429, 500 and 504; an endpoint declares any other status it answers with `ProducesProblem` (`POST /api/auth/logout` its 400 and 401) or `Produces` (the 302 of both sign-in routes).
- Every operation carries its `security` requirement and `components.securitySchemes` declares exactly the schemes they name, from `AddErpSecurityDescription` ([ADR-0034](../adr/0034-session-endpoints-bearer-tokens-per-route-and-the-security-description.md)): `SessionCookie` (apiKey in the cookie `__Host-erp-session`), `AntiforgeryToken` (apiKey in the header `X-XSRF-TOKEN`) and, once a route takes bearer tokens, `BearerToken` (http bearer, JWT). An anonymous GET requires `[]`, an anonymous change `[{}, {SessionCookie, AntiforgeryToken}]`, a signed-in GET `[{SessionCookie}]`, a signed-in change `[{SessionCookie, AntiforgeryToken}]`, and a bearer route one `{BearerToken: [name]}` alternative per scope or application role; the requirement comes from the endpoint metadata, never from the schemes the running host registered (`OpenApiSecurityTests`).
- Operations are described with `.WithName("<Domain>.<Module>.<Action>")` (`Auth.Login` and `Auth.Logout` for the sign-in routes) and `.WithSummary(…)`. Response records stay internal to the module, so their XML comments do not reach the document.
- `docs/openapi/erp.json` is the committed contract. After changing an endpoint, refresh it; the test host needs `ERP_TEST_SQL_CONNECTION` and `ERP_TEST_BLOB_EMULATOR_HOST` with a running Azurite, like every host test ([testing](../guides/testing.md)):

  ```
  cd backend && ERP_OPENAPI_SNAPSHOT=update dotnet test --project Tests/Host/Dewiride.Erp.Host.Api.IntegrationTests/Dewiride.Erp.Host.Api.IntegrationTests.csproj --filter-class "*OpenApiSnapshotTests"
  ```

- `OpenApiSchemaShapeTests` rejects composed or conditional schemas (`oneOf`, `anyOf`, `allOf`, `not`, `discriminator`, `patternProperties`, `if`/`then`/`else`) and schema ids that are not PascalCase identifiers, because the TypeScript generator mishandles them. Two response types with the same class name in different modules fail the document build; rename one.

## The generated client

| Piece | Location |
|---|---|
| Generator | Kiota CLI, local tool `kiota` in `backend/.config/dotnet-tools.json` (`dotnet tool restore`) |
| Arguments | `scripts/api-client/lib/kiota.ts` |
| Output (committed) | `frontend/packages/api-client/src/generated`, including `kiota-lock.json` |
| Package | `@dewiride/erp-api-client`: `connect()`, the `ErpApiClient` type and every model type; built to `dist/` by `pnpm build:api-client` |
| Web entry point | `frontend/apps/web/src/shared/api/client.ts` (`apiClient()`, `callApi()` for calls that answer a body, `sendApi()` for calls that answer none, such as a 204), the only HTTP client of the web app, which sends `X-XSRF-TOKEN` on every call that changes data (section "Antiforgery"); the exceptions are the browser's own requests: the file upload (`uploadFile` in `shared/api/upload.ts`, section "Files on the wire"), the antiforgery renewal (`renewBrowserAntiforgeryTokens`, `shared/api/browser-antiforgery.ts`) and the session watch (`readSessionTimes`, `renewSessionTimes`, `shared/api/session/session-watch.ts`; ADR-0036) |
| Errors | `frontend/apps/web/src/shared/api/problem-details.ts` (`ApiError`, `toApiError`, and `problemFromBody` for a problem body read outside the generated client) |
| Errors in a form | `frontend/apps/web/src/shared/forms/errors/problem-to-form-state.ts` (`problemToFormState`, [ADR-0025](../adr/0025-forms-typed-submissions-and-form-composites.md)): a Server Function turns the `ApiError` or the network failure of its call into the form's `FormState`, the validation keys mapped onto form fields with `apiKeyToFormPath`. It sees a problem's `code` and `detail` only for statuses the endpoint declares, so an endpoint a form posts to declares its 409 and 422 answers with `ProducesProblem` |

Regenerate after refreshing the document, or both in one go:

```
node scripts/api-client/generate.ts                 # refreshes docs/openapi/erp.json (needs ERP_TEST_SQL_CONNECTION and ERP_TEST_BLOB_EMULATOR_HOST), then regenerates
node scripts/api-client/generate.ts --skip-snapshot # regenerates from the committed document only
node scripts/api-client/drift.ts                    # the CI check: fails when the committed client differs or generation is not deterministic
```

A query reads through `callApi`, which throws `ApiError` for any problem the API answered and lets a network failure through unchanged:

```ts
export const getRecentStartups = cache(() =>
  callApi((client) => client.api.platform.systemInfo.startups.get({ queryParameters: { take: 20 } })),
);
```

Model members are optional and a JSON `null` arrives as `undefined`; read them with `??`. Date-time members arrive as `Date`.
