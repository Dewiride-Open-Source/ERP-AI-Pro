# Adding a module

A Community module starts from one command, which writes it and registers it everywhere ([ADR-0061](../adr/0061-a-module-scaffolder-that-registers-what-it-writes-proven-on-every-push.md)); the sections after "Generating a module" are what it automates, and what a module that grows beyond its first feature keeps following by hand. `backend/Modules/Platform/SystemInfo` remains the smallest reference implementation.

## Generating a module

```bash
node scripts/scaffold/new-module.ts <Domain>/<Module> --entity <Entity> \
  --title "<navigation title>" --description "<one sentence>" \
  --read-permission "<one sentence>" --create-permission "<one sentence>" \
  [--entities <Entities>] [--singular "<words>"] [--plural "<words>"] \
  [--area-title "<title>"] [--icon <LucideIcon>] [--files-only]
```

- **Names.** PascalCase words: `Clients/Core --entity Client`. The plural defaults to an English plural of the entity and the prose to its words in lower case (`--singular person --plural people` where English differs); `--area-title` is required for a new domain and refused for an existing one; the icon is a `lucide-react` export, `FileTextIcon` by default. A module may share its name with a module of another domain (`Clients/Core`, `Vendors/Core`); its schema, route, flag, context key and API model names may not clash with any other. The command also refuses a name the compiler or the build would misread: a type of a namespace that a generated file naming the entity imports (`Environment`, `Record`, `Result`) or a member of a generated type that names the entity (`Name`, `Create`, `Field`), a domain, module or plural that would hide a type of the namespaces every module imports (`Path`, `Lock`) or that names a folder git or the repository checks treat as generated (`Migrations`, `Bin`), a domain or module containing `Tests`, prose holding a word the comment policy refuses (`legacy`), and a name that makes a path git ignores (`TestResults`, `bin`). Prose is lower-case words and acronyms in capitals (`--singular "GST return"`).
- **Texts the owner approves first.** The navigation title and description and the two permission sentences (one sentence each, ADR-0045) are shown to people, so they are agreed with the owner before the command runs.
- **What it writes.** The module's four projects and README in the anatomy of [module anatomy](module-anatomy.md), with one feature that lists, opens and adds one kind of record (an `IAuditable` aggregate with a required `Name` of at most 100 characters, recorded under `<domain>.<module>.<entities>`, read and create permissions held by administrators alone), its unit and integration tests, its first migration, the web module with its list, record and add pages behind the module flag, and its Playwright page objects and specs, gated and API-unavailable included. Edit, delete and every business rule are the module's own to add.
- **What it registers.** `Modules.All` and the composition project, `backend/Dewiride.Erp.slnx` and the domain's solution filter (a new domain gets its filter and its row in `backend/solutions/README.md`), the host lock files, `infra/appconfig/feature-flags.json`, `docs/configuration.md`, `docs/routing.md`, the web registry and, for a new domain, its area, the e2e navigation list `registeredNavigation`, the audit trail's record types and labels, `docs/openapi/erp.json` and the generated client.
- **Before it writes.** It refuses, listing every problem and changing nothing (a clash that depends on a name once the name is well formed), a malformed or reserved name, a clash, a missing anchor in a file it edits, and a file it edits or regenerates that has uncommitted changes, so the `git restore` and `git clean` lines it prints at the end undo it whole. Without `--files-only` it also needs `ERP_TEST_SQL_CONNECTION`, `ERP_TEST_BLOB_EMULATOR_HOST` and `dotnet`, because it then restores, formats the C# it wrote, adds the migration (`ef.ts add Initial<Entities>`) and regenerates the contract and the client; `--files-only` stops after writing and prints those commands. A write that fails part of the way puts back every file it touched and names any it could not; a completion step that fails leaves the module written and prints the steps that remain; and every run that writes ends with the `git restore` and `git clean` lines that undo it. Either way it reads the icons from `frontend/apps/web/node_modules`, so `pnpm install` comes first.
- **After it writes.** The new flag still has to reach the configuration store: `bash scripts/azure/seed.sh --dry-run --label all`, then the same without `--dry-run`, with the owner's consent ([adding a setting](../guides/adding-a-setting.md)).
- **Proof.** `node scripts/scaffold/prove.ts [--e2e [--all-projects | --project <name>…]]` generates the throwaway module `ScaffoldProof/Jobs` in a worktree of HEAD beside the repository, naming the changes of the checkout it leaves out, and runs every check over it, the registration audit included; the specs run on Chromium unless `--all-projects` or `--project` names others, and never while another server holds Playwright's ports. ci-backend runs it in place on every push to `main`, the generated specs on Firefox included.
- **Type names.** The .NET type names the command checks names against are `scripts/scaffold/lib/dotnet-type-names.json`, which `node scripts/scaffold/type-names.ts` writes from the documentation files of the SDK's reference packs and of the restored packages; it runs again after a .NET or package upgrade and whenever a template that names the entity imports another namespace, which a scaffold test refuses until it does. The building blocks' own types are read from their sources on every run.

## Edition

Every module belongs to one edition. Decide it by [ADR-0030](../adr/0030-community-and-enterprise-editions.md) and have the owner confirm it before the module's first sub-phase starts: `node scripts/roadmap/roadmap.ts edition <community|enterprise> <id…> --confirm` records the confirmation, and `start` refuses a sub-phase whose edition is not confirmed.

- A Community module is generated in this repository by the command above; the steps below are what it does, and what a module that grows beyond its first feature follows by hand.
- An Enterprise module is built by the same steps in the private repository `Dewiride-Enterprise/ERP-AI-Pro-Enterprise`, under the root namespace `Dewiride.Erp.Enterprise.Modules` (`Dewiride.Erp.Enterprise.Modules.<Domain>.<Module>` in place of `Dewiride.Erp.Modules.<Domain>.<Module>` in every project name below), and references only Community `*.Contracts`, `BuildingBlocks.*` and Enterprise `*.Contracts` ([dependency rules](dependency-rules.md#editions), [Enterprise modules](module-anatomy.md#enterprise-modules)). Nothing in this repository names it: `Modules.All` lists Community modules only, and the Enterprise solution and hosts that compose Enterprise modules arrive with the roadmap item `business-building-blocks-enterprise-edition-composition`.

## Backend

1. Create `backend/Modules/<Domain>/<Module>/` with `README.md` and four projects:
   - `Contracts/Dewiride.Erp.Modules.<Domain>.<Module>.Contracts/` — class library; references `Dewiride.Erp.BuildingBlocks.Kernel`.
   - `Module/Dewiride.Erp.Modules.<Domain>.<Module>/` — class library with `FrameworkReference Microsoft.AspNetCore.App`; references its Contracts, `Dewiride.Erp.BuildingBlocks.Persistence` and the other BuildingBlocks it needs.
   - `Tests/UnitTests/Dewiride.Erp.Modules.<Domain>.<Module>.UnitTests/` and `Tests/IntegrationTests/Dewiride.Erp.Modules.<Domain>.<Module>.IntegrationTests/` — test projects (the `build/Tests.props` defaults apply by the `Tests` suffix); the integration project references `Tests/Shared/Dewiride.Erp.Testing` and `Hosts/Api`.
2. Add `<Module>Module.cs` implementing `IModule`: the `ModuleDescriptor` (domain, module, schema, route prefix, feature flag, permissions, capabilities), `AddServices` (options, DbContext, handlers, `AddValidation()`) and `MapEndpoints(RouteGroupBuilder)`. Each permission is a `PermissionDeclaration` naming the built-in roles that hold it besides Administrator, who holds every permission, so one no role is named for is an administrator's alone, and one plain sentence, approved by the owner, saying what a holder may do, which the roles and permissions page shows; its name is a constant of `<Module>Permissions` in the Contracts project, and every route calls `RequirePermission` with one of them ([ADR-0041](../adr/0041-roles-and-permissions.md), [ADR-0045](../adr/0045-people-pages-and-the-permission-catalogue.md)). The module flag `Erp.Modules.<Domain>.<Module>` gates the whole route group and evaluates enabled until a configuration source switches it off; each `ModuleCapability(Name, EnabledByDefault)` becomes the flag `Erp.Modules.<Domain>.<Module>.<Name>` (declare AI capabilities with `EnabledByDefault: false`).
3. Add `<Module>DbContext` under `Persistence/` deriving from `ModuleDbContext`, with the schema constant `SchemaName = "<domain>_<module>"`; register it in `AddServices` with `builder.AddModuleDbContext<<Module>DbContext>(<Module>DbContext.SchemaName)` and set `Schema` on the descriptor to the same constant. There is no design-time factory: `dotnet ef` runs the API host offline (`persistence.md`). Create the first migration from the repository root after `cd backend && dotnet tool restore`; `scripts/ef/ef.ts` discovers the new context by itself, and the migrator, the test databases and CI pick it up through the catalogue and the same discovery ([migrations guide](../guides/migrations.md)):

   ```bash
   node scripts/ef/ef.ts add Initial<Aggregate>s --context <domain>-<module>
   ```

   Reference data the module needs goes in an `ISeeder` registered with `builder.Services.AddSeeder<TSeeder>(order)`, idempotent and tested by running it twice.

   Every entity type the context maps implements `IAuditable`, whose every change the persistence building block records in `audit.ChangeRecords`, or `IAppendOnly`, for a row inserted once and never changed. Each `IAuditable` type's configuration calls `builder.RecordChangesAs("<domain>.<module>.<feature>")` with the module's permission prefix, a child type's also `builder.FileChangesUnder(c => c.<ParentId>)`, and a property whose every change is noise `ExcludeFromChangeRecords()`; the module registers an `IRecordNames` for the keys whose records have a name, so the history and its export name them, and the audit trail lists every key in `changeKeys` of `frontend/apps/web/src/features/platform/audit/changes/lists/changes.list.ts` and labels it in `recordTypes` of `frontend/apps/web/src/features/platform/audit/changes/components/change-text.ts`, so a person can filter by it and read its name ([persistence](persistence.md), section "Change records"; [ADR-0043](../adr/0043-change-records-and-the-append-only-audit-schema.md)).

4. Add feature folders following `module-anatomy.md`.
5. Register the module in `Modules.All` (`backend/Hosts/Composition/Dewiride.Erp.Host.Composition/Modules.cs`, one entry `new ErpModules.<Domain>.<Module>.<Module>Module()` through the alias `using ErpModules = Dewiride.Erp.Modules;`) and reference its module project from `Dewiride.Erp.Host.Composition.csproj`; add its Contracts and Module projects to `backend/Dewiride.Erp.slnx` under the solution folder `/Modules/<Domain>/<Module>/` and its two test projects under `/Modules/<Domain>/<Module>/Tests/`, and all four to `backend/solutions/<Domain>.slnf` (a new domain's filter lists every project outside `Modules/` and its own, and gets a row in `backend/solutions/README.md`); then restore, so the host lock files take the new projects.
6. Add the module's routes to `docs/routing.md`, its configuration keys and feature flag to `docs/configuration.md`, and its flag for both labels to `infra/appconfig/feature-flags.json`, then seed the flag with the owner's consent ([adding a setting](../guides/adding-a-setting.md)). The flag seed and the solution filters keep the layout `JSON.stringify` writes with two spaces; the command edits a file only in a layout `JSON.stringify` writes, and keeps it.
7. Run the architecture tests: they verify the module is listed, its four projects and `README.md` exist under `Modules/<Domain>/<Module>/`, its namespaces match folders, no folder holds more than 12 source files, its descriptor follows the naming table (permissions start with `<domain>.<module>.`), every endpoint requires a permission the catalogue declares and none of those allows anonymous callers, it references only contracts of other modules, its DbContext derives from `ModuleDbContext` in the namespace `<Module>.Persistence`, maps only entity types from its own assembly (and the change records every context maps) with a schema equal to the descriptor's `Schema`, and maps every strongly-typed id through `StronglyTypedIdConverter`, every entity type implements `IAuditable` or `IAppendOnly`, every recorded type declares a change key of its own under the module's prefix, keeps a `Guid` key set in code and has no owned type, complex collection or foreign key that a principal's delete cascades or sets to null, and the module neither calls `Update` or `Attach` nor runs raw SQL. `node --test scripts/scaffold/tests/audit.test.ts`, which `verify.ts` and every ci-backend run include, checks each registration of steps 5 and 6, the audit trail's keys and labels and the e2e navigation list for every module of `Modules.All`.

## Frontend

1. Create `frontend/apps/web/src/features/<domain>/<module>/` with `index.ts` (the public surface: the components `app/` renders and the `nav` manifest, never Server Functions, queries or schemas) and `nav.ts` (one `as const` `<page>Navigation` object per navigation entry, named after the page it opens and unique across the web app because the registry imports every one by name, of the `NavigationEntry` shape with the `featureFlag` that reveals it, the domain's `area` from `features/<domain>/_shared/<domain>-area.ts` (create it with the domain's first module) a `lucide-react` `icon` and the `permission` the entry needs, the read permission of the page it opens, without which the shell, the page search and the start page leave it out). Put each feature in its own folder holding only `components/`, `server/`, `forms/`, `lists/`, `hooks/` and, in an Enterprise module, `ai/` (`module-anatomy.md`); features of the module import each other by relative path.
2. Register each manifest in `features/registry.ts`, importing it from the module's `index.ts`, and add its entry, in the registry's order, to `registeredNavigation` of `frontend/e2e/fixtures/navigation.ts`, from which the shell's specs build every expectation.
3. Add routes under `app/(app)/<domain>/<module>/...`. Route files only compose and import only the module's `index.ts`, `@/features/registry`, `@/shared/**`, `next` and `react`: gate the segment with `await requireFeature(<page>Navigation.featureFlag)` in its `layout.tsx`, so a disabled module renders the in-shell not-found page; each `page.tsx` renders one export of the module's `index.ts`, wrapped in `RequirePermission` (`@/shared/auth/require-permission`) with the permission the page needs, so a person without it sees the no-access message; `loading.tsx` renders the module's skeleton (`components/<name>-skeleton.tsx`, exported through `index.ts`, wrapped in `LoadingStatus` with `pageTitle` naming the page), and every page that takes noticeable time to prepare has one, below the segment's gating `layout.tsx`, because the shell has no loading status of its own and a navigation otherwise keeps the old page on screen until the new one is ready ([ADR-0027](../adr/0027-feedback-motion-and-the-accessibility-baseline.md)); any other UI a segment needs lives in the feature and is exported the same way. A page or layout that reads `params` or `searchParams` types its props with `PageProps<"/<route>">` or `LayoutProps<"/<route>">`.
4. Run `node scripts/checks/feature-boundaries.ts` from the repository root and `pnpm lint` and `pnpm typecheck` from `frontend/`: they check the module's folders and files, its imports in both directions and every route it links to (the rule register is in `dependency-rules.md`).
5. Add page objects and specs under `frontend/e2e/{pages,tests}/<domain>/<module>/`.

## Splitting a module

When a module outgrows its schema or team ownership, the feature becomes its own module: new four-project set, new schema, data moved by a forward migration, contracts introduced for what the old module still needs, and the old code deleted in the same pull request. No compatibility shims.
