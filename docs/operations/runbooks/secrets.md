# Secrets runbook

How secrets are named, stored, refreshed, rotated and revoked. Every command runs from the repository root with the parameters in `scripts/azure/params.env` (`ERP_AZURE_APPCONFIG_NAME`, `ERP_AZURE_KEYVAULT_DEV_NAME`, `ERP_AZURE_KEYVAULT_PROD_NAME`, `ERP_AZURE_KEYVAULT_OPS_NAME`); the examples use today's names (`appcs-erp-ai-pro`, `kv-erp-ai-pro-dev`, `kv-erp-ai-pro-prod`, `kv-erp-ai-pro-ops`).

## 1. Principles

- Key Vault is the only home of a secret value. The API reads a secret only through an App Configuration Key Vault reference (`infra/appconfig/key-vault-references.json`, written by `scripts/azure/seed.sh`), the developer through `az login`, the api container through the runtime service principal's certificate, and the migrator container through the migrator service principal's, which may read only the production database's two connection strings. The server's nightly backup reads no secret: it signs in as the backup service principal, which reaches only the backup container, and seals its archives to a public certificate. The client certificates of the three service principals, and the backup encryption certificate whose private key alone opens the archives, live in `kv-erp-ai-pro-ops`, which only the operator reads ([ADR-0050](../../adr/0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md), [azure-bootstrap.md](../azure-bootstrap.md) section 5a). A developer machine additionally keeps copies of development values in `dotnet user-secrets` for `dotnet ef` and store-less runs (the database connection string, the development attachments keys), written without display and never committed; the sign-in certificate is never copied anywhere, because only `dotnet run` with the store signs anyone in (ADR-0031). The only secrets with no home in a vault belong to the local container stack, which cannot sign in to Azure and reads its SQL logins, its attachments encryption key and a throwaway sign-in certificate from git-ignored file secrets under `infra/compose/secrets/` (sections 5b, 5d and 5f).
- Storage accounts hold no secret at all. Every account has Shared Key authorization disabled (`allowSharedKeyAccess` `false`), so no account key, connection string or key-signed shared access signature can reach its data; the API, the developers and the scripts reach Blob Storage only with an Entra ID token and a data role. Never list, rotate or copy storage account keys: they grant nothing and are not part of any procedure here.
- Nothing secret is ever committed: not in code, compose files, workflows, `.env` files, `CLAUDE.md`, memory or documentation. Three layers enforce it: GitHub secret scanning with push protection (repository setting, [github-repository-settings.md](../github-repository-settings.md)), the in-repo check `node scripts/checks/secret-patterns.ts` (every tracked and new file that git does not ignore; runs in `node scripts/verify/verify.ts` and in the `ci-backend` workflow), and `scripts/azure/lib/seed-files.ts`, which refuses credentials and environment identifiers in the seed files.
- A push-protection block or a check finding is fixed at the root: rotate the value in Key Vault (section 5), then remove it from the change. Never bypass the block, never rewrite pushed history to hide a value that has already left the machine.
- Placeholders in committed examples are written as `<name>`, `${VAR}` or `CHANGE_ME`; the check recognises those shapes and reports everything else that looks like a credential.

## 2. Naming

| Kind | Shape | Example |
|---|---|---|
| Key Vault secret, certificate or key | `Erp--<Domain>--<Module>--<Name>` | `Erp--Platform--Identity--ClientCertificate` |
| App Configuration key that references a secret | `Erp:<Domain>:<Module>:<Setting>` | `Erp:Platform:Identity:ClientCertificate` |
| Compose secret file | `<name>.pem` for a certificate with its private key, `<name>.crt` for a public certificate alone, `Erp__<Domain>__<Module>__<Name>` for a configuration value read by the key-per-file provider, under `infra/compose/secrets/` (git-ignored) | `erp-runtime-client.pem`, `erp-backup-recipient.crt`, `Erp__Platform__Database__ConnectionString` |

## 4. Refresh intervals

| Interval | Default | Where |
|---|---|---|
| Change check (`Erp:Sentinel` and feature flags) | 30 minutes (Free tier, ADR-0010) | `Erp:Platform:Configuration:RefreshInterval`, bootstrap-only |
| Secret re-read after a Key Vault reference resolved | 1 hour | `Erp:Platform:Configuration:SecretRefreshInterval`, bootstrap-only |
| First load timeout | 1 minute | `Erp:Platform:Configuration:StartupTimeout`, bootstrap-only |

A new secret *version* behind an existing reference is picked up within the secret refresh interval, except the sign-in certificate, which the API reads only when it starts (section 5b); a new *reference* or any other key change is picked up at the next change check after the labelled sentinel is bumped. `scripts/azure/seed.sh` bumps the sentinel on every run (unless `--no-sentinel`); `provision.sh` bumps a label's sentinel only when it changes that label's `Erp:Platform:Attachments:BlobServiceUri` and otherwise never bumps an existing value. By hand, per label:

```bash
az appconfig kv set --name appcs-erp-ai-pro --auth-mode login --key Erp:Sentinel --label production --value "$(date -u +%Y-%m-%dT%H:%M:%SZ)" --yes
```

Recreating the api container applies everything at once: `flock /srv/erp-ai-pro/deploy.lock docker compose -f infra/compose/compose.yaml -f infra/compose/compose.production.yaml up --detach --wait --wait-timeout 300 --force-recreate --no-deps --no-build --pull never api`, on the server as the deploy account `erp-ai-pro` from the deployment checkout `/srv/erp-ai-pro/ERP-AI-Pro`, where every `docker compose` command of this runbook runs; placing a certificate is the administrator's, with sudo ([host setup runbook](host-setup.md)). `--force-recreate` is required: a plain `up -d` leaves a running container untouched when its definition has not changed, so it keeps the old configuration and the old bind-mounted certificate file. `--no-deps` is required too: without it compose removes the running api first and then runs the migrator again as its dependency, so a migrator that fails, or that exits 4 while the database is ahead of the running release, leaves no api running ([ADR-0053](../../adr/0053-the-release-public-images-a-dependabot-gate-attestations-verified-on-the-server-and-the-deployment-scripts.md)). `flock` waits while `deploy.sh`, `rollback.sh`, `erp-ai-pro.service` or `erp-ai-pro-retain.service` holds the deployment lock ([deploy runbook](deploy.md)), and `--wait` returns once the api is healthy, or fails after five minutes.

## 5. Rotation

### 5a. Ordinary secret

1. Change the value at its issuer first (the SQL login, the third-party service, the token provider): Key Vault only stores a copy, so a new vault version alone changes nothing and an old value stays valid until the issuer forgets it.
2. Write the new value to a file with an editor or `read -rs` (never as a command argument), then create a new version in the vault of each environment: `az keyvault secret set --vault-name kv-erp-ai-pro-prod --name Erp--<Domain>--<Module>--<Name> --file ~/new-value --encoding utf-8 --output none` (without `--output none` the command prints the secret it stored); delete the file.
3. The reference points at the secret without a version, so the API re-reads it within the secret refresh interval; bump the sentinel (section 4) or recreate the api container to apply it sooner.
4. Once the consumer is confirmed on the new version, disable the previous version: `az keyvault secret set-attributes --vault-name kv-erp-ai-pro-prod --name <secret> --version <old version> --enabled false`.

### 5b. Sign-in certificate (per label)

1. `bash scripts/azure/entra.sh --rotate-signin-certificate production` creates a new certificate version in the label's vault and registers its public key on the sign-in registration alongside the current one.
2. Restart every API that reads the label's certificate, because the API loads it only when it starts and neither a sentinel bump nor the secret refresh interval reaches it: for `production` on the server `flock /srv/erp-ai-pro/deploy.lock docker compose -f infra/compose/compose.yaml -f infra/compose/compose.production.yaml up --detach --wait --wait-timeout 300 --force-recreate --no-deps --no-build --pull never api`, for `local-dev` every `dotnet run` against the store. The restart keeps every existing session (the token cache and the Data Protection key ring outlive it, ADR-0032), and an existing session never redeems a code, so confirm the new certificate with a fresh sign-in: sign out, or open a private browser window, sign in through the browser and confirm the session works. The local containers and the store-less APIs of the browser tests use throwaway certificates and need nothing.
3. `bash scripts/azure/entra.sh --prune-old-credentials production` removes every key credential that is not the current certificate; `bash scripts/azure/verify.sh --entra` must stay green.

`entra.sh --rotate-signin-certificate` prints the restart of step 2 for its label. The throwaway certificate of the local container stack (`infra/compose/secrets/Erp__Platform__Identity__ClientCertificate`, self-signed for 365 days) belongs to no registration and is not rotated: once it expires the api refuses to start, and it is written again as [docs/guides/local-development.md](../../guides/local-development.md), section "Containers", step 7 describes.

### 5c. Client certificates (the containers' own identities)

The api container signs in as the runtime service principal with `erp-runtime-client.pem`, the migrator container as the migrator service principal with `erp-migrator-client.pem`, and the Azure CLI container of the nightly backup and of a restore as the backup service principal with `erp-backup-client.pem`. For `<target>` `runtime`, `migrator` or `backup`:

1. `bash scripts/azure/entra.sh --rotate-client-certificate <target>` creates a new version in `kv-erp-ai-pro-ops` and registers it on that registration.
2. `bash scripts/azure/export-client-certificate.sh <target>` downloads the PEM (private key included) to `scripts/azure/out/erp-<target>-client.pem` (git-ignored). The script refuses to overwrite, so a copy left from the previous rotation must be shredded first (step 6).
3. Copy it to the server's administrator over SSH only: `scp scripts/azure/out/erp-<target>-client.pem <administrator>@<server>:~/erp-<target>-client.pem`; then, on the server as the administrator: `sudo install -o 1654 -g 1654 -m 0400 ~/erp-<target>-client.pem /srv/erp-ai-pro/ERP-AI-Pro/infra/compose/secrets/erp-<target>-client.pem` (1654 is the user of the three containers; the host bootstrap made the folder, private to `erp-ai-pro`, [host setup runbook](host-setup.md)).
4. For `runtime`, as `erp-ai-pro` from `/srv/erp-ai-pro/ERP-AI-Pro`: `flock /srv/erp-ai-pro/deploy.lock docker compose -f infra/compose/compose.yaml -f infra/compose/compose.production.yaml up --detach --wait --wait-timeout 300 --force-recreate --no-deps --no-build --pull never api` (the secret is a bind-mounted file, and a plain `up -d` keeps the running container with the old one); `/healthz/ready` must report Healthy. For `migrator` and `backup` nothing restarts: every migrator run, the nightly `retain` included, and every backup or restore starts a new container; the next night's backup, or `sudo systemctl start erp-ai-pro-backup.service` as the administrator at once, proves the new certificate ([restore runbook](restore.md)).
5. `bash scripts/azure/entra.sh --prune-old-credentials <target>`, then `bash scripts/azure/verify.sh --entra`.
6. Shred both staging copies, on the server `shred -u ~/erp-<target>-client.pem` and on the workstation `shred -u scripts/azure/out/erp-<target>-client.pem` (`rm -P` on macOS; on Windows delete it from a volume without shadow copies). Only `/srv/erp-ai-pro/ERP-AI-Pro/infra/compose/secrets/erp-<target>-client.pem` on the server remains.

### 5d. Database connection string

The value differs per consumer, so rotate the one that changed:

1. Host processes on the owner's machine (`dotnet run`, `dotnet ef`, tests) sign in with Windows authentication, so `Erp--Platform--Database--ConnectionString` in `kv-erp-ai-pro-dev` carries no credential and changes only when the server or database name does: set a new secret version (5a step 2), bump the `local-dev` sentinel (section 4) or restart `dotnet run`, and set the same value again with `dotnet user-secrets set "Erp:Platform:Database:ConnectionString" ... --project Hosts/Api/Dewiride.Erp.Host.Api` from `backend/` so `dotnet ef` follows.
2. The container stack signs in with a SQL login carried by the file secret `infra/compose/secrets/Erp__Platform__Database__ConnectionString` (`erp_local`: `db_datareader`, `db_datawriter` and the role `erp_audit_append_only`, which may only insert into the schema `audit`): change the login's password in SQL Server first (`ALTER LOGIN <login> WITH PASSWORD = ...` from SQL Server Management Studio, the same rule as 5a step 1), rewrite the file with the new password, then `docker compose -f infra/compose/compose.yaml -f infra/compose/compose.override.yaml up -d --force-recreate api`. A password change keeps the login's user and its roles.
   The migrator container signs in as the separate login `erp_local_migrator` (`db_ddladmin`, `db_datareader`, `db_datawriter`, the database permission `CREATE ROLE` and `CONTROL` on the schema `audit`, on `ErpAiPro`; never `db_owner`) carried by `infra/compose/secrets/Erp__Platform__Database__MigratorConnectionString`; rotate it the same way (new password in SQL Server first, then the file) and rerun the stack, which runs the migrator before the api. A login made anew for either needs its rights again ([local development](../../guides/local-development.md), section "Containers", step 3).
3. Production uses `Authentication="Active Directory Default"` and holds no password; the identities sign in with their certificates (section 5c). A restore leaves the strings as they are, because the restored database takes the name `ErpAiPro` ([restore runbook](restore.md)); they change only when the data moves to another server or database name, which is a move with steps of its own: changing `ERP_AZURE_SQL_SERVER_NAME` or `ERP_AZURE_SQL_DATABASE_NAME` alone makes `provision.sh` create a new, empty server or database and point both strings at it ([azure-bootstrap.md](../azure-bootstrap.md) section 9). Once the data is in place, `bash scripts/azure/provision.sh` writes both new versions to `kv-erp-ai-pro-prod`, then a `production` sentinel bump and `flock /srv/erp-ai-pro/deploy.lock docker compose -f infra/compose/compose.yaml -f infra/compose/compose.production.yaml up --detach --wait --wait-timeout 300 --force-recreate --no-deps --no-build --pull never api`; the next migrator run reads its own.

### 5e. Data-protection key

`Erp--Platform--DataProtection--Key` wraps the keys of the API's Data Protection key ring, the files `key-<guid>.xml` in `%LOCALAPPDATA%\ERP-AI-Pro\DataProtection-Keys` on a developer machine and in the external volume `erp-ai-pro-data-protection-keys` in the production stack (ADR-0032). Data Protection creates a new key of its own every 90 days and wraps it with the newest version of this Key Vault key; it never re-wraps a key it already wrote, and each file records the version that wrapped it. Key Vault keys have no expiry or rotation policy here, so a rotation is a deliberate act:

1. Rotate (Key Vault Crypto Officer): `az keyvault key rotate --vault-name <vault> --name Erp--Platform--DataProtection--Key --output none`. `Erp:Platform:DataProtection:KeyIdentifier` names the key without a version, so nothing else changes and no restart is needed: the keys already written stay wrapped by the old version, and the next key Data Protection creates is wrapped by the new one.
2. Never disable or delete a version while any key file of that environment names it in its `<kid>`: the API refuses to start when it cannot unwrap a key that could still protect a live session (`KeyRingStartupCheck`), and once a version is gone the keys it wrapped are unreadable for good. A version that has merely expired still unwraps. Purge protection keeps a deleted key recoverable for 90 days.
3. Read the result back: the API starts, and `bash scripts/azure/verify.sh --labels` still finds `Erp:Platform:DataProtection:KeyIdentifier` under both labels.

When the key ring is lost (the volume deleted, a server rebuilt without a restore, a developer's folder removed), everyone is signed out and the stored tokens become unreadable; the API reads an unreadable token cache entry as signed out, so each person simply signs in again, and nothing else is lost. Restore the volume from the nightly backup ([restore runbook](restore.md)) with the stack stopped, before the api starts and writes a new ring; every key version an archive's key files name must still be enabled (step 2). Never point a run without `Erp:Platform:DataProtection:KeyIdentifier`, a test or a tool at a real key folder: it cannot unwrap the keys there. The api container's identity needs `keys/read`, wrap and unwrap on this key only, which Key Vault Crypto Service Encryption User grants; without `keys/read` new keys would record a versionless identifier that a later rotation breaks, so the startup check refuses it.

### 5f. Attachments encryption key

`Erp--Platform--Attachments--EncryptionKey` is the key-encryption key of the attachments envelope: the API wraps every attachment's random data key with it (AES-256-GCM) before the ciphertext reaches Blob Storage. Its value is `<key id>:<32 random bytes, base64>`; the key id is 1 to 32 characters from `A-Z`, `a-z`, `0-9`, `.`, `_` and `-`, is stored in plain text in every envelope header and in `files.StoredContents.KeyId`, and must never be reused: the API refuses a configuration in which one id names two different keys. The key itself is never typed, pasted, echoed or passed as a command argument, and it has no issuer: the vault is its home (a developer machine keeps a copy of the development keys in `dotnet user-secrets` for store-less runs; production keys exist nowhere else), so losing every copy of a key makes every attachment it wrapped unreadable (soft delete and purge protection on the vault guard against that).

The block below creates the key once per vault (the reference in `infra/appconfig/key-vault-references.json`, written under both labels, makes `seed.sh` stop until the label's secret exists) and every new current key of a rotation (step 4). It runs from the repository root in a subshell that stops at the first failed command, so a failed read or key generation never uploads a malformed key. It refuses to replace a current key that `Erp--Platform--Attachments--RetiredEncryptionKeys` does not list, so it can never strand the attachments that key wrapped. The bytes are generated inside it, every value passes through private temporary files that are shredded when the block ends, whether or not a step succeeded, and `--output none` keeps the stored value off the screen. With `user_secrets=true` (the development vault, on the operator's machine) it also pipes the same value as JSON into `dotnet user-secrets set` for the API project, which merges it into the secrets already there with the tool's output discarded, so store-less runs use the same key; every other developer copies it with the block in [docs/guides/local-development.md](../../guides/local-development.md), section "Attachments storage", which also creates the development key when the vault has none.

```bash
(
  set -euo pipefail
  umask 077
  vault=kv-erp-ai-pro-dev
  prefix=dev
  user_secrets=true
  key_file="$(mktemp)"
  current_file="$(mktemp)"
  retired_file="$(mktemp)"
  trap 'shred -u "$key_file" "$current_file" "$retired_file"' EXIT
  key_count="$(az keyvault secret list --vault-name "$vault" --query "length([?name=='Erp--Platform--Attachments--EncryptionKey'])" --output tsv | tr -d '\r')"
  retired_count="$(az keyvault secret list --vault-name "$vault" --query "length([?name=='Erp--Platform--Attachments--RetiredEncryptionKeys'])" --output tsv | tr -d '\r')"
  if [ "$key_count" != 0 ]; then
    az keyvault secret show --vault-name "$vault" --name Erp--Platform--Attachments--EncryptionKey --query value --output tsv | tr -d '\r\n' > "$current_file"
    if [ "$retired_count" = 1 ]; then
      az keyvault secret show --vault-name "$vault" --name Erp--Platform--Attachments--RetiredEncryptionKeys --query value --output tsv | tr -d '\r\n' | tr ';' '\n' > "$retired_file"
    fi
    if ! grep -qxFf "$current_file" "$retired_file"; then
      echo "The current attachments key in $vault is not in Erp--Platform--Attachments--RetiredEncryptionKeys; retire it first (rotation step 1)." >&2
      exit 1
    fi
  fi
  material="$(openssl rand -base64 32)"
  printf '%s-%s:%s' "$prefix" "$(date -u +%Y%m%d%H%M%S)" "$material" > "$key_file"
  az keyvault secret set --vault-name "$vault" --name Erp--Platform--Attachments--EncryptionKey --file "$key_file" --encoding utf-8 --output none
  if [ "$user_secrets" = true ]; then
    { printf '{"Erp:Platform:Attachments:EncryptionKey":"'; cat "$key_file"; printf '"}'; } | dotnet user-secrets set --project backend/Hosts/Api/Dewiride.Erp.Host.Api > /dev/null
  fi
)
```

The production key comes from the same block with `vault=kv-erp-ai-pro-prod`, `prefix=prod` and `user_secrets=false`, never from the development value, and lives in `kv-erp-ai-pro-prod` alone: no user secret, file or other vault holds a copy. The local container stack uses a separate key of the same shape in the file secret `infra/compose/secrets/Erp__Platform__Attachments__EncryptionKey`, created as [docs/guides/local-development.md](../../guides/local-development.md) describes; it protects only the attachments the stack keeps in its storage emulator and never enters a vault.

Rotation, per vault (the example rotates `kv-erp-ai-pro-dev` under `local-dev`). Attachments already stored stay wrapped by the key that wrote them, so the old key moves to `Erp--Platform--Attachments--RetiredEncryptionKeys`, a `;`-separated list of `<key id>:<key>` entries the API reads only to decrypt. The API accepts the same key in both settings (an id that names two different keys is still refused), so the current key is retired first and replaced afterwards, and every state the vault passes through is a valid configuration: a restart, a sentinel bump or the hourly secret re-read of section 4 at any moment of the rotation is harmless, and the steps need not run in one sitting. The one ordering rule is step 3: every running API must hold the retired list of step 1 before the current key changes, because an API that picks up the new current key while still holding an older retired list keeps uploading but answers 404 `attachment.not-found` for every attachment the old key wrapped until it next reloads.

1. Append the current value to the retired list without displaying either. The block stops at the first failed command, so a failed read never writes a shortened list; running it twice leaves a duplicate entry, which the API ignores. With `user_secrets=true` (the development vault, on the operator's machine) it also copies the new list into your user secrets, so your store-less runs keep reading the old attachments after step 4:

   ```bash
   (
     set -euo pipefail
     umask 077
     vault=kv-erp-ai-pro-dev
     user_secrets=true
     retired_file="$(mktemp)"
     trap 'shred -u "$retired_file"' EXIT
     retired_count="$(az keyvault secret list --vault-name "$vault" --query "length([?name=='Erp--Platform--Attachments--RetiredEncryptionKeys'])" --output tsv | tr -d '\r')"
     if [ "$retired_count" = 1 ]; then
       az keyvault secret show --vault-name "$vault" --name Erp--Platform--Attachments--RetiredEncryptionKeys --query value --output tsv | tr -d '\r\n' > "$retired_file"
       printf ';' >> "$retired_file"
     fi
     az keyvault secret show --vault-name "$vault" --name Erp--Platform--Attachments--EncryptionKey --query value --output tsv | tr -d '\r\n' >> "$retired_file"
     az keyvault secret set --vault-name "$vault" --name Erp--Platform--Attachments--RetiredEncryptionKeys --file "$retired_file" --encoding utf-8 --output none
     if [ "$user_secrets" = true ]; then
       { printf '{"Erp:Platform:Attachments:RetiredEncryptionKeys":"'; cat "$retired_file"; printf '"}'; } | dotnet user-secrets set --project backend/Hosts/Api/Dewiride.Erp.Host.Api > /dev/null
     fi
   )
   ```

2. On the first rotation only, add `{ "key": "Erp:Platform:Attachments:RetiredEncryptionKeys", "secret": "Erp--Platform--Attachments--RetiredEncryptionKeys", "labels": ["local-dev"] }` to `infra/appconfig/key-vault-references.json` in your working copy (listing each label whose vault holds the secret) and write the reference with `bash scripts/azure/seed.sh --label local-dev`, which also bumps the label's sentinel. Commit the change in a pull request afterwards like any other seed change.
3. Make sure every running API holds the new retired list: restart `dotnet run` (every developer who runs it against the store) and recreate the api container as section 4 shows, or wait until both the change check after the sentinel bump and the secret refresh interval have passed (section 4: 30 minutes and 1 hour). A store-less `dotnet run` reads the list from user secrets: step 1 put it in yours, and every other developer runs the block in [docs/guides/local-development.md](../../guides/local-development.md), section "Attachments storage", before restarting.
4. Create the new current key with the creation block above, with the same `vault`, `prefix` and `user_secrets`: it finds the current key in the retired list, writes a new version of `Erp--Platform--Attachments--EncryptionKey` with a new id and, with `user_secrets=true`, puts the same value in your user secrets.
5. Bump the sentinel of the label (section 4), or restart `dotnet run` and recreate the api container, so every API encrypts with the new key; every other developer runs the local-development block again, which copies the new current key and the retired list into their user secrets.
6. Confirm that an attachment uploaded before the rotation still downloads and that a new upload succeeds, then disable the previous version of `Erp--Platform--Attachments--EncryptionKey` (5a step 4); the retired list now holds the old key's only live copy in the vault. The ids in `files.StoredContents.KeyId` show which attachments each retired key still protects; a retired entry is removed only after no row in any database that uses the vault names its id (for the development vault that is every developer's `ErpAiPro`, so development keys stay retired).

Never write a new current key with a bare `az keyvault secret set`: a key that replaces one the retired list does not hold makes every attachment the old key wrapped unreadable until the old key is taken from the secret's previous version and retired as in step 1.

After an exposure, rotate the same way and treat every attachment wrapped by the exposed key as readable by whoever holds it together with blob read access: Blob Storage never received the key, so the exposure matters only in combination with a storage role or the account itself. A copy of the development key sits in the user secrets of every developer machine that ran the local-development block, so a lost or compromised developer machine counts as an exposure of the development key.

### 5g. Backup encryption certificate

`Erp--Platform--Backup--EncryptionCertificate` in `kv-erp-ai-pro-ops` is the recipient every backup archive is sealed to: the server encrypts each archive with OpenSSL CMS, AES-256-GCM under a new random key, and seals that key with RSA-OAEP-SHA256 to the certificate's public key, `erp-backup-recipient.crt` on the server ([restore runbook](restore.md)). Only the private key of the version an archive was sealed to opens it. Every version has a key of its own (`reuseKey` `false`), and the private keys exist only in the vault and, for the length of a restore, in the copy the operator exports; the server never holds one, so a compromised server cannot read the archives it already stored.

Rotate it once a year with the client certificates, before the end date that `verify.sh --entra` warns about 30 days ahead, or at once after an exposure:

1. `bash scripts/azure/entra.sh --rotate-encryption-certificate` creates a new version with a new key; it is no registration's credential, so nothing is registered and nothing is pruned.
2. `bash scripts/azure/export-client-certificate.sh backup-recipient` downloads the new public certificate and prints its SHA-256 fingerprint. Copy it to the server's administrator, who places it in place of the old one with the host bootstrap's `--backup-recipient` option ([host setup runbook](host-setup.md)), removes the copy in their home and compares the fingerprint `sudo openssl x509 -in /srv/erp-ai-pro/ERP-AI-Pro/infra/compose/secrets/erp-backup-recipient.crt -noout -fingerprint -sha256` prints (the folder is the deploy account's, so the administrator reads it with `sudo`). From the next backup on, archives are sealed to the new version.
3. Keep every earlier version enabled. The archives sealed before the rotation open with their own version's key alone, until they are past their 90 days and the backup job has deleted them; disabling or deleting that version sooner makes them unopenable (purge protection keeps a deleted version recoverable for 90 days). Once the newest archive sealed to a version is past its 90 days, that version may be disabled: `az keyvault certificate set-attributes --vault-name kv-erp-ai-pro-ops --name Erp--Platform--Backup--EncryptionCertificate --version <version> --enabled false`.
4. `bash scripts/azure/verify.sh --entra`.

A restore takes the version its archive needs. Without `--version` the export takes the current version, which opens every archive sealed since the last rotation. For an older archive, a dry run of `scripts/deploy/restore.sh --name <archive> --key <file> --dry-run` with the key at hand names the serial number the archive is sealed to, in the hexadecimal form without leading zeros that the export prints; `az keyvault certificate list-versions --vault-name kv-erp-ai-pro-ops --name Erp--Platform--Backup--EncryptionCertificate --query '[].{version: id, created: attributes.created, enabled: attributes.enabled}' --output table` lists the versions, and `bash scripts/azure/export-client-certificate.sh backup-recipient-key --version <version>` exports the one whose printed serial number matches. `restore.sh` shreds the key on the server once it is done; shred the workstation's copy as well.

An exposure of a private key matters together with the archives sealed to it, which the backup account gives only to the home's address and the backup service principal. Those archives hold the proxy's root key in the clear, while the key ring's keys in them stay wrapped by `Erp--Platform--DataProtection--Key`, which only the runtime service principal can use (section 5e). After an exposure, rotate as above and treat the proxy's root as exposed too: replacing it means a new authority that every device trusts again ([proxy runbook](proxy.md)).

## 6. Emergency revocation

Order: revoke, rotate, investigate — never investigate first.

1. Revoke the exposed credential immediately. Certificate: `az ad app credential delete --id <appId> --key-id <keyId> --cert` (the key id is listed by `az ad app credential list --id <appId> --cert`; without `--cert` the command lists password credentials, of which there must be none). The backup encryption certificate is no credential and cannot be revoked: rotate it as section 5g says. An application token the API received with the sign-in certificate before the revocation stays valid until it expires, about an hour later, so the directory can be read with it until then. Ordinary secret: revoke it at the issuer (drop or reset the SQL login, revoke the token at the provider), then disable the vault version: `az keyvault secret set-attributes --vault-name <vault> --name <secret> --version <version> --enabled false`.
2. Rotate as in section 5, bump the sentinel for every affected label and recreate the api container as section 4 shows.
3. Investigate with the API and container logs, the vault's diagnostic log and the Entra sign-in log; record what was exposed, when, and what was rotated.
4. If the value reached git history, rotate first and only then decide with the owner whether history is rewritten; a rotated value is worthless, an unrotated one stays dangerous whatever happens to the history.
