# Azure bootstrap (operator guide)

The scripts under `scripts/azure/` create and converge the only Azure resources this project uses: one App Configuration store, one Key Vault per environment and one for the certificates of the server identities and of the backups, one storage account per environment that holds attachments ([ADR-0051](../adr/0051-the-production-attachments-storage-geo-redundant-and-reachable-from-the-homes-address-alone.md) for the production one), one storage account for the server's nightly backups and its journal (section 5f, [restore runbook](runbooks/restore.md)), one storage account for the records of the Azure resources, the subscription, the production database and Microsoft Entra ID, kept a year inside India (section 5g, [records runbook](runbooks/records.md)), the production Azure SQL database ([ADR-0050](../adr/0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md), [database runbook](runbooks/database.md)) and the Entra app registrations. Every script is idempotent: a second run with the same parameter file changes nothing, with one deliberate exception: `seed.sh` bumps the labelled `Erp:Sentinel` on every run unless `--no-sentinel` is given (section 5b). Nothing in this guide or in the scripts deletes or purges a resource; what the scripts delete are credentials and one role: `entra.sh --prune-old-credentials` removes the key credentials that are not a registration's current certificate (section 5a), and `provision.sh` removes a role the migrator holds on the whole production vault (section 5).

## 1. Purpose and resources

Resource names come from `scripts/azure/params.env`; the defaults below are the values in `scripts/azure/params.env.example`.

| Resource | Default name | Purpose |
|---|---|---|
| Resource group | `rg-erp-ai-pro` | holds everything below; the group, the store, the three vaults, the four storage accounts and the SQL server and database are tagged `project=erp-ai-pro`, `managedBy=scripts/azure` |
| App Configuration store | `appcs-erp-ai-pro` | every non-secret setting and feature flag, unlabelled defaults overridden by the labels `local-dev` and `production`; local authentication disabled, Entra ID only |
| Key Vault (development) | `kv-erp-ai-pro-dev` | secrets and certificates for `local-dev`, reached by the API only as App Configuration Key Vault references |
| Key Vault (production) | `kv-erp-ai-pro-prod` | secrets and certificates for `production`, such as the production sign-in certificate and the production database's connection strings |
| Key Vault (operations) | `kv-erp-ai-pro-ops` | the client certificates the runtime, migrator and backup service principals sign in with, and the backup encryption certificate, whose public part the server seals every backup archive and every copy of its journal to and whose private key alone opens them; only the operator holds a role on it, and no application reads it ([ADR-0050](../adr/0050-the-production-database-azure-sql-basic-with-microsoft-entra-only-users.md), section 5a) |
| Data-protection key | `Erp--Platform--DataProtection--Key` in the development and production vaults | RSA 2048 key with `wrapKey`/`unwrapKey` that wraps every key of the API's ASP.NET Core Data Protection key ring (ADR-0032); `provision.sh` writes its versionless URI to the store as `Erp:Platform:DataProtection:KeyIdentifier` (section 5c) |
| Storage account (development) | `sterpaiprodev` | attachment content for `dotnet run` against the `local-dev` label (the Playwright suite keeps its files in Azurite); `StorageV2`, `Standard_LRS`, access tier Hot, in the resource group's region |
| Storage account (production) | `sterpaiproprod` | attachment content of the server's api under the `production` label; `StorageV2`, `Standard_GRS` (a second copy in South India), access tier Hot, in the resource group's region, reachable only from the home's public IPv4 address (section 5e) |
| Storage account (backups) | `sterpaiprobackup` | the server's nightly backups, one sealed archive a night of the two volumes, `.env` and `.env.previous` ([restore runbook](runbooks/restore.md)), and a sealed copy of each day of the server's journal ([records runbook](runbooks/records.md)); used for nothing else; `StorageV2`, `Standard_GRS`, access tier Hot, in the resource group's region, reachable only from the home's public IPv4 address (section 5f) |
| Storage account (logs) | `sterpaiprologs` | the records of the three vaults, the blob services of the other three storage accounts, the store, the subscription's activity log, the production database's auditing and Microsoft Entra ID's audit and sign-in logs, each write-once for 365 days and deleted a day later; used for nothing else; `StorageV2`, `Standard_LRS` (one copy, in Central India), access tier Hot, in the resource group's region, reachable only from the home's public IPv4 address and by trusted Microsoft services (section 5g) |
| Blob container | `attachments` in the development and production accounts; `host-backups` and `host-journal` in the backup account | private (`publicAccess` `None`) and created by the template, so neither the API nor the server's jobs need the right to create containers; `host-backups` keeps every archive write-once for 90 days and `host-journal` every copy of the journal for 365 days (section 5f). The logs account's containers (`insights-logs-<category>`, `insights-activity-logs`, `sqldbauditlogs`) are created by the services that write the records, when they first write (section 5g) |
| Resource lock | `do-not-delete` (`CanNotDelete`) on each storage account | blocks deletion of the account, which blob and container soft delete do not cover |
| Diagnostic settings | `erp-ai-pro-records` on the three vaults, on the blob service of the development, production and backup accounts, on the store, on the subscription and on Microsoft Entra ID | send those resources' logs, the activity log and Entra's audit and sign-in logs to the logs account, and nothing else anywhere (section 5g) |
| Azure SQL server (production) | `sql-erp-ai-pro` | Microsoft Entra-only authentication with the operator as its Microsoft Entra admin, TLS 1.2 at least, IPv6 off, one firewall rule `home` for the home's public IPv4 (kept by `home-address.sh`, never by the template), a system-assigned identity, and server-level auditing of sign-ins and of changes of structure, users and permissions, never statements, written to the logs account with that identity (section 5g) |
| Azure SQL database (production) | `ErpAiPro` | the production ERP database: Basic, 5 DTU, at most 2 GB, 7 days of point-in-time restore, each weekly full backup kept 5 weeks and the first of each month 12 months (long-term retention, section 5d), geo-redundant backups to South India |
| Resource lock | `do-not-delete` (`CanNotDelete`) on the SQL server | blocks deletion of the server and its database; the firewall rule can still be changed |

All three vaults use RBAC authorization, soft delete with a 90-day retention and purge protection. The store runs on the Free tier by the owner's decision (ADR-0010); it has no soft delete, so the seed files in the repository are its recovery path.

All four storage accounts accept Entra ID only: `allowSharedKeyAccess` is `false`, so no account key, connection string, account SAS or service SAS can authorize a request, and `defaultToOAuthAuthentication` makes the portal use Entra ID as well. Public blob access and cross-tenant object replication are disallowed, the minimum TLS version is 1.2, only HTTPS is accepted, and the hierarchical namespace, SFTP, NFS 3.0 and local users are off. All four keep their public endpoint (`publicNetworkAccess` `Enabled`), because developer machines and the on-premises server have no virtual network to restrict to, and every request still needs an Entra token and a data role. The development account admits every address (network rule `defaultAction` `Allow`), because developers work from changing addresses; the production and backup accounts refuse every request (`defaultAction` `Deny`, `bypass` `None`) except from their one IP rule, the home's public IPv4 address (sections 5e and 5f); the logs account refuses every request except from that one IP rule and from trusted Microsoft services (`bypass` `AzureServices`), the way Azure Monitor and the SQL server's auditing deliver its records (section 5g). Blob soft delete and container soft delete keep deleted data for 7 days in the development, backup and logs accounts and 90 in the production account; the change feed is off everywhere, and versioning is off in the first three, because the API writes each blob once under a new unique name (the version-7 id of its stored-content row) and never overwrites it, and the server's jobs write each archive and each copy of the journal once under a new name too. Versioning is on in the logs account alone, because version-level immutability needs it (section 5g). The API encrypts every attachment with its own AES-256-GCM envelope before upload (key in Key Vault as `Erp--Platform--Attachments--EncryptionKey`, [runbooks/secrets.md](runbooks/secrets.md) section 5f), and the server seals every backup archive before upload (section 5f); Azure's server-side encryption with Microsoft-managed keys stays on underneath.

```bash
cp scripts/azure/params.env.example scripts/azure/params.env
```

## 4. Order of operations

Run every command from the repository root.

| Step | Command | What it does |
|---|---|---|
| 1 | `bash scripts/azure/check.sh` | compiles the Bicep template with the linter and syntax-checks every script; no sign-in needed |
| 2 | `bash scripts/azure/provision.sh --dry-run` | checks the four storage account names and the SQL server name (read-only), prints the `what-if` result and every data-plane command, the activity log's and Microsoft Entra ID's diagnostic settings included, without writing anything |
| 3 | `bash scripts/azure/provision.sh` | creates or converges the resource group, the store, the three vaults, the data-protection keys of the development and production vaults, the four storage accounts with their containers and locks (the production, backup and logs accounts admitting the address of the database's rule `home` alone, none on the first run, and the logs account trusted Microsoft services too; the backup account's `host-backups` and `host-journal` under their write-once policies, unlocked, section 5f; the logs account under its write-once account policy, unlocked, with its lifecycle rule, section 5g), the production SQL server with its identity, its auditing, its database, its long-term retention and its lock, the diagnostic settings `erp-ai-pro-records`, the role assignments, the two labelled `Erp:Sentinel` keys, `Erp:Platform:Attachments:BlobServiceUri` and `Erp:Platform:DataProtection:KeyIdentifier` under both labels (section 5c), the production database's connection strings in the production vault (section 5d), and last the diagnostic settings of the subscription's activity log and of Microsoft Entra ID (section 5g; Entra's needs the operator to hold Security Administrator or Global Administrator, and a refusal makes the run exit 1 after every other step) |
| 4 | `bash scripts/azure/entra.sh --dry-run` | prints every Graph, Key Vault and App Configuration write it would make, with `<pending>` in place of the ids a create would produce; writes nothing |
| 5 | `bash scripts/azure/entra.sh` | creates or converges the five app registrations, their service principals, app roles, Graph consent, certificates (the runtime's, the migrator's and the backup's in the operations vault, with the backup encryption certificate) and key credentials, assigns the operator `Erp.Admin` and writes the identity ids and web origins to App Configuration (section 5a) |
| 6 | `bash scripts/azure/provision.sh` | run again: grants the runtime and migrator service principals their roles on the store, the production vault, the production `attachments` container and the two connection strings the first run wrote, and the backup service principal its roles on `host-backups` and `host-journal`, none of which can be granted before step 5 |
| 7 | `bash scripts/azure/seed.sh --dry-run` | previews every import with the CLI's own `--dry-run` and prints every other write; writes nothing. Create `Erp--Platform--Attachments--EncryptionKey` in the development and the production vault first, each with a value of its own ([runbooks/secrets.md](runbooks/secrets.md) section 5f): the reference to it, written under both labels, stops the real run while either secret is missing |
| 8 | `bash scripts/azure/seed.sh` | imports `infra/appconfig` (unlabelled defaults, each label file, feature flags, Key Vault references) and bumps the labelled sentinels (section 5b) |
| 9 | `bash scripts/azure/home-address.sh`, then `bash scripts/azure/database.sh` | from a computer on the home network, without a VPN: the rules that admit the home's address to the production database and the production, backup and logs storage accounts ([runbooks/home-address.md](runbooks/home-address.md)), then the database's users (section 5d); the second command reports that the migrations have not run yet; `--dry-run` first |
| 10 | the first migration | the migrator, run once from the operator's computer as its own identity, creates every schema and the role `erp_audit_append_only` ([runbooks/database.md](runbooks/database.md), section "First migration") |
| 11 | `bash scripts/azure/database.sh` | run again: adds the runtime's user to `erp_audit_append_only`, then to the data roles, and proves both users' rights |
| 12 | `bash scripts/azure/verify.sh` | reads the provisioned resources back and prints `[ok]` or `[FAIL]` per assertion; for each storage account it checks the account properties, the redundancy, the blob service settings and retention, the private containers, the lock and the roles, for the development account a read-only blob listing signed in with Entra ID (`--auth-mode login`), for the production, backup and logs accounts their network rules (the address of the database's rule `home` alone, and trusted Microsoft services for the logs account alone), for the backup account the write-once policies of `host-backups` (90 days) and `host-journal` (365 days), each without protected append writes or legal hold, and for the logs account its write-once account policy (365 days, protected append writes) and its lifecycle rule (366 days), with a `[warn]` line while a policy is unlocked; it reads back the SQL server's identity and auditing (the logs account, the action groups, 366 days, no auditing of the database's own), the diagnostic settings `erp-ai-pro-records` of the three vaults, the three other accounts' blob services, the store, the activity log and Microsoft Entra ID; it checks that the runtime, migrator and backup service principals and the SQL server's identity hold exactly their roles, directly or through a group, that only the operator holds a role on or in the operations vault, that only the runtime service principal holds one on or in the production storage account, only the backup service principal on or in the backup storage account, and only the SQL server's identity and the operator on or in the logs account |
| 13 | `bash scripts/azure/verify.sh --entra` | reads the registrations, service principals, grants (including `offline_access`), certificates, key credentials, identity ids and web origins back, and the backup encryption certificate (RSA 4096, key encipherment only, exportable, a new key per version, only in the operations vault), and fails while a registration signs in with anything but its current certificate or the production vault holds a client certificate or the encryption certificate; the production web origin is skipped while `ERP_AZURE_PRODUCTION_WEB_ORIGIN` is empty |
| 14 | `bash scripts/azure/verify.sh --labels` | reads every seeded value, flag and reference back, proves the `local-dev` label overrides the unlabelled default and compares `Erp:Platform:Attachments:BlobServiceUri` under each label with that label's storage account and `Erp:Platform:DataProtection:KeyIdentifier` under each label with that label's vault key |
| 15 | `bash scripts/azure/verify.sh --database` | reads the production SQL server, its Microsoft Entra admin, its firewall (with no virtual network rule, private endpoint or IPv6 rule), the database, its point-in-time restore and long-term retention policies, both connection strings and, through the Go sqlcmd, the database users and their rights back |
| 16 | after the first restore rehearsal succeeds ([restore runbook](runbooks/restore.md)), after a day of the journal has been read back ([records runbook](runbooks/records.md)) and after the first records have reached the logs account | lock the write-once policies of `host-backups` and `host-journal` (section 5f) and of the logs account (section 5g), each when its own proof is done; later `provision.sh` runs leave each locked policy as it is |

`provision.sh` ends by printing `APPCONFIG_ENDPOINT=https://<store>.azconfig.io`, the three vault URIs, `DATA_PROTECTION_KEY_URI_DEV` and `DATA_PROTECTION_KEY_URI_PROD` (the versionless key identifiers it writes to the store itself, so they need no copying), `ATTACHMENTS_BLOB_ENDPOINT_DEV` and `ATTACHMENTS_BLOB_ENDPOINT_PROD` (`https://<account>.blob.core.windows.net/`), `BACKUP_BLOB_ENDPOINT` and `BACKUP_CONTAINER` (the backup account's endpoint and its container, which the store never holds: the server puts both lines in `infra/compose/.env` for its backup, [runbooks/host-setup.md](runbooks/host-setup.md)) and `SQL_SERVER_PROD=<server>.database.windows.net`. Keep the store endpoint: developers put it in `dotnet user-secrets`, and the server puts it in `infra/compose/.env`, from which `compose.yaml` passes it to the api container as `APPCONFIG_ENDPOINT`. The blob endpoints need no copying when the API loads the store, because `provision.sh` writes them there itself (section 5c); a store-less `dotnet run` reads the development endpoint from `dotnet user-secrets` instead ([docs/guides/local-development.md](../guides/local-development.md), section "Attachments storage").

Key Vault Certificate User is deliberately unassigned: the API reads sign-in certificates through the secret endpoint, which Key Vault Secrets User covers. Key Vault Crypto User is unassigned too: the API only reads the data-protection key and wraps and unwraps with it, which Crypto Service Encryption User grants (the built-in role also carries Event Grid subscription management on the vault, its only control-plane part), while Crypto User would also let it update the key or use it to encrypt, decrypt, sign and verify; `verify.sh` fails while a Crypto User assignment remains for the developers group, and `az role assignment delete --assignee <principal object id> --role "Key Vault Crypto User" --scope <vault resource id>` removes it. The migrator holds no crypto role and no role on the vault as a whole: Key Vault Secrets User on the two connection strings, a role assignment at secret scope, which Microsoft reserves for secrets shared between applications, and its host opens no other Key Vault reference of the store (ADR-0050). `provision.sh` grants each of the two once it exists and removes a Key Vault Secrets User the migrator holds on the whole production vault. The backup service principal holds no Key Vault, App Configuration or database access at all: one role on each of the backup account's two containers. `verify.sh` fails on any role of the runtime, migrator or backup service principal or of the SQL server's identity beyond this table, held directly or through a group, on any assignment on or in the operations vault but the operator's, and on a Key Vault data role above that vault, and likewise on any assignment on or in the production storage account but the runtime service principal's, on or in the backup storage account but the backup service principal's, or on or in the logs account but the SQL server's identity's and the operator's, and on a Storage data role above any of the three.

The production database grants no Azure role: the api and the migrator reach it as contained users of the database, which `database.sh` converges as the Microsoft Entra admin (section 5d), and the operator administers it through that admin role.

The storage roles are scoped to the one container, not to the account, following Microsoft's advice to scope data roles as narrowly as possible. They are the developers group's first write permission in Azure: `dotnet run` uploads, reads and deletes attachment blobs as the developer's own `az login` identity, so every member of the group can change development attachment data (never production data, which lives in a separate account). The runtime service principal and the migrator hold no role on the development account. On the production account the runtime service principal alone holds one, Storage Blob Data Contributor on its container: no person, group or the migrator reads production files, which a restore changes for its duration only (section 8). On the backup account the backup service principal alone holds one, Storage Blob Data Contributor on `host-backups` and on `host-journal`, the least privileged built-in role that both creates blobs and lists, reads and deletes them: the nightly jobs upload an archive or a copy of the journal, read it back and delete those past their period, a restore on the server downloads one, and the write-once policies keep that identity, like everyone else, from overwriting any blob or deleting one younger than its 90 or 365 days (section 5f). The logs account's two roles are scoped to the account, because the services that write the records create their own containers: the SQL server's identity holds Storage Blob Data Contributor, which Azure SQL needs to create `sqldbauditlogs` and write its audit records past the account's firewall, and the operator Storage Blob Data Reader, which reads every container, so records are read and handed over without a temporary role (section 5g). Diagnostic settings need no role: Azure Monitor writes as a trusted Microsoft service. The scripts assign nobody Storage Account Contributor (it includes the account keys), Storage Blob Data Owner or Storage Blob Delegator: with Shared Key disabled no key or key-signed SAS works anyway, and the API streams every download itself, so no user delegation SAS is ever issued. A new or removed storage role takes up to 10 minutes to take effect on blob requests; a `403` from blob storage inside that window is expected.

## 5a. Entra app registrations

`bash scripts/azure/entra.sh` creates or converges five single-tenant app registrations. Each one is found by its exact display name from `params.env`: no match creates it, one match converges it property by property, more than one match stops the script and names the duplicates. A second run with the same parameters performs no Microsoft Graph or Key Vault write. No registration ever holds a client secret; every credential is a certificate whose private key lives only in Key Vault (and, for the runtime, migrator and backup registrations, whose certificates live in the operations vault, in the server's compose secret files).

| Registration | Parameter | Platform | Used by |
|---|---|---|---|
| local-dev sign-in | `ERP_AZURE_APP_WEB_LOCAL_DEV_NAME` | web | the API on a developer machine, which signs employees in on the browser's behalf (the browser holds only a cookie) |
| production sign-in | `ERP_AZURE_APP_WEB_PRODUCTION_NAME` | web | the deployed API, in the same way |
| runtime | `ERP_AZURE_APP_RUNTIME_NAME` | none | the service principal the api container signs in as to read the store and the production vault and to read and write the production `attachments` container, and the api's database user; no redirect URIs, no app roles, no Graph permissions |
| migrator | `ERP_AZURE_APP_MIGRATOR_NAME` | none | the service principal the migrator container signs in as to read the store and its two connection strings, and the migrator's database user with the schema rights; no redirect URIs, no app roles, no Graph permissions |
| backup | `ERP_AZURE_APP_BACKUP_NAME` | none | the service principal the server's nightly backup signs in as to write, read back and prune archives in `host-backups` of the backup account, its nightly copy of the journal (`scripts/deploy/journal.sh`, `erp-ai-pro-journal.service`) to do the same with the copies in `host-journal`, and a restore and `journal.sh --fetch` to download them; no redirect URIs, no app roles, no Graph permissions, no database user, no Key Vault or App Configuration role |

Properties every registration converges to: `signInAudience` `AzureADMyOrg`; implicit grant off (`enableIdTokenIssuance` and `enableAccessTokenIssuance` both `false`); `api.requestedAccessTokenVersion` `2`; no single-page, mobile or fallback public client platform. The operator is added as owner of every registration (Microsoft Graph does not record the creator as owner); a same-named registration owned by someone else is refused, never adopted, while one without owners is adopted, and `verify.sh --entra` then fails on every credential it carries besides the certificate `entra.sh` made. Sign-in registrations additionally get a service principal with `appRoleAssignmentRequired` `true`, so only assigned users can sign in; the optional claim `login_hint` on ID tokens (exactly that claim, `scripts/azure/entra/optional-claims.json`), which the API sends back as `logout_hint` so Entra signs the account out without asking which one; and, when their web origin is https, the front-channel logout URL `<web origin>/api/auth/signout-oidc` (section "Redirect URIs").

### Redirect URIs

| Registration | Redirect URIs |
|---|---|
| local-dev sign-in | `<ERP_AZURE_LOCAL_WEB_ORIGIN>/api/auth/signin-oidc`, `<ERP_AZURE_LOCAL_WEB_ORIGIN>/api/auth/signout-callback-oidc`; the API builds every redirect URI from `Erp:Platform:Identity:WebOrigin`, so no redirect URI names the API's own origin and Entra sends no code to a port the web app does not serve |
| production sign-in | `<ERP_AZURE_PRODUCTION_WEB_ORIGIN>/api/auth/signin-oidc`, `<ERP_AZURE_PRODUCTION_WEB_ORIGIN>/api/auth/signout-callback-oidc`; while the parameter is empty no redirect URI is requested and the script warns that production sign-in stays impossible until the parameter is set and `entra.sh` is run again. A re-run with an empty parameter never removes redirect URIs that are already registered: it stops and lists them, and only `bash scripts/azure/entra.sh --clear-production-redirect-uris` removes them deliberately |
| runtime, migrator, backup | none |

The API sends the redirect URIs it builds from `Erp:Platform:Identity:WebOrigin` (the value `entra.sh` writes from the web origin parameter), never from the request, so Entra always returns to the web origin, and no registration lists a redirect URI on the API's own origin ([ADR-0038](../adr/0038-sign-in-limit-security-events-and-the-audit-schema.md)). A sign-in registration whose web origin is https gets the front-channel logout URL (`web.logoutUrl`) `<web origin>/api/auth/signout-oidc`, which Entra loads in a hidden frame when the person signs out of another app of the tenant, so the API ends that person's sessions as its own sign-out does ([ADR-0036](../adr/0036-web-sign-in-the-session-in-the-browser-and-single-sign-out.md)); Entra refuses an http front-channel logout URL, `http://localhost` included, so the local-dev registration (`http://localhost:3000`) has none, and the production registration gets it once `ERP_AZURE_PRODUCTION_WEB_ORIGIN` is set and `entra.sh` is run again. `entra.sh` sets the URL with a Microsoft Graph PATCH of `web`, removes one where none belongs, and a dry run names both changes as `logoutUrl` and `optionalClaims`; `verify.sh --entra` checks them. The API's front-channel route finds the person from the Entra session the request names, never from a cookie, so a page that sends a browser there without that session's id signs nobody out. `RedirectPathsTests` compares `REDIRECT_PATHS` and `FRONT_CHANNEL_SIGN_OUT_PATH` in `scripts/azure/lib/graph.sh` with the API's paths, and checks that `optional-claims.json` names exactly `login_hint`.

### App roles

The roles live in `scripts/azure/entra/app-roles.json` with fixed ids, so the same ids exist in every tenant the scripts are ever run against.

| Value | Display name | Id | Purpose |
|---|---|---|---|
| `Erp.User` | ERP User | `3f1c9a6e-2b4d-4e8f-9c1a-5d7e8f0a1b2c` | signed-in employee with the baseline permissions |
| `Erp.Admin` | ERP Administrator | `a8d2e4f6-1c3b-4a5d-8e9f-0b1c2d3e4f5a` | administers the ERP and holds every permission |

Both roles are assignable to users only and enabled. `entra.sh` updates the roles only when the registration's roles differ from the file (compared on id, value, enabled state, display name, description and member types). A role that is enabled on the registration but absent from the file is never removed: Entra requires it to be disabled first, so the script warns and skips the role update. The operator who runs the script is assigned `Erp.Admin` on both sign-in service principals; further assignments are made in the Entra portal or with `az rest` against `appRoleAssignedTo`.

### Consent path

Each sign-in registration requests the Microsoft Graph delegated permissions `openid`, `profile`, `offline_access`, `User.Read` and `User.ReadBasic.All`; the API asks for `openid profile offline_access` when it signs someone in (Microsoft.Identity.Web adds `offline_access` because it redeems the code through MSAL, ADR-0031), and for `User.ReadBasic.All` only when an administrator searches the company directory or invites someone from it, redeeming the refresh token of their session (ADR-0040). Their permission ids are read from the Microsoft Graph service principal at run time, never hard-coded. `entra.sh` then grants them for the whole tenant with `az ad app permission grant --scope "openid profile offline_access User.Read User.ReadBasic.All"` as the operator, so no employee sees a consent prompt. Only the tenant-wide grant counts: a per-user consent recorded by an interactive sign-in never satisfies the check, and a tenant-wide grant whose scopes differ from exactly these five is re-issued (the Azure CLI deletes the existing grant for the registration and Microsoft Graph and creates the new one, so a registration granted four scopes gains `User.ReadBasic.All` on the next run, as both did on 2026-10-10). When the tenant's consent policy refuses that grant, the script prints the exact command for a Global Administrator to run:

```bash
az ad app permission admin-consent --id <application id>
```

The script still finishes every other step for every registration, then exits 1 so the refusal is not missed. Run the printed command, then run `entra.sh` again; it will find the grant in place and report it unchanged.

Each sign-in registration also requests one application permission, `User.Read.All` ("Read all users' full profiles"), which the API uses only without a signed-in person, for the account check of [ADR-0047](../adr/0047-user-lifecycle-the-account-check-and-the-team-handover.md): with an application token made from the registration's certificate, it reads `id` and `accountEnabled` of the accounts linked to people's records, to deactivate those disabled or deleted in Entra. `requiredResourceAccess` lists it as a `Role` beside the five delegated scopes, and `entra.sh` grants it with an app role assignment of the registration's service principal to Microsoft Graph's service principal (`POST /servicePrincipals/{id}/appRoleAssignments`), found again by its resource and app role id on the next run. Granting a Microsoft Graph application permission needs a Privileged Role Administrator or a Global Administrator; when Graph refuses the assignment, the script prints the same `admin-consent` command, which grants every permission the registration lists. Both registrations gained it on 2026-10-18, after a dry run that listed only those four changes. `verify.sh --entra` checks that each registration requests it and holds the assignment.

### Certificates

| Registration | Vault | Certificate and secret name | Content type | Subject |
|---|---|---|---|---|
| local-dev sign-in | `ERP_AZURE_KEYVAULT_DEV_NAME` | `Erp--Platform--Identity--ClientCertificate` | `application/x-pkcs12` | `CN=erp-ai-pro-web-local-dev` |
| production sign-in | `ERP_AZURE_KEYVAULT_PROD_NAME` | `Erp--Platform--Identity--ClientCertificate` | `application/x-pkcs12` | `CN=erp-ai-pro-web-production` |
| runtime | `ERP_AZURE_KEYVAULT_OPS_NAME` | `Erp--Platform--Identity--RuntimeClientCertificate` | `application/x-pem-file` | `CN=erp-ai-pro-runtime-production` |
| migrator | `ERP_AZURE_KEYVAULT_OPS_NAME` | `Erp--Platform--Identity--MigratorClientCertificate` | `application/x-pem-file` | `CN=erp-ai-pro-migrator-production` |
| backup | `ERP_AZURE_KEYVAULT_OPS_NAME` | `Erp--Platform--Identity--BackupClientCertificate` | `application/x-pem-file` | `CN=erp-ai-pro-backup-production` |
| none: the backup encryption certificate | `ERP_AZURE_KEYVAULT_OPS_NAME` | `Erp--Platform--Backup--EncryptionCertificate` | `application/x-pem-file` | `CN=erp-ai-pro-backup-encryption-production` |

Every sign-in and client certificate is self-signed by Key Vault from the policy in `scripts/azure/entra/certificate-policy.json`: RSA 2048, exportable, key usage `digitalSignature` and `keyEncipherment`, valid for 12 months, and deliberately without auto-renewal. Auto-renewal would create a new key in the vault that the registration never learns about, so rotation is an explicit loop the operator runs:

1. `bash scripts/azure/entra.sh --rotate-signin-certificate local-dev|production` or `bash scripts/azure/entra.sh --rotate-client-certificate runtime|migrator|backup` creates a new certificate version with the same policy and appends its public key to the registration as a further key credential (`az ad app credential reset --keyvault --cert --append`; the private key never leaves the vault). The sign-in variant prints how to restart the APIs of that label, because the API loads the sign-in certificate only when it starts ([runbooks/secrets.md](runbooks/secrets.md) section 5b); the client variant prints the export step below.
2. Once every API instance, and for a client certificate the container on the server, uses the new version, `bash scripts/azure/entra.sh --prune-old-credentials local-dev|production|runtime|migrator|backup` deletes every key credential whose thumbprint differs from the current vault version. It refuses to run when the current version is not among the registration's credentials. A credential's thumbprint is the SHA-1 of the certificate Microsoft Graph returns for it, never its `customKeyIdentifier`, which whoever adds a credential chooses.

The backup encryption certificate is no registration's credential. It is the recipient the server seals every backup archive (`backup.sh`) and every copy of its journal (`journal.sh`) to: OpenSSL CMS with AES-256-GCM and a new random key per archive or copy, that key sealed with RSA-OAEP-SHA256 to the certificate's public key ([restore runbook](runbooks/restore.md), [records runbook](runbooks/records.md)). Key Vault makes it from `scripts/azure/entra/encryption-certificate-policy.json`: RSA 4096, key usage `keyEncipherment` alone, exportable, a new key for every version (`reuseKey` `false`), valid for 12 months, without auto-renewal, as PEM. The server holds only its public certificate; its private key leaves the operations vault, which only the operator reads, only when the operator exports it for a restore or to read days of the journal back (`journal.sh --fetch`). `bash scripts/azure/entra.sh --rotate-encryption-certificate` makes a new version with a new key; there is no credential to prune, and every earlier version stays enabled until the newest archive sealed to it is past its 90 days and the newest copy of the journal sealed to it is past its 365 days, because each opens with that version's key alone; with a yearly rotation, the version a rotation replaces stays enabled until the next rotation ([runbooks/secrets.md](runbooks/secrets.md) section 5g).

`verify.sh --entra` prints a `[warn]` line, not a failure, for a certificate that expires within 30 days, and fails while a registration holds a key credential besides its current certificate (between the two steps above), a federated credential or a credential on its service principal, or while the encryption certificate differs from its policy. No script prints certificate, key or secret material.

### Client certificate export

The api and migrator containers, and the server's nightly backup and nightly copy of the journal, sign in as their service principals with PEM files from the operations vault, placed on the server as compose secrets; the backup and the journal copy seal their archives and copies to the encryption certificate's public part, placed beside them. The export is done by hand, once per certificate version:

1. `bash scripts/azure/export-client-certificate.sh runtime|migrator|backup [--out <file>]` (default `scripts/azure/out/erp-runtime-client.pem`, `scripts/azure/out/erp-migrator-client.pem` or `scripts/azure/out/erp-backup-client.pem`; the folder and every `.pem` file are gitignored). The script refuses an existing path, accepts only a `.pem` destination that git ignores, downloads the current secret version with a restrictive umask and mode 600 (on Windows the file inherits the folder's permissions instead, so keep it inside your user profile), and checks it with `openssl x509 -noout -subject -enddate` and `openssl rsa -check -noout`; when either check fails the file is deleted and the script stops. It never echoes the content.
2. Copy the file to the server over an encrypted channel, never through chat, email or a ticket.
3. On the server, as the administrator: `sudo install -o 1654 -g 1654 -m 0400 erp-<runtime|migrator|backup>-client.pem /srv/erp-ai-pro/ERP-AI-Pro/infra/compose/secrets/`, the folder the host bootstrap made private to the deploy account ([runbooks/host-setup.md](runbooks/host-setup.md)). 1654 is the uid and gid of the `app` user in the chiseled aspnet image the api and migrator containers run as (`APP_UID` in the image), and the user the backup's Azure CLI container runs as; each compose file mounts each file as the secret of the same name under `/run/secrets/`, and a file with any other owner is unreadable to the container. The migrator's certificate goes there only together with the deployment's images, because from then on `erp-ai-pro-retain.timer` runs `retain` every night.
4. Shred both staging copies (`shred -u` on Linux, `rm -P` on macOS; on Windows delete the file from a volume without shadow copies): the one on the workstation and the one copied to the server's home directory. Later rotations follow [runbooks/secrets.md](runbooks/secrets.md), which also covers recreating the running api container.

The encryption certificate has two targets of its own. `bash scripts/azure/export-client-certificate.sh backup-recipient` downloads its public certificate alone (`az keyvault certificate download --encoding PEM`, default `scripts/azure/out/erp-backup-recipient.crt`, a `.crt` destination git ignores), checks that it holds no private key and prints its subject, end date and SHA-256 fingerprint; on the server the administrator places it as `/srv/erp-ai-pro/ERP-AI-Pro/infra/compose/secrets/erp-backup-recipient.crt` with the host bootstrap's `--backup-recipient` option ([runbooks/host-setup.md](runbooks/host-setup.md)) and compares the fingerprint. It is not secret. `bash scripts/azure/export-client-certificate.sh backup-recipient-key [--version <version>]` downloads the certificate with its private key (default `scripts/azure/out/erp-backup-recipient-key.pem`), for a restore or for reading days of the journal back only: it checks it like a client certificate, prints the certificate's serial number, which names the archives and copies the key opens (their CMS recipient), and the steps of the [restore runbook](runbooks/restore.md); `--version` exports an earlier version for an archive or a copy sealed before a rotation (`az keyvault certificate list-versions --vault-name kv-erp-ai-pro-ops --name Erp--Platform--Backup--EncryptionCertificate` lists them). The key goes to the server only for that, over SSH, as `scripts/deploy/restore.sh --key <file>` or `scripts/deploy/journal.sh --fetch <first yyyy-mm-dd> [--through <last yyyy-mm-dd>] --key <file>` ([records runbook](runbooks/records.md)), each of which shreds it there once it is done; shred the workstation's copy as well.

### Second provision.sh run

The runtime, migrator and backup service principals do not exist until `entra.sh` has created them, so the role assignments for them are skipped on the first `provision.sh` run. Run `bash scripts/azure/provision.sh` again after `entra.sh`: it resolves each service principal by the display name in `ERP_AZURE_APP_RUNTIME_NAME`, `ERP_AZURE_APP_MIGRATOR_NAME` and `ERP_AZURE_APP_BACKUP_NAME` and grants the runtime and the migrator App Configuration Data Reader on the store, the runtime Key Vault Secrets User and Key Vault Crypto Service Encryption User on the production vault and Storage Blob Data Contributor on the production `attachments` container, the migrator Key Vault Secrets User on the production database's two connection strings, which the first run wrote, and the backup service principal Storage Blob Data Contributor on `host-backups` and `host-journal`. `verify.sh --entra` reports `[FAIL] ... run provision.sh again` while those rows are missing.

## 5b. Seeding the store

`bash scripts/azure/seed.sh` is the only writer of the keys in `infra/appconfig/` and never deletes a key. Per run it validates the seed files (`node scripts/azure/lib/seed-files.ts validate`), imports `defaults.json` unlabelled and each label file under its label with `az appconfig kv import --format json --separator : --import-mode ignore-match` (only a changed or missing value is written), creates each feature flag of `feature-flags.json` under each label and enables or disables it to match the file, writes each Key Vault reference of `key-vault-references.json` after confirming the secret exists in that label's vault (`kv-erp-ai-pro-dev` for `local-dev`, `kv-erp-ai-pro-prod` for `production`), bumps the labelled `Erp:Sentinel` and prints a read-back table per label. Options: `--label local-dev|production|all` (default `all`), `--no-sentinel` (seed without triggering a reload), `--dry-run`.

- A missing secret stops the run with the vault and secret name: create the secret first (the sign-in certificates come from `entra.sh`); the script never writes a placeholder, because an unresolvable reference fails API startup and a placeholder would later be read as the real value.
- The sentinel bump is the only write an unchanged re-run performs; a running API reloads within `Erp:Platform:Configuration:RefreshInterval`, and restarting the api container applies the change at once.
- How to add a setting, a flag or a secret: [docs/guides/adding-a-setting.md](../guides/adding-a-setting.md).

## 5c. What provision.sh writes to App Configuration

| Key | Label | Value |
|---|---|---|
| `Erp:Sentinel` | `local-dev` and `production` | a UTC timestamp, written when the key is absent, and under a label also whenever the run changed that label's blob endpoint below |
| `Erp:Platform:Attachments:BlobServiceUri` | `local-dev` | the development account's blob endpoint from the deployment output `developmentAttachmentsBlobEndpoint` (`https://<account>.blob.core.windows.net/`) |
| `Erp:Platform:Attachments:BlobServiceUri` | `production` | the production account's blob endpoint from the deployment output `productionAttachmentsBlobEndpoint` |
| `Erp:Platform:DataProtection:KeyIdentifier` | `local-dev` and `production` | the versionless URI of `Erp--Platform--DataProtection--Key` in that label's vault, from the deployment outputs `developmentDataProtectionKeyUri` and `productionDataProtectionKeyUri` (`https://<vault>.vault.azure.net/keys/Erp--Platform--DataProtection--Key`) |

`provision.sh` writes each endpoint after every deployment, but only when the stored value differs, and bumps that label's sentinel only in that case, so an unchanged re-run stays write-free; the API builds its storage clients when it starts, so a running API uses a new endpoint once it is restarted. An endpoint names a provisioned resource, so it never appears in a seed file: `seed-files.ts` refuses the key and any value containing `.blob.core.windows.net`. `Erp:Platform:DataProtection:KeyIdentifier` is written the same way, under both labels and only when it differs, but bumps no sentinel: the API reads it only when it starts, so a change reaches a running API through a restart; it names a vault, so it never appears in a seed file either. The API reads no other storage setting from the store that a script writes: the container name comes from `appsettings.json`, the tunables from `infra/appconfig/defaults.json` and the encryption key from its Key Vault reference.

## 5d. The production database

## 5f. The backup storage account

The server's own files (the Data Protection key ring, the proxy's certificate authority, `.env` and `.env.previous`) are backed up every night into an account that holds nothing else but the sealed copies of the server's journal ([ADR-0056](../adr/0056-the-servers-own-files-backed-up-nightly-sealed-to-an-operator-key-and-the-restore-drill.md)); the job, the archive format and the restore are in the [restore runbook](runbooks/restore.md).

- `provision.sh` deploys `storage-account.bicep` a third time as `backupStorageAccount`: `ERP_AZURE_STORAGE_BACKUP_NAME` (`sterpaiprobackup`, checked with `az storage account check-name` while it does not exist), `Standard_GRS`, Hot, Shared Key off, 7 days of blob and container soft delete (`backupStorageDeleteRetentionDays`), versioning and the change feed off, the `CanNotDelete` lock `do-not-delete`, and the production account's network rules: `defaultAction` `Deny`, `bypass` `None`, one IP rule. It reads the address of the database's rule `home` before the deployment and passes it as `backupStorageHomeAddress`, by the same rules as the production account's (section 5e); while that rule admits no single address, each account keeps its own single public address. `home-address.sh` moves this rule with the other three.
- Its first container, `host-backups` (`backupContainerName`), is private and carries a container-level time-based retention policy (`immutabilityPolicies/default`): every archive is write-once for 90 days from its creation (`backupImmutabilityPeriodDays`), with no protected append writes. While the policy is in effect, nobody, the account's owners included, can overwrite an archive or delete one younger than 90 days; a new archive can always be created. After its 90 days an archive can be deleted but still not overwritten. The policy needs no versioning, which stays off, and takes up to 35 seconds to apply after a change. Lifecycle rules cannot delete blobs in an immutable container, so the account has none: the backup job deletes its own archives once they are past 90 days, which soft delete then keeps for 7 more days.
- The backup service principal holds Storage Blob Data Contributor on `host-backups` and `host-journal` alone, granted by the run after `entra.sh` made it, and nobody else holds a role on the account or in it; `verify.sh` checks this, the account like the production one, and each policy (90 or 365 days, no protected append writes, no legal hold, which would stop the jobs' deletions), warning while one is unlocked.
- **The policy starts unlocked.** An unlocked policy already stops every overwrite and early delete, but the operator can still shorten, lengthen or remove it (removing it is a delete, which the account's lock blocks until lifted), so a mistake the first restore rehearsal finds can still be corrected. Once the first rehearsal succeeds, the operator locks it, from any computer signed in as the operator, because locking is a management action the network rules do not guard:

  ```bash
  az storage container immutability-policy show --resource-group rg-erp-ai-pro --account-name sterpaiprobackup --container-name host-backups --output table
  etag="$(az storage container immutability-policy show --resource-group rg-erp-ai-pro --account-name sterpaiprobackup --container-name host-backups --query etag --output tsv | tr -d '\r')"
  az storage container immutability-policy lock --resource-group rg-erp-ai-pro --account-name sterpaiprobackup --container-name host-backups --if-match "$etag"
  bash scripts/azure/verify.sh
  ```

  The first command shows 90 days and the state `Unlocked`; the lock takes the policy's ETag, so it locks exactly the policy just read, and `verify.sh` then reports it locked. The Azure portal does the same from the container's **Access policy** page (**Lock policy**).
- **Locking cannot be undone.** A locked policy can never be removed or shortened, and a container under it can be deleted only once it is empty, so the account cannot be deleted while `host-backups` exists: retiring it means waiting until the newest archive is past its period, deleting the archives and the container, then the account. It can be lengthened at most five times, in this order:
  1. The same number of days goes into the four places that hold the period: `backupImmutabilityPeriodDays` in `scripts/azure/bicep/main.bicep`, `BACKUP_IMMUTABILITY_DAYS` in `scripts/azure/verify.sh`, `BACKUP_IMMUTABILITY_DAYS` in `scripts/deploy/lib/backup.sh` (the backup job deletes an archive one day after that many days, and `check.sh` refuses a value that differs from the other two), and the prune scenario of `scripts/deploy/tests/backup-decisions.sh`, together with the texts that say 90 days (this section, the [restore runbook](runbooks/restore.md), the [host setup runbook](runbooks/host-setup.md) and `secrets.md` section 5g, whose rule for disabling an old version of the encryption certificate counts this period beside the journal's).
  2. That change is released and deployed to the server, which runs `backup.sh` from the deployed release's checkout.
  3. Only then: `az storage container immutability-policy extend --resource-group rg-erp-ai-pro --account-name sterpaiprobackup --container-name host-backups --if-match "$etag" --period <days>`, with the ETag read as for the lock, and `bash scripts/azure/verify.sh`.

  Extending first makes every nightly backup fail at the step `prune` until the deployment, after its archive has uploaded, because the job asks to delete archives the policy now keeps; a later rollback to a release from before the change does the same until the next deployment.
- **Later deployments leave a locked policy alone.** A locked policy accepts the extension alone: the create-or-update a deployment sends is refused, so a template that kept the policy would fail every later `provision.sh`. `provision.sh` therefore reads the container before the what-if (`properties.hasImmutabilityPolicy` and `properties.immutabilityPolicy.properties.state`, api-version 2026-04-01) and passes `backupImmutabilityPolicyLocked`: `false` while there is no policy or it is unlocked, so the deployment creates it or converges it back to 90 days, and `true` once it is locked, which leaves the policy out of the template, and an incremental deployment does not touch a resource its template leaves out. It stops on any other state.
- **The journal container.** The second container, `host-journal` (`backupJournalContainerName`), holds the sealed copy of each India day of the server's journal that the server uploads every night as the backup service principal ([records runbook](runbooks/records.md)). It carries the same kind of policy, 365 days long (`backupJournalImmutabilityPeriodDays`): every copy is write-once for a year from its creation, again without protected append writes, because each copy is written once and whole; no lifecycle rule can delete in it, so the journal job deletes the copies past their year itself. It starts unlocked, `provision.sh` reads its state before the what-if as it reads `host-backups`' and passes `backupJournalImmutabilityPolicyLocked`, leaving a locked policy out of the deployment, and the operator locks it once a day of the journal has been read back with the operator's exported key, with the three commands above for `--container-name host-journal`, where the first shows 365 days. Locking it cannot be undone either; lengthening it follows the three steps above, with the new number of days in `backupJournalImmutabilityPeriodDays` in `scripts/azure/bicep/main.bicep`, `BACKUP_JOURNAL_IMMUTABILITY_DAYS` in `scripts/azure/verify.sh`, `JOURNAL_IMMUTABILITY_DAYS` in `scripts/deploy/lib/backup.sh` (`journal.sh` deletes a copy one day after that many days, and `check.sh` refuses a `main.bicep` or `verify.sh` value that differs), the prune scenarios of `scripts/deploy/tests/journal-decisions.sh`, and, for a period above 369 days, `MaxRetentionSec` in `infra/host/journald/50-erp-ai-pro.conf`, which `check.sh` requires to be at least the period and 31 days, with `SystemMaxUse` and `SystemMaxFiles` raised if the disk needs it (only a bootstrap run installs that file, [host setup runbook](runbooks/host-setup.md)), together with the texts that say 365 days, `secrets.md` section 5g among them, whose rule for disabling an old version of the encryption certificate the journal's period now sets; the extension's command then names `--container-name host-journal`.
- The account answers only the home's address, from which the server writes and a restore on the server reads, and its archives are ciphertext that only the private key of the backup encryption certificate opens (section 5a); its management, like the production account's, stays reachable from anywhere for whoever holds the rights.

## 5g. The logs storage account

The company keeps the records of every ICT system for a year, inside India, and hands them to CERT-In when asked (CERT-In Directions of 28 April 2022, direction (iv); DPDP Rules 2025, rules 6(1)(e) and 8(3)). The records of the Azure resources, the subscription, the production database and Microsoft Entra ID go to one account that holds nothing else ([ADR-0058](../adr/0058-records-kept-a-year-inside-india.md)); which record lives where, for how long, and how a time range is handed over are in the [records runbook](runbooks/records.md).

- **The account.** `provision.sh` deploys `scripts/azure/bicep/modules/logs-storage-account.bicep` as `logsStorageAccount`: `ERP_AZURE_STORAGE_LOGS_NAME` (`sterpaiprologs`, checked with `az storage account check-name` while it does not exist), `StorageV2`, Hot, in the resource group's region, with the hardening of the other three (Shared Key off, Entra ID by default, no public blob access, no cross-tenant replication, TLS 1.2, HTTPS only, no hierarchical namespace, SFTP, NFS 3.0 or local users), 7 days of blob and container soft delete (`logsStorageDeleteRetentionDays`), versioning on, the change feed off and the `CanNotDelete` lock `do-not-delete`. It has a module of its own because nearly everything that sets it apart (one copy, the trusted-services exception, version-level immutability, versioning, the lifecycle rule, roles on the account instead of on a container, no container of its own, no diagnostic setting of its own) would otherwise be a switch in `storage-account.bicep`.
- **One copy** (owner decision of 2026-10-31): `Standard_LRS` keeps the records in Central India alone, three times within one datacentre. They are a copy kept for the law, which the business does not run on, so a regional disaster that took them is accepted for half the price of a second region.
- **Its network.** `defaultAction` `Deny`, one IP rule, the home's address (`logsStorageHomeAddress`, read from the database's rule `home` before the deployment like the production and backup accounts', and moved by `home-address.sh` with them), empty IPv6, virtual network and resource instance rule lists, and `bypass` `AzureServices`, which no other account has: Azure Monitor (`Microsoft.Insights`) writes resource logs, the activity log and Microsoft Entra ID's sign-in and audit logs to an account behind a firewall only as a trusted Microsoft service, and Azure SQL writes its audit records there only as one, with its managed identity (Azure Storage, "Trusted Azure services"; Azure Monitor, "Diagnostic settings in Azure Monitor"; Azure SQL, "Write audit to a storage account behind VNet and firewall"). The operator reads the records from the home's address.
- **Shared Key stays off.** Microsoft describes trusted access as the way such services still reach an account that disallows Shared Key ("If you have disabled shared key access and you are seeing Shared Key authorization reported in the diagnostic logs, this indicates that trusted access is being used", "Authorize access to data in Azure Storage"), but documents diagnostic settings to such an account neither way. The first real provisioning proves delivery: the `insights-logs-*` and `insights-activity-logs` containers appear within about 90 minutes of a new diagnostic setting, and `sqldbauditlogs` after the next sign-in to the database.
- **Write-once for 365 days.** Version-level immutability is on (`immutableStorageWithVersioning.enabled`), which Azure allows only when it creates the account, so `provision.sh` refuses an existing account of that name without it; its default account policy covers every blob version of every container, those the services create later included: 365 days (`logsImmutabilityPeriodDays`), with protected append writes, because Azure Monitor writes hourly append blobs (`…/PT1H.json`) and Azure SQL `.xel` append blobs, both keep appending to them, and SQL auditing refuses an immutable destination without protected append writes. An append blob's period counts from its last append. While the policy is in effect nobody, the operator included, can delete or change a record; writing over a blob keeps the old version.
- **Deleted a day later.** The lifecycle rule `delete-records-past-their-period` (`managementPolicies/default`) deletes, for append and block blobs alike, a current version 366 days after its last write and a previous version 366 days after its creation (`logsDeleteAfterDays` in `main.bicep`, the period and one day), and soft delete then keeps each 7 more days. SQL auditing's own retention is the same 366 days, because Azure SQL needs it longer than the storage policy's period. The lifecycle documentation says its delete action does not act on blobs in an immutable container, while the version-level documentation lets a version be deleted once its policy has expired; the first records reach their 367th day a year after the first provisioning, and only then does the account show whether the rule deletes them ([records runbook](runbooks/records.md)).
- **The policy starts unlocked.** An unlocked policy already stops every change and early delete, but the operator can still shorten, lengthen, disable or remove it, so a mistake the first records show can still be corrected. Once they have arrived and `verify.sh` passes, the operator locks it, from any computer signed in as the operator:

  ```bash
  az storage account show --resource-group rg-erp-ai-pro --name sterpaiprologs --query immutableStorageWithVersioning
  az storage account update --resource-group rg-erp-ai-pro --name sterpaiprologs --immutability-state Locked --immutability-period 365 --allow-protected-append-writes true
  bash scripts/azure/verify.sh
  ```

  The first command shows `enabled` `true`, 365 days, protected append writes and the state `Unlocked`; the second locks the policy with exactly those values, and `verify.sh` then reports it locked.
- **Locking cannot be undone.** A locked policy can never be removed, disabled or shortened, and the account, like any account with version-level immutability, cannot be deleted while a container in it holds a blob version. `provision.sh` reads the state before the what-if (`immutableStorageWithVersioning.immutabilityPolicy.state`) and passes `logsImmutabilityPolicyLocked`: `false` while the policy is unlocked, disabled or absent, so the deployment converges it to the template, unlocked, and `true` once it is locked, so the deployment sends the state `Locked`, the only one Azure accepts for it, with the template's period. Lengthening a locked policy is therefore a template change, with no step outside the scripts: the new number of days goes into `logsImmutabilityPeriodDays` in `scripts/azure/bicep/main.bicep` and `LOGS_IMMUTABILITY_DAYS` in `scripts/azure/verify.sh`, together with the texts that say 365 days, and `provision.sh` then lengthens the policy, the lifecycle rule and SQL auditing's retention together; Azure refuses any shorter period.
- **Who reads it.** The operator holds Storage Blob Data Reader on the account, the SQL server's identity Storage Blob Data Contributor, and nobody else holds a role on it or in it (section 5); Azure Monitor needs none.
- **What it receives.** Every setting sends logs alone, no metric, to the logs account alone, named `erp-ai-pro-records`; the resource settings live in the modules of their resources (`key-vault.bicep`, `storage-account.bicep`, `configuration-store.bicep`, `#disable-next-line use-recent-api-versions` on each, because the one stable version the linter accepts, 2016-09-01, allows a single setting, named `service`).

  | Source | Categories | Containers | Export billed |
  |---|---|---|---|
  | the three vaults | `AuditEvent` | `insights-logs-auditevent` | no |
  | the blob service of the development, production and backup accounts | `StorageRead`, `StorageWrite`, `StorageDelete` | `insights-logs-storageread`, `insights-logs-storagewrite`, `insights-logs-storagedelete` | per GB |
  | the store | `Audit`, `HttpRequest` | `insights-logs-audit`, `insights-logs-httprequest` | per GB |
  | the subscription's activity log | `Administrative`, `Security`, `ServiceHealth`, `Alert`, `Recommendation`, `Policy`, `Autoscale`, `ResourceHealth` | `insights-activity-logs` | no |
  | Microsoft Entra ID (needs Microsoft Entra ID P1 or P2, which the tenant has) | `AuditLogs`, `SignInLogs`, `NonInteractiveUserSignInLogs`, `ServicePrincipalSignInLogs`, `ManagedIdentitySignInLogs` | `insights-logs-<category in lower case>` | no |
  | the production SQL server's auditing | the action groups below | `sqldbauditlogs` | not an Azure Monitor export: the records take storage like the others |

- **The activity log and Microsoft Entra ID** are not resources of the resource group, so `provision.sh` writes their settings after the deployment instead of the template: the activity log's with `az monitor diagnostic-settings subscription create`, Entra's with `az rest --method put` on `/providers/microsoft.aadiam/diagnosticSettings/erp-ai-pro-records` (api-version 2017-04-01). Each is read first and written only when its destination or categories differ, so a second run writes nothing, and `--dry-run` prints each write instead. Entra's needs the operator to hold the Microsoft Entra role Security Administrator or Global Administrator (Entra's documentation also asks for `ListKeys` on the account, which the operator's subscription rights include). `provision.sh` requests all five categories, which Microsoft Entra ID's documentation of the logs it routes names, though its template reference lists only `AuditLogs` and `SignInLogs`, then reads the setting back and names the categories Microsoft Entra ID accepted; a refusal, the service's own message included, or a category it did not keep makes the run exit 1 after every other step, and `verify.sh` fails until all five are kept.
- **SQL auditing.** `scripts/azure/bicep/modules/sql-auditing.bicep` sets the server-level `auditingSettings/default` (api-version 2025-01-01), which covers every database of the server: state `Enabled`, the logs account's blob endpoint, the server's system-assigned identity (`isManagedIdentityInUse`, no access key; `sql-database.bicep` gives the server that identity), a retention of 366 days and these action groups alone: `SUCCESSFUL_DATABASE_AUTHENTICATION_GROUP`, `FAILED_DATABASE_AUTHENTICATION_GROUP`, `DATABASE_CHANGE_GROUP`, `DATABASE_OBJECT_CHANGE_GROUP`, `DATABASE_OBJECT_OWNERSHIP_CHANGE_GROUP`, `DATABASE_OBJECT_PERMISSION_CHANGE_GROUP`, `DATABASE_OWNERSHIP_CHANGE_GROUP`, `DATABASE_PERMISSION_CHANGE_GROUP`, `DATABASE_PRINCIPAL_CHANGE_GROUP`, `DATABASE_PRINCIPAL_IMPERSONATION_GROUP`, `DATABASE_ROLE_MEMBER_CHANGE_GROUP`, `SCHEMA_OBJECT_CHANGE_GROUP`, `SCHEMA_OBJECT_OWNERSHIP_CHANGE_GROUP`, `SCHEMA_OBJECT_PERMISSION_CHANGE_GROUP` and `USER_CHANGE_PASSWORD_GROUP`. `ERP_ENVIRONMENT=production` selects the label. The placement of the certificate on the host is described in section 5a; the first deployment that uses these values belongs to the `first-deployment` phase. The api reaches the production storage account as the same identity: the endpoint and the encryption key's reference come from the store under `production` (sections 5c and 5e), so the server's `.env` holds no storage setting, and the account answers only from the home's address. The server's nightly backup and its nightly copy of the journal read no store and no vault: each signs in as the backup service principal with `erp-backup-client.pem` and seals its archives or copies to `erp-backup-recipient.crt`, both placed as section 5a shows ([runbooks/host-setup.md](runbooks/host-setup.md), [restore runbook](runbooks/restore.md), [records runbook](runbooks/records.md)).

## 8. Re-running and recovery

- Re-running is the normal way to converge: every run performs the same exists-and-diff checks, and a run that changes nothing exits 0 with `unchanged` in its log lines.
- `--dry-run` writes nothing: control-plane changes are shown through `az deployment group what-if`, and every data-plane command is printed with a `[dry-run]` prefix instead of being executed. Before the resource group exists the what-if step is skipped, because what-if needs a scope to run against.
- What-if noise: on a converged deployment what-if still reports `Modify` lines for properties Azure fills in or does not echo back: on the store `dataPlaneProxy`, `defaultKeyValueRevisionRetentionPeriodInSeconds` and, on the Free tier, `softDeleteRetentionInDays: 0 => 7`; on each vault, the operations vault included, `networkAcls` shown as added; on each key `rotationPolicy` shown as removed; on the SQL server `isIPv6Enabled` shown as added, because Azure does not echo it back, and `version` as `NoEffect`; on the database's short-term retention policy `diffBackupIntervalInHours` and on its long-term retention policy `yearlyRetention: "PT0S"` shown as removed, and on the database `sku.capacity` and `sku.tier` as `NoEffect`; on each blob service `deleteRetentionPolicy.allowPermanentDelete` and `staticWebsite`, and on each container (`attachments` and `host-backups`) `defaultEncryptionScope` and `denyEncryptionScopeOverride`, shown as removed; on each role assignment `principalType` as `NoEffect`. None of these is applied: a second run leaves the store settings, the key versions and the rotation policies exactly as they were. A run is converged when what-if shows no `Create` or `Delete` entry and no `Modify` beyond this list.
- Soft-deleted vault: `az keyvault recover --name <vault>` and then run `provision.sh` again, because recovery restores the vault and its keys but drops the role assignments.
- Soft-deleted certificate (deleted in the portal to start over): `entra.sh` stops and prints `az keyvault certificate recover --vault-name <vault> --name <certificate>`; purge protection keeps the name reserved, so recovery is the only way forward.
- Store on the Free tier: there is no soft delete, so a deleted store is recreated by `provision.sh` and repopulated by `seed.sh` (and `entra.sh`, which writes the identity ids). On `Standard` or `Premium` run `az appconfig recover --name <store>` first.
- `NameUnavailable` on the store or `VaultAlreadyExists` on a vault means the name is taken globally, either by another subscription or by a soft-deleted vault of your own (`az keyvault list-deleted`). Recover your own vault as above or choose a new name in `params.env`.
- `provision.sh` stopping with `storage account name '<name>' cannot be used (AlreadyExists: ...)` or `(AccountNameInvalid: ...)` means the name is taken by any Azure customer or breaks the naming rule; set another `ERP_AZURE_STORAGE_DEV_NAME`, `ERP_AZURE_STORAGE_PROD_NAME`, `ERP_AZURE_STORAGE_BACKUP_NAME` or `ERP_AZURE_STORAGE_LOGS_NAME`, whichever the message names, in `params.env`. The check runs only while the account is not in the resource group, so a converged account never trips it. When `az storage account check-name` itself fails with `MissingSubscriptionRegistration`, the subscription has never used storage: `az provider register --namespace Microsoft.Storage --wait` once, then re-run.
- `provision.sh` stopping with `SQL server name '<name>' cannot be used (AlreadyExists: ...)` means another Azure customer holds the name; set another `ERP_AZURE_SQL_SERVER_NAME`. The check runs only while the server is not in the resource group. `MissingSubscriptionRegistration` means the subscription has never used Azure SQL: `az provider register --namespace Microsoft.Sql --wait` once, then re-run.
- `provision.sh` stopping with `the Microsoft Entra admin of <server> is <id>, not the signed-in operator` means the Azure CLI is signed in with another account of the tenant: sign in again as the admin (`az login --tenant <id>`), or change the admin deliberately as in section 5d.
- SQL server lock: `do-not-delete` makes deleting the server, its database or a firewall rule fail until the lock is removed (`az lock delete --name do-not-delete --resource-group <group> --resource-type Microsoft.Sql/servers --resource-name <server>`); changing the rule's address is an update, which the lock allows. Run `provision.sh` afterwards, which puts the lock back.
- Storage account lock: `do-not-delete` makes deleting any of the four storage accounts, and deleting the resource group that holds them, fail until the lock is removed (`MSYS_NO_PATHCONV=1 az lock delete --name do-not-delete --resource <account resource id>`; `MSYS_NO_PATHCONV=1` keeps Git Bash on Windows from rewriting the id `/subscriptions/…` into a Windows path, as `scripts/azure/lib/common.sh` does for the scripts). A `CanNotDelete` lock also blocks deleting role assignments at the account and its container, and every other delete through Azure Resource Manager of something inside the account, an unlocked write-once policy of `host-backups` included, so removing a storage role assigned directly to a person, or the developers group's own assignment, means lifting the lock first and running `provision.sh` afterwards, which puts the lock back. Removing a person from the developers group is a group-membership change and works with the lock in place. The backup account cannot be deleted at all while `host-backups` or `host-journal` exists under a locked policy, lock or no lock (section 5f), and the logs account not while any of its containers holds a blob version (section 5g).
- Production storage: nobody but the runtime service principal holds a data role there, and the account answers only the home's address. A restore below is run from a computer on the home network, after granting yourself Storage Blob Data Contributor on the account for its duration (`MSYS_NO_PATHCONV=1 az role assignment create --assignee <your object id> --role "Storage Blob Data Contributor" --scope <account resource id>`), which `verify.sh` reports as a failure until it is removed with the lock lifted, as above.
- Backup storage: nobody but the backup service principal holds a data role there, and archives and copies of the journal are read back only on the server, as that identity, by a restore or by `journal.sh --fetch` ([restore runbook](runbooks/restore.md), [records runbook](runbooks/records.md)). An archive or a copy its job deleted after its 90 or 365 days stays soft-deleted for 7 days.
- `verify.sh` warning that the write-once policy of `host-backups` is unlocked is expected until the first restore rehearsal has succeeded and the operator has locked it (section 5f); failing with `keeps every archive write-once` means the policy is missing or was changed while unlocked, which `provision.sh` puts back; failing with `carries no legal hold` means someone placed a legal hold, which keeps the job from deleting archives past their 90 days: clear it with `az storage container legal-hold clear --resource-group rg-erp-ai-pro --account-name sterpaiprobackup --container-name host-backups --tags <tag>...`. The same holds for `host-journal`, with `keeps every copy of the journal write-once`, until a day of the journal has been read back and its policy locked.
- `verify.sh` warning that the write-once policy of the logs account is unlocked is expected until the first records have arrived and the operator has locked it (section 5g); failing with `keeps every record write-once for 365 days` or `lets Azure Monitor and SQL auditing append` means the policy was changed while unlocked, which `provision.sh` puts back; failing with `keeps every record write-once (it has no version-level immutability` means the account was made outside the template, which cannot give it the policy: set another `ERP_AZURE_STORAGE_LOGS_NAME` and run `provision.sh`.
- `provision.sh` stopping with `the storage account <name> exists without version-level immutability` means the logs account's name belongs to an account the template did not create; set another `ERP_AZURE_STORAGE_LOGS_NAME`.
- The first deployment after this change failing at `sql-auditing-production` with an error about access to the storage account means the SQL server's new role on the logs account had not taken effect yet (up to 10 minutes); run `provision.sh` again. `MissingSubscriptionRegistration` for `Microsoft.Insights` on a diagnostic setting means the subscription has never used Azure Monitor: `az provider register --namespace Microsoft.Insights --wait` once, then re-run.
- `provision.sh` exiting 1 after every other step with `Microsoft Entra ID's logs are not exported` means Entra refused its diagnostic setting, the reason quoted: the operator lacks Security Administrator or Global Administrator (activate or ask for the role, then re-run), the tenant has neither Microsoft Entra ID P1 nor P2, or the service did not keep a category it names; `verify.sh` fails on the same setting until all five categories are kept.
- `verify.sh` failing under `Diagnostic settings erp-ai-pro-records` names the resource and what differs (its destination, a category left out or added, a metric or a second destination); `provision.sh` puts every setting back to the template. Records that do not arrive although `verify.sh` passes (no `insights-logs-*` container a few hours after a setting was written) point at the trusted-services exception or at Shared Key being off (section 5g); report it to the owner rather than turning Shared Key on.
- `home-address.sh` failing with `the storage account <account> does not admit the home's address alone` (for the logs account, `the home's address and trusted Microsoft services alone`), or `verify.sh` failing under `Network rules of <account>`, means the account's network settings were changed outside the scripts, or its rule has not yet followed the database's, which `home-address.sh` moves. Each line names its remedy ([runbooks/home-address.md](runbooks/home-address.md), section "Never"): `provision.sh` puts the account's own settings back to the template, the address of the database's rule `home` alone, and its what-if lists the change first; a private endpoint connection is rejected with `az storage account private-endpoint-connection reject`, a published IPv6 endpoint turned off with `az storage account update --publish-ipv6-endpoint false`, and a network security perimeter association removed on the perimeter's page in the portal, none of which the template touches.
- `verify.sh` failing with `<account> allows Shared Key for no service` or `<account> allows no data share`, on any of the four accounts, means a setting the template does not carry was turned on. Turn it off with a `PATCH` of the account whose body is a file, since the Azure CLI under Git Bash mangles double quotes in arguments: `az rest --method patch --url "<account resource id>?api-version=2026-04-01" --body @body.json`, with `body.json` holding `{"properties":{"allowSharedKeyAccessForServices":{"blob":{"enabled":false},"file":{"enabled":false},"queue":{"enabled":false},"table":{"enabled":false}}}}` or `{"properties":{"dataCollaborationPolicyProperties":{"allowStorageDataShares":false,"allowCrossTenantDataSharing":false}}}`, then `bash scripts/azure/verify.sh`.
- Deleted blob: blob soft delete keeps it for 7 days in the development account and 90 in the production one; restore it with `az storage blob undelete --account-name <account> --container-name attachments --name <blob name> --auth-mode login` (the blob name is the `Id` of its row in `files.StoredContents`, written as 32 hexadecimal digits without hyphens). A blob can only be restored while its container exists.
- Deleted container: container soft delete keeps it, with every blob in it, for the account's retention (7 or 90 days), but only while no container with the same name exists, so restore it before `provision.sh` runs again, because the template would create a new empty `attachments` container and make the deleted one unrestorable. Listing and restoring containers are account-level operations that the container-scoped roles do not cover: grant yourself Storage Blob Data Contributor on the account for the duration, find the version with `az storage container list --account-name <account> --prefix attachments --include-deleted --auth-mode login`, restore it with `az storage container restore --account-name <account> --name attachments --deleted-version <version> --auth-mode login`, then remove the temporary assignment (the lock must be lifted for that, as above).
- Deleted storage account: the lock makes this a deliberate act. Microsoft recovers a deleted account on a best-effort basis for 14 days, from the portal's storage account list (**Restore**), only while no new account with the same name has been created and only into an existing resource group (recreate `rg-erp-ai-pro` with the same name first if it was deleted); the person restoring needs `Microsoft.Storage/storageAccounts/write`, which the operator's subscription rights include; run `provision.sh` afterwards to restore the lock and role assignments.
- A `403` immediately after a fresh role assignment is propagation delay: the scripts retry data-plane calls for about five minutes (20 attempts, 15 seconds apart) and then stop with a message that role assignments can take up to 15 minutes to propagate; re-run when it does. Storage data roles take up to 10 minutes; `verify.sh` reports a failed blob listing inside that window with the same hint.

## 9. Never automated

- Deleting or purging the resource group, the store, a vault, a key, a secret, a certificate, a storage account, its container, the SQL server, its database, a database user, a firewall rule of the SQL server or a lock is never scripted. Deletion is a deliberate owner action in the portal or with the CLI, and purge protection makes a purged vault impossible before the retention period ends. The network rules of the production, backup and logs storage accounts are converged instead: `provision.sh` sets them whole, the home's address alone (and trusted Microsoft services for the logs account), which removes any other rule added by hand (it stops instead while the database's rule `home` admits no single address and the account admits more than one), and `home-address.sh` refuses to run until only the home's rule is left.
- Locking the write-once policy of `host-backups`, and lengthening a locked one, are the operator's deliberate steps (section 5f); no script locks, lengthens or removes it, and none deletes an archive but the backup job itself, once the archive is past its 90 days. The same holds for `host-journal` and its year.
- Locking the logs account's write-once policy is the operator's deliberate step (section 5g); no script locks or removes it. Nothing deletes a record but the account's lifecycle rule and SQL auditing's own retention, each 366 days after the record was written, a day after its write-once period.
- Changing `ERP_AZURE_STORAGE_LOGS_NAME` after the account exists creates a second logs account with an unlocked policy on the next run and points every diagnostic setting and the SQL server's auditing at it; the old account keeps its records, its lock and its policy until each record's year has passed, and its role assignments until removed with the lock lifted.
- Changing `ERP_AZURE_STORAGE_BACKUP_NAME` after the account exists creates a second, empty backup account with an unlocked policy on the next run; the old account keeps its archives, its lock and, once locked, its policy, and the server goes on writing wherever its own backup settings point ([restore runbook](runbooks/restore.md)).
- A vault name stays reserved for the 90-day soft-delete retention after deletion; plan renames accordingly. A storage account name carries no such guarantee: once the account is gone, anyone may create an account with that name, which also ends any chance of recovering it.
- Changing `ERP_AZURE_STORAGE_DEV_NAME` or `ERP_AZURE_STORAGE_PROD_NAME` after the account exists creates a second, empty account on the next run and points `Erp:Platform:Attachments:BlobServiceUri` of that label at it, so every attachment stored before answers 404 there; the old account and its lock stay behind for the owner to remove by hand once its data is no longer needed.
- Changing `ERP_AZURE_SQL_SERVER_NAME` or `ERP_AZURE_SQL_DATABASE_NAME` after the database exists creates a new, empty server or database on the next run, with no firewall rule and no users, and points both production connection strings at it, so the api fails at its next restart; the old server keeps its data and its lock.
- Changing `ERP_AZURE_APP_RUNTIME_NAME` or `ERP_AZURE_APP_MIGRATOR_NAME` creates a new registration with a new client id on the next `entra.sh` run and a new database user on the next `database.sh` run, while the old ones stay; a new migrator cannot take over the schemas its predecessor owns ([runbooks/database.md](runbooks/database.md), section "Recovery").
